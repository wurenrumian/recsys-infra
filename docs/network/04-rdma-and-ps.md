# 网络 4. RDMA 与参数服务器：什么时候不该用集合通信

<div class="deep-anchor">

**在教程的哪一层** 对应[第 6 章](../guide/06-communication)的"第三种策略：改通信原语本身"；这里回答什么时候该换、换了付什么。

</div>

## 一句话版本

集合通信不是唯一选项。换不换原语，看的是负载是否均衡，不是数据量大小：均衡时集合通信最简单，变长、按 key 取值时点对点或参数服务器更合适。

换原语省下的不是带宽，是等待。屏障把每一层的最慢者层层相加，点对点只等总量最慢的那一台；在 128 卡上这个差约 15.6 ms，比压缩省下的 9.4 ms 更多。

## 这篇的地图

全篇分四块，加一个算例。顺序是：先看原语本身长什么样，再看它们的完成时间差在哪，然后看推荐系统的负载为什么会选那个看起来更笨的方案，最后压成一张选型表。

1. 三种用法，谁等谁 —— read、write、send/recv 差在远端进程要不要参与。
2. max 在 Σ 里面还是外面 —— 同一个 max 放在不同位置，完成时间差多少。
3. 参数服务器为什么没死 —— 它对应的不是落后，是另一种访问单位。
4. 判据 —— 三个问题依次定原语，以及本篇在第 5、6 篇里的位置。

四块由"谁能省什么"串起来：原语、等待、访问单位、判据；算例把那个差算成毫秒。

| 概念 | 一句话 |
|---|---|
| RDMA | 远端直接内存访问：本端网卡绕过对端 CPU 直接读写对端内存 |
| one-sided | 只有发起端提交请求，远端进程不参与、也不被通知 |
| two-sided | send/recv：收发两端都要挂好缓冲，两端都在协议里 |
| 屏障 | 每一层或每一轮结束时所有参与方对齐，一起等最慢的那个 |
| 参数服务器 | 一个或一组进程集中存参数，worker 按 key 来 pull / push |
| 不均衡比 | 最慢设备的工作量除以平均设备的工作量 |
| incast | 很多发送方同时打向同一个接收方，把接收队列压满 |

术语到此交代完毕，后面各块直接使用。先从原语本身开始。

## 第一块 · 三种语义，谁等谁

这块要回答的是：让远端帮忙取一份参数，两边的进程各自要做到什么。

第 6 章把压缩、融合、换拓扑、缩范围四种策略摆在同一个平面，但它们都默认传输还在用集合通信。这一层可以再往下拆：同步原语本身是可选项。

`C-12` 把这件事讲得最直白。数据并行十年里从参数服务器（PS）转向集合通信，理由只有一句——负载均衡时集合通信更简单、更高效。这句话有前提，前提一破，结论就要重算。

RDMA（remote direct memory access，远端直接内存访问）是一类让本端网卡直接读写对端内存的机制。路径上不经过对端 CPU，也不需要对端进程执行任何指令，所以它首先取消的是"对端要配合"这件事。

这条路径上也没有第二份数据，叫零拷贝：

```
GPU HBM (A) → NIC(A) ──网络──→ NIC(B) → GPU HBM 或 DRAM (B)
              ↑ 不经 OS 缓冲、不经 CPU 拷贝、不切内核态
```

### 三种用法差在谁等谁

load/store 是硬件语义：本端对远端内存发读或写，地址事先注册过，操作完成后本端在自己的完成队列里看到结果。远端进程既不知道，也不必先准备缓冲。

two-sided 是 send/recv：本端发，但远端必须已经挂好接收缓冲。这时两端都在协议里——接收端在等数据到，发送端在等接收端把缓冲交出来，谁都不能单方面完成。

one-sided 是 read / write 用在"远端当服务端"的场合：worker 主动拉参数，server 不知情。它的硬件基础与 load/store 是同一件事，差别在谁是发起方、谁被当成一块被动的存储。

三种用法放在一张表里，看的就是"远端要不要参与"这一列：

| 语义 | 谁发起 | 远端进程要参与吗 | 远端事先知道吗 | 典型用途 |
|---|---|---|---|---|
| read | 本端 | 不要 | 不知道 | worker 主动拉参数 |
| write | 本端 | 不要 | 不知道 | 把梯度推到持有者 |
| send / recv | 本端发，但远端必须已挂好接收缓冲 | 要 | 要 | MPI、NCCL 的基础 |

三行里只有前两行是被动的：read 与 write 合称 one-sided，只有发起端提交工作请求，远端网卡按目标地址直接 DMA，远端进程一行代码都不用跑。这就是"worker 主动、server 不知情"的物理基础。

集合通信建不到这上面，因为它的每一步都是"收上一跳、发下一跳"，收方必须先把接收缓冲挂上。`C-12` 把这条写成了选型理由（事实）：MPI / NCCL 需要显式接收方参与，所以 server 无法被动响应 worker 的按需请求。

`C-12` 的替代栈：节点内用 CUDA IPC，节点间用 NVSHMEM，梯度累加另配一个轻量 daemon（累加是读-改-写，不是纯传输），通信 kernel 基于 Triton-Distributed。

原语交代完了，时间差不在传输上，在一个 max 的位置。

## 第二块 · max 在 Σ 里面还是外面

这块要回答的是：计算量完全一样，为什么同步方式一变，完成时间就不同。

先把符号摆出来，这张表后面算例要用：

| 符号 | 含义 | 单位 | 出处 |
|---|---|---|---|
| `P` | 参与方（worker / GPU）数 | 个 | 算例取 128 |
| `n` | 一轮交换的字节数 | B | 算例取 525 MB |
| `B_net` | 单方有效网络带宽 | GB/s | `B-09`：100 Gb RDMA → 12.5（换算） |
| `t_i` | 设备 i 本 batch（或本层）耗时 | ms | 对应 `C-12` 的 `T_{m,d,l}` |
| `r` | 每迭代的通信轮数 | 次 | `C-06`：≥3 次 AlltoAll + 1 次 AllReduce |
| `α` | 单条消息的固定开销 | µs | 第 6 章算例假设 50 µs |

两个完成时间模型，一个每层对齐一次，一个按需拉取：

```
集合通信（每层/每轮一个屏障）
  T_coll = Σ_rounds  max_i t_i^(round)  +  n / B_net

P2P / one-sided（按需拉取，无屏障）
  T_p2p  = max_i ( t_i + n_i / B_net )      n_i = 该设备真正缺的字节
```

两式唯一的区别是 `max` 的位置。传输项 `n/B_net` 在量级上一样，所以换原语省的不是带宽，是等待。这一点决定了后面所有的判据。

### 屏障为什么每层收一次税

`C-12` 给 FSDP 的完成时间写了一个式子（事实）：

```
T(P_M) = Σ_m Σ_l  max_d T_{m,d,l}(P_M)
```

`d` 在内层：每一层都要等最慢的那台设备。把集合通信换成 P2P 之后设备解耦，同样的量变成：

```
T = max_d  Σ_m Σ_l T_{m,d,l}
```

`d` 跑到外层：只等总量最慢的那台。两种算法做的计算量完全一样，差别全在这个位置。

玩具例子（数字示意，4 设备 × 4 层，单位 ms）。读法是看最后一行 d4：它的长尾集中在 L4，但屏障在每一层都要对齐一次：

| 设备 | L1 | L2 | L3 | L4 | 合计 |
|---|---|---|---|---|---|
| d1 | 5 | 5 | 5 | 5 | 20 |
| d2 | 5 | 5 | 5 | 5 | 20 |
| d3 | 5 | 5 | 5 | 5 | 20 |
| d4 | 2 | 2 | 2 | 14 | 20 |

```
屏障口径：5 + 5 + 5 + max(5,5,5,14) = 29 ms
P2P 口径：max(20, 20, 20, 20)      = 20 ms
差：1.45×
```

d4 的总工作量一分钟没少，只是它的长尾挪到了最后一层，而屏障不关心长尾落在哪层——它每层都收一次税。

时间轴上看是这样（`▓` 计算，`·` 空等）：

```
屏障口径
 d1 ▓▓▓▓▓ ·····▓▓▓▓▓ ·····▓▓▓▓▓ ·············
 d2 ▓▓▓▓▓ ·····▓▓▓▓▓ ·····▓▓▓▓▓ ·············
 d3 ▓▓▓▓▓ ·····▓▓▓▓▓ ·····▓▓▓▓▓ ·············
 d4 ▓▓ ·········▓▓ ·········▓▓ ·········████████
    └─ 每层一次屏障，四次空等全部记在墙钟上 ─┘  29 ms

P2P 口径
 d1 ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ 20 ms
 d2 ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ 20 ms
 d3 ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓ 20 ms
 d4 ▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓████████  20 ms
    └─ 只有最慢的那条线决定墙钟 ─┘         20 ms
```

两条口径下 `t_i` 的方差一模一样，唯一的区别是空等能不能被填掉。

把这个结论写成期望形式。设每设备耗时是均值 `μ`、标准差 `σ`，则 P 个独立值取最大值的常用近似是：

```
E[max_i t_i] ≈ μ + σ · sqrt(2 ln P)
```

P2P 口径下只剩一个常数项（最后一次传输）。所以屏障的惩罚随 `P` 缓慢增长但没有上界，P2P 的惩罚是常数。`P=128` 时 `sqrt(2 ln 128) = sqrt(9.70) = 3.11`，代入算例。

3.11 乘的是抖动，而抖动只能靠减少对齐次数来消。下一块看的是另一种负载，它的问题不在抖动。

## 第三块 · 参数服务器就是 one-sided 的语义

这块要回答的是：参数服务器看起来是把集合通信拆散重做，为什么在推荐系统里反而一直有人用。

PS（parameter server，参数服务器）的 pull 是一次 read，push 是一次 write 或远端累加。语义上它和 one-sided 是同一件事，只是"server"这个角色被显式命名了。

`B-09` 的架构是 PS 的完整形态（事实）：

```
HBM-PS (L1)  4 节点 × 8 卡，多 GPU 分布式哈希表，参数非重叠分区
     ↕ NVLink（卡间）/ RDMA（机间，绕过 CPU）
MEM-PS (L2)  ~1TB/节点，汇集本 batch 引用到的参数，缓存命中率 46%
     ↕
SSD-PS (L3)  NVMe RAID-0，~20TB/节点，按文件组织 + 后台压实
```

三个可引用的点：

- 4 级流水：传输、参数分区、物化数据加载、训练各占一种硬件（网络 / CPU / SSD / GPU），各配一个线程和一个预取队列，下游队列满则上游阻塞。目的是把 I/O 延迟藏到 GPU 计算后面。
- 46% 命中率：模型 E 上 40 个 batch 后稳定。意思是超过一半的参数请求要走 SSD。
- 4 vs 150：4 个 GPU 节点在 1.8–4.8× 上打过 75–150 个 MPI 节点的基线，成本归一后 4.4–9.0×，扩展性 3.57/4。

### 46% 这个数值得单独算一遍

把一次参数 pull 的期望延迟写成：

```
t_avg = h · t_MEM + (1 - h) · t_SSD
      = t_MEM · [ h + (1 - h) · k ]        k = t_SSD / t_MEM

h = 0.46, k = 10（示意：SSD 比远端内存慢一个量级）
t_avg = t_MEM × (0.46 + 0.54 × 10) = t_MEM × 5.86

若 h = 0.90：
t_avg = t_MEM × (0.90 + 0.10 × 10) = t_MEM × 1.90   →  快 3.1×
```

结论是 46% 不是"够用"，是"还有 3 倍空间留在 SSD 上"。这解释了 `B-14` 那类把命中率往上推的工作为什么值钱——它改的不是带宽，是这个期望值。

### 为什么推荐系统里 PS 一直没死

因为访问单位长什么样变了。集合通信要求"每个参与方发等长、连续、大小已知的一块"；推荐的一次迭代要发的是"本 batch 命中的那些 key 的向量"，条数和长度都不定。

`B-15` 把这条写成了核心论断（事实）：交换嵌入向量比简单的 all-to-all 复杂得多，因为要先把分散在 chunk 里的向量聚集成一个临时连续张量，才能用满网络带宽。这一步是额外的，all-to-all 里不存在。

`B-15` 的做法是换抽象：把嵌入表当分布式 KV 库，按 chunk 分配（避免哈希碰撞、已分配内存全利用），每张 GPU 放一个复制 chunk 装热点向量，用去中心化索引表（DIT）定位，再配一个无竞争调度把"聚集 / 遍历索引"错开。32 GPU 上 2.16–16.8×。

所以 PS 解决的不是通信问题，是访问单位的问题。它的边界留给最后一块。

## 第四块 · 判据：先看均衡，再看长度，最后看量

这块要回答的是：面对一个具体负载，怎么在几张表之间做选择。

判据表把前面的结论按负载特征排开。读法是先找到自己最像的那一行，再看"为什么"那一列说的是不是你的瓶颈：

| 负载特征 | 该用 | 为什么 | 代表 |
|---|---|---|---|
| 每步字节数固定、参与方均衡 | 集合通信 | ring / 树的实现最成熟，带宽打满 | 标准 FSDP 前向 |
| 变长、条数不均、按 key 取 | P2P | 没有等长假设，谁缺什么拉什么 | `C-12` 的 gather |
| 表远大于显存、访问稀疏 | 分层 PS | 问题在存储层级，不在原语 | `B-09`、`B-15` |
| 需要"被动拉取" | one-sided read | 远端不参与，不打断它的计算 | `C-12` 跨节点 |
| 需要"推过去"且不惊动对方 | one-sided write | 同上，方向相反 | 梯度累加 daemon |

判据可以压成一句话：先看负载均不均衡，再看访问单位等不等长，最后才看数据量。

### 这三问在专栏里的位置

这三问对应专栏的读法：先判断瓶颈是不是"等待"（本篇），再判断是不是"路径"（第 5 篇），最后判断是不是"字节"（第 6 篇）。顺序反了就会花钱压一个本来不占时间的部分。

同一个栈，`C-12` 在 SFT + packing 场景最高拿到 36%，RL 只有 10%，后者受框架约束。

## 算例：这份差在毫秒上有多大

<div class="example">

这几步在算什么：用教程的算例参数，把"换原语"的收益算成毫秒和吞吐，再和压缩比一次。

设定用[贯穿全教程的算例](../guide/running-example)：每迭代 525 MB（去重后），`P=128`，预算 51 ms。网络按 `B-09` 的 100 Gb RDMA 换算：`100 Gbit/s ÷ 8 = 12.5 GB/s`。

⚠️ 51 ms 是 `A-10` 的 16 trainer 口径。128 卡时把每卡耗时与预算同时 ÷8（约 6.4 ms），`sqrt(2 ln P)` 与下面所有比值不变，只有绝对毫秒数变。这里保留 51 ms 是为了与教程对齐。

⚠️ 525 MB 沿用[教程第 6 章](../guide/06-communication)算例的口径；[算例页](../guide/running-example)按"10 倍去重"给的示意值是 210 MB，两处差异来自去重率假设。本篇结论只依赖"量级在几百 MB"，不依赖具体值。

第一步：传输项

```
全对全：每卡发 525 / 128 ≈ 4.1 MB
        4.1 MB ÷ 12.5 GB/s ≈ 0.33 ms
one-sided pull：只拉本 batch 缺的那 4.1 MB
        4.1 ÷ 12.5 ≈ 0.33 ms
```

两项一样。换原语在传输项上收益为零，这条要先钉死，否则后面的判断全是错的。

第二步：等待项（推导）

假设每设备本 batch 耗时 `μ = 51 ms`、抖动 `σ = 10% μ = 5.1 ms`（示意，抖动量级参照 `A-03` 报的负载不均比）。

```
sqrt(2 ln 128) = sqrt(9.70) = 3.11

屏障口径：51 + 5.1 × 3.11 = 66.9 ms
P2P 口径：51 + 0.33      ≈ 51.3 ms
差：15.6 ms
```

第三步：换成吞吐

```
屏障：16,384 / 0.0669 s ≈ 245K 样本/秒
P2P： 16,384 / 0.0513 s ≈ 319K 样本/秒
```

320K 是 `A-10` 报告的 16 trainer 吞吐。也就是说，同样的硬件，只因为同步原语选错，吞吐从目标值掉到 245K。

第四步：和压缩比一比

第 6 章的算例里，压缩把 525 MB 的传输从 10.5 ms 压到 1.1 ms，省 9.4 ms。本篇换原语省 15.6 ms。两者改的不是同一项（一个改字节数、一个改等待），可以叠。

第五步：单 server 撑不住

经典 PS 是"一个 server 存全表、128 个 worker 都来拉"：

```
server 单口 12.5 GB/s
128 个 worker 各拉 4.1 MB，总出流量 525 MB
525 MB ÷ 12.5 GB/s = 42 ms        ← 占 51 ms 预算的 82%
```

所以"用 PS"这三个字是不够的，PS 必须变成分层的：参数按 key 分给 4 台机器（`B-09` 的取模哈希），每台再往自己 8 张卡上非重叠分区，worker 优先从本地 L2 拿。`B-09` 的 46% 命中率就是这一步的产物——命中率是分层的结果，不是设计参数。

</div>

算例的落点是：传输项 0.33 ms 两边完全相同，收益全部来自那 15.6 ms 的空等。下一篇处理空等的另一种形态：路径。

## 模型在哪里不成立

- 跨节点是硬伤。`C-12` 明确写了跨节点 ODC 明显慢于集合通信，因为放弃了分层拓扑（先节点间广播、再节点内广播）。它给出的补丁是 Hybrid Sharding——也就是说，节点内用 P2P、节点间退回集合通信。所以它的收益面很窄：多节点、但每节点 GPU 数多、且序列很长的场景（论文页的推断）。
- 小集群和短序列会亏。这不是论文的实测，是从"屏障惩罚 = `σ·sqrt(2 ln P)`"推出来的：P 小的时候 `sqrt(2 ln P)` 接近 1，屏障几乎不收税，而 P2P 的固定开销和栈复杂度照付。
- 收益受框架限制。`C-12` 的 RL 只有 10%，原因是 verl 要求每设备样本数相同，`LB-Mini` 的自由度用不上。它同时承认 minibatch size = 1 时所有方法一样快——P2P 退化成集合通信。
- 它没有变成异步。`C-12` 故意保留了 minibatch 边界的同步，以保证训练语义不变。屏障从"每层"放宽到"每 minibatch"，仅此而已。
- 栈依赖 NVIDIA。NVSHMEM、CUDA IPC、Triton-Distributed 这套东西换平台要重做。
- PS 的边界在命中率。`B-09` 的 46% 意味着过半请求打 SSD；访问越均匀，命中率越低，SSD 就越硬。而且 `B-09` 是静态分片，新 ID 出现要扩容——这件事由 `B-15` 的 chunk 分配接手。
- PS 的收益有规模门槛。`B-09` 的时间分布分析说：小模型瓶颈在 HDFS 读样本，参数涨到 6–10 TB 时 pull/push 才成为主导。表不够大时不用上三层。
- 判据表里的"均衡"要实测。`A-03` 报的传统 MP 负载不均比是 5.70（CTR）/ 5.18（ExFM），这不是通信抖动，是分片大小不均，但算术上是同一件事：`max/mean` 直接吃掉利用率。这类比值要在自己的集群上量一遍再套。
- "被动"不等于"免费"。one-sided 的发起端要轮询完成队列才知道传输结束了，这份开销在 CPU 或在 GPU 线程上。`C-12` 把通信写成 Triton-Distributed 的 kernel，就是为了让轮询和计算在同一个流里。
- 算例里的 12.5 GB/s 是理论上限。100 Gb 是峰值，小消息打不满，incast 会把它压成 `B/N`（第 5 篇）。所以 0.33 ms 是乐观值，真实值要按消息尺寸打折扣。
- 本篇没有直接测过任何硬件。`σ = 10% μ`、`k = 10`、0.33 ms、15.6 ms 全部标了"示意/推导"，换集群要重算。可引用的实测只有 `C-12` 的 36% / 10%、`B-09` 的 46% / 3.57×、`B-15` 的 2.16–16.8×。
- `B-09` 的三层是 2020 年的设计。它按取模哈希静态分片，新 ID 出现要扩容；这件事 `B-15` 用 chunk 分配解决了，但那意味着元数据从"每节点一张表"涨到"每个 chunk 一条索引"。选型时这一半成本也要算进去。

<div class="takeaway">

选原语的判据是负载均衡度，不是数据量。均衡用集合通信，变长/不均由 P2P，表在显存外用分层 PS。

换原语的收益来自把 `max_i(t_i)` 从求和的里面搬到外面：`C-12` 在 SFT 场景拿到 36%，代价是放弃分层拓扑、跨节点变慢。它不改变训练数学，只是把屏障从"每层"放宽到"每 minibatch"。

动手前先把每设备的 `t_i` 打出来算 `max/mean`。这个比值小于 1.2 时换原语是白费力气，大于 1.5 时它的收益通常超过任何压缩手段，因为压缩改的是字节，它改的是等待。

</div>
