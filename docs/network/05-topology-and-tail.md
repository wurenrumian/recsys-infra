# 网络 5. 拓扑与尾延迟：同样的字节，为什么差 18 倍

<div class="deep-anchor">

**在教程的哪一层** 对应[第 6 章](../guide/06-communication)里 `C-06` 那一段"机内 shuffle 走 NVLink、全局 all-to-all 走 IB，差 18 倍"；这里拆开这 18 倍由什么构成，以及什么时候轮不到你选。

</div>

## 一句话版本

同一份字节，在机箱内走 NVLink 和在机箱外走网络，带宽差 18 倍。这个数没错，但它是带宽之比，不是延迟之比，而且假设了字节只走一次、每次都跑到标称速度、没有别人跟你抢同一个接收端。

真实的一步通信里还有两件事：几个发送方同时挤一个接收口时，每人只能分到带宽的几分之一；一批任务要等最慢的那条流结束才算完成。

把这两件事算进来，同样的字节能差出两个数量级。而最常被拿出来说的"交换机过了几级"，在这套算例里只占 51 ms 预算的 1.9%。

## 这篇的地图

全篇四块，加一个算例。

1. **拓扑买的是什么** —— 全交换只认任意两点之间的带宽，总带宽再大也补不上最差的那一对。
2. **跳数** —— 树形要过 7 级、全互联只过 1 级（`P = 128`），这个差额算出来占 51 ms 的 1.9%。
3. **incast** —— 多个发送方打同一个接收口，共享端口的带宽要除以发送方个数。
4. **平均与最大** —— 一批的完成时间取最慢的那条流，利用率是平均值除以最大值。

前三块各算一项代价，一块比一块更贴近真实的一步通信；第四块换一个角度，说明为什么"平均带宽"不能用来做容量规划。最后的算例把三项放进同一组参数里排序。

这张表是查用的，不必先记：

| 概念 | 一句话 |
|---|---|
| AlltoAll（全交换） | 每个参与方都要给其他每一个参与方各发一份不同数据的一次通信 |
| 任意两点带宽 `B_pair` | 一对端点之间能跑到的速度，单位 GB/s，由拓扑决定；全交换只认这一项 |
| 参与方 `P` 与一轮字节 `V` | 有多少张卡或节点在交换（`P`，单位个，算例 128），以及一轮要搬多少（`V`，单位 B，算例 525 MB，全批口径） |
| 拓扑跳数 `h` 与单跳延迟 `τ_hop` | 数据要过几级交换（`h`，单位跳；树形 `log₂P`、全互联 1）与每跳耗时（`τ_hop`，单位 µs，示意 2） |
| incast 扇入 `N` | 同时打向同一个接收端的发送方个数（单位个，算例 8）；接收口带宽按 `B/N` 分 |
| 每迭代通信轮数 `r` | 一轮迭代里通信发生几次（单位次），`C-06` 是 ≥3 AlltoAll + 1 AllReduce |
| 有效利用率 `U` | 无量纲，`mean/max`，一批里真正用上的比例 |

这四块的顺序也是一张排查顺序表。现场遇到"通信慢"，先看是不是 8 个以上进程在打同一个 rank，再看这批字节里有多少比例真的出机箱，最后才数交换机层级。倒过来查，通常会在最后一步找到 1.9% 的解释力，然后继续慢。

## 第一块 · 拓扑买的是什么

这块要回答的是：给全交换买网络，钱该花在总带宽上，还是花在别的什么地方。

全交换（AlltoAll）是推荐模型里最重的通信形态：每个参与方都有一份自己的数据，要发给其他每一个参与方，每人一份不同的；一轮走完，每个参与方手里凑齐了来自所有人的分片。

判断一条网络适不适合承载它，只需要问一句：任意两点之间能不能跑满。这句话写进式子，就是那个取最小值的 `min`：

```
T ≈ (P-1)/P · V / min_{i≠j} B_pair(i, j)
```

左边是一轮全交换的时间。`V` 是一轮要搬的字节，`P` 是参与方个数，分母是"所有点对里最慢的那一对"的带宽。前面的 `(P-1)/P` 扣掉发给自己那一份，`P` 很大时接近 1。

这个式子说的是：整体进度由最慢的一对决定。一条总带宽很大的网络，只要有一对端点之间只有窄路，全交换就卡在那一对上。

### 为什么总带宽不够

先把表里的形态说清楚。胖树（fat tree）把节点接在叶子交换机上，再用脊交换机把叶子连起来；脊层的总带宽小于叶子层之和时叫超售（oversubscription），`k:1` 就是脊上只给了叶子总带宽的 1/k。rail-optimized 让每张卡接到"同号"的叶子交换机，同号的卡之间直连。3D torus 是三个维度各成环，邻居之间一跳直达。

| 拓扑 | 形态 | 任意两点带宽 | 端口成本 | 对 AlltoAll |
|---|---|---|---|---|
| 全互联 | 任意两节点直连 | 满速 `B`，1 跳 | `O(P)`，实际是 `O(P²)` 根线 | 最好，但扩不起来 |
| 无阻塞胖树 | leaf + spine，两级交换 | 满速 `B` | `P·B` 的脊带宽，最贵 | 好，等价于全互联 |
| 超售胖树 | 同上但 spine 收敛比 `k:1` | 同 leaf `B`，跨 spine `B/k` | 便宜 | 跨 spine 那部分先打结 |
| rail-optimized | 每张卡接到"同号" leaf，rail 内全互联 | 同 rail 满速，跨 rail 走 spine | 居中 | 好，前提是流量能按 rail 打散 |
| 3D torus | 三个维度各成环 | 满速但跳数 `O(P^{1/3})` | 每卡固定几根线 | 对邻域友好，对任意两点不友好 |

这张表怎么读：最后两列都在回答同一个问题，最差的那一对能不能跑满。全互联和 rail-optimized 说能，前者每个点对直连，后者靠 rail 内直连；无阻塞胖树也说能，代价是 `P·B` 的脊带宽，最贵；超售胖树说跨 spine 时不能，那部分先降到 `B/k`；3D torus 每一跳都是满速，但任意两点要绕 `O(P^{1/3})` 跳。

`A-06` 选的是第一行。ZionEX 的规格是每 GPU 一块专用 200 Gbps RoCE 网卡、单节点 scale-out 1600 Gbps 单向，拓扑是全互联。理由写在论文里（事实）：DLRM 的性能主导通信是 AlltoAll / ManyToMany，这类通信对"任意两节点之间的带宽"敏感，树形拓扑会在根节点打结——所有跨叶子的流量都要经过脊层，脊层不够宽就在那里堵住。

`C-06` 的立论走反面：它不换拓扑，而是换模型结构，把全局 AlltoAll 拆成"机内局部 shuffle + 塔间少量通信"。依据是带宽层级，机内是 NVLink、跨机是 RDMA/InfiniBand，"带宽低得多"（论文原话如此，没给具体数字；H100 那一代的 NVLink 是 900 GB/s 双向，见 `B-04`）。全局 AlltoAll 的延迟由最慢的跨机链路决定，机内那段高速带宽一点忙都帮不上。

三组旁证说明这件事随规模恶化，不是常数：

- `C-06` 观察到 NCCL 集合通信的 bus bandwidth 随规模急剧下降（8 GPU/节点做弱扩展）。论文只给了曲线，没有可引用的点数，所以这里只记定性。
- `B-04` 给了另一组数：集群从 8 卡扩到 128 卡，嵌入通信占比从 25% 涨到 51%。这是"占比"不是"带宽比"，但它说明同一份优化在不同规模上价值不同。
- `A-03` 给的是第三个角度：把跨组同步限制在同一台机器内（8 卡同 host），实测比跨 host 快 7×。同一份字节、同一个算法，只因为没出机箱就快 7 倍，这是 18× 在"同步"这种小消息上的另一个投影。

还有一条放大器：hybrid parallelism 每轮至少调 3 次 AlltoAll 加 1 次 AllReduce。通信次数是乘在单次代价上的，所以拓扑的短板会被乘 4 倍。

`A-12` 给了一个同量级、但尺度更小的对照：单节点内 4 卡 NVLink 下，all-to-all 仍吃掉近 12% 总时间；一旦跨节点，InfiniBand 只有 100 Gbps 而 NVLink 有 2400 Gbps，通信占比超过 50%。也就是说 18× 这个比值不是某一代的特例，它是"电信号在机箱内"和"光信号出机箱"之间的固有差，每代硬件都在这个数量级上重演一次。

全交换的代价由最慢的一对决定，拓扑的好坏就是"把最差那一对抬高"的能力。下一块先算被高估最多的那一项：跳数。

## 第二块 · 跳数

这块要回答的是：交换机多过几级，在 51 ms 的一轮里到底值多少。

跳数（hop count）是一份数据从一张卡走到另一张卡要经过几级交换。每过一级，数据要排队、被转发、再排队，延迟按级数叠加。

树形的级数随参与方数按 2 的幂增长，全互联两端直连，只有 1 跳：

```
树形：  h = log₂ P
全互联：h = 1

P = 128  →  h = 7  vs  1
τ_hop = 2 µs（示意，单跳交换 + 排队）
T_lat = 7 × 2 = 14 µs  vs  1 × 2 = 2 µs
```

`P = 128` 时树高 7 级，因为 `2^7 = 128`。单跳按 2 µs 计（示意值，含交换与排队），延迟下界是 14 µs 对 2 µs，差 12 µs。

只算一次的差额很小，麻烦的是它按通信次数累加：

```
12 µs × 4 × 20 = 960 µs ≈ 0.96 ms
0.96 / 51 = 1.9%
```

每轮 4 次集合通信（`C-06`：≥3 AlltoAll + 1 AllReduce），每迭代假设 20 轮，得到 0.96 ms，占 51 ms 预算的 1.9%。

### 什么时候它才重要

跳数只在两种负载上变成主要项：迭代很短（比如几十微秒的 LLM decode 步），或者每迭代通信轮数极多（比如 FSDP 的 per-layer 同步，`C-12` 里每层一次）。推荐训练一轮 51 ms，跳数被摊薄。

所以标题里的 18 倍不可能来自跳数。它来自带宽，而带宽那一项还要先过 incast 这一关。

## 第三块 · incast

这块要回答的是：多个发送方同时打一个接收方，会慢多少。

incast 指多个发送方同时把数据发往同一个接收方。接收端只有一个入端口，带宽 `B` 由 `N` 条流公平分享，每条流拿到 `B/N`：

```
        s0 ──┐
        s1 ──┤
        s2 ──┼──→ [ 一个接收端口, 带宽 B ] ──→ 收端
        s3 ──┤        每条流拿到 B/N
        …    │
        s7 ──┘
```

一条流送 `s` 字节要花 `s / (B/N)`，也就是 `N·s / B`；`N` 条流全部完成也是 `N·s / B`，正好等于总字节除以端口带宽。接收端把并发串行化了，字节数没变，时间一点没省。

### 有多狠

代进算例的数字：`B = 50 GB/s`、`N = 8`、每流 `s = 4.1 MB`（每卡出站量）：

```
独立走：  4.1 / 50      = 0.082 ms
incast：  8 × 0.082     = 0.66 ms       ← 8 倍
```

八条流各自只要 0.082 ms，挤在同一个端口上就变成 0.66 ms，慢 8 倍。再叠一层队头阻塞（HOL blocking）：交换机的一个出端口是共享的，被 incast 堵住的流量会连带拖慢同端口的其他流，所以受影响的不只是这 8 个发送方。

尾延迟（tail latency）是这件事在整批口径下的名字。一批里最慢的那条流决定整批完成时间，而最慢的流往往不是"平均值偏大"，是"恰好撞上了最挤的那个时刻"。拿平均带宽做的容量规划，在 incast 场景下系统性偏乐观。

`A-06` 的全互联正是从结构上消掉 incast 的一种办法：每一对都有独立路径，没有共享的根。代价也清楚，它扩不起来，这是论文自己承认的（非标准硬件，云上拿不到）。

incast 的倍数是结构性的，等于扇入个数 `N`，与字节多少无关；绝对时间才取决于每卡要发多少字节。最后一块换到"整批什么时候算完"，那里还有一项比拓扑更大的损耗。

## 第四块 · 平均与最大

这块要回答的是：一批任务里各条流快慢不一，整批的完成时间由谁决定。

一步迭代要等最后一个分片交上来，所以完成时间是各分片耗时的最大值，不是平均值。有效利用率定义为平均值除以最大值：

```
T = max_i (t_i^compute + t_i^comm)
U = mean(t_i) / max(t_i) = 1 / (max/mean)
```

`t_i^compute + t_i^comm` 是第 `i` 个分片自己的计算加通信时间。`U` 越接近 1，说明各分片越齐整，整批里被空等吃掉的时间越少。

### 一个实测的不均比

`A-03` 报的传统 MP 负载不均比是 5.70（CTR）/ 5.18（ExFM），分 4 组后降到 1.57 / 1.65。把第一组数代进去：

```
U = 1 / 5.70 = 17.5%  ≈ 18%
U = 1 / 1.57 = 63.7%
```

切分的价值不在"少传了点数据"，而在把 `max` 往 `mean` 拉。分 4 组把利用率从 18% 拉到 64%，这个幅度比任何一项通信优化都大。

这条算术同时解释三个观察：

| 观察 | 表面说法 | 同一套算术 |
|---|---|---|
| `A-03` 5.70 → 1.57 | 切得更均衡 | `U = mean/max` 从 18% 到 64% |
| `B-04` 25% → 51% | 通信占比随规模涨 | 分母（计算）缩小，分子（通信）不变 |
| `A-06` 全互联 | 消掉根节点打结 | 抬高 `min_{i≠j} B_pair` |

三个观察用的是同一个前提：一批的墙钟由最慢的那条线决定。换个口径看得更清楚，把利用率折算成等效卡数：

| 不均比 | 利用率 `U` | 128 卡的等效卡数 |
|---|---|---|
| 1.00 | 100% | 128 |
| 1.57 | 63.7% | 82 |
| 5.18 | 19.3% | 25 |
| 5.70 | 17.5% | 22 |

5.70 那一行意味着：你付了 128 张卡的钱，拿到 22 张卡的吞吐。这比"通信慢 18 倍"更能解释账单。

口径要标一句。`A-03` 的 imb ratio 是分片大小的不均，不是网络尾延迟；论文页也没写清它是 `max/min` 还是 `max/mean`。若按 `max/min` 解释，两点分布下 `U = 2r/(1+r)`，5.70 对应约 59% 而不是 18%。两种解释差三倍，⚠️ 待核实。本篇按 `max/mean` 走，与任务书口径一致，但结论对定义敏感这件事要记着。

完成时间取最大，纯收益按 `mean/max` 打折。三项代价各自算完，下面放进同一组参数里比一次。

## 算例：把 18 倍拆开算

<div class="example">

这一步在算什么：把同一份 525 MB 分别按路径带宽、incast、整批完成时间算一遍，看三项各占多少，再按真实的分层路径重算一次。

设定：[贯穿全教程的算例](../guide/running-example)，每迭代 525 MB，`P=128`，预算 51 ms。

⚠️ 先明确口径：525 MB 是全批去重量，每卡出站约 4.1 MB。下文凡出现 525 MB 的表都标了"全批"，每卡口径把字节与时间同时除以 128。比值（18×、8 倍、145 倍）两种口径完全相同，只有"占 51 ms 多少"会变。

第一步：三条路径，同一份字节

```
机内 NVLink 900 GB/s         525 / 900 = 0.58 ms
跨机 RDMA ~50 GB/s           525 / 50  = 10.5 ms
A-06 单卡 200 Gbps = 25 GB/s 525 / 25  = 21.0 ms
```

`900 / 50 = 18`，这就是标题里的那个数。它有一个隐藏前提：整个 525 MB 都走同一条路。真实负载是分层的，机内那段走 NVLink、跨机那段走 RDMA，所以 18× 只在"同一段字节被从机内搬到机外"时成立。

`C-06` 做的恰好是这件事的反面：把跨机的 all-to-all 换成机内 shuffle。但论文自己承认（事实）：SPTT 并不减少线上总字节数，收益来自"同样的数据量在小 world size 下跑更快"和"机内那部分走 NVLink"。

第二步：incast

```
全批口径（525 MB）：
N = 8，B = 50 GB/s  →  B_eff = 6.25 GB/s
525 MB ÷ 6.25 GB/s = 84 ms

每卡口径（4.1 MB）：
4.1 MB ÷ 6.25 GB/s = 0.66 ms
```

全批口径下 84 ms 超出 51 ms 预算 65%，比无阻塞慢 8 倍、比机内慢 145 倍。但这是"整批打到一个接收端"的极端形状；每卡口径下同一件事只有 0.66 ms。incast 的倍数是结构性的，绝对时间取决于每卡要发多少字节——global batch 到 256K（`A-06` 的配置）时，每卡出站 65 MB，incast 才会变成毫秒级的大项。

第三步：完成时间与利用率

```
imb ratio 1.57（A-03 四组）：max = 51 × 1.57 = 80.1 ms
  U = 63.7%，吞吐 = 16,384 / 0.0801 ≈ 205K 样本/秒
imb ratio 5.70（A-03 传统 MP）：max = 51 × 5.70 = 290.7 ms
  U = 17.5%，吞吐 = 16,384 / 0.2907 ≈ 56K 样本/秒
```

第四步：三项的权重排序

```
incast（N=8，全批）  84 - 10.5 = 73.5 ms
带宽（跨机 vs 机内，全批） 10.5 - 0.58 = 9.9 ms
跳数（7 vs 1）        0.96 ms
```

排序是 incast 大于带宽、带宽大于跳数，相差三个量级。调优顺序照这个排序走就行：先问"有没有多点打一点"，再问"这段字节走的是哪条路"，最后才问交换机跳了几级。换成每卡口径，前三项同时除以 128，排序不变。

第五步：把分层真实地算一遍

算例的 128 张卡按 8 卡一节点，是 16 个节点。假设 7/8 的字节在机内交换、1/8 跨机（这是假定，用于演示量级）：

```
全批口径（525 MB）
机内：525 × 7/8 = 459 MB ÷ 900 GB/s = 0.51 ms
跨机：525 × 1/8 = 66 MB  ÷ 50  GB/s = 1.31 ms
串行相加：1.82 ms；两者重叠：max(0.51, 1.31) = 1.31 ms

每卡口径（4.1 MB）：0.014 ms（重叠），全部 ÷128
```

对照第一步的"全部跨机 10.5 ms"，分层把它压到 1.8 ms，5.8×。这就是 `C-06` 声称的收益来源，也是它为什么坚持把塔 pin 在单台主机内的原因——塔一旦被迫横跨主机，那个 7/8 就守不住了。

算例里能抄的只有排序。哪些参数经不起追问，下面逐条列出来。

## 模型在哪里不成立

- 拓扑参数是厂商规格，不是论文实测：NVLink 900 GB/s 双向（`B-04` 的 DGX H100 规格）、IB 8×400 Gbps（同）、每 GPU 200 Gbps RoCE（`A-06` 的 ZionEX）、跨节点 800 Gbps（`C-12` 的 RoCE）。这些是端口能力，端到端能拿到多少要看协议、消息尺寸和拥塞，不同集群之间不能直接套用。
- `C-06` 的实验网络过于理想。原文写明实验环境"保证任意两台主机之间全双工带宽、无超售"。真实共享集群很少这么干净，超售会放大局部性收益（对它有利），也会放大洗牌开销（对它不利），方向不确定，⚠️ 待核实。
- `A-06` 的全互联买不到。每 GPU 独立 RoCE 网卡加全互联是非标准设计，论文自己的局限一节承认云上拿不到，所以 model-I 那个 75% 扩展效率无法在通用集群复现。
- NCCL bus bandwidth 的下降只有定性。`C-06` 的 Fig.5 是曲线，论文页没有可引用的数值，所以本篇没有给它任何数字；要引用得回原文读图。
- `A-03` 的 5.70 不是网络尾延迟。它是分片大小的不均，成因是表大小倾斜，与交换机的排队无关。用同一套 `mean/max` 算术是合理的，但它不叫"网络尾延迟 5.70"。
- imb ratio 的定义未在论文页给出（`max/min` 还是 `max/mean`），两种解释让利用率差三倍，⚠️ 待核实。
- `B-04` 的 25%→51% 是占比不是带宽比。它随规模上升，但上升的是"通信在迭代里占多少"，不是"网络变慢了多少"。
- 3D torus 那行的跳数 `O(P^{1/3})` 是结构推导，没有论文实测；本篇只把它当定性对照用。
- 18× 本身也可能被误读成延迟比。第 6 章的对照是带宽，若按延迟算，同一份字节的差距会小得多——延迟几乎不随带宽线性变化。两件事分开记。
- "差 18 倍"在文献里至少有三组数：教程/`C-06` 用的 900 GB/s 对 ~50 GB/s、`A-12` 的 2400 Gbps 对 100 Gbps、`B-04` 的 NVLink 900 GB/s 双向对节点间 IB 8×400 Gbps。三组都指向"机内与跨机差一个量级"，但比值从 2.25× 到 24× 都有，差别来自"双向还是单向""整机还是单口""8 张卡还是 1 张卡"。引用时写清两侧各自的口径，否则同一个 18× 可以被改成 2× 也可以被改成 24×。
- 尾延迟不能靠平均值规划。本篇的 incast 模型假设 `N` 条流公平分享，真实交换机上还有优先级流控（PFC）、拥塞标记（ECN）、重传，以及别的租户。所以 `B_eff = B/N` 是下界性质的估计，不是预测值。
- 本篇的 0.96 ms 与 1.9% 依赖"每迭代 20 轮"这个假设。轮数是推导用的，不是论文给的；`C-06` 只说每轮 ≥3 AlltoAll + 1 AllReduce。轮数翻 10 倍，跳数项就到 19%，那时它才值得单独优化。
- 全互联不是唯一解。`C-06` 用"改模型结构"绕开跨机 all-to-all，`A-03` 用"缩小组"绕开，`A-06` 用"换拓扑"硬扛。
- 三条路的成本结构完全不同：改模型最贵（要重训、checkpoint 不兼容），缩组最便宜（改配置），换拓扑最不可得（要换硬件）。

<div class="takeaway">

**本篇结论**：18× 是带宽比，而且是最乐观的那一版——它假设字节只走一次、每次都跑到标称速度、没有第二个人抢接收端。

把 incast 和 `max/mean` 算进来，同样的字节能差两个数量级。调优顺序是 incast → 带宽 → 跳数。

规模也要看：在 16,384 的 global batch 下，每卡只有 4.1 MB，三者在 51 ms 预算里都不到 1%，这个排序只在 payload 变大（batch ≥ 256K、或卡数很少）时才决定墙钟。它决定的是同一份字节的效率，不是"这一步慢不慢"。

一个自检办法：把同一次 all-to-all 分别在单机内和跨两台机器做一遍。若实测比值远大于 18，跨机那一侧多半已经吃到 incast 或超售了，问题不在拓扑形态，在流量形状。
