# 网络 5. 拓扑与尾延迟：同样的字节，为什么差 18 倍

<div class="deep-anchor">

**在教程的哪一层** 对应[第 6 章](../guide/06-communication)里 `C-06` 那一段"机内 shuffle 走 NVLink、全局 all-to-all 走 IB，差 18 倍"；这里拆开这 18 倍由什么构成，以及什么时候轮不到你选。

</div>

## 本篇要算的问题

第 6 章给了一个很抓人的对照：机内 900 GB/s，跨机 50 GB/s，18 倍。这个数没错，但它是最乐观的版本——它假设字节只走一次、每次都能打满、没有第二个发送方跟你抢同一个接收端。

本篇把"同样的字节差 18 倍"拆成三个独立的项，各自算一遍：

1. 带宽项：路径本身的上限差，也就是那个 18×；
2. incast 项：多个发送方同时打一个接收方，有效带宽变成 `B/N`；
3. 尾延迟项：`log₂P` 跳 vs 1 跳，以及 batch 完成时间为什么要取 `max`。

拆完会发现**三者的量级不在一个层次上**，而选型时最容易被拿出来讲的那个（跳数）恰恰最小。

## 先给结论

- 18× 是带宽比（NVLink 900 GB/s vs 跨机 ~50 GB/s），不是延迟比。两者不能互换，混用会把结论放大几十倍。
- AlltoAll **只认"任意两点带宽"，不认总带宽**。所以树形会在根节点打结，全互联和 rail-optimized 都是在买"任意两点"这件事，不是在买总带宽。
- 延迟下界确实是 `log₂P` vs 1，但 `P=128` 时它只占 51 ms 预算的 1.9%。它是真的，但它解释不了 18×。
- batch 完成时间是 `max_i(t_i)`，有效利用率 `U = mean/max`。`A-03` 的不均比 5.70 换过来约 18%——这是比拓扑更狠的一项。

这四条合起来是一张排查顺序表。造一个"通信慢"的现场，先看是不是 8 个以上进程在打同一个 rank（incast），再看这批字节里有多少比例真的出机箱（带宽），最后才数交换机层级（跳数）。倒过来查，通常会在最后一步找到 1.9% 的解释力，然后继续慢。

## 符号与模型

| 符号 | 含义 | 单位 | 出处 |
|---|---|---|---|
| `P` | 参与方（GPU / 节点）数 | 个 | 算例取 128 |
| `V` | 一轮要搬的字节 | B | 算例取 525 MB |
| `h` | 拓扑跳数 | 跳 | 树 `log₂P`，全互联 1 |
| `τ_hop` | 单跳延迟 | µs | 示意 2 |
| `B_pair` | 任意两点之间的带宽 | GB/s | 由拓扑决定 |
| `N` | incast 扇入的发送方数 | 个 | 算例取 8 |
| `r` | 每迭代通信轮数 | 次 | `C-06`：≥3 AlltoAll + 1 AllReduce |
| `U` | 有效利用率 | — | `mean/max` |

四个式子，后面全靠它们：

```
AlltoAll 完成时间    T ≈ (P-1)/P · V / min_{i≠j} B_pair(i, j)
延迟下界            T_lat = h · τ_hop
incast 有效带宽      B_eff = B / N
batch 完成时间       T = max_i t_i,   U = mean(t_i) / max(t_i)
```

注意第一式里的 `min`。AlltoAll 的代价由**最差的两点**决定，不是由平均值决定。这一条是所有拓扑设计的起点。

## 推导

### 一、四种拓扑，问的是同一个问题

判断一种拓扑适不适合 AlltoAll，只需要问一句：任意两点之间能不能满速？总带宽再大也补不上某一对的短板。

| 拓扑 | 形态 | 任意两点带宽 | 端口成本 | 对 AlltoAll |
|---|---|---|---|---|
| 全互联 | 任意两节点直连 | 满速 `B`，1 跳 | `O(P)`，实际是 `O(P²)` 根线 | 最好，但扩不起来 |
| 无阻塞胖树 | leaf + spine，两级交换 | 满速 `B` | `P·B` 的脊带宽，最贵 | 好，等价于全互联 |
| 超售胖树 | 同上但 spine 收敛比 `k:1` | 同 leaf `B`，跨 spine `B/k` | 便宜 | 跨 spine 那部分先打结 |
| rail-optimized | 每张卡接到"同号" leaf，rail 内全互联 | 同 rail 满速，跨 rail 走 spine | 居中 | 好，前提是流量能按 rail 打散 |
| 3D torus | 三个维度各成环 | 满速但跳数 `O(P^{1/3})` | 每卡固定几根线 | 对邻域友好，对任意两点不友好 |

`A-06` 选的是第一行。ZionEX 的规格是每 GPU 一块专用 200 Gbps RoCE 网卡、单节点 scale-out 1600 Gbps 单向，拓扑是全互联。理由写在论文里（事实）：DLRM 的性能主导通信是 AlltoAll / ManyToMany，这类通信对"任意两节点之间的带宽"敏感，树形拓扑会在根节点打结。

这段论证值得逐字读一遍，因为它把"买总带宽"和"买任意两点"分开了。全互联买的不是带宽总量，买的是**最差的那一对也不慢**——式子里那个 `min` 被抬高了。

`C-06` 的立论走反面：它不换拓扑，而是换模型结构，把全局 AlltoAll 拆成"机内局部 shuffle + 塔间少量通信"。它的依据是带宽层级——机内是 NVLink、跨机是 RDMA/InfiniBand，"带宽低得多"（论文原话如此，没给具体数字；H100 那一代的 NVLink 是 900 GB/s 双向，见 `B-04`）；而全局 AlltoAll 的延迟由最慢的跨机链路决定，机内那段高速带宽一点忙都帮不上。

三组旁证说明这件事随规模恶化，不是常数：

- `C-06` 观察到 NCCL 集合通信的 bus bandwidth 随规模急剧下降（8 GPU/节点做弱扩展）。论文只给了曲线，没有可引用的点数，所以这里只记定性。
- `B-04` 给了另一组数：集群从 8 卡扩到 128 卡，嵌入通信占比从 25% 涨到 51%。这是"占比"不是"带宽比"，但它说明同一份优化在不同规模上价值不同。
- `A-03` 给的是第三个角度：把跨组同步限制在同一台机器内（8 卡同 host），实测比跨 host 快 7×。同一份字节、同一个算法，只因为没出机箱就快 7 倍——这是 18× 在"同步"这种小消息上的另一个投影。

还有一条放大器：hybrid parallelism 每轮至少调 3 次 AlltoAll + 1 次 AllReduce。通信次数是乘在单次代价上的，所以拓扑的短板会被乘 4 倍。

`A-12` 给了一个同量级、但尺度更小的对照：单节点内 4 卡 NVLink 下 all-to-all 仍吃掉近 12% 总时间；一旦跨节点，InfiniBand 只有 100 Gbps 而 NVLink 有 2400 Gbps，通信占比超过 50%。也就是说 18× 这个比值不是某一代的特例，它是"电信号在机箱内"和"光信号出机箱"之间的固有差，每代硬件都在这个数量级上重演一次。

### 二、跳数：`log₂P` vs 1，算出来比想象的小

```
树形：   h = log₂ P
全互联： h = 1

P = 128  →  h = 7  vs  1
τ_hop = 2 µs（示意，单跳交换 + 排队）
T_lat = 7 × 2 = 14 µs  vs  1 × 2 = 2 µs
```

差额 12 µs。乘上每轮 4 次通信、每迭代假设 20 轮：

```
12 µs × 4 × 20 = 960 µs ≈ 0.96 ms
0.96 / 51 = 1.9%
```

1.9%。这就是跳数在算例参数下的**真实权重**。

这不是说跳数不重要。它说明跳数只在两种情况下变成主要项：迭代很短（比如几十微秒的 LLM decode 步），或者每迭代通信轮数极多（比如 FSDP 的 per-layer 同步，`C-12` 里每层一次）。在推荐训练这种 51 ms 一轮的负载上，跳数是被摊薄的。

所以"18 倍"这个标题里的差距不可能来自跳数。它来自带宽，而且被 incast 放大了。

### 三、incast：`B` 变成 `B/N`

`N` 个发送方同时打同一个接收方，接收端只有一个出（入）端口：

```
        s0 ──┐
        s1 ──┤
        s2 ──┼──→ [ 一个接收端口, 带宽 B ] ──→ 收端
        s3 ──┤        每条流拿到 B/N
        …    │
        s7 ──┘
```

```
接收端口带宽 B，N 条流公平分享
→ 每条流拿到 B/N
→ 单条流送 s 字节的完成时间 = s / (B/N) = N·s / B
→ 全部完成 = N·s / B = 总字节 / B   （接收端被串行化了）
```

代进去看有多狠。`B = 50 GB/s`、`N = 8`、每流 `s = 4.1 MB`：

```
独立走：  4.1 / 50      = 0.082 ms
incast：  8 × 0.082     = 0.66 ms       ← 8 倍
```

再叠一层：队头阻塞。交换机的一个出端口是共享的，被 incast 堵住的流量会连带拖慢同端口的其他流，所以受影响的不只是这 8 个发送方。

尾延迟是这件事在 batch 口径下的名字。一批里最慢的那条流决定整批完成时间，而最慢的流往往不是"平均值偏大"，是"恰好撞上了最挤的那个时刻"。所以拿平均带宽做的容量规划，在 incast 场景下系统性偏乐观。

`A-06` 的全互联正是**从结构上消掉 incast** 的一种办法：每一对都有独立路径，没有共享的根。代价也清楚——它扩不起来，这是论文自己承认的（非标准硬件，云上拿不到）。

### 四、batch 完成时间取 `max`，利用率是 `mean/max`

一次迭代的完成时间不是平均，是最后一个分片：

```
T = max_i (t_i^compute + t_i^comm)
U = mean(t_i) / max(t_i) = 1 / (max/mean)
```

`A-03` 报的传统 MP 负载不均比是 5.70（CTR）/ 5.18（ExFM），分 4 组后降到 1.57 / 1.65。把第一组数代进去：

```
U = 1 / 5.70 = 17.5%  ≈ 18%
U = 1 / 1.57 = 63.7%
```

也就是说，切分的价值不在"少传了点数据"，而在把 `max` 往 `mean` 拉。分 4 组把利用率从 18% 拉到 64%，这个数比任何通信优化都大。

这条算术把两件事统一了：

| 观察 | 表面说法 | 同一套算术 |
|---|---|---|
| `A-03` 5.70 → 1.57 | 切得更均衡 | `U = mean/max` 从 18% 到 64% |
| `B-04` 25% → 51% | 通信占比随规模涨 | 分母（计算）缩小，分子（通信）不变 |
| `A-06` 全互联 | 消掉根节点打结 | 抬高 `min_{i≠j} B_pair` |

三个观察用的是同一个前提：**批处理的墙钟由最慢的那条线决定**。

换个口径看得更清楚——把利用率折算成"等效卡数"：

| 不均比 | 利用率 `U` | 128 卡的等效卡数 |
|---|---|---|
| 1.00 | 100% | 128 |
| 1.57 | 63.7% | 82 |
| 5.18 | 19.3% | 25 |
| 5.70 | 17.5% | 22 |

5.70 那一行意味着：你付了 128 张卡的钱，拿到 22 张卡的吞吐。这比任何"通信慢 18 倍"的说法都更能解释账单。

这里必须标一句口径问题。`A-03` 的 imb ratio 是分片大小的不均，不是网络尾延迟；论文页也没写清它是 `max/min` 还是 `max/mean`。若按 `max/min` 解释，两点分布下 `U = 2r/(1+r)`，5.70 对应约 59% 而不是 18%。两种解释差三倍，⚠️ 待核实。本篇按 `max/mean` 走，与任务书口径一致，但结论对定义敏感这件事要记住。

## 算例

<div class="example">

设定：[贯穿全教程的算例](../guide/running-example)，每迭代 525 MB，`P=128`，预算 51 ms。

⚠️ 先明确口径：525 MB 是全批去重量，每卡出站约 4.1 MB。下文凡出现 525 MB 的表都标了"全批"，每卡口径把字节与时间同时 ÷128；**比值（18×、8 倍、145 倍）两种口径完全相同**，只有"占 51 ms 多少"会变。

第一步：三条路径，同一份字节

```
机内 NVLink 900 GB/s         525 / 900 = 0.58 ms
跨机 RDMA ~50 GB/s           525 / 50  = 10.5 ms
A-06 单卡 200 Gbps = 25 GB/s 525 / 25  = 21.0 ms
```

`900 / 50 = 18`。这就是标题里的那个数。但它有个隐藏前提：整个 525 MB 都走同一条路。真实的负载是分层的——机内那段走 NVLink、跨机那段走 RDMA，所以 18× 只在"同一段字节被从机内搬到机外"时成立。

`C-06` 做的恰好是这件事的反面：它把跨机的 all-to-all 换成机内 shuffle。但论文自己承认（事实）：SPTT 并不减少线上总字节数，收益来自"同样的数据量在小 world size 下跑更快"和"机内那部分走 NVLink"。

第二步：incast

```
全批口径（525 MB）：
N = 8，B = 50 GB/s  →  B_eff = 6.25 GB/s
525 MB ÷ 6.25 GB/s = 84 ms

每卡口径（4.1 MB）：
4.1 MB ÷ 6.25 GB/s = 0.66 ms
```

全批口径下 84 ms 超出 51 ms 预算 65%，比无阻塞慢 8 倍、比机内慢 145 倍。但这是"整批打到一个接收端"的极端形状；每卡口径下同一件事只有 0.66 ms。**incast 的倍数是结构性的，绝对时间取决于每卡要发多少字节**——global batch 到 256K（`A-06` 的配置）时，每卡出站 65 MB，incast 才会变成毫秒级的大项。

第三步：完成时间与利用率

```
imb ratio 1.57（A-03 四组）：max = 51 × 1.57 = 80.1 ms
  U = 63.7%，吞吐 = 16,384 / 0.0801 ≈ 205K 样本/秒
imb ratio 5.70（A-03 传统 MP）：max = 51 × 5.70 = 290.7 ms
  U = 17.5%，吞吐 = 16,384 / 0.2907 ≈ 56K 样本/秒
```

第四步：三项的权重排序

```
incast（N=8，全批）  84 - 10.5 = 73.5 ms
带宽（跨机 vs 机内，全批） 10.5 - 0.58 = 9.9 ms
跳数（7 vs 1）        0.96 ms
```

排序是 **incast > 带宽 > 跳数**，相差三个量级。调优顺序照抄这个排序就行：先问"有没有多点打一点"，再问"这段字节走的是哪条路"，最后才问交换机跳了几级。换成每卡口径，前三项同时 ÷128，排序不变。

第五步：把分层真实地算一遍

算例的 128 张卡按 8 卡一节点，是 16 个节点。若 7/8 的字节在机内交换、1/8 跨机（这是假定，用于演示量级）：

```
全批口径（525 MB）
机内：525 × 7/8 = 459 MB ÷ 900 GB/s = 0.51 ms
跨机：525 × 1/8 = 66 MB  ÷ 50  GB/s = 1.31 ms
串行相加：1.82 ms；两者重叠：max(0.51, 1.31) = 1.31 ms

每卡口径（4.1 MB）：0.014 ms（重叠），全部 ÷128
```

对照第一步的"全部跨机 10.5 ms"，分层把它压到 1.8 ms，5.8×。这就是 `C-06` 声称的收益来源，也是它为什么坚持把塔 pin 在单台主机内的原因——塔一旦被迫横跨主机，那个 7/8 就守不住了。

## 代价与边界

- **拓扑参数是厂商规格，不是论文实测**。NVLink 900 GB/s 双向（`B-04` 的 DGX H100 规格）、IB 8×400 Gbps（同）、每 GPU 200 Gbps RoCE（`A-06` 的 ZionEX）、跨节点 800 Gbps（`C-12` 的 RoCE）。这些是端口能力，端到端能拿到多少要看协议、消息尺寸和拥塞。不同集群之间不可直接套用。
- `C-06` 的实验网络过于理想。原文写明实验环境"保证任意两台主机之间全双工带宽、无超售"。真实共享集群很少这么干净，超售会放大局部性收益（对它有利），也会放大洗牌开销（对它不利），方向不确定，⚠️ 待核实。
- `A-06` 的全互联买不到。每 GPU 独立 RoCE 网卡 + 全互联是非标准设计，论文自己的局限一节承认云上拿不到，所以 model-I 那个 75% 扩展效率无法在通用集群复现。
- NCCL bus bandwidth 的下降只有定性。`C-06` 的 Fig.5 是曲线，论文页没有可引用的数值，所以本篇没有给它任何数字。要引用必须回原文读图。
- **`A-03` 的 5.70 不是网络尾延迟**。它是分片大小的不均，成因是表大小倾斜，与交换机的排队无关。用同一套 `mean/max` 算术是合理的，但别说成"网络尾延迟 5.70"。
- imb ratio 的定义未在论文页给出（`max/min` 还是 `max/mean`），两种解释让利用率差三倍，⚠️ 待核实。
- `B-04` 的 25%→51% 是占比不是带宽比。它随规模上升，但上升的是"通信在迭代里占多少"，不是"网络变慢了多少"。
- 3D torus 那行的跳数 `O(P^{1/3})` 是结构推导，没有论文实测；本篇只把它当定性对照用。
- 18× 本身也可能被误读成延迟比。第 6 章的对照是带宽，若按延迟算，同一份字节的差距会小得多——延迟几乎不随带宽线性变化。两件事分开记。
- **"差 18 倍"在文献里至少有三组数**：教程/`C-06` 用的 900 GB/s vs ~50 GB/s、`A-12` 的 2400 Gbps vs 100 Gbps、`B-04` 的 NVLink 900 GB/s 双向 vs 节点间 IB 8×400 Gbps。三组都指向"机内与跨机差一个量级"，但比值从 2.25× 到 24× 都有——差别来自"双向还是单向""整机还是单口""8 张卡还是 1 张卡"。引用时必须写清两侧各自的口径，否则同一个 18× 可以被改成 2× 也可以被改成 24×。
- 尾延迟不能靠平均值规划。本篇的 incast 模型假设 N 条流公平分享，真实交换机上还有 PFC、ECN、重传、以及别的租户。所以 `B_eff = B/N` 是下界性质的估计，不是预测值。
- 本篇的 0.96 ms 与 1.9% 依赖"每迭代 20 轮"这个假设。轮数是推导用的，不是论文给的；`C-06` 只说每轮 ≥3 AlltoAll + 1 AllReduce。轮数翻 10 倍，跳数项就到 19%，那它才值得单独优化。
- 全互联不是唯一解。`C-06` 用"改模型结构"绕开跨机 all-to-all，`A-03` 用"缩小组"绕开，`A-06` 用"换拓扑"硬扛。
- 三条路的成本结构完全不同：改模型最贵（要重训、checkpoint 不兼容），缩组最便宜（改配置），换拓扑最不可得（要换硬件）。

<div class="takeaway">

**本篇结论**：18× 是带宽比，而且是最乐观的那一版——它假设字节只走一次、每次都打满、没有第二个人抢接收端。

把 incast 和 `max/mean` 算进来，同样的字节能差两个数量级。调优顺序是 incast → 带宽 → 跳数，别倒过来。

注意规模：在 16,384 的 global batch 下，每卡只有 4.1 MB，三者在 51 ms 预算里都不到 1%，这个排序只在 payload 变大（batch ≥ 256K、或卡数很少）时才决定墙钟。它决定的是**同一份字节的效率**，不是"这一步慢不慢"。

一个自检办法：把同一次 all-to-all 分别在单机内和跨两台机器做一遍。若实测比值远大于 18，跨机那一侧多半已经吃到 incast 或超售了，问题不在拓扑形态，在流量形状。

</div>
