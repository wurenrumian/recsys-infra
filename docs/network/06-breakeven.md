# 网络 6. 通信优化的盈亏平衡：四个反直觉结果的同一张表

## 本篇要算的问题

前面三篇分别处理了等待（第 4 篇）、路径（第 5 篇）和字节（这一篇）。字节这一层被讲得最多，也最容易被讲错，因为论文报的通常是局部加速比。

四个结果放在一起看很刺眼：

| 论文 | 报了什么 | 端到端 |
|---|---|---|
| `A-14` | all-to-all 快 8.6× | 1.38× |
| `B-14` | 同一份调度，TCP 2.11×、RDMA 1.61× | — |
| `B-11` | 通信量降 4× | 变慢（61 → 110 ms） |
| `A-10` | 消除 75% 的迭代开销 | 5.6×，但另一个模型只有 1.2× |

这四个数看起来互不相干，其实都能用一个成本式和一条 Amdahl 关系解释。本篇要算的就是：**什么时候压缩值得做，什么时候它只是在给别人做贡献**。

## 先给结论

- 端到端收益的上限由瓶颈占比 `f` 决定，不由局部加速比决定。`A-14` 的 1.38× 精确等于 Amdahl 值 1.382，误差 0.1%。
- 网络越快，同一份传输量节省越不值钱。`B-14` 的 TCP 2.11× 与 RDMA 1.61× 是同一份 `q`、两个 `f`。
- 压缩率不是收益，**压/解压吞吐才是**。盈亏平衡带宽是 `B* = (1-1/CR) / (1/B_c + 1/B_d)`，`A-14` 的压缩器在 32.1 GB/s 以上就不划算了。
- 重叠口径下条件更简单：只要 `min(B_c, B_d) > B_net` 就赚，此时压缩率只决定省多少，不决定赚不赚。

## 符号与模型

| 符号 | 含义 | 单位 | 出处 |
|---|---|---|---|
| `V` | 每迭代要传的字节 | GB | 算例 0.525 |
| `B_net` | 单方有效网络带宽 | GB/s | `B-09`：100 Gb → 12.5（换算） |
| `B_c` / `B_d` | 压缩 / 解压吞吐 | GB/s | `A-14`：40.5 / 205.4 |
| `CR` | 压缩率 | × | `A-14`：19.9 平均 |
| `f` | 被优化部分占原墙钟的比例 | — | `A-14`：31.3% |
| `s` | 该部分的局部加速比 | × | `A-14`：8.6 |
| `q` | 传输量被省掉的比例 | — | `B-14`：48%–89% |
| `α` | 单条消息固定开销 | µs | 第 6 章 50 |
| `m` | 每轮消息条数 | 条 | 碎片化程度 |

统一成本式，四项分开写，每项写清依赖谁：

```
T = T_transfer + T_codec + T_queue + T_sync

T_transfer = V / B_net                    依赖 V、B_net
T_codec    = V / B_c + V / B_d            依赖 V、两端吞吐
T_queue    = α · m                        依赖消息条数，不依赖字节数
T_sync     = max_i t_i                    见第 4、5 篇；可重叠时为 0
```

**哪些能重叠，决定了后面的两种口径**：

```
可重叠：T_codec 与 T_transfer（GPU 上压、网卡同时在发）
不可重叠：T_sync（屏障）、T_queue 里的 kernel launch（串在同一个流上）
```

Amdahl 关系用这一条：

```
S = 1 / ( (1 - f) + f / s )
```

## 推导

### 一、`A-14`：8.6× 只值 1.38×，而且三个数字自洽

把 `f = 0.313`、`s = 8.6` 代进去，一步一步写：

```
1 - f        = 0.687
f / s        = 0.313 / 8.6 = 0.036395
分母         = 0.687 + 0.036395 = 0.723395
S            = 1 / 0.723395 = 1.3824
```

实测是 1.38×。差 0.2%。

真正有意思的不是这个吻合，而是它和论文另一个数字的关系。论文报"压缩后 all-to-all 占比降到 5.03%"。用上面的中间量算：

```
压缩后 all-to-all 占新总时间的比例
= 0.036395 / 0.723395
= 0.05031
= 5.03%
```

**完全对上。** 31.3%、8.6×、5.03%、1.38× 四个数在 Amdahl 关系下互相约束，误差在千分位。

这个自洽说明了一件具体的事：`s = 8.6` 是墙钟意义上的加速比，不是"压缩率换算出来的理论值"。如果压/解压在关键路径上占了一部分，那么实测的 all-to-all 时间会比 `0.036395` 大，反推出的占比会大于 5.03%，`S` 也会小于 1.382。三项数字同时对上，只能解释为 **codec 开销被完全隐藏在通信后面**。

用成本式说：`T_codec` 被 `T_transfer` 掩盖了，所以 `T` 里看不到它。这就是"重叠"的价值——同样的压缩器不重叠时，`s` 会明显低于 8.6。

顺带修一个常见的口径错误。有的地方算成"31.3% − 5.03% = 26.3%，所以上限 1/(1−0.263) ≈ 1.36×"。这个算法把"占旧总时间的比例"和"占新总时间的比例"混在一个减法里了。正确口径是省下 27.66 个百分点：

```
省下 = 0.313 - 0.036395 = 0.2766
1 / (1 - 0.2766) = 1.3824
```

两个算法差 0.02，方向一致，但只有后者能和 1.38× 对上到小数点后两位。

### 二、`B-14`：网络越快，同一份节省越不值钱

`B-14` 报的是"嵌入传输减少 48%–89%"，端到端最高 2.11×（TCP）/ 1.61×（RDMA），网络都是 100 Gbps 以太网。

用 `q` 表示省掉的比例，端到端就是：

```
S = 1 / ( (1 - f) + f (1 - q) )
  = 1 / (1 - f·q)
```

注意 `S` 只依赖乘积 `f·q`，而 `f` 本身是 `V/(B_net·T)` 量级——带宽越高，`f` 越小。于是：

```
TCP：  1 - 1/2.11 = 0.5261 = f_TCP · q
RDMA： 1 - 1/1.61 = 0.3789 = f_RDMA · q

同一份 q，两个 f 的比：0.5261 / 0.3789 = 1.39
```

结论可以直接读出来：同样的传输量节省，**在 TCP 上的价值是 RDMA 上的 1.39 倍**。原因不是 Herald 在 RDMA 上做得差，是分母变了。

再往前推一步，把这个趋势写成可操作的判据。若带宽提高到 `k` 倍，`f` 降到 `f/k`，要维持同一个 `S` 需要：

```
f/k · q' = f · q   →   q' = k · q
```

带宽翻倍，省掉的比例也得翻倍。而 `q ≤ 1`，所以这条路有硬顶：当 `f/k → 0` 时 `S → 1`。`B-14` 论文页里那句"网络越快它越不值钱"，在式子上就是这个。

### 三、`B-11`：两个不同的 8×，和一次诚实的失败

`B-11` 常被引成"压缩 8×，通信快 4×"，这两件事必须拆开：

| 数字 | 是什么 | 谁的功劳 | 有损吗 |
|---|---|---|---|
| 2.161 GB → 2.010 MB | 稀疏梯度只传非零行 | PyTorch `EmbeddingBag` 的 specified sparsity | 无损 |
| 2.161 GB → 0.270 GB | 模型体积 | `B-11` 的 INT4 量化 | 有损（精度反而升） |
| 2.010 MB → 0.509 MB | 通信量 | `B-11` 的 INT8 梯度 + 只给 MLP 做误差补偿 | 有损（−0.057% acc） |

三行里只有一个 8×：第二行是模型体积（2.161 GB → 0.270 GB）。第一行是 1075×（2.161 GB → 2.010 MB），第三行是 3.95×（2.010 MB → 0.509 MB）。所以"压缩 8×、通信快 4×"这句话把模型大小和通信量两个不同的 8× 混成了一个。

真正值得看的是第三行带来的后果（事实，Table 4 脚注 3）：每迭代延迟从 61 ms 涨到 110 ms，原因是 PyTorch 的稀疏 tensor all-reduce 不支持低精度算术，加上稀疏张量合并（coalescing）的开销。作者自己写"从通信减少里拿到加速仍然困难"。

用成本式解释这件事。设压缩前 `T_other + V/B_net = 61 ms`，压缩后通信量变成 `V/3.95`：

```
61  = T_other + V/B_net
110 = T_other + V/(3.95·B_net) + T_codec + T_queue

相减：
49 = T_codec + T_queue + V/B_net · (1/3.95 - 1)
49 = T_codec + T_queue - 0.747 · V/B_net
```

现在算一下 `V/B_net` 的量级。`V = 2.010 MB`，若 `B_net = 12.5 GB/s`（100 Gb 口径，论文未报，⚠️ 假设）：

```
V/B_net = 2.010 MB / 12.5 GB/s = 0.16 ms
理想压缩后： 0.16 / 3.95 = 0.04 ms
省下的传输时间：0.12 ms
```

**0.12 ms。** 而实测多了 49 ms。

这个对比把所有争论都终结了：在 Kaggle 这个规模上，通信量本身只值 0.16 ms，压 4× 只能省 0.12 ms；而 coalescing 和"框架不支持低精度稀疏 all-reduce"带来 49 ms。**`f` 小到 0.3% 的时候，压缩率再高也没有可省的空间。**

所以 `B-11` 的正确读法不是"压缩没用"，是"先算 `V/B_net`，再决定要不要压"。它的 8× 是模型大小的 8×，对训练时间没有贡献。

### 四、盈亏平衡带宽：`B*` 与重叠口径

不重叠口径（codec 串在通信后面）下，压缩带来的净收益是：

```
净省 = V/B_net - [ V/(CR·B_net) + V/B_c + V/B_d ]
     = V · [ (1 - 1/CR)/B_net - 1/B_c - 1/B_d ]
```

让它大于零，解出带宽：

```
(1 - 1/CR) / B_net  >  1/B_c + 1/B_d

B_net  <  (1 - 1/CR) · B_c · B_d / (B_c + B_d)
```

记这个临界值为 `B*`。网络带宽低于 `B*` 时压缩才赚钱，高于它就亏。代入 `A-14` 的实测吞吐（`B_c = 40.5`、`B_d = 205.4`，`CR = 19.9`）：

```
1/B_c + 1/B_d = 0.024691 + 0.004869 = 0.029560  s/GB
1 - 1/19.9    = 0.949749

B* = 0.949749 / 0.029560 = 32.13 GB/s
```

**32.1 GB/s 是分水岭。** `A-14` 的评测网络是 4 GB/s，离这条线还有 8 倍余量，所以它那 8.6× 拿得稳。换个 25 GB/s 的集群，余量只剩 1.3 倍；到 50 GB/s 就亏了。

重叠口径（codec 与通信并行）下式子变简单：

```
T_after = max( V/(CR·B_net), V/B_c, V/B_d )
T_before = V/B_net

盈利条件： max(...) < V/B_net
```

因为 `V/(CR·B_net) < V/B_net` 永远成立，所以条件只剩一个：

```
B_c > B_net  且  B_d > B_net
即  min(B_c, B_d) > B_net
```

这个结论比 `B*` 更强，也更好用：重叠时压缩率不参与"赚不赚"的判断，只参与"赚多少"的判断。`A-14` 的 `min(40.5, 205.4) = 40.5 GB/s`，只要网络低于 40.5 GB/s，codec 就能被完全藏住——这正是它的 1.38× 顶到 Amdahl 上限的原因。

代价是这条路有硬顶：网络一旦超过 codec 吞吐，压缩就从"免费"变成"瓶颈"。所以**真正要投资的是压/解压吞吐，不是压缩率**。

## 算例

<div class="example">

设定：[贯穿全教程的算例](../guide/running-example)，每迭代 `V = 525 MB = 0.525 GB`，预算 51 ms。压缩器按 `A-14` 的向量式 LZ 性能（`B_c = 40.5`、`B_d = 205.4`、`CR = 19.9`）。

第一步：四档带宽下的净收益（不重叠口径）

```
每 GB 净省 = 0.949749 / B_net - 0.029560   （秒）

B_net = 4 GB/s    0.237437 - 0.029560 = 0.207877 s/GB
B_net = 12.5      0.075980 - 0.029560 = 0.046420
B_net = 25        0.037990 - 0.029560 = 0.008430
B_net = 50        0.018995 - 0.029560 = -0.010565   ← 亏
```

乘上 0.525 GB：

| 网络 | 每迭代净省 | 占 51 ms 预算 |
|---|---|---|
| 4 GB/s（`A-14` 条件） | 109 ms | 远超预算（传输本身 131 ms） |
| 12.5 GB/s（100 Gb） | 24.4 ms | 48% |
| 25 GB/s（`A-06` 每 GPU 200 Gbps） | 4.4 ms | 8.6% |
| 50 GB/s（跨机 NVLink 级） | −5.5 ms | 负收益 |

⚠️ 这张表按**全批口径**（`V = 525 MB`）。每卡口径 `V = 4.1 MB`，净省与占比同时 ÷128：4 GB/s 下净省 0.85 ms、25 GB/s 下 0.034 ms、50 GB/s 下 −0.043 ms。**比率与 `B*` 不变**，变的只是"这点收益在你 51 ms 的预算里值多少"。也正因为如此，压缩在小 batch 上通常不是第一优先级——`α·K` 那种与字节无关的开销往往更大。

同一个压缩器，从 4 GB/s 换到 25 GB/s，**收益掉 24.7 倍**。

第二步：重叠口径

```
min(B_c, B_d) = min(40.5, 205.4) = 40.5 GB/s

B_net = 25 GB/s  <  40.5  →  codec 被藏住，赚
B_net = 50 GB/s  >  40.5  →  codec 变瓶颈

50 GB/s 下的实际完成时间：
T_after = max(0.525/(19.9×50), 0.525/40.5, 0.525/205.4)
        = max(0.000528, 0.012963, 0.002556)
        = 0.012963 s = 13.0 ms
T_before = 0.525/50 = 10.5 ms
→ 变慢 23%
```

这就是"压缩器成为瓶颈"的样子：压缩率 19.9× 完全没用，因为你根本没时间把它解开。

第三步：换一个角度算 `B*`

若你的集群实际带宽是 25 GB/s，`B* = 32.1` 说明还有 28% 的余量。要让压缩在这条链路上持续值得，需要把 `min(B_c, B_d)` 从 40.5 提上去——或者接受"网络升级到 32 GB/s 那天，这套压缩就该下线"。

</div>

## 代价与边界

- `f` 是会漂移的量。`A-14` 的 31.3% 是在 32×A100 + 4 GB/s 网络下测的；换网络、换模型、换 batch，`f` 就变，天花板跟着变。凡是引用 Amdahl 结论的地方都必须带上 `f` 的测量条件。
- `A-14` 的精度影响只有定性。"minimal accuracy impact"是摘要的说法，正文给了误差界-精度的曲线，但没有"最终 NE / AUC 差多少"这一个数，⚠️ 待核实。有损方案最该量化的就是它。
- 压缩率方差极大。`A-14` 单表压缩率从 2.25× 到 41.92×，平均 19.9× 是被高压缩率表拉起来的。用平均值做规划，会在低压缩率的表上系统性落空。
- `B-11` 的负面结果不是"压缩无效"，是"框架不支持"。它的 4× 通信量节省是真实的，卡在 PyTorch 的低精度稀疏 all-reduce 上。这类失败换框架就能修，但它提醒你：`T_codec` 和 `T_queue` 的实现往往不在你手里。
- `B-14` 的 `f` 没报。所以本篇只能反解出 `f·q` 的比，不能反解出 `f` 本身。2.11× 与 1.61× 的差是可靠的，具体对应哪档 `f` 是 ⚠️ 待核实。
- **`A-10` 的两个数对不上，需要标出来**。论文页写"75% 在嵌入访问上，所以最多 4×"，但关键数字表写的是最高 5.6×（DLRM 对 FB-Research 基线）。5.6 > 4，说明二者至少有一处口径不一：要么 75% 是相对某个更旧的实现的观测比例，要么 5.6× 的基线本身还带着别的开销被一并消掉了。同一篇里 W&D 只有 1.2×、DeepFM 3.7×——这反倒印证了 `f` 决定一切，只是 75% 那个 `f` 和 5.6× 的基线不是同一次测量。⚠️ 待核实。
- 盈亏平衡式假设带宽是唯一瓶颈。真实的 `T_transfer` 里还有固定开销、重传、拥塞，所以 `B*` 是乐观边界：实际的分水岭比它更低，也就是压缩更早失效。
- 重叠能吃掉的只有 codec。若 `T_queue` 和 `T_sync` 也不可重叠，压缩仍然亏，这时压缩率再高也救不回来。

**把四篇放一张表里看。**最后一列才是重点：这个结论能不能核算。

| 论文 | 改了哪一项 | `f` | 局部 `s` | 端到端 | 口径可核算吗 |
|---|---|---|---|---|---|
| `A-14` | 通信字节（有损压缩） | 31.3% | 8.6× | 1.38× | 可。Amdahl 给 1.382，5.03% 自洽 |
| `B-14` | 传输量（调度） | 未给 | 传输 −48%–89% | 2.11×（TCP）/ 1.61×（RDMA） | 半可。只能反解 `f·q` 的比值 1.39 |
| `B-11` | 通信字节（INT8 梯度） | 未给（Kaggle 规模极小） | 通信量 3.95× | 0.55×（61 → 110 ms，变慢） | 方向可算，项不可拆 |
| `A-10` | 等待（预取 + 缓存） | ~75% | — | 5.6×（DLRM）/ 1.2×（W&D）/ 3.7×（DeepFM） | 不可。5.6× 超过 75% 给的 4× 天花板 |

**决策顺序**，按这张表推出来：

1. 先测 `f`。不知道瓶颈占多少，任何加速比都不可解释。
2. 算 Amdahl 天花板 `1/(1-f)`。这是你这件事的最大价值，超过它的数字一定口径有问题（见 `A-10`）。
3. 算 codec 开销：`min(B_c, B_d)` 与 `B_net` 比。这一步决定压缩是"免费"还是"负债"。
4. 最后才看压缩率 `CR`。它只决定净收益的斜率，不决定正负。

这个顺序和工程直觉相反——多数人从 `CR` 开始。`B-11` 就是从这个顺序走反了之后的结果。

<div class="takeaway">

**本篇结论**：端到端收益的上限由 `f` 决定，`A-14` 的 1.38× 精确等于 `1/(0.687 + 0.313/8.6) = 1.382`。

压缩赚不赚，看 `min(B_c, B_d)` 和 `B_net` 谁大；差多少钱，才看压缩率。`A-14` 的分水岭是 32.1 GB/s，`B-11` 的分水岭它自己都没跨过去。
