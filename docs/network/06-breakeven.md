# 网络 6. 通信优化的盈亏平衡：四个反直觉结果的同一张表

**在教程的哪一层** 对应[第 6 章](../guide/06-communication)末尾那张"四种策略的对照"；这里把它换成一张能核算的表，回答"这个优化在你的集群上还成不成立"。

</div>

## 一句话版本

论文报的加速比，多半是"这一段自己快了几倍"，不是"整轮训练快了几倍"。这篇用四个案例说明同一件事：端到端收益的天花板由被优化那部分占多少时间决定；压缩划不划算，看压/解压吞吐能不能跑赢网络；压缩率只决定赚多少，不决定赚不赚。

四个案例的数字看着互不相干，放进同一套成本式里都能对上。

## 四个结果先摆在一起

| 论文 | 报了什么 | 端到端 |
|---|---|---|
| `A-14` | all-to-all 快 8.6× | 1.38× |
| `B-14` | 同一份调度，TCP 2.11×、RDMA 1.61× | — |
| `B-11` | 通信量降 4× | 变慢（61 → 110 ms） |
| `A-10` | 消除 75% 的迭代开销 | 5.6×，但另一个模型只有 1.2× |

这张表怎么读：左边一列是论文强调的数字，右边一列是落到整轮训练上的数字。两列之间的落差，就是下面要解释的东西。

## 这篇的地图

全篇五块，加一个算例。先给一把尺，再用它量三个案例，最后把尺反过来解出一个判据。

1. **先有一把尺** —— 端到端加速比只由两个量决定：被优化部分占多少时间，它自己快了多少倍。
2. **8.6× 只值 1.38×** —— `A-14` 的四个数字在同一套算术下互相咬合，说明它的压缩开销被通信藏住了。
3. **网络越快越不值钱** —— `B-14` 的同一份节省，在 TCP 上值 2.11×，在 RDMA 上只值 1.61×。
4. **压下去的是模型，不是通信** —— `B-11` 的 8× 是模型体积，通信量只省 0.12 ms，延迟反而从 61 ms 涨到 110 ms。
5. **盈亏平衡带宽** —— 把成本式解出临界带宽，网络低于它压缩才赚；能重叠时判据更简单。

这五块是一条线：第 1 块定天花板，第 2 到 4 块用三个真实案例看天花板怎么被误读，第 5 块把成本式反过来解成一条可以直接查的线。算例把第 5 块的判据代进教程参数，看四档带宽下各赚多少。第四个案例 `A-10` 不单独成块，它的数字放在最后的对照表里一起看。

| 概念 | 一句话 |
|---|---|
| 瓶颈占比 `f` | 被优化的那一部分占原来墙钟的比例（无量纲），`A-14` 是 31.3% |
| 局部加速比 `s` | 这一部分自己快了多少倍（单位 ×），`A-14` 是 8.6 |
| 省掉的比例 `q` | 传输量被省下的份额（无量纲），`B-14` 是 48%–89% |
| 压缩率 `CR` | 压完只剩下原来的几分之一（单位 ×），`A-14` 平均 19.9（单表 2.25–41.92） |
| 压/解压吞吐 `B_c`、`B_d` | 每秒能压、能解多少数据（单位 GB/s），`A-14` 是 40.5 / 205.4 |
| 网络带宽 `B_net` 与每轮字节 `V` | 单方有效带宽（GB/s，`B-09`：100 Gb → 12.5）与每迭代要传的量（GB，算例 0.525） |
| 盈亏平衡带宽 `B*` | 网络低于这条线压缩才划算（单位 GB/s），`A-14` 是 32.1 |

表里没列的两个符号：`α` 是单条消息的固定开销（µs 计，第 6 章取 50），`m` 是每轮消息条数，它们只出现在成本式的排队项里。术语到这里交代完毕，后面各块直接使用。

## 第一块 · 先有一把尺

这块要回答的是：一个优化最多能把端到端时间压到多少。

端到端加速比记作 `S`，它回答的是"整轮训练快了几倍"。这个数由两个量决定，两个都先讲成白话：

- 瓶颈占比 `f`：被优化的那一段，占原来整轮时间的比例。`A-14` 里是 31.3%，意思是压缩前 all-to-all 占了 31.3% 的墙钟。
- 局部加速比 `s`：这一段自己被优化后快了多少倍。`A-14` 报的 8.6× 就是这个量。

两者接起来的式子叫 Amdahl 关系：

```
S = 1 / ( (1 - f) + f / s )
```

括号里是"新时间除以旧时间"：没被碰过的那部分 `1 - f` 原样保留，被优化过的那部分 `f` 缩成 `f/s`。整个分数取倒数，就是旧时间除以新时间，也就是加速比。

这个式子只认 `f` 和 `s`，不解释 `s` 从哪来。把一轮通信拆成四项，才能看出 `s` 被什么卡住：

```
T = T_transfer + T_codec + T_queue + T_sync

T_transfer = V / B_net                    依赖 V、B_net
T_codec    = V / B_c + V / B_d            依赖 V、两端吞吐
T_queue    = α · m                        依赖消息条数，不依赖字节数
T_sync     = max_i t_i                    见第 4、5 篇；可重叠时为 0
```

四项分别是：搬字节的时间、压与解的时间、每轮固定开销、等最慢分片的时间。第三项里 `α · m` 是消息条数乘单条开销，与字节数无关；第四项取各分片耗时的最大值。

哪些项能同时跑，决定了后面两种口径：

```
可重叠：T_codec 与 T_transfer（GPU 上压、网卡同时在发）
不可重叠：T_sync（屏障）、T_queue 里的 kernel launch（串在同一个流上）
```

可重叠的意思是两件事并行，总时间取两者中较长的那个；不可重叠是一件事做完才开始下一件，时间要相加。

天花板是 `1/(1-f)`：`s` 再大，`S` 也只能逼近这个数。下一块拿 `A-14` 的四个数来量，看 8.6× 为什么只落到 1.38×。

## 第二块 · 8.6× 只值 1.38×

这块要回答的是：论文报的局部加速是 8.6×，到端到端为什么只剩 1.38×。

`A-14` 做的是对 all-to-all 的字节做有损压缩，把占 31.3% 的那段通信压下去。把 `f = 0.313`、`s = 8.6` 代进去，一步一步写：

```
1 - f        = 0.687
f / s        = 0.313 / 8.6 = 0.036395
分母         = 0.687 + 0.036395 = 0.723395
S            = 1 / 0.723395 = 1.3824
```

逐行读：没被压缩碰到的那部分原样留下；被压缩碰到的 31.3% 除以 8.6，缩到 0.036395；两者相加得到括号里的 0.723395；取倒数得到 1.3824。实测是 1.38×，与 1.382 比差 0.1%，与未取整的 1.3824 比差 0.2%。

### 三个数字互相咬合

比这个吻合更有意思的，是它和论文另一个数字的关系。论文报"压缩后 all-to-all 占比降到 5.03%"。用上面的中间量算：

```
压缩后 all-to-all 占新总时间的比例
= 0.036395 / 0.723395
= 0.05031
= 5.03%
```

完全对上。31.3%、8.6×、5.03%、1.38× 四个数在 Amdahl 关系下互相约束，误差在千分位。

这个自洽说明一件具体的事：`s = 8.6` 是墙钟意义上的加速比，不是"压缩率换算出来的理论值"。如果压/解压在关键路径上占了一部分，实测的 all-to-all 时间会比 0.036395 大，反推出的占比会大于 5.03%，`S` 也会小于 1.382。三项数字同时对上，只能解释为 codec 开销被完全隐藏在通信后面。

用成本式说：`T_codec` 被 `T_transfer` 掩盖了，所以 `T` 里看不到它。这就是重叠的价值——同一个压缩器不重叠时，`s` 会明显低于 8.6。

### 一个常见的口径错误

有的地方算成"31.3% 减 5.03% 等于 26.3%，所以上限是 1/(1−0.263) ≈ 1.36×"。这个算法把"占旧总时间的比例"和"占新总时间的比例"混在一个减法里。正确口径是省下 27.66 个百分点：

```
省下 = 0.313 - 0.036395 = 0.2766
1 / (1 - 0.2766) = 1.3824
```

两个算法差 0.02，方向一致，但只有后者能和 1.38× 对上到小数点后两位。

1.38× 不是"打了折的 8.6×"，是 `f = 31.3%` 给定之后的必然结果。下一块换一个变量：网络变快以后，同一个 `f` 会缩水，同样的节省就不值钱了。

## 第三块 · 网络越快越不值钱

这块要回答的是：把同一套节省搬到更快的网络上，还能换到多少端到端收益。

`B-14` 报的是"嵌入传输减少 48%–89%"，端到端最高 2.11×（TCP）/ 1.61×（RDMA），网络都是 100 Gbps 以太网。

用 `q` 表示省掉的比例，端到端就是：

```
S = 1 / ( (1 - f) + f (1 - q) )
  = 1 / (1 - f·q)
```

这个式子只依赖乘积 `f·q`，而 `f` 本身是 `V/(B_net·T)` 量级——带宽越高，`f` 越小。把两个实测值反过来解：

```
TCP：  1 - 1/2.11 = 0.5261 = f_TCP · q
RDMA： 1 - 1/1.61 = 0.3789 = f_RDMA · q

同一份 q，两个 f 的比：0.5261 / 0.3789 = 1.39
```

结论可以直接读出来：同样的传输量节省，在 TCP 上的价值是 RDMA 上的 1.39 倍。原因不是 Herald 在 RDMA 上做得差，是分母变了——同一份字节在更快的链路上占的墙钟比例更小。

再往前推一步，把这个趋势写成可操作的判据。若带宽提高到 `k` 倍，`f` 降到 `f/k`，要维持同一个 `S`：

```
f/k · q' = f · q   →   q' = k · q
```

带宽翻倍，省掉的比例也得翻倍。而 `q ≤ 1`，所以这条路有硬顶：当 `f/k → 0` 时 `S → 1`。`B-14` 论文页里那句"网络越快它越不值钱"，在式子上就是这个。

同一个优化在不同网络上值不同的钱。`B-14` 没报 `f`，所以只能反解出 `f·q` 的比值，这一点边界里还会再说。下一块看更极端的情形：通信量确实降了，墙钟反而变长。

## 第四块 · 压下去的是模型，不是通信

这块要回答的是：一个把通信量降了 4 倍的工作，为什么每迭代反而慢了一倍。

`B-11` 常被引成"压缩 8×，通信快 4×"。这两件事要拆开看：

| 数字 | 是什么 | 谁的功劳 | 有损吗 |
|---|---|---|---|
| 2.161 GB → 2.010 MB | 稀疏梯度只传非零行 | PyTorch `EmbeddingBag` 的 specified sparsity | 无损 |
| 2.161 GB → 0.270 GB | 模型体积 | `B-11` 的 INT4 量化 | 有损（精度反而升） |
| 2.010 MB → 0.509 MB | 通信量 | `B-11` 的 INT8 梯度 + 只给 MLP 做误差补偿 | 有损（−0.057% acc） |

这张表怎么读：三行里只有一个 8×，就是第二行的模型体积（2.161 GB → 0.270 GB）。第一行是 1075×（2.161 GB → 2.010 MB），第三行是 3.95×（2.010 MB → 0.509 MB）。"压缩 8×、通信快 4×"这句话，把模型大小和通信量两个不同的 8× 说成了同一件事。

真正值得看的是第三行的后果（事实，Table 4 脚注 3）：每迭代延迟从 61 ms 涨到 110 ms。原因是 PyTorch 的稀疏 tensor all-reduce 不支持低精度算术，加上稀疏张量合并（coalescing）的开销。作者自己写"从通信减少里拿到加速仍然困难"。

### 用成本式对一遍

设压缩前 `T_other + V/B_net = 61 ms`，压缩后通信量变成 `V/3.95`：

```
61  = T_other + V/B_net
110 = T_other + V/(3.95·B_net) + T_codec + T_queue

相减：
49 = T_codec + T_queue + V/B_net · (1/3.95 - 1)
49 = T_codec + T_queue - 0.747 · V/B_net
```

现在算一下 `V/B_net` 的量级。`V = 2.010 MB`，若 `B_net = 12.5 GB/s`（100 Gb 口径，论文未报，⚠️ 假设）：

```
V/B_net = 2.010 MB / 12.5 GB/s = 0.16 ms
理想压缩后： 0.16 / 3.95 = 0.04 ms
省下的传输时间：0.12 ms
```

0.12 ms，而实测多了 49 ms。在 Kaggle 这个规模上，通信量本身只值 0.16 ms，压 4× 只能省 0.12 ms；coalescing 和"框架不支持低精度稀疏 all-reduce"带来 49 ms。`f` 小到 0.3% 的时候，压缩率再高也没有可省的空间。

所以 `B-11` 的正确读法不是"压缩没用"，是"先算 `V/B_net`，再决定要不要压"。它的 8× 是模型大小的 8×，对训练时间没有贡献。

三个案例里，两个的收益被 `f` 卡住，一个的失败卡在实现上。下一块把成本式反过来解，给出一个可以直接查的临界值。

## 第五块 · 盈亏平衡带宽

这块要回答的是：网络快到什么程度，这套压缩就不划算了。

盈亏平衡带宽（`B*`）是这样一条线：网络带宽低于它，压缩省下的传输时间大于压/解压缩的开销；高于它，压/解本身比省下的传输时间还长，压缩就从收益变成净亏。

不重叠口径（codec 串在通信后面）下，压缩带来的净收益是：

```
净省 = V/B_net - [ V/(CR·B_net) + V/B_c + V/B_d ]
     = V · [ (1 - 1/CR)/B_net - 1/B_c - 1/B_d ]
```

方括号里第一项是省下的传输时间，后两项是压与解各要花的时间。让它大于零，解出带宽：

```
(1 - 1/CR) / B_net  >  1/B_c + 1/B_d

B_net  <  (1 - 1/CR) / (1/B_c + 1/B_d)
```

右边这个临界值就是 `B*`。代入 `A-14` 的实测吞吐（`B_c = 40.5`、`B_d = 205.4`，`CR = 19.9`）：

```
1/B_c + 1/B_d = 0.024691 + 0.004869 = 0.029560  s/GB
1 - 1/19.9    = 0.949749

B* = 0.949749 / 0.029560 = 32.13 GB/s
```

32.1 GB/s 是分水岭。`A-14` 的评测网络是 4 GB/s，离这条线还有 8 倍余量，所以它那 8.6× 拿得稳。换个 25 GB/s 的集群，余量只剩 1.3 倍；到 50 GB/s 就亏了。

### 能重叠时，判据更简单

codec 与通信并行时，完成时间取三者中最大的那个：

```
T_after = max( V/(CR·B_net), V/B_c, V/B_d )
T_before = V/B_net

盈利条件： max(...) < V/B_net
```

因为 `V/(CR·B_net) < V/B_net` 永远成立，所以条件只剩一个：

```
B_c > B_net  且  B_d > B_net
即  min(B_c, B_d) > B_net
```

这个结论比 `B*` 更强，也更好用：重叠时压缩率不参与"赚不赚"的判断，只参与"赚多少"的判断。`A-14` 的 `min(40.5, 205.4) = 40.5 GB/s`，只要网络低于 40.5 GB/s，codec 就能被完全藏住，这正是它的 1.38× 顶到 Amdahl 上限的原因。

代价是这条路有硬顶：网络一旦超过 codec 吞吐，压缩就从"不额外花时间"变成瓶颈。真正要投资的是压/解压吞吐，不是压缩率。

判据最后落在两个数上：`min(B_c, B_d)` 和 `B_net`。下面把教程参数代进去，看四档带宽各赚多少。

## 算例：四档带宽，一张收支表

<div class="example">

这一步在算什么：把每迭代 525 MB 分别放进四档网络，算不重叠口径下的净省；再用 50 GB/s 那一档验证重叠口径会不会翻车。

设定：[贯穿全教程的算例](../guide/running-example)，每迭代 `V = 525 MB = 0.525 GB`，预算 51 ms。压缩器按 `A-14` 的向量式 LZ 性能（`B_c = 40.5`、`B_d = 205.4`、`CR = 19.9`）。

第一步：四档带宽下的净收益（不重叠口径）

```
每 GB 净省 = 0.949749 / B_net - 0.029560   （秒）

B_net = 4 GB/s    0.237437 - 0.029560 = 0.207877 s/GB
B_net = 12.5      0.075980 - 0.029560 = 0.046420
B_net = 25        0.037990 - 0.029560 = 0.008430
B_net = 50        0.018995 - 0.029560 = -0.010565   ← 亏
```

乘上 0.525 GB：

| 网络 | 每迭代净省 | 占 51 ms 预算 |
|---|---|---|
| 4 GB/s（`A-14` 条件） | 109 ms | 远超预算（传输本身 131 ms） |
| 12.5 GB/s（100 Gb） | 24.4 ms | 48% |
| 25 GB/s（`A-06` 每 GPU 200 Gbps） | 4.4 ms | 8.6% |
| 50 GB/s（跨机 NVLink 级） | −5.5 ms | 负收益 |

这张表怎么读：带宽越宽，每 GB 的净省越薄；到 50 GB/s 变成负数，压缩开始倒贴。⚠️ 整张表按全批口径（`V = 525 MB`）。每卡口径 `V = 4.1 MB`，净省与占比同时除以 128：4 GB/s 下净省 0.85 ms、25 GB/s 下 0.034 ms、50 GB/s 下 −0.043 ms。比率与 `B*` 不变，变的只是"这点收益在你 51 ms 的预算里值多少"。也正因为如此，压缩在小 batch 上通常不是第一优先级——`α·K` 那种与字节无关的开销往往更大。

同一个压缩器，从 4 GB/s 换到 25 GB/s，收益掉 24.7 倍。

第二步：重叠口径

```
min(B_c, B_d) = min(40.5, 205.4) = 40.5 GB/s

B_net = 25 GB/s  <  40.5  →  codec 被藏住，赚
B_net = 50 GB/s  >  40.5  →  codec 变瓶颈

50 GB/s 下的实际完成时间：
T_after = max(0.525/(19.9×50), 0.525/40.5, 0.525/205.4)
        = max(0.000528, 0.012963, 0.002556)
        = 0.012963 s = 13.0 ms
T_before = 0.525/50 = 10.5 ms
→ 变慢 23%
```

这就是"压缩器成为瓶颈"的样子：压缩率 19.9× 完全没用，因为你根本没时间把它解开。

第三步：换一个角度算 `B*`

若你的集群实际带宽是 25 GB/s，`B* = 32.1` 说明还有 28% 的余量。要让压缩在这条链路上持续值得，需要把 `min(B_c, B_d)` 从 40.5 提上去——或者接受"网络升级到 32 GB/s 那天，这套压缩就该下线"。

</div>

四档带宽算完，判据也解出来了。剩下的是这些数字各自的适用边界。

## 模型在哪里不成立

- `f` 是会漂移的量。`A-14` 的 31.3% 是在 32×A100 + 4 GB/s 网络下测的；换网络、换模型、换 batch，`f` 就变，天花板跟着变。凡是引用 Amdahl 结论的地方，都要带上 `f` 的测量条件。
- `A-14` 的精度影响只有定性。"minimal accuracy impact"是摘要的说法，正文给了误差界-精度的曲线，但没有"最终 NE / AUC 差多少"这一个数，⚠️ 待核实。有损方案最该量化的就是它。
- 压缩率方差极大。`A-14` 单表压缩率从 2.25× 到 41.92×，平均 19.9× 是被高压缩率表拉起来的。用平均值做规划，会在低压缩率的表上系统性落空。
- `B-11` 的负面结果不是"压缩无效"，是"框架不支持"。它的 4× 通信量节省是真实的，卡在 PyTorch 的低精度稀疏 all-reduce 上。这类失败换框架就能修，但它提醒你：`T_codec` 和 `T_queue` 的实现往往不在你手里。
- `B-14` 的 `f` 没报。所以本篇只能反解出 `f·q` 的比，不能反解出 `f` 本身。2.11× 与 1.61× 的差是可靠的，具体对应哪档 `f` 是 ⚠️ 待核实。
- `A-10` 的两个数对不上，需要标出来。论文页写"75% 在嵌入访问上，所以最多 4×"，但关键数字表写的是最高 5.6×（DLRM 对 FB-Research 基线）。5.6 > 4，说明二者至少有一处口径不一：要么 75% 是相对某个更旧的实现的观测比例，要么 5.6× 的基线本身还带着别的开销被一并消掉了。同一篇里 W&D 只有 1.2×、DeepFM 3.7×，这反倒印证了 `f` 决定一切，只是 75% 那个 `f` 和 5.6× 的基线不是同一次测量。⚠️ 待核实。
- 盈亏平衡式假设带宽是唯一瓶颈。真实的 `T_transfer` 里还有固定开销、重传、拥塞，所以 `B*` 是乐观边界：实际的分水岭比它更低，也就是压缩更早失效。
- 重叠能吃掉的只有 codec。若 `T_queue` 和 `T_sync` 也不可重叠，压缩仍然亏，这时压缩率再高也救不回来。

**把四篇放一张表里看。** 最后一列才是重点：这个结论能不能核算。

| 论文 | 改了哪一项 | `f` | 局部 `s` | 端到端 | 口径可核算吗 |
|---|---|---|---|---|---|
| `A-14` | 通信字节（有损压缩） | 31.3% | 8.6× | 1.38× | 可。Amdahl 给 1.382，5.03% 自洽 |
| `B-14` | 传输量（调度） | 未给 | 传输 −48%–89% | 2.11×（TCP）/ 1.61×（RDMA） | 半可。只能反解 `f·q` 的比值 1.39 |
| `B-11` | 通信字节（INT8 梯度） | 未给（Kaggle 规模极小） | 通信量 3.95× | 0.55×（61 → 110 ms，变慢） | 方向可算，项不可拆 |
| `A-10` | 等待（预取 + 缓存） | ~75% | — | 5.6×（DLRM）/ 1.2×（W&D）/ 3.7×（DeepFM） | 不可。5.6× 超过 75% 给的 4× 天花板 |

**决策顺序**，按这张表推出来：

1. 先测 `f`。不知道瓶颈占多少，任何加速比都不可解释。
2. 算 Amdahl 天花板 `1/(1-f)`。这是你这件事的最大价值，超过它的数字一定口径有问题（见 `A-10`）。
3. 算 codec 开销：`min(B_c, B_d)` 与 `B_net` 比。这一步决定压缩是"不额外花时间"还是"净亏"。
4. 最后才看压缩率 `CR`。它只决定净收益的斜率，不决定正负。

多数人从 `CR` 开始算，顺序正好反过来。`B-11` 就是顺序走反之后的结果。

<div class="takeaway">

**本篇结论**：端到端收益的上限由 `f` 决定，`A-14` 的 1.38× 精确等于 `1/(0.687 + 0.313/8.6) = 1.382`。

压缩赚不赚，看 `min(B_c, B_d)` 和 `B_net` 谁大；差多少钱，才看压缩率。`A-14` 的分水岭是 32.1 GB/s，`B-11` 的分水岭它自己都没跨过去。

</div>
