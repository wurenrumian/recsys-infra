# 网络 3. all-to-all 的成本模型：消息尺寸、碎片与尾延迟

<div class="deep-anchor">

**在教程的哪一层** 对应[第 6 章](../guide/06-communication)的"最优消息尺寸"这个开放问题；这里把它写成一个可代入参数的极小化问题。

</div>

## 本篇要算的问题

一句话：all-to-all 的耗时不是"字节数 ÷ 带宽"，而是三块加起来——固定开销乘消息条数、字节数除带宽、排队与尾延迟。前两块能算，第三块只能建模。

读完能算四件事：给定 V 字节与 `α`，算出融合（`A-15`）省下多少毫秒；给定压缩与解压吞吐，算出压缩在什么网络带宽下才划算（`A-14` 的适用边界）；算出最优消息尺寸 `s*` 落在哪里；把不均衡比换成有效利用率，看它怎么把 10.4 ms 变成 59 ms。

## 先给结论

1. 三块成本写出来是 `T(s) = α·V/s + V/B + β·s/B`。`s` 是消息尺寸，第一块随 `s` 减小而爆，第三块随 `s` 增大而爆，极小点在中间。
2. 融合省的是 `α(K−1)`：200 条 → 1 条，`α = 0.05 ms` 时省 9.95 ms，占总时间 48%。`A-15` 实测 37.8%，反推的 `α` 约 0.032 ms——与假设值同量级。
3. 压缩的盈亏平衡带宽约 38 GB/s（用 `A-14` 的压缩 40.5、解压 205.4、压缩率 19.9 算出）。在 400 Gbps（50 GB/s）的链路上压缩**不划算**；`A-14` 能拿 8.6× 是因为它跑在 4 GB/s 上。
4. 尾延迟不属于这三项，它乘在后面：不均衡比 5.70 的有效利用率是 1/5.70 ≈ 18%，10.4 ms 的传输因此变成 59 ms。**平均带宽够不够不是问题，最慢的那一对才是。**

## 符号与模型

| 符号 | 含义 | 单位 |
|---|---|---|
| `V` | 一次 all-to-all 要传的总字节（本篇按全批口径取 525 MB） | 字节 |
| `s` | 单条消息的字节数 | 字节 |
| `K` | 消息条数 `V/s` | 条 |
| `α` | 每条消息的固定开销 | ms |
| `B` | 网络单向有效带宽 | GB/s |
| `B_c` | 压缩吞吐（单向） | GB/s |
| `B_d` | 解压吞吐（单向） | GB/s |
| `r` | 压缩率（原字节 / 压后字节） | 倍 |
| `β` | 阻塞系数（无量纲） | — |
| `T_q` | 排队与尾延迟 | ms |

五条假设，每条都会在后面被点名：

1. `α` 与消息大小无关。真实值随语义和框架略有变化，取常数是最坏情况的简化。
2. `r` 与块大小无关。这一条在第 4 节会被 `A-14` 自己的窗口数据部分推翻，届时单独讨论。
3. 压缩、传输、解压**串行**。真实系统把三者重叠，串行口径给出的是保守上界。
4. 链路无拥塞。排队单独用一个 `β` 项建模，不混进 `V/B`。
5. `V = 525 MB` 是**全批口径**（整批去重量记在一张卡上，与[第 2 篇](02-collectives)和教程对齐）。真实每卡出站是 `V_card = 525/128 ≈ 4.1 MB`；`B*`、`s*` 的形状与 `α·K` 不随口径变，绝对时间按 P 缩放。`α = 0.05 ms` 沿用[第 6 章](../guide/06-communication)的假设值。

## 推导

### 一、三块成本与极小点

把一次 all-to-all 的耗时按"会不会随消息尺寸变化"分成三块：

```
T(s) = α·(V/s)  +  V/B  +  β·(s/B)
       ↑固定开销     ↑传输     ↑阻塞
```

- 第一块：共 `K = V/s` 条消息，每条付 `α`。消息越小，条数越多，这一块越大。
- 第二块：`V` 字节走完链路。这一块与 `s` 无关——总字节不变，怎么切都一样。
- 第三块：一条大小为 `s` 的消息占用链路 `s/B`；调度若不能把这段时间完全重叠掉，就有 `β·s/B` 的暴露阻塞。`β` 是"同时在链路里排队的消息数"这类量的替身，无量纲。

对 `s` 求极小：

```
dT/ds = −α·V/s² + β/B = 0
⇒ s* = sqrt(α·V·B/β)
```

代 `α = 5×10⁻⁵ s`、`V = 5.25×10⁸ B`、`B = 5×10¹⁰ B/s`：

```
α·V·B = 5×10⁻⁵ × 5.25×10⁸ × 5×10¹⁰ = 1.3125×10¹⁵
β = 1  → s* = 3.62×10⁷ B = 36.2 MB
β = 8  → s* = 1.28×10⁷ B = 12.8 MB
β = 64 → s* = 4.53×10⁶ B = 4.53 MB
```

三个端点值得一起看（`β = 8`）：

```
200 条 × 2.6 MB：  10.0 + 10.5 + 0.42 = 20.9 ms
1 条 × 525 MB：     0.05 + 10.5 + 84.0 = 94.6 ms
41 条 × 12.8 MB：   2.05 + 10.5 + 2.05 = 14.6 ms
```

中间那条比两头都快。两头各自被不同的项拖死：碎被 `α·K` 拖，整被 `β·s/B` 拖。

最优点上第一块与第三块恰好相等，把 `s*` 代回去就能看出来：

```
α·V/s* = β·s*/B = sqrt(α·β·V/B)
β=8 时各为 2.05 ms
```

于是极小点的总时间有闭式：

```
T(s*) = V/B + 2·sqrt(α·β·V/B)
```

这个式子说明一件反直觉的事：调消息尺寸能削掉的只有那 `2·sqrt(αβV/B)`，而 `V/B` 那一项一分都省不掉。`β=8` 时它是 4.1 ms，占 14.6 ms 的 28%——这是"调消息尺寸"这一招的天花板。它永远不能把 all-to-all 变便宜，只能把额外开销堆出来的那部分削到最小。

这里必须说清楚一件事：**这是模型，不是论文结论。**`α` 与 `β` 都没有人测过；`β` 甚至是纯占位——它只是把"大消息会阻塞别人"这件事写进公式的一种方式。[第 6 章](../guide/06-communication)的开放问题（最优消息尺寸是多少）在这里被参数化成 `sqrt(α·V·B/β)`，不是被解决。谁测出 `α` 和 `β`，谁才能真正回答那个问题。

还有一层：上面这三个数只能横着比，不能竖着当预测。`β = 8` 换成 `β = 1`，`s*` 从 12.8 MB 变成 36.2 MB，最优总时间从 14.6 ms 变成 12.0 ms——参数一变，结论跟着变。这就是为什么第 6 章只能留下一个开放问题：不是没人算，是缺两个测不出来的常数。

把敏感性摊开成一张表更直白（`V = 525 MB`、`B = 50 GB/s`）：

| `α` | `β = 1` | `β = 8` | `β = 64` |
|---|---|---|---|
| 0.01 ms | 16.2 MB | 5.7 MB | 2.0 MB |
| 0.05 ms | 36.2 MB | 12.8 MB | 4.5 MB |
| 0.20 ms | 72.4 MB | 25.6 MB | 9.1 MB |

九格里只有中间那一格对应本文的算例。`β` 每涨 8 倍，`s*` 缩到 1/2.8；`α` 每涨 4 倍，`s*` 涨一倍。**"最优消息尺寸"这个说法之所以危险，就是因为它听起来像一个常数，实际上是一个随两个未测参数漂移的量。**

模型还有一个盲点：它假设每卡要传的 `V` 相同。真实 all-to-all 的 `V` 逐卡不同，差值就是 `A-03` 的不均衡比。所以 `T(s)` 算出来的是平均卡的耗时，不是步时间——两者差一个 5.70 的因子，第 4 节补这一步。

### 二、融合：省的是 α(K−1)

融合（`A-15`）做的事情是把 K 条消息并成更少的条数：`K → K'`，`V` 不变。代入成本式，省下的是

```
ΔT = α·(K − K')
```

用[第 6 章](../guide/06-communication)的算例：200 张表 → 200 条消息、每条 2.6 MB、`α = 0.05 ms`。

```
融合前：200 × 0.05 + 10.5 = 10.0 + 10.5 = 20.5 ms
融合后：  1 × 0.05 + 10.5 =  0.05 + 10.5 = 10.55 ms
省下：  0.05 × 199 = 9.95 ms            降幅 48.5%
```

`A-15` 报的是吞吐提升 37.8%。两个数不一致，把 37.8% 反推一下：

```
0.378 = α(K−1) / (αK + V/B)
0.378 = 199α / (200α + 10.5)
199α − 75.6α = 3.969
α = 0.0322 ms
```

也就是说，37.8% 与 `α ≈ 0.032 ms` 自洽——比第 6 章假设的 0.05 ms 小三分之一。这个反推有三处不能当结论用：

1. `A-15` 的 37.8% 是吞吐提升，不是通信层时间下降。若通信只占端到端的一部分，通信层的降幅必须更大才对得上，所以真实 `α` 比 0.032 更小。
2. 200 张表未必能并成 1 条。融合受显存与传输时机限制，`A-15` 的原文只说"把多个类别合成一组"，没说全并。若只能并成 20 条，`ΔT = 0.05 × 180 = 9.0 ms`。
3. `α` 本身可能随消息变大而上升（大消息的 kernel 更贵），这时 `α(K−1)` 是高估。

**所以这条反推的用途只是确认量级**：模型算 48.5%、实测 37.8%，说明"固定开销主导"这个机制是对的，具体数值要按自己的框架测。`A-15` 的 37.8% 里还可能含别的成分（去重效率、内存局部性），本文不拆。

两个参数各动一下，看哪个更敏感：

```
K' = 20（只并成 20 条）：ΔT = 0.05 × 180 = 9.0 ms，降幅 43.9%
α  = 0.02 ms（α 变小）：  降幅 = 3.98 / 14.50 = 27.4%
```

"并成几条"只让降幅移 5 个百分点，`α` 一变就是 20 个百分点。所以在没测过 `α` 的集群上，任何关于融合收益的具体数字都不可信——包括本文算出的 48.5%。

同一个 `α·K` 在不同的层次上反复出现。`A-06` 的 hybrid kernel fusion 把"上千个 GPU kernel"压到"每迭代两个"（一个前向、一个反向+更新）。它省下的东西也是 `α·K`——只不过这里的 K 是 kernel 数，`α` 是 kernel launch 的开销。传输层的融合（`A-15`）、算子层的融合（`A-06`）、去重（把重复向量从消息里删掉）是三件不同的事，但在成本式里都落在同一个位置：

```
ΔT = α·(K − K')
```

省的都是条数，不是字节。这条式子对 kernel、对算子、对消息同时成立。它也给出一条排序原则：**在网络慢、α 大的时候，"少发几次"永远比"少发几字节"划得来**——因为前者除的是 `α`，后者除的是 `B`。

一个容易忽略的副作用：融合把 K 降下来，同时把 `s` 抬上去，第三块 `β·s/B` 会变大。融合的净收益是

```
ΔT = α(K−1) − β(s' − s)/B
```

在 `β` 小的时候这笔账几乎全是赚的；`β` 大（链路拥挤、缓冲浅）时，融合的收益会被阻塞项吃掉一部分。这也解释了为什么 `A-15` 的 37.8% 比模型的 48.5% 小——不只是 `α` 的差别，也是 `β` 的差别。

融合还有一条硬上限：缓冲。把 K 条并成 1 条，中间得有一个装得下 V 的缓冲。

```
缓冲需求 = V = 525 MB（全批去重后；每卡口径下是 4.1 MB）
若用未去重的 2.1 GB，缓冲需求 2.1 GB
```

80 GB 的卡上，模型分片、优化器状态、激活之后能留给通信缓冲的余量，量级在 1–2 GB。`A-06` 的描述很直接：model-A 用 TF32 时"模型大小逼近 128 卡 5TB 聚合 HBM 的上限，扣掉 PyTorch 与 NCCL 保留后，Neo 几乎没有放置策略的探索空间"。那样的余量下，融合只能分批做——先并到几十条，再逐批发出去。所以 K 不是自由变量，它被显存卡住，这也是 `A-15` 到不了模型 48.5% 的第二个原因。

### 三、压缩：什么时候划算

压缩（`A-14`）改的是 `V`：`V → V/r`。但它要付两次钱——压缩一次、解压一次。串行口径下：

```
不压缩：T₀ = V/B
压缩后：T₁ = V/(r·B) + V/B_c + V/(r·B_d)
```

`T₁ < T₀` 的条件，两边同除 `V`：

```
1/(r·B) + 1/B_c + 1/(r·B_d) < 1/B
(1 − 1/r)/B < 1/B_c + 1/(r·B_d)
B < (r−1) / (r/B_c + 1/B_d)  ≡  B*
```

代 `A-14` 的三个吞吐与压缩率（`r = 19.9`、`B_c = 40.5 GB/s`、`B_d = 205.4 GB/s`）：

```
r/B_c     = 19.9 / 40.5  = 0.4914 s/GB
1/B_d     = 1 / 205.4    = 0.00487 s/GB
分母      = 0.4963 s/GB
分子 r−1  = 18.9
B*        = 18.9 / 0.4963 = 38.1 GB/s  ≈ 305 Gbps
```

**结论：网络慢于约 38 GB/s 时压缩划算，快于它时压缩是净亏。**`A-14` 的实验网络是 4 GB/s，远在阈值以下——所以它能拿 8.6×，而同一套方案搬到 400 Gbps 集群上会变成负收益。

⚠️ 这个式子把解压吞吐按压缩后字节计（解压 `V/r` 字节需要 `V/(r·B_d)`）。若按常见的"解压后字节"口径（`V/B_d`），阈值降到 32.1 GB/s，见[第 6 篇](06-breakeven)。两种口径差 19%（250 vs 305 Gbps），不影响"4 GB/s 远低于阈值"这个结论；引用时写清用的是哪一种。

如果把压缩/解压与通信完全重叠，条件换成 `max(V/(r·B), V/B_c + V/(r·B_d)) < V/B`，解得 `B* = 1/(1/B_c + 1/(r·B_d)) = 40.1 GB/s`。两个口径差 5%，落在同一个量级：约 40 GB/s，即 300–320 Gbps。

这张阈值表解释了 `A-14` 为什么强调"按表选压缩器"。单表压缩率的跨度是 2.25× 到 41.92×；把 `r = 2.25` 代进同一个式子：

```
B* = (2.25−1) / (2.25/40.5 + 1/205.4)
   = 1.25 / (0.05556 + 0.00487)
   = 1.25 / 0.06043 = 20.7 GB/s
```

低压缩率的表，阈值掉到 21 GB/s。同一份 all-to-all 里，高压缩率的表值得压，低压缩率的表不值得——这不是"平均 19.9×"能表达的信息。

把这个式子推到极限还能看出一个结构性质。让 `r → ∞`：

```
lim B* = lim (r−1)/(r/B_c + 1/B_d) = B_c = 40.5 GB/s
```

压缩率无限高时，盈亏平衡带宽的上限就是压缩器自身的吞吐。原因很直白：即使压后数据变成 0 字节，你仍然要把 V 字节喂进压缩器，那一步就是 `V/B_c`。所以压缩永远不可能在比压缩器吞吐更快的网络上划算——这条与压缩算法做得多好无关，是流程结构决定的。

反过来说，`B_c` 是这套方案最值得优化的硬件指标：压缩率只决定阈值落在 `(0, B_c)` 区间的哪个位置，而 `B_c` 决定整个区间的上界。`A-14` 的向量式 LZ 是 40.5 GB/s，熵编码是 78.4 GB/s——后者把上界抬高一倍。把熵编码的两个吞吐代进同一个式子：

```
B* = (19.9−1) / (19.9/78.4 + 1/38.9) = 18.9 / 0.2795 = 67.6 GB/s
```

同样的压缩率，换个编码器，阈值从 38 GB/s 涨到 68 GB/s（仍按本篇"解压按压缩后字节"口径）。但若按解压后字节口径，熵编码的解压只有 38.9 GB/s，反而会成为瓶颈，阈值降到约 25 GB/s。所以"按表选编码器"要同时看压缩与解压两个吞吐，并说清口径——`A-14` 认为熵编码更快，是在它自己的测量口径下。

### 四、叠加顺序与均值陷阱

`A-14` 与 `A-15` 可以叠，但顺序必须是先融合再压缩：

```
T = α·1 + V/(r·B) + V/B_c + V/(r·B_d)
```

三个理由，一个有数据支撑：

1. 固定开销只付一次。先压缩会把压缩器调用次数保持在 K 次，`α·K` 一分不省；先融合则压缩器只调一次。
2. 压缩率随块变大而提高。`A-14` 自己的 LZ 窗口实验就是这个证据：窗口从 32 放大到 128，压缩收益 3.9×；放大到 255，5.2×。大块意味着更长的重复距离，`r` 更高——所以融合之后压缩，`r` 也会比融合之前更好。这条与本文的假设 2（`r` 与块无关）冲突，冲突的方向对"先融合"有利。
3. 误差界是表级的。`A-14` 的三档误差界按表分配，融合时必须保住类别边界（`A-15` 用 categorical-aware hashing 把类别信息编进 ID），否则表级误差界失效，等于退回单一误差界。

数值上，把叠加与单独用各算一遍（`α = 0.05`、`r = 19.9`）：

| 方案 | 4 GB/s | 50 GB/s |
|---|---|---|
| 不优化（200 条） | 141.3 ms | 20.5 ms |
| 只融合 | 131.3 ms | 10.55 ms |
| 只压缩 | 19.7 ms | 13.6 ms |
| 先融合再压缩 | 19.7 ms | 13.7 ms |

读法：在 4 GB/s 上，压缩那一项（12.96 ms）已经吃掉全部收益，融合省下的 9.95 ms 被压到 0.05 ms 的固定开销里，几乎看不见；在 50 GB/s 上，压缩反而把 10.55 ms 拖到 13.7 ms。**两篇的可叠加性成立，但同时划算的窗口很窄**——只有"网络慢到需要压缩"且"消息碎到需要融合"同时成立时，两招才一起赚。

最后一块成本不在这三项里，它乘在后面：尾延迟。

`A-03` 的不均衡比是 5.70（传统模型并行，CTR）。它的含义是最慢的卡做 5.7 倍的活，其余卡在等。把有效利用率写成 `1/imbalance`：

```
1 / 5.70 = 17.5% → 有效带宽 50 × 0.175 = 8.8 GB/s
10.4 ms 的传输 ÷ 0.175 = 59.4 ms
```

59.4 ms 已经超过 51 ms 的整步预算。这就是"平均带宽够、实际跑不完"的具体形态。`A-03` 的 2D 并行把不均衡比降到 1.57，有效利用率回到 64%——同一份字节，时间从 59.4 ms 降回 16.3 ms。这部分收益与压缩、融合完全无关，它来自切分方式。

两条改进路径可以并排放在 50 GB/s 上（把工作量时间乘上不均衡比，得到步时间）：

| 手段 | 改的是哪一项 | 工作量时间 | 步时间 | 相对基线 |
|---|---|---|---|---|
| 基线 | — | 10.4 ms | 59.3 ms | 1.00× |
| 压缩（`r=19.9`） | `V` | 13.6 ms | 77.5 ms | 1.31× |
| 2D 并行（1.57） | imbalance | 10.4 ms | 16.3 ms | 0.27× |
| 压缩 + 2D | 两者 | 13.6 ms | 21.4 ms | 0.36× |

结论有点刺眼（全批口径）：在 400 Gbps 上，压缩单独用是负收益（59.3 → 77.5 ms）；先修不均衡再考虑压缩，压缩仍然是负收益（16.3 → 21.4 ms）。**因为不均衡比乘在传输时间上，而压缩把"可乘的传输时间"换成了"不可乘的压缩时间"。**压缩器不看数据分布，它老老实实把每卡分到的字节压一遍——倾斜在它那里不消失，只是换了个位置。

⚠️ 这一列乘法是粗略的：把 imbalance 乘在"传输 + 压缩 + 解压"的串行和上，隐含假设压缩开销也随倾斜同比放大。真实情况是压缩时间与字节成正比，而倾斜也是按字节计的，所以方向对、数值只能当量级。

关于 P99，要精确一点。在同步循环里，吞吐由 `E[T]` 决定，P99 不直接进吞吐公式。但 P99 决定三件事：在途缓冲要开多大、超时阈值定多高、以及"这一步算不算过了预算"。更要紧的是一个区别——all-to-all 的尾不是随机抖动，是结构倾斜：每一步都有 straggler，因为它来自"1% 的行承担 92% 的访问"，不是来自偶发故障。所以正确的统计量是每一步的 max（跨卡取最大），而不是跨卡的平均。用跨卡平均算出来的 10.4 ms 是下界，不是预期值。

这里有两个容易混淆的统计量：不均衡比是跨卡的（同一时刻，最慢卡 / 平均卡），P99 是跨时间的（同一张卡，第 99 百分位的步 / 平均步）。前者决定同步循环的步时间，后者决定尾部事件的处理策略。把两者相乘或相加都是错的——它们是两个正交的维度。

## 算例

<div class="example">

设定：`V = 525 MB`（全批口径）、`α = 0.05 ms`、`B = 50 GB/s`、51 ms 预算。

① 融合（200 条 → 1 条）

```
融合前：200 × 0.05 + 10.5 = 20.5 ms
融合后：  1 × 0.05 + 10.5 = 10.55 ms
省下 9.95 ms，占 51 ms 的 19.5%
```

② 压缩的盈亏表（`r = 19.9`、`B_c = 40.5`、`B_d = 205.4`，两列都不含 `α·K`，即假设已融合成 1 条）

| 网络 `B` | 不压缩 | 压缩后 | 加速比 | 结论 |
|---|---|---|---|---|
| 4 GB/s | 131.3 ms | 6.60 + 12.96 + 0.13 = 19.7 ms | 6.7× | 划算 |
| 10 GB/s | 52.5 ms | 2.64 + 12.96 + 0.13 = 15.7 ms | 3.3× | 划算 |
| 25 GB/s | 21.0 ms | 1.06 + 12.96 + 0.13 = 14.1 ms | 1.5× | 勉强 |
| 38 GB/s | 13.8 ms | 0.69 + 12.96 + 0.13 = 13.8 ms | 1.0× | 平衡 |
| 50 GB/s | 10.5 ms | 0.53 + 12.96 + 0.13 = 13.6 ms | 0.77× | 亏 |
| 100 GB/s | 5.25 ms | 0.26 + 12.96 + 0.13 = 13.4 ms | 0.39× | 大亏 |

压缩后的时间在 13.4–13.6 ms 处收敛。那个常数就是压缩器自身的吞吐上限（`525 MB ÷ 40.5 GB/s = 12.96 ms`），与网络无关。**压缩把一个"会随网络变快而变快"的开销，换成了一个不会变快的开销。**

③ 最优消息尺寸（`β = 8`）

| 消息尺寸 | 条数 | `α·K` | `V/B` | `β·s/B` | 总计 |
|---|---|---|---|---|---|
| 2.6 MB | 200 | 10.0 ms | 10.5 ms | 0.42 ms | 20.9 ms |
| 12.8 MB | 41 | 2.05 ms | 10.5 ms | 2.05 ms | 14.6 ms |
| 105 MB | 5 | 0.25 ms | 10.5 ms | 16.8 ms | 27.6 ms |
| 525 MB | 1 | 0.05 ms | 10.5 ms | 84.0 ms | 94.6 ms |

极小点 12.8 MB 在中间，且与第 6 章的两个方案（200 条、1 条）都不重合。

④ 三种网络档位 × 三种方案

| 方案 | 4 GB/s | 25 GB/s | 50 GB/s |
|---|---|---|---|
| 基线（200 条） | 141.3 ms | 31.0 ms | 20.5 ms |
| 融合（41 条） | 133.3 ms | 23.1 ms | 12.6 ms |
| 融合 + 压缩 | 19.7 ms | 14.1 ms | 13.7 ms |

读法：4 GB/s 上压缩是唯一出路（133.3 → 19.7，6.8×）；25 GB/s 上压缩仍然赢（23.1 → 14.1）；50 GB/s 上融合反而更好（12.6 < 13.7）。交叉点正好落在前面算出的 38 GB/s 附近——这张表是那个不等式的数值版本。

⑤ 怎么测 α 与 β

```
α：固定 V，改变 K（1、2、4、8…），对 T 关于 K 做线性拟合，
   斜率就是 α。取每组消息都落在 1–4 MB，避免 β 项干扰。
β：固定 K=1，改变 V（64、128、256、525 MB），对 T 关于 V 拟合，
   斜率减去 1/B 之后剩下的就是 β/B。
   这一组最难：大消息必然触发拥塞，β 本身会随 V 变。
重要：都要在真实的 all-to-all 上测。点对点测出来的 α、β 不含 incast，
      与本篇模型里的含义不是同一个量。
```

⑥ 尾延迟

```
不均衡比 1.57（2D 并行）：10.4 ÷ (1/1.57) = 16.3 ms
不均衡比 5.70（传统 MP）  ：10.4 ÷ (1/5.70) = 59.4 ms
```

⑦ 预算的最后一张账

| 项 | 时间 | 占 51 ms |
|---|---|---|
| 单次 all-to-all（融合成 1 条，全批） | 10.55 ms | 21% |
| 其中：传输 `V/B` | 10.50 ms | 21% |
| 其中：固定开销 `α·1` | 0.05 ms | 0.1% |
| 第 6 章口径的 3 次 A2A + 1 次 AR（全批） | 52.0 ms | 102% |

一句话：在全批口径下，单次 all-to-all 装得进预算，一轮里的三次装不进。换成每卡口径（全部 ÷128）后，三次传输合计约 0.4 ms，预算不再是问题；此时排在最前面的是 `α·K`——200 条消息就是 10 ms，与口径无关——以及同步等待。

所以真正的优化目标不是"把一次 all-to-all 做快"（`V/B` 那 10.5 ms 是硬底），而是**减少消息条数**与**减少一轮里的次数**。前者是 `A-15` 的融合，后者是 `C-06` 拆塔、`A-03` 分组的动机。本篇的三项成本里，唯一能压到零的是 `α·K` 和 `β·s/B`，`V/B` 只能靠降 V 或换更快的链路。

⚠️ 三条假设要点名：`α = 0.05 ms` 来自第 6 章；`β = 8` 是纯占位，没有任何测量支撑；`1/imbalance` 作为利用率假设"工作量线性映射到时间"，忽略了重叠能把一部分等待藏起来。

</div>

## 代价与边界

- 模型的三个参数里只有 `r` 是论文实测的（`A-14` 的 19.9）。`α` 是第 6 章的假设值，`β` 是我编的占位符。把 `β` 从 8 改到 1，`s*` 从 12.8 MB 漂到 36.2 MB——**在最优点上给不出可信数字，只能给出结构**。
- 压缩吞吐是峰值。`A-14` 还给了另一套编码器（熵编码：压 78.4 / 解 38.9 GB/s），换它就把 `B_c` 与 `B_d` 的角色互换，`B*` 随之改变。这也是 `A-14` 按表选编码器的定量理由。
- 串行口径是保守界。`A-14` 的系统把压缩/解压与通信重叠，真实时间是 `max` 而不是 `sum`，所以第 2 节那张表在慢网络一侧偏悲观（论文实测 8.6× 高于模型算的 6.7×）。
- 有损不是免费的。`r` 越大误差界越松，`A-14` 的 19.9× 是带三档误差界的结果。无界压缩会把收敛崩掉——`B-02` 的对照很直白：过期阈值 `s=100` 时 AUC 79.62，`s=0` 是 79.64，而 `s=∞` 崩到 74.61。压缩的极端情形与之同构。
- 口径要一致。本篇的 `V = 525 MB` 沿用第 2 篇的全批口径（整批去重量记在一张卡上），真实每卡出站约 4.1 MB；换成每卡口径后所有时间 ÷128，`B*` 不变（它是带宽阈值，与体积无关）。这个不变性值得记：**"压缩划不划算"与数据量无关，只与网络快慢有关。**
- 融合与压缩都假设"消息可以任意切"。真实系统里消息边界受表边界、去重结果、传输时机约束，`K` 不能取任意整数。
- 尾延迟那一段用的是不均衡比，不是真实的耗时分布。真实分布要实测，`A-03` 的 5.70 是它在两个模型上的结果，不是通用常数。
- 本篇没有建模"融合后压缩"里压缩器对表边界的处理。`A-14` 的误差界按表分三档，融合打破表边界后，一次压缩调用里混着不同误差界的行——真实实现要么分段压、要么统一取最严的那档，两者都影响 `r`。
- `β` 这一项的物理来源被本文藏起来了。真实机制是交换机缓冲、网卡队列深度的组合，它随集群规模、超售比变化，不是硬件常数。想要一个可迁移的 `β`，得对着拓扑建模，那是另一篇的工作。

<div class="takeaway">

三块成本：`α·K`（碎）、`V/B`（量）、`β·s/B`（堵）。`s* = sqrt(α·V·B/β)` 是模型，不是论文结论。

融合省 `α(K−1)`：200 → 1 条省 9.95 ms。压缩在 `B < (r−1)/(r/B_c + 1/B_d)` 时划算，`A-14` 的参数给出约 38 GB/s。

先融合再压缩，因为固定开销只付一次、大块压得更好。尾延迟乘在后面：5.70 的不均衡比把 10.4 ms 变成 59.4 ms。

</div>
