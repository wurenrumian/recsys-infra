# 网络 1. 互联的物理层与语义层：从 NVLink 到 RoCE

<div class="deep-anchor">

**在教程的哪一层** 对应[第 3 章](../guide/03-bandwidth-wall)的“通信占 55%”；这里把它换成一份可以逐项相加的带宽账本。

</div>

## 一句话版本

一次通信的耗时是可以算出来的：字节数 ÷ 单向有效带宽，再加上固定开销。算之前要把三件事对齐——单位、方向、语义。

对齐之后有两个结果。机内到跨机是台阶而不是斜坡，单向差 9 倍，双向差 18 倍。带宽也不是打开就有的，它要用“在途字节”换：400 Gbps、20 µs 的链路要 1 MB 数据在路上才跑得满，比这小的消息按比例浪费。

## 这篇的地图

全篇分四块，最后跟一个算例。

1. **单位与方向** —— 把散在各篇论文里的带宽折成同一把尺子：GB/s、单向、有效值。
2. **延迟与带宽延迟积** —— 说明小消息为什么再快也没用，以及填满一条链路需要多少字节在途。
3. **三种语义** —— 分清谁发起、对端要不要配合，这个差别把谁绑在了关键路径上。
4. **带宽悬崖** —— 按“跨不跨机”重排所有档位，把台阶换算成一条汇率。

四块是递进的。第 1 块立尺子，把“多久搬完”变成一个除法；第 2 块补上尺子量不出的那一维，即“开始搬之前要等多久”；第 3 块从搬多久转到谁被阻塞；第 4 块把前三条合成一张按距离排序的表。算例再拿 525 MB 把五个档位各走一遍。

四块走完，三件事都能自己算：给定字节数和一条具体路径（同机 NVLink / 同机 PCIe / 跨机 RDMA / TCP），算出毫秒数及其占 51 ms 预算的比例；给定延迟，算出填满这条链路需要多少字节在途，从而判断某个消息尺寸是不是注定浪费带宽；说出这条路径走的是三种语义中的哪一种，以及这种语义把哪一方绑在了关键路径上。

| 概念 | 一句话 |
|---|---|
| 有效带宽 | 实际跑出来的带宽，通常只有标称值的 50–80% |
| 单向 / 双向 | 厂商常按双向标数；两个方向各占一半，比较前要先折成单向 |
| 延迟 | 一个字节从发出到到达要等的时间，与带宽是两件事 |
| BDP | 带宽延迟积 `B × L`，把管道填满所需的在途字节 |
| 链路利用率 | 单条消息能用上几成标称带宽，等于 `min(1, S/BDP)` |
| 语义 | 一次传输由谁发起、对端要不要执行指令、谁会被阻塞 |
| 带宽悬崖 | 机内与跨机之间的数量级落差，按级变化，不按斜率变化 |

术语到此交代完毕，后面各块直接使用。

## 第一块 · 单位与方向

这块要回答的是：论文里那些“100 Gbps”“900 GB/s”“2.4 TB/s”，能不能放到同一把尺子上比。

写法确实杂。有的按比特计（100 Gbps），有的按字节计（900 GB/s），有的按整机汇总（1600 Gbps），有的按整卡双向（2400 Gbps）。折成同一口径之前，任何比较都可能差出整数倍。

### 符号先定死

后面四块只用这九个符号。

| 符号 | 含义 | 单位 |
|---|---|---|
| `S` | 一次传输的字节数 | B |
| `B` | 单向有效带宽 | GB/s |
| `B_nom` | 标称带宽（厂商写的那个） | GB/s |
| `L` | 单程延迟 | µs |
| `BDP` | 带宽延迟积 `B × L` | B |
| `U` | 链路利用率 | 无量纲 |
| `t` | 传输耗时 | ms |
| `n` | 单次传输的固定开销（握手、寻址、kernel launch） | ms |
| `η` | 有效带宽 / 标称带宽 | 无量纲 |

换算之前还有四条约定，本篇后面每个数字都挂在它们上面：

1. 十进制单位：1 GB = 10⁹ 字节，1 GB/s = 8 Gbps，不换算成 GiB。
2. 除以 8：Gbps → GB/s 一律 ÷8，这是最容易抄错的一步。
3. 单向优先：所有对比先折成单向。厂商写“双向”时，默认两个方向各占一半。
4. `B` 指有效带宽，不是标称值。真实集群里 `η` 通常只有 50–80%，第 3 章的算例取 100%。

另两条约定在用到它们的块里交代：单流串行的假设在第二块的 `BDP` 一节，只算传输时间的约定在第二块末尾。

### 两个换算撑起全篇

第一个是比特到字节。厂商和标准按比特标带宽，程序按字节搬数据，一字节 8 比特，所以换算是除以 8：

```
GB/s = Gbps ÷ 8
400 Gbps ÷ 8 = 50 GB/s
```

第二个是方向。厂商写“双向”时，两个方向各占一半带宽，折成单向要除以 2。`B-04` 的 NVLink 是 900 GB/s 双向，单向是 450 GB/s。这一步不做，比出来的是“NVLink 是 IB 的 18 倍”；做了以后是 9 倍。两个数都在这篇里出现，差别只在口径。后面凡是要跟跨机比，一律用单向。

这张表是同一把尺子的第一次使用。第二列照抄论文原写法，避免转述失真；后两列是折成 Gbps 与单向 GB/s 之后的值；最后一列说明这个数覆盖的是哪一段。

| 出处 | 论文原写法 | Gbps | GB/s（单向） | 口径说明 |
|---|---|---|---|---|
| `A-12` | InfiniBand 100 Gbps | 100 | 12.5 | 跨机，被同文的 NVLink 2400 Gbps 比下去 |
| `B-09` | 100Gb RDMA | 100 | 12.5 | 每节点一块 RDMA 网卡 |
| `B-14` | 100 Gbps 以太网 | 100 | 12.5 | TCP 与 RDMA 两种跑法对照 |
| `A-06` | 每 GPU 一块 200 Gbps RoCE 网卡 | 200 | 25 | ZionEX 的 scale-out |
| `A-06` | scale-out 1600 Gbps（单向） | 1600 | 200 | 8 GPU × 200 Gbps 汇总 |
| `A-12` | NVLink 2400 Gbps | 2400 | 300 | V100 级，整卡双向 |
| `C-12` | RoCE RDMA 800 Gbps/节点 | 800 | 100 | 节点级汇总 |
| `B-04` | 节点间 IB 8×400 Gbps | 3200 | 400 | 每节点 8 卡，均摊 50 GB/s |
| 教程第 3 章 | IB 400 Gbps | 400 | 50 | 单端口 |
| `A-06` | scale-up 2.4 TB/s（单向） | 19200 | 2400 | 机内聚合，单向 |
| `B-04` | NVLink 900 GB/s 双向 | — | 450 | 折单向要 ÷2 |

### 机内和跨机差在哪里

表里有两处值得单独看。

第一处是机内与跨机的差距。`A-06` 的同一台机器上，机内 scale-up 是 2.4 TB/s（单向），每卡跨机是 200 Gbps：

```
2400 GB/s ÷ 25 GB/s = 96 倍
```

同一个机箱里，内外两套互联差 96 倍。这不是设计失误，是距离决定的：机内是米级、走铜缆、不需要光模块；跨机是百米到公里级、走光、每个端口都要收发器和协议栈。一台机器之所以算“一台”，就是因为这 96 倍。

第二处是机内最窄的那一档。PCIe 4.0 ×16 单独算一遍：

```
16 GT/s/通道 × 16 通道 = 256 GT
128b/130b 编码 → × 128/130 = 252 Gbps
÷ 8 = 31.5 GB/s（单向）
双向 ≈ 63 GB/s
```

⚠️ 这组数是 PCI-SIG 规范的算术，不是任何一篇论文的数字。它决定了“半机内”路径的上限：一张卡从 PCIe 出去，单向只有 31.5 GB/s，比 NVLink 的 450 GB/s 窄一个数量级。

同样容易被忽略的，是每卡独立网卡与共享上行的区别。`A-06` 给每张 GPU 配一块独立的 200 Gbps RoCE 网卡，节点侧合计 1600 Gbps。如果反过来让 8 张卡共享一条 400 Gbps 上行：

```
共享：400 Gbps ÷ 8 = 50 Gbps/卡 = 6.25 GB/s/卡
独立：200 Gbps/卡 = 25 GB/s/卡
差 4 倍
```

差的不只是总带宽，还有出口的数量。共享口只有一个出口，任意两卡之间的 all-to-all 都要从这个口挤出去，排队堵在出口处，这就是队头阻塞。`A-06` 造 ZionEX 时选全互联加每卡独立网卡，买的是“任意两对通信都走最短路径”。

尺子到这里立好了：字节、单向、有效值。它回答“搬完 `S` 字节要多久”，回答不了“开始搬之前要等多久”。下一块补上延迟这一维。

## 第二块 · 延迟与带宽延迟积

这块要回答的是：为什么把带宽翻倍，小消息一点没快；以及一条链路要多少数据在路上才算跑满。

### 延迟是另一条轴

带宽说“每秒能灌多少”，延迟说“第一个字节什么时候到”。两者独立，各算各的。下面这张表给的是常见路径的量级：

| 路径 | 单程延迟量级 | 主要构成 |
|---|---|---|
| 片上（SM ↔ HBM） | 0.1–1 µs | 内存访问 + 同步原语 |
| NVLink（同机 GPU 间） | 1–5 µs | 链路协议 + 交换 |
| 同机 PCIe（GPU ↔ CPU） | 2–10 µs | 事务层 + 根复合体 |
| 跨机 RDMA（IB / RoCE） | 5–30 µs | 网卡 + 交换机跳 + 线缆 |
| 跨机 TCP | 50–200 µs | 协议栈 + 拥塞控制 + 重传 |

这张表是示意范围，不能当测量值。数字来源是公开微基准的常见区间，不是本专栏的测量，也不是任何一篇论文的原文。它只有五个数量级的分辨率，用法只有一种：判断一件事由延迟主导还是由带宽主导。

有一个能自我校验的算术。光纤里光速约 2×10⁸ m/s，即 5 ns/米，100 米光缆的传播延迟是 0.5 µs。RDMA 那 5–30 µs 里，光速只贡献了个零头，其余全是网卡、交换机和排队。延迟的成本在协议里，不在物理里，这也是换更快的线不会降低延迟的原因。

### 小消息慢在等，不在搬

在 12.5 GB/s 的链路上发 1 KB：

```
传输：1 KB ÷ 12.5 GB/s = 80 ns
固定往返：约 10 µs
```

传输只占 0.8%。小消息的性能几乎完全由固定开销 `n` 决定，把带宽翻倍等于没做。

把这一条做成表，取 `n = 5 µs`、400 Gbps（50 GB/s），看固定开销占多少：

| 消息大小 | 传输 `S/B` | 总时间 `n + S/B` | 固定开销占比 |
|---|---|---|---|
| 1 KB | 0.02 µs | 5.02 µs | 99.6% |
| 64 KB | 1.3 µs | 6.3 µs | 80% |
| 512 KB | 10.2 µs | 15.2 µs | 33% |
| 1 MB | 20 µs | 25 µs | 20% |
| 10 MB | 200 µs | 205 µs | 2.4% |

这张表是[第 3 篇](03-all-to-all-cost)里 `α` 那个符号的来源：`α` 不是玄学，就是这一列。表中 `n = 5 µs` 是假设值，真实值取决于框架与消息语义。

### 填满管道要多少字节

带宽也不是打开就有的。发送方要先把足够多的字节推到链路上，管道才被填满。这个量叫带宽延迟积，记作 `BDP`：

```
BDP = B × L
```

等式右边只有两个量：`B` 是单向带宽，`L` 是单程延迟。相乘之后单位是字节，含义是“要让链路一刻不停，任意时刻在路上的字节数”。

用 400 Gbps（50 GB/s）、单程延迟 10 µs 算：

```
BDP = 50 GB/s × 10 µs = 5 × 10¹⁰ B/s × 1 × 10⁻⁵ s = 5 × 10⁵ B = 500 KB
```

延迟换成 20 µs（跨机 RDMA 的常见档位），BDP 变成 1 MB。也就是说，这条链路要跑满，任意时刻得有 1 MB 数据在途。

这里加上单流串行的约定：一条消息要等上一条完成（request-response 语义，或每条消息一次同步）。单流下在途量不超过一条消息的大小，于是

```
U = min(1, S / BDP)
```

按 400 Gbps / 20 µs 代进去：

| 单条消息 | 在途上限 | 链路利用率 | 等效带宽 |
|---|---|---|---|
| 64 KB | 64 KB | 6.4% | 3.2 GB/s |
| 256 KB | 256 KB | 26% | 13 GB/s |
| 512 KB | 512 KB | 51% | 26 GB/s |
| 1 MB | 1 MB | 100% | 50 GB/s |
| 2.6 MB | 2.6 MB | 100% | 50 GB/s |

这张表是 `A-15`（FusedRec）立论的物理基础。它的结论是“去重让消息变小，反而把带宽用废了”，机制就在这一列：消息从 2.6 MB（一张表一条）掉到 100 KB（去重后的一千条小消息）时，单流利用率从 100% 掉到 10%。碎片化的代价不是多几次握手，是带宽本身被浪费掉九成。

同一条算术放到 NVLink 上更狠。单向 450 GB/s、延迟 2 µs：

```
BDP = 450 GB/s × 2 µs = 900 KB
```

900 KB 的在途需求意味着：任何小于 1 MB 的消息，在机内链路上也浪费带宽。碎片化不是跨机专有的病，它是“低延迟 + 高带宽”链路的通病——链路越好，填满它需要的消息越大。

延迟还直接乘在 `BDP` 里：延迟翻倍，填满链路所需的字节也翻倍。所以越是远的链路越需要大消息，远和碎是相乘的，不是相加的。

本篇的推导只算传输时间，不含固定开销的多次累加 `n·K`，那一项留给[第 3 篇](03-all-to-all-cost)。第二块里出现的 `n` 只是为了单独看它一次占多少。

延迟和带宽都量完了，账面上还差一样：一次传输由谁发起，对端要不要在场。这个差别不改带宽，改的是谁被挂在关键路径上。

## 第三块 · 三种语义

这块要回答的是：同样搬一批字节，为什么有的写法会让对端决定你的快慢。

物理带宽决定多久搬完，语义决定这段时间里谁可以被阻塞。三种语义的差别不在快慢，在谁掌握时机。

| 语义 | 谁发起 | 对端是否需要执行指令 | 前置条件 | 典型接口 |
|---|---|---|---|---|
| load/store | 发起方直接读写对端地址 | 不需要 | 对端内存映射进本方地址空间 | CUDA IPC、NVSHMEM 的 load/store |
| two-sided send/recv | 双方各自投递 | 需要，收发必须配对 | 匹配的 recv 已挂上 | MPI_Send/Recv、NCCL |
| one-sided RDMA read/write | 发起方单边读写远端内存 | 不需要 | 远端内存已注册并授权 | IB verbs、RoCE |

读这张表只需看一列：对端是否需要执行指令。load/store 不需要——发起方把对端 HBM 映射进自己的地址空间，一条普通的写指令就落到对方显存里，NVLink 能做到 load/store 就是靠这个。two-sided 需要，收发必须配对，对端没挂上 recv，发起方就得等。one-sided 也不需要，发起方自己决定什么时候读、什么时候写，对端甚至不知道发生过。

前两种把对端绑在关键路径上，第三种不绑。三种语义的失败模式也不一样，这一列决定了出错时你能不能查得出来：

| 语义 | 对端慢时的发起方 | 消息丢失时 | 怎么观测 |
|---|---|---|---|
| load/store | 读到旧值、写下去丢失（静默） | 一般不在这一层重传 | 校验和、结果比对 |
| two-sided | 阻塞在匹配的 recv 上 | 传输层重传，应用无感 | 通信耗时打点 |
| one-sided | 照常返回（完成 ≠ 对端已处理） | 传输层重传 + 完成队列报错 | 轮询完成队列的深度 |

最后一行是 one-sided 最容易踩的地方：完成队列说“发完了”，只表示本地网卡收下了，不表示对端的内存序已经让你看得见。所有 one-sided 系统都要自己补一道 fence 或确认。

三种语义跑在三种传输层上，差别不在快慢一档，而在谁保证不丢包：

| | IB | RoCEv2 | TCP |
|---|---|---|---|
| 跑在 | 专用 IB 网络 | 以太网 + UDP/IP | 以太网 |
| 流控 | 链路层信用（保证不丢） | PFC 逐跳暂停 | 无，靠重传 |
| 拥塞控制 | 网卡自带 | ECN 标记 | 窗口制 |
| 单程延迟 | 最低 | 略高 | 最高 |
| 是否需要专网 | 是 | 可与普通流量共网（PFC 有死锁风险） | 否 |
| one-sided 支持 | verbs 原生 | verbs 经 RoCE 映射 | 无 |

⚠️ 这张表是通用网络知识，延迟一列与本篇的示意表同源，不可当测量值。它解释的是“无损以太网”为什么是个工程问题：PFC 用逐跳暂停上游发包来模拟不丢包，代价是可能死锁；IB 用信用机制从设计上避免，代价是必须专网。

### 选语义等于选谁等谁

`C-12` 的选择就是这几列的直接后果：它选 NVSHMEM 与 CUDA IPC，理由不是它们更快，而是它们不需要对端配合。它要把 FSDP 的 all-gather / reduce-scatter 拆成点对点请求，让每台设备同时是 server 和 worker，并且要求 server 在算的时候被打断也不受影响。原文的理由很干脆：MPI / NCCL 需要显式的接收方参与，server 无法被动响应 worker 的按需请求；它要的正是“worker 主导、server 不知情”的传输。所以节点内用 CUDA IPC，节点间用 NVSHMEM；唯一例外是梯度累加，那是读-改-写，不是纯传输，需要一个轻量 daemon。

one-sided 省掉的是对端的等待，代价转到发起方这边：它要自己确认写完了，要么在 CPU 上轮询完成队列，要么在 kernel 里 spin 等内存序。`C-12` 把通信 kernel 写在 Triton-Distributed 上，本质是把这份轮询搬进 GPU，用 SM 的算力换掉 CPU 的等待。

这份自由是拿拓扑优化换来的。`C-12` 自己的实测：节点内 ODC 与集合通信相当，跨节点 ODC 明显慢于集合通信。原因是集合通信能利用分层拓扑（先机间广播、再机内广播），而纯 P2P RDMA 放弃了这个优化。所以 one-sided 买到的是时间解耦，不是带宽；用它在快网络上替代 all-reduce，通常会更慢。

two-sided 还有一层不对称：它的配对要求把两个进程的时间轴对齐。小规模时它就是一致性的附带保证，大规模时它就是同步屏障。这正对应[第 4 章](../guide/04-data-parallel-limits)讲的 straggler：屏障越多，最慢者的代价被摊到越多人头上。

### 粒度是隐性成本

最后一项隐性成本是粒度，它常被误当成语义问题。算例里每迭代 819 万次查询，摊到 128 卡：

```
每卡查询数 = 819 万 ÷ 128 ≈ 6.4 万条
若每条一次消息、固定开销 5 µs：6.4 万 × 5 µs = 320 ms
预算 51 ms → 超 6 倍
```

逐条发在数量级上就不成立。所以任何真实实现都得把 6.4 万条查询压成几十个大消息（按目的地分桶后合并），all-to-all 因此不是“819 万次 send/recv”，而是“每卡几十次大传输”。这一层批处理不额外花时间，但它掩盖了一件事：消息尺寸是被实现选出来的，不是被物理决定的。选小了浪费带宽（上一块的 `BDP` 那一列），选大了阻塞队列（[第 3 篇](03-all-to-all-cost)的 HOL 项）。

语义交代完了。第 1 块折出的单位、第 2 块给出的 `BDP`、这一块分出的三种阻塞关系，现在可以合成一张表：按“跨不跨机”排序，看台阶有多高。

## 第四块 · 带宽悬崖

这块要回答的是：单位折好、语义选对之后，剩下最大的那个差距有多大，换成人话值多少钱。

把单位折好以后，按“跨不跨机”重排所有档位，得到本篇最重要的一张表。这张表怎么读：最后一列是相对跨机 400 Gbps 的倍数；“路径”和“依据”要一起看，依据写规范算术的行是算出来的，不是测出来的。

| 路径 | 单向 GB/s | 相对跨机 400 Gbps | 依据 |
|---|---|---|---|
| 同机 NVLink（H100 级） | 450 | 9× | `B-04` 的 900 GB/s 双向折半 |
| 同机 NVLink（V100 级） | 300 | 6× | `A-12` 的 2400 Gbps |
| 同机 PCIe 4.0 ×16 | 31.5 | 0.6× | 规范算术 |
| 跨机 RoCE 800 Gbps/节点 | 100 | 2× | `C-12` |
| 跨机 IB / RoCE 400 Gbps | 50 | 1× | 教程第 3 章 |
| 跨机 200 Gbps/GPU | 25 | 0.5× | `A-06` |
| 跨机 100 Gb | 12.5 | 0.25× | `B-09`、`B-14` |

称它为悬崖而不是斜坡，有四个独立的原因。

1. 拓扑。跨机要过交换机，超售比把标称带宽变成只在峰值时成立的数。`C-06` 明说它的实验网络“任意两台主机间满二分、无超售”，真实共享集群没这么干净。
2. 协议。跨机要走网卡、DMA，RoCE 还要无损以太网。`B-14` 给了一个干净的对照：同一份“嵌入传输减少 48%–89%”，在 TCP 上换来 2.11×，在 RDMA 上只有 1.61×。协议栈本身就是一层税，而且网络越快，这层税占的比例越高。
3. 参与方。跨机路径的参与方随卡数增长，机内路径不增长。`A-03` 的实测很直接：把同步组限制在同一台机器内（8 卡同 host），比跨 host 快 7×。
4. 距离。机内可以走铜缆和 PCB（NVLink 几米内），跨机要走光模块（几十米到几公里）。距离决定了介质，介质决定了每通道的速率上限与功耗。这一层没有数字可抄，它只解释为什么机内那一档的提升不能简单复制到跨机。

悬崖的形状决定了优化的形状：能把流量从跨机搬到机内，比把跨机流量压小更值钱。`C-06` 的拆塔、`A-03` 的分组，做的都是搬流量，不是压流量。

这个结论可以换成一条汇率。同样 1 GB 走两条路径，耗时差是：

```
跨机 1 GB ÷ 50 GB/s   = 20.0 ms
机内 1 GB ÷ 450 GB/s  = 2.22 ms
差                    = 17.8 ms
```

每把 1 GB 流量从跨机搬到机内，省 17.8 ms，相当于 51 ms 预算的 35%。反过来，把跨机流量压缩 2 倍只省 5.3 ms（10.5 → 5.25 ms）。同样是“少搬一半”，搬位置比压体积便宜三倍多。这条汇率是 `C-06` 拆塔的定价依据，也是[第 3 篇](03-all-to-all-cost)讨论压缩盈亏平衡时的参照物。

悬崖还有一个容易被忽略的后果：它让“平均带宽”这个指标失去意义。`C-06` 的原话是“为了在 GPU 显存里读/写一个字节，你需要在网络上发一个字节”——全局 all-to-all 的延迟由最慢的跨机链路决定，机内 NVLink 的高速带宽完全帮不上忙。带宽是一个分层的量，不是标量。

## 算例：同一份 525 MB 走遍五个档位

这一步在算什么：拿一份固定的数据量，放到前面四块给出的每一档链路上，看它各占多少时间预算。

设定：每次迭代要过网的嵌入数据 525 MB（第 3 章口径，算术上是未去重 2.1 GB 的 1/4），时间预算 51 ms。

⚠️ 两个口径先钉住。525 MB 是全批去重后的总量，128 卡分摊后每卡出站约 4.1 MB，不是每卡要搬这么多。51 ms 是 `A-10` 的 16 trainer 口径，128 卡时预算约为 51 ÷ 8 ≈ 6.4 ms；下面所有百分比都拿 51 ms 当分母，只用来比较不同档位的相对权重。

<div class="example">

① 同一份数据，两条路径

```
跨机 400 Gbps（50 GB/s）
525 MB ÷ 50 GB/s = 10.5 ms      → 占 51 ms 的 20.6%

同机 NVLink（450 GB/s 单向）
525 MB ÷ 450 GB/s = 1.17 ms     → 占 51 ms 的 2.3%
```

② 同一份数据，按网络档位排一遍

| 链路 | 单向 GB/s | 耗时 | 占 51 ms |
|---|---|---|---|
| 100 Gb | 12.5 | 42.0 ms | 82% |
| 200 Gbps/GPU（`A-06`） | 25 | 21.0 ms | 41% |
| 400 Gbps（第 3 章） | 50 | 10.5 ms | 21% |
| 800 Gbps/节点（`C-12`） | 100 | 5.25 ms | 10% |
| NVLink 单向（`B-04`） | 450 | 1.17 ms | 2.3% |

③ 一步里其实有三类流量，不止一类

| 流量 | 体积 | 依据 |
|---|---|---|
| 前向：查询路由（ID 与目的 rank） | 约 131 MB | 推导：819 万次 × 16 B/条（id 8 + 表 4 + rank 4） |
| 前向：嵌入向量回传 | 525 MB | 算例去重后体积 |
| 反向：更新后的行回传 | 525 MB | 推导：要更新的行数约等于查过的行数 |
| 组间同步（2D 并行） | 全表 10.2 TB | 算例参数；`A-03` 同步的是权重而非梯度 |

前三项合计 1.18 GB：

```
1.18 GB ÷ 50 GB/s = 23.6 ms    → 占 51 ms 的 46%
```

还没算第四项。全表同步 10.2 TB 走 50 GB/s 是 204 秒，单步根本不可能。这解释了 `A-03` 为什么把缓解手段写成三条：减少组数、把组限制在同一台机器内、降低同步频率。

④ 反推：需要买多大带宽

把 51 ms 里的一半（25.5 ms）留给通信，搬运 1.18 GB：

```
1.18 GB ÷ 25.5 ms = 46 GB/s  → 约 370 Gbps
```

所以 400 Gbps 是“刚好够”的那一档，没有任何余量。想去重把体积压到 1/4（295 MB），需求降到 11.6 GB/s ≈ 93 Gbps，100 Gb 就够。压体积和买带宽是可以互换的两种货币，汇率就是这条除法。

⑤ 拓扑占比：机内那一份其实很小

128 卡按 16 节点 × 8 卡摆放。all-to-all 时每卡要发给其余 127 卡，其中 7 张同节点、120 张跨节点：

```
机内份额 7/127 = 5.5%
跨机份额 120/127 = 94.5%
```

按 525 MB 分摊（假设全二分、无超售）：

```
跨机 496 MB ÷ 50 GB/s  = 9.92 ms
机内 29 MB ÷ 450 GB/s  = 0.06 ms
合计                   = 9.98 ms
```

对比全跨机的 10.5 ms，只快了 5%。这就是“机内带宽很快但帮不上忙”的算术版：机内份额太小，快 9 倍也只摊到 5% 的流量上。`C-06` 的拆塔本质是把这个 5.5% 抬高，塔越大，留在机内的份额越多。

⑥ 口径对账：525 MB 是全局还是每卡

```
全局 1.18 GB ÷ 128 卡 = 9.2 MB/卡
若 525 MB 是每卡量：525 MB × 128 = 67 GB → 1.3 s @50 GB/s，超预算 26 倍
```

所以第 3 章与第 6 章的 525 MB 只能是全局量（整批去重后的总量），真实每卡出站约 4.1 MB。第 2 篇把它当“一张卡独自推完全批”代入集合通信公式（那边叫全批口径），为的是跟第 6 章的“0.05 ms/条”直接对账；换成每卡口径只是全部除以 128，`W/S` 与 `D` 这些比值形状完全不变。

把 ② 那张表竖着读一遍：在 100 Gb 那一档，光搬数据就吃掉 82% 的预算，任何算法优化都没有余地。到 400 Gbps 还有 54% 留给计算和同步。到 NVLink 那一档，传输变成 2% 的噪声，瓶颈只能去别处找。

⚠️ 这里叠了五个假设：`η = 100%`（标称跑满）、反向与去重量相同、查询路由按 16 B/条估、去重后 525 MB 是全量而非每卡、第四项每步都做（实际必须降频）。按 `η = 70%` 算，400 Gbps 那几行整体放大 1.43 倍：10.5 ms → 15.0 ms，1.18 GB 那一项 → 33.7 ms（66%）。

百分比的分母也要对齐：第 3 章的“通信占 55%”是“通信 /（计算 + 内存 + 通信）”，本篇的 46% 是“通信 / 51 ms 预算”。两个数不矛盾，但含义不同，不能直接相加。

</div>

这张表解释了为什么“通信占 55%”这个结论对硬件极度敏感：它不是一个模型的属性，是模型 × 网络档位的联合属性。同一份 525 MB，在 100 Gb 集群上是灾难，在 NVLink 内是舍入误差。

## 模型在哪里不成立

- 标称不等于有效。全篇用 `η = 100%` 是为了算术干净；真实集群 50–80% 更常见，随机访问、小消息、超售都会往下压。结论的结构性部分（台阶、口径）不变，绝对值会整体偏移。
- 单向与双向的口径陷阱会反复出现。同一篇论文里“900 GB/s”和“450 GB/s”都可能指同一块 NVLink。跨论文比带宽时先确认方向，否则 2 倍的错误会一路传到结论里。
- 延迟表不可当测量值。它只有五个数量级的分辨率。要定超时阈值或缓冲大小，得在自己集群上测。
- `BDP` 那一节用单流口径，是保守界。真实的传输层可以流水多打几条消息，在途量能超过单条消息大小，利用率会高于 `S/BDP`。但“每消息一次同步”的实现确实吃这个上限，而 all-to-all 常常就是这种实现。
- 语义的选择有隐性成本。one-sided 要求内存注册、地址可见、权限管理。表规模固定时这是一次性开销；ID 集合持续增长、分片频繁重排时，这套簿记会变成运行期负担（`B-09` 的静态分片就卡在这一步）。
- “省字节”的价值随网络变快而衰减。`B-02` 的对照很清楚：1 Gbps 上缓存方案拿到 20× 级加速，10 Gbps 上只有 5.2×。`B-14` 是同一个规律的另一种测法（TCP 2.11× / RDMA 1.61×）。推论是：在 400 Gbps 以上的集群里，压缩与去重的收益会被网络本身吞掉，这条推论在[第 3 篇](03-all-to-all-cost)会用具体的不等式算出来。
- 525 MB 是“总量”还是“每卡”，本篇按总量处理。集合通信的公式里 `S` 是每卡消息量，两者混用会让结果差 P 倍。第 2 篇会把这个口径固定下来。
- 本篇没有算协议开销和重传。TCP 的 50–200 µs 延迟里有一部分是重传超时，它的分布是重尾的，平均值不说明问题，这也是为什么第 3 篇要用 P99 而不是均值收尾。
- 算例里的 131 MB 元数据是估算。真实实现会把 ID 压缩、按目的地分桶后合并，体积可能小一个数量级。这一项不影响结论的方向（向量搬运仍是大头），但会影响 1.18 GB 这个总数的精度。
- 算例 ⑤ 假设了全二分。真实集群的跨机路径要过两层甚至三层交换，超售比 3:1 到 8:1 很常见。超售下 9.98 ms 会变成 20–30 ms，那时“把流量搬进机内”的汇率会从 17.8 ms/GB 涨到 50 ms/GB 以上，`C-06` 一类方案的价值随之放大。
- 本篇的“台阶”是两级模型。真实数据中心是三到四级（机内 NVLink / 同机架 TOR / 跨机架 spine）。级数越多，“平均带宽”越没有意义，只能按每一级分别算。
- 三种语义可以同时存在。`A-06` 的 4D 并行里，row-wise 切分用 ReduceScatter、column-wise 与 table-wise 用 alltoall、data 维用 allreduce。同一份模型里三种原语并存，因为每一种都对应一种“谁需要知道谁的哪些字节”。选语义的单位是算子，不是集群。
- 延迟和带宽不是二选一，它们在 `BDP` 里相乘。本篇分开讲只是为了各自算得清；判断一条消息会不会浪费带宽时，两个量要同时代入。
- 五个档位其实可以用一条公式串起来：`t = n + S/(η·B_nom)`。档位之间的差别只是 `n`、`η`、`B_nom` 三个参数各取什么值，不需要五套理论。
- 不覆盖推理侧与存储侧。推理的查表是“少量 key、低延迟”，结构与训练的大批量 all-to-all 不同；嵌入从内存/SSD 搬进 HBM 的那段带宽属于[第 7 章](../guide/07-storage-hierarchy)，不属于互联。
- 本篇的数字都能用一条命令复算。`525 MB ÷ 50 GB/s`、`2.4 TB/s ÷ 200 Gbps`、`B × L` 三个式子加一台计算器即可；对不上就是哪一步的单位或口径错了。

<div class="takeaway">

**本篇结论**：比带宽之前先折成 GB/s、单向、有效值——Gbps 除以 8，双向再除以 2。

机内到跨机是台阶，单向 9 倍，双向 18 倍。填满链路要 `B × L` 的在途字节：400 Gbps / 20 µs 是 1 MB，小于它的消息按比例浪费。语义决定谁被阻塞，不决定快慢，one-sided 买到的是时间解耦而不是带宽。

算例里 525 MB 走 50 GB/s 是 10.5 ms（预算 21%），走 450 GB/s 是 1.17 ms（2.3%），三类流量合计 1.18 GB / 23.6 ms。

</div>
