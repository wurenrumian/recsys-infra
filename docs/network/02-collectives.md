# 网络 2. 集合通信的字节账本

<div class="deep-anchor">

**在教程的哪一层** 对应[第 6 章](../guide/06-communication)的"all-to-all 到底在传什么"；这里把它换成每卡出站字节与同步步数两个量。

</div>

## 一句话版本

一次集合通信要花多久，由两个数决定：每张卡自己发出去多少字节，以及要串行等多少轮。前者除以带宽是传输时间，后者乘以每轮的固定开销是延迟。

这一篇把这两个数算给三种常用算法：ring all-reduce、halving-doubling 和 all-to-all。算完会发现一件不太直观的事：字节最少的那个并不最快，因为它在步数和尾延迟上把钱又付了回去。

最后把 `C-06` 报的"每轮 3 次 AlltoAll + 1 次 AllReduce"折算成毫秒，套进 51 ms 的整步预算里看它够不够。

## 这篇的地图

全篇分五块，加一个算例。

1. **两个数，一条公式** —— 出站字节与同步步数分别乘什么，变成时间的两项。
2. **在环上走两圈** —— ring all-reduce 的两个阶段，以及为什么加卡不会让每卡出站变多。
3. **折半与倍增** —— halving-doubling 用对数步数做同样的事，以及它为什么没有全面替代环。
4. **all-to-all 的另一本账** —— 字节只有一半，却要在步数、倾斜与 incast 上付回去。
5. **两种带宽口径** —— 应用视角与链路口径怎么换算，弱扩展下曲线难看的原因。

五块是一条链。第 1 块立成本模型；第 2、3 块用同一份模型算两种 all-reduce，把差别压到一个阈值上；第 4 块换到 all-to-all 这个不规则的原语；第 5 块交代读论文时最容易混的带宽口径。算例把前面所有公式代进 128 卡的设定，最后做一次全批与每卡的口径对账。

| 概念 | 一句话 |
|---|---|
| 集合通信 | 一组卡一起完成的一次数据交换，全体求和、广播、互相分发都算 |
| 出站字节 `W` | 每张卡自己发出去多少字节，决定传输时间 |
| 同步步数 `D` | 要串行等多少轮，决定固定开销累积多少 |
| ring | 所有卡排成一个环，数据沿环一格一格走 |
| halving-doubling | 每一轮把参与集合对折，用对数步数完成 all-reduce |
| 满二分 | 任意两张卡之间都能同时以满带宽互传 |
| busbw | 把应用层看到的速度按算法折算回链路口径，用来看链路被用到几成 |

术语到此交代完毕。符号表在第一块里一次性给出，后面不再重复。

## 第一块 · 两个数，一条公式

这块要回答的是：一次集合通信的耗时，能拆成哪几项。

集合通信（collective communication）是一组卡一起完成的一次数据交换。常见的有三种语义：全体求和后每张卡都拿到结果（all-reduce）、求和后每张卡分走一部分（reduce-scatter）、每张卡把自己的数据切碎发给所有卡（all-to-all）。

不管哪一种，成本都落在两类事情上。一类是搬字节，取决于每张卡发出去多少，记作 `W`；另一类是等轮次，取决于要串多少步，每步有一次固定的握手与协议开销，步数记作 `D`。
两个量分别乘上各自的价格，就是总时间：`W` 除以带宽是传输项，`D` 乘以每步开销是延迟项。

下面这张表是本篇全部符号，单位一并列出。

| 符号 | 含义 | 单位 |
|---|---|---|
| `P` | 参与通信的卡数（rank 数） | 个 |
| `S` | 每卡要贡献的消息字节数 | 字节 |
| `W` | 每卡出站字节数 | 字节 |
| `D` | 同步步数 | 步 |
| `B` | 单向有效带宽 | GB/s |
| `α` | 每步固定开销（握手、协议、kernel） | ms |
| `t` | 完成时间 | ms |
| `algbw` | 应用视角带宽 `S/t` | GB/s |
| `busbw` | 归一化总线带宽 | GB/s |

后面每个公式都挂在这六条假设上：

1. 同构链路：所有卡之间的带宽都是 `B`，没有远近之分。
2. 无拥塞、无重传：`B` 是有效带宽，不是标称。
3. 满二分：任意两卡之间都能同时以 `B` 互传。`C-06` 明说它的实验网络满足这一条，真实集群通常不满足。
4. 每步消息大小相同：忽略尾部不足一块的填充。
5. `S` 是每卡贡献的字节。算例按全批口径取 `S = 525 MB`（等价于把整批记在一张卡上），以便和第 3、6 章直接对账；真实每卡出站量是 4.1 MB，见算例末尾的口径对账。`W/S`、`D` 与口径无关。
6. 除显式引入 `α` 的地方，公式只算传输时间。

六种算法或原语的总公式如下，本篇后面要做的只是把它们拆开验算一遍：

```
ring all-reduce:        W = 2·S·(P−1)/P        D = 2·(P−1)
reduce-scatter:         W = S·(P−1)/P          D = P−1
all-gather:             W = S·(P−1)/P          D = P−1
halving-doubling:       W = 2·S·(1−1/P)        D = 2·log2(P)
all-to-all（全互联）:    W = S·(P−1)/P          D = 1
all-to-all（ring）:      W = S·(P−1)/P          D = P−1
```

以上全部是集合通信的标准结果，不是任何一篇论文的原文。

成本模型只有加法和除法：搬字节的那一项，和数轮次的那一项。这两项逐项相加，就是这篇说的字节账本。下一块从最大的那个原语开始，把 `W` 与 `D` 一项一项算出来。

## 第二块 · 在环上走两圈

这块要回答的是：all-reduce 为什么加卡不会让每张卡出站变多。

all-reduce 的语义是：所有卡把自己那份数据加起来，每张卡最终拿到完整的和。梯度同步用的就是它。

ring 的做法是把消息切成 `P` 块，每块 `S/P`，让数据沿着环一格一格往前走，分两个阶段完成。
第一阶段叫 reduce-scatter（归约分散）：每张卡把手上的一块发给右邻，同时从右邻收一块并累加，走 `P−1` 步之后，每张卡手里剩下一块完整的部分和，而不是完整结果。
第二阶段叫 all-gather（全收集）：每张卡手里那块部分和沿环再传一圈，其余卡依次复制并累加，于是每张卡都拿到全部 `P` 块。

### 为什么出站是两倍消息量

第一阶段每步发 `S/P` 字节，走 `P−1` 步：

```
W₁ = (S/P) × (P−1) = S·(P−1)/P
```

第二阶段同样 `P−1` 步，同样每步 `S/P`：

```
W₂ = S·(P−1)/P
```

两个阶段相加：

```
W = W₁ + W₂ = 2·S·(P−1)/P
D = (P−1) + (P−1) = 2·(P−1)
```

用 4 卡画一遍。`k` 是卡号，箭头是每步的收发方向，`→` 表示数据前进一格：

```
阶段一 reduce-scatter（3 步）
 步1   k0→k1  k1→k2  k2→k3  k3→k0     每步：一块 S/4
 步2   k0→k1  k1→k2  k2→k3  k3→k0
 步3   k0→k1  k1→k2  k2→k3  k3→k0
 结果   每卡持有一块的完整和

阶段二 all-gather（3 步，方向同）
 步1..3 同样 3 次，把各自那块传遍全环
 结果   每卡持有全部 P 块
```

### 加卡以后

`P` 变大时 `(P−1)/P → 1`，所以 `W → 2S`。加卡不会让每张卡的出站字节变多：`P=8` 时是 1.75S，`P=128` 时是 1.984S，`P=1024` 时是 1.998S。all-reduce 能扩展到千卡，就建立在这个极限上。

| P | `W/S`（ring all-reduce） | `D` |
|---|---|---|
| 8 | 1.75 | 14 |
| 64 | 1.969 | 126 |
| 128 | 1.984 | 254 |
| 1024 | 1.998 | 2046 |

这张表怎么读：第二列很快贴住 2 不动，第三列一直在涨。`D = 2(P−1)` 是线性的，字节数却是常数，这两件事决定了 ring 从什么规模开始吃亏。

这也解释了 [第 4 章](../guide/04-data-parallel-limits)里"DP 的 all-reduce 规则可预测"的确切含义：每一步的大小和方向都是编译期已知的，可以提前流水。它的成本与数据分布无关，只与 `P` 有关。

ring 的字节账已经封顶，涨的是步数。下一块换一种切法，看能不能只把步数压下去。

## 第三块 · 折半与倍增

这块要回答的是：同样一次 all-reduce，能不能少等几十轮。

halving-doubling（递归折半再倍增，Rabenseifner 提出，常简称 HDR）换了一个切法：不沿环传，而是每一步把参与者集合对折，通信对象的距离依次取 1、2、4……
reduce-scatter 阶段，第 1 步与距离 `P/2` 的邻居交换一半数据，第 2 步与距离 `P/4` 的邻居交换四分之一，依此类推，每步把待处理的数据量减半。all-gather 阶段做相反的事。

### 为什么步数是对数

第一阶段出站：

```
W₁ = S/2 + S/4 + S/8 + ... = S·(1−1/P)
```

第二阶段出站同样 `S·(1−1/P)`，合起来：

```
W = 2·S·(1−1/P)        D = 2·log2(P)
```

`2·S·(1−1/P)` 与 ring 的 `2·S·(P−1)/P` 是同一个式子，字节数完全一样，差别只在步数：

| P | ring `D` | HDR `D` | 倍数 |
|---|---|---|---|
| 8 | 14 | 6 | 2.3× |
| 64 | 126 | 12 | 10.5× |
| 128 | 254 | 14 | 18× |
| 1024 | 2046 | 20 | 102× |

### 步数乘上每步开销，就是钱

取 `α = 5 µs`、`P=128`、50 GB/s，两种消息尺寸各算一遍：

```
S = 1 MB  ring: 1.984 MB ÷ 50 GB/s + 254 × 5 µs = 0.04 + 1.27 = 1.31 ms
          HDR : 1.984 MB ÷ 50 GB/s +  14 × 5 µs = 0.04 + 0.07 = 0.11 ms
          差 12 倍

S = 525 MB ring: 1041.8 MB ÷ 50 GB/s + 1.27 ms = 20.84 + 1.27 = 22.1 ms
          HDR : 1041.8 MB ÷ 50 GB/s + 0.07 ms = 20.84 + 0.07 = 20.9 ms
          差 6%
```

同一对算法，在 1 MB 上差 12 倍，在 525 MB 上只剩 6%。`α` 是唯一的自变量。

把这一点解出来会得到一个阈值。令步数项等于字节项：

```
α · 2(P−1) = 2·S·(P−1)/(P·B)
⇒ S* = α · P · B
P=128、B=50 GB/s、α=5 µs 代入：
S* = 5 µs × 128 × 50 GB/s = 3.2 × 10⁷ B = 32 MB
```

`S << 32 MB` 时步数项主导，HDR 值钱；`S >> 32 MB` 时字节项主导，ring 的拓扑优势值钱。`S*` 与 `P` 成正比，所以卡越多这个阈值越高，碎片化在大规模上才是真问题。这条推论在第 3 篇会变成成本模型的主线。

### 那为什么不全用 HDR

先给一个反直觉的结论：在这个成本模型里，HDR 永远不差于 ring，因为它的 `W` 与 ring 相同，`D` 更小。ring 存在的原因是模型之外的三件事。

1. HDR 每一步都是全对全的模式：这一轮与距离 1 的邻居换，下一轮与距离 2 的换。在分层拓扑上，这种模式会把跨机链路打满（每条连接都同时跑到标称带宽）。ring 只跟左右邻居说话，跨机流量被限制在相邻节点之间，对"机内有 NVLink、机间只有 100 Gbps"的机器更友好。
2. HDR 要求 `P` 是 2 的幂。非 2 的幂要退化处理，多出一步，而这一步在 `P` 很大时并不便宜。
3. 大消息时字节项主导，步数项可以忽略，ring 的拓扑优势就白拿了。

所以选择规则要补一句限定：`α·D` 与 `W/B` 谁大就优化谁，但两者很接近时，拓扑决定。真实的 NCCL 会在不同规模、不同拓扑下切换算法，而不是选一个用到底。

all-reduce 的两个版本都交代完了：字节相同，步数差一个数量级，分界线在 32 MB。下一块换成 all-to-all，字节更少，故事更麻烦。

## 第四块 · all-to-all 的另一本账

这块要回答的是：字节只有一半的 all-to-all，为什么在实践中更贵。

all-to-all 的语义是：每张卡有 `S` 字节要分给其余 `P−1` 张卡，每个对端拿 `S/P`。于是每张卡出站：

```
W = (S/P) × (P−1) = S·(P−1)/P
D = 1（满二分，一枪打完）  或  P−1（只有邻居链路，ring 化）
```

只有 all-reduce 的一半。按纯字节算，它应该便宜一半；实践中它更贵，原因有四条。

1. 没有 reduction 可以摊薄。all-reduce 的每个字节在途中被 `P` 次累加摊过，一份字节干了 `P` 份活；all-to-all 的每个字节只有一次用处，没有摊薄空间。
2. 最慢的一对决定整体。ring all-reduce 是流水线，慢链路只影响自己那一环，其余继续走；all-to-all 里任意一对慢，整步就慢。
3. 不可预测。all-reduce 每步的大小已知、可以提前流水；all-to-all 每个目的地的量取决于数据分布，[第 4 章](../guide/04-data-parallel-limits)的"1% 承担 92% 访问"直接落到这里。
4. incast。热点行集中在少数卡上时，多个源同时打一个目的，队列在目的端堆积。这是排队问题，加带宽不一定解决。

### 第 4 条可以算

按 [第 4 章](../guide/04-data-parallel-limits)引用的分布（`A-10`：1% 的行承担 92% 以上的访问），摆两个极端：

```
均匀分布（假设）
  2.1 GB（未去重）÷ 128 卡 = 16.4 MB/卡
  16.4 MB ÷ 50 GB/s = 0.33 ms

最坏倾斜：92% 的查询落到 1% 的行，而这些行恰好集中在 1% 的卡上
  1.28 张卡承担 819 万 × 92% = 753 万次查询
  753 万 × 256 B = 1.93 GB，分摊到 1.28 张卡 = 1.51 GB/卡
  1.51 GB ÷ 50 GB/s = 30.1 ms
```

同一个 all-to-all，字节总量相同，耗时差 90 倍。这就是"平均带宽"在 all-to-all 上失效的原因：它假设每张卡拿到的份额一样，而倾斜把这个假设直接推翻。`A-03` 的不均衡比 5.70 是这个现象的另一种度量方式。

### 第二个结构差别在消息粒度

all-to-all 对每个对端只发 `S/P`，所以单条消息的尺寸随 `P` 缩小：

| P | 每个对端的消息 | 相对 BDP（1 MB） | ring 形式下的在途利用率 |
|---|---|---|---|
| 128 | 4.1 MB | 4.1× | 100% |
| 1024 | 512 KB | 0.5× | 51% |
| 8192 | 64 KB | 0.06× | 6% |

这张表怎么读：第三列是单条消息能装下几个带宽时延积（BDP），即一条链路在途能装多少字节。小于 1 就意味着消息发完时，链路还没被填满。

满二分（`D = 1`）时 `P−1` 条消息同时在途，总在途量约等于 `S`，链路填得满。ring 化（`D = P−1`）之后每步只有一条 `S/P` 的消息在途，`P` 一大就掉到 BDP 以下。这时步数不只影响延迟，还直接浪费带宽。第 1 篇的利用率公式在这里第二次出现，说明它不是传输层细节，而是集合通信算法选择的一个约束。

这也正是[第 4 章](../guide/04-data-parallel-limits)说的"断裂点二"。把两种通信并排看：

| | DP 的 all-reduce | 嵌入的 all-to-all |
|---|---|---|
| 每卡每步字节 | `2·参数·(P−1)/P`，与 batch 无关 | `S·(P−1)/P`，与 batch 成正比 |
| 规则性 | 完全规则，每步同大小 | 取决于数据分布，每步不同 |
| 负载 | 天然均衡 | 倾斜，不均衡比 5.70 |
| 失败模式 | 带宽打满 | 最慢一对 + incast |
| 该看的指标 | busbw | P99 尾延迟 |

`A-06` 的 4D 并行是这张表的最好注脚：row-wise 切分用 ReduceScatter，column-wise 与 table-wise 用 alltoall，data 维用 allreduce。三种原语并存，因为切的维度不同，"谁需要知道谁的哪些字节"就不同。

all-to-all 的字节最少，账却最不好算，因为它把成本从传输项挪到了排队和尾延迟上。下一块回到最基础的读法问题：论文报的那个带宽，到底是哪一层的带宽。

## 第五块 · 两种带宽口径

这块要回答的是：为什么论文里的 bus bandwidth 能和链路带宽对上，而应用视角的数字对不上。

NCCL 报两个带宽。混淆这两个数，是读论文最常见的错误。

```
algbw = S / t                       应用视角：我这份消息多快传完
busbw = algbw × f                   归一化：这条链路被用到了几成
```

前者站在应用这一头，只关心自己那份消息多久送完。后者站在链路那一头，把这套算法折算成"如果链路跑满会是多少"。
归一化因子 `f` 取决于算法：对 ring all-reduce 是 `2(P−1)/P`，对 reduce-scatter、all-gather、all-to-all 是 `(P−1)/P`。这是标准约定，构造它有一个明确目的：让带宽最优的算法在理想链路上，`busbw` 正好等于链路带宽。

### 验算一遍

all-reduce，链路跑满：

```
t = W/B = 2·S·(P−1)/(P·B)
algbw = S/t = P·B/(2(P−1))
busbw = algbw × 2(P−1)/P = B          ✓ 正好是链路带宽
```

all-to-all，链路跑满：

```
t = S·(P−1)/(P·B)
algbw = S/t = P·B/(P−1)
busbw = algbw × (P−1)/P = B           ✓ 同样
```

两处都对上了，说明 `busbw` 的物理含义是"这条算法把链路峰值用到了几成"。它低于 `B` 的部分，就是算法本身的结构性损失，来自步数、空转和拥塞。

### 弱扩展下为什么掉

弱扩展指每卡的工作量固定、卡数增长。按理想模型：

```
S 固定，P ↑ ⇒ W → 2S（常数）⇒ t → 2S/B（常数）⇒ busbw 稳定在 B
```

理想模型里它不该掉。真实集群里它掉，原因不在公式，在假设：

1. 同构链路不成立。`P` 增长意味着节点数增长，跨机跳数增加，每条链路的有效带宽下降。
2. 满二分不成立。超售比暴露出来，`(P−1)/P` 那个"每对都能同时跑满"的前提破了。
3. `α` 开始计入。`D = 2(P−1)` 随规模线性增长，`α·D` 从舍入误差变成主项。
4. incast 概率上升。参与方越多，同一时刻打同一个目的地的概率越大。

`C-06` 的观测就是这件事：8 GPU/节点做弱扩展时，NCCL 集合通信的 bus bandwidth 随规模急剧下降（原文 Figure 5）。这里只引用这个定性判断，不给曲线数值——论文的横轴是 GPU 数、纵轴是 busbw，具体读数要从原图取，本专栏不转述近似值。

顺带一个容易搞混的对照。`busbw` 的曲线难看，是因为它测的是弱扩展：每卡工作量固定、卡数增长。而推荐训练的 batch 是全局固定的，实际更接近强扩展。两个口径的结论不能互相搬运；本篇算例用的是全批口径，换成每卡口径的换算见 ⑥。

口径分清了，公式和阈值也齐了。下面把它们代进一组具体设定，看每一项各占多少。

## 算例：把五块代进 128 卡

这一步在算什么：前面五块给的公式，在同一套设定与同一条 51 ms 预算下各占多少，以及换成每卡口径之后主项会变成什么。

<div class="example">

设定：`P=128`、`S=525 MB`（全批口径）、`B=50 GB/s`（400 Gbps 单向）。预算 51 ms。

① ring all-reduce

```
W = 2 × 525 MB × 127/128 = 1041.8 MB ≈ 1.04 GB
t = 1.04 GB ÷ 50 GB/s    = 20.8 ms          → 占 51 ms 的 41%
algbw = 525 MB ÷ 20.8 ms = 25.2 GB/s
busbw = 25.2 × 2×127/128 = 50.0 GB/s        → 链路跑满
```

② 拆开看两个阶段

| 阶段 | 出站字节（全批口径） | 时间 | 占 51 ms |
|---|---|---|---|
| reduce-scatter | 520.9 MB | 10.4 ms | 20% |
| all-gather | 520.9 MB | 10.4 ms | 20% |
| 合计 | 1041.8 MB | 20.8 ms | 41% |

③ all-to-all（满二分，`D = 1`）

```
W = 525 MB × 127/128 = 520.9 MB ≈ 521 MB
t = 521 MB ÷ 50 GB/s = 10.4 ms              → 占 51 ms 的 20%
```

④ 把 `C-06` 的一轮通信次数乘进去

`C-06` 报告 hybrid parallelism 每轮至少 3 次 AlltoAll + 1 次 AllReduce。套上本算例的单次代价：

```
3 × 10.4 ms + 1 × 20.8 ms = 31.2 + 20.8 = 52.0 ms
```

比 51 ms 的整步预算多 1 ms。在全批口径下，光通信就把预算吃光了，计算和访存没有位置。这不是"通信占比高"，是"这套组合在算术上不可能收敛到 51 ms"。换成每卡口径（÷128）后，传输只剩 0.4 ms，主项变成固定开销与同步——两句话描述的是同一个系统的两个尺度，不能混着引用。

⑤ 加上步数项

```
α = 5 µs
all-reduce:  254 步 × 5 µs = 1.27 ms
一次 all-to-all（ring，P−1=127 步）：127 × 5 µs = 0.64 ms
一轮合计：1.27 + 3 × 0.64 = 3.2 ms
52.0 + 3.2 = 55.2 ms
```

⑥ 强扩展与弱扩展的对照

先说口径：这一段用每卡口径，避免和全批口径的 525 MB 混起来。

```
每卡口径下 S_card = 4.1 MB（P=128）
强扩展（全批固定 ⇒ S_card 减半）：P 128 → 256，t 减半
弱扩展（S_card 固定 4.1 MB）    ：P 128 → 256，t 不变
```

all-reduce 的"通信量与卡数无关"指的是弱扩展下 `W → 2S_card` 这个极限，不是"加卡不提速"。加卡仍然提吞吐，只是不提单次的延迟。

⑦ 如果换成 1024 卡（全批 S 仍是 525 MB）

```
W = 2 × 525 MB × 1023/1024 = 1048.9 MB ≈ 1.05 GB
传输：1.05 GB ÷ 50 GB/s = 21.0 ms    → 摊到每卡是 21.0 / 1024 = 0.021 ms
步数：2046 步 × 5 µs    = 10.2 ms    → 不随卡数摊薄
```

传输项随卡数摊薄，步数项不摊薄，因为 `α·D` 是整条流水线的串行前缀。所以规模越大，`α·D` 越可能变成主项。"通信量与卡数无关"这条结论只在忽略 `α` 时成立，而 `α` 恰恰是碎片化派（`A-15`）的全部论据。

⚠️ 上面几段有四个假设要单独点名：

- 把 `C-06` 的"每轮通信次数"套到本算例的"每步消息量"上，是一个混合假设。`C-06` 自己的模型约 90 GB 参数、512 GPU，不是 10 TB / 128 卡。
- 三次 AlltoAll 不一定是同一种尺寸。真实系统里前向查询的 AlltoAll、向量回传的 AlltoAll、反向的 AlltoAll 量级相近但不等；这里按同尺寸算，是上界。
- `α = 5 µs` 是假设值，与[第 1 篇](01-interconnect-layers)的固定开销表同源。
- 没有计入通信与计算的重叠。`A-06` 把 batch i 的输入 AlltoAll 与 batch i−1 的顶部 MLP 前向重叠，这类重叠能压墙钟时间，但不改变字节账本。

⑧ 口径对账

525 MB 是全批去重量，每卡出站是它的 1/128：

```
全批口径（本节采用）：      S = 525 MB  → W、t 如上表
每卡口径（真实 outbound）： S = 4.1 MB  → 所有 W、t ÷ 128
```

每卡口径下：ring all-reduce 8.1 MB / 0.16 ms；all-to-all 4.1 MB / 0.082 ms；3 次 A2A + 1 次 AR 共 0.41 ms（固定开销另算，见 ⑤）。

本节用全批口径，是为了跟第 6 章的 525 MB 与 0.05 ms/条直接对账；换到每卡口径后，传输项小到 0.4 ms，固定开销与同步变成主项——这正是第 3 篇"碎片化"的入口。两种口径的公式结构完全相同，只差一个 `P` 的因子。

⚠️ 顺带纠正一个容易跟着犯的错：51 ms 是 `A-10` 的 16 trainer 口径（16,384 ÷ 320K）。128 卡时预算约 6.4 ms，拿 51 ms 比较只用于看相对权重。

⑨ 汇总（`α = 5 µs`）

| 原语 | 出站字节（全批口径） | `D` | 时间（只算字节） | 含 `α·D` |
|---|---|---|---|---|
| ring all-reduce | 1041.8 MB | 254 | 20.8 ms | 22.1 ms |
| reduce-scatter | 520.9 MB | 127 | 10.4 ms | 11.1 ms |
| all-gather | 520.9 MB | 127 | 10.4 ms | 11.1 ms |
| all-to-all（满二分） | 520.9 MB | 1 | 10.4 ms | 10.4 ms |
| all-to-all（ring） | 520.9 MB | 127 | 10.4 ms | 11.1 ms |
| 3 次 A2A + 1 次 AR | — | — | 52.0 ms | 55.2 ms |

读法：字节账本给出的答案是"all-to-all 比 all-reduce 便宜一半"，而 ④ 给出的答案是"三次 all-to-all 就是全部预算"。两者不矛盾，前者算的是字节，后者算的是次数。第 3 篇会把"次数"单独建一个成本项。

</div>

## 模型在哪里不成立

- 公式是标准结果，不是论文。所有推导都在理想假设下成立：同构、无拥塞、满二分、`α` 忽略。任何一条破了，`busbw` 都会低于 `B`，而低多少只能实测。
- `busbw` 的归一化因子依赖算法。跨论文比 `busbw` 时先确认对方用的是哪个因子、哪个版本；不同框架、不同算法报出来的数不可直接比。
- `D = 1` 的 all-to-all 需要满二分。`C-06` 明确说它的基础设施保证"任意两台主机间满二分、无超售"；共享集群里这个前提通常不成立，`D` 要按 `P−1` 或按分层拓扑重算。
- HDR 要求 `P` 是 2 的幂。非 2 的幂时多出一步，`P` 越大这一步越贵，因为它要处理剩余的那一块。
- 本篇假设 `S` 固定。真实训练里 all-to-all 的 `S` 每步都在变（取决于本 batch 的 ID 与去重结果），所以"平均 10.4 ms"是稳态估计，不是每步的保证。
- 本模型不含排队项。第 4 块那个 90 倍的倾斜算例说明：排队一旦成为主项，`W/B` 这个式子就不再解释实际耗时。第 3 篇把这个缺口补成一个显式的项。
- 本节没算梯度压缩、FP16 通信这类"把 `S` 变小"的手段。它们改的是 `S`，不是 `W/S` 这个比例，所以公式不变，只是代入更小的 `S`。
- 步数项用 `α` 乘步数是粗略的：ring 的每步开销随消息大小略有变化，`α` 取常数是最坏情况的简化。
- `S*` 阈值 32 MB 依赖 `α = 5 µs`。`α` 取 2 µs 时阈值降到 12.8 MB，取 10 µs 时升到 64 MB。"多大算小消息"不是硬件常数，是"框架 + 硬件"的联合属性。
- `D = 1` 假设 `P−1` 条消息能同时在途。真实网卡的在途队列深度有限，拥挤时会退化成若干批，实际时间介于 `D = 1` 与 `D = P−1` 之间。
- 本篇只算一轮。真实训练里 all-to-all 要重复成千上万次，每一轮的倾斜都不同，累积效应只能用尾延迟描述——那是第 3 篇最后一节的内容。

<div class="takeaway">

all-reduce 每卡 `2S(P−1)/P`，`P` 大时趋近 `2S`，与卡数无关；all-to-all 每卡 `S(P−1)/P`，只有一半的字节。

ring 的步数是 `2(P−1)`，HDR 是 `2·log2(P)`。`P=128` 时 254 步对 14 步，1 MB 消息上差 12 倍，525 MB 上只差 6%。

算例（全批口径）：all-reduce 20.8 ms、all-to-all 10.4 ms；`C-06` 的 3+1 次套上去是 52 ms，超预算。每卡口径全部 ÷128；比率与 `B*`（压缩盈亏平衡带宽，见[第 6 篇](06-breakeven)）不受口径影响。

</div>
