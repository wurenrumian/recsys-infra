## 一句话

prefill 和 decode 分时段做，别混在一批里，气泡就没了。

## 背景与问题

先说明场景边界，这决定了整篇的适用性（**事实**，§1）：目标场景是**没有严格延迟 SLO**的离线推理——batch API、RLHF 的 rollout 阶段、推荐系统的数据增广，这些场景里**吞吐优先**。不是在线 serving。这点很重要，因为所有"为了吞吐牺牲 TTFT/TPOT"的设计在这个前提下才成立。

那为什么需要 PP？两个理由（**事实**，§2.2）：① **显存**——权重（7B–175B，几十到几百 GB）+ KV cache（Llama-30B 单 token 的 KV 占 **1.52 MB**；400 个平均长 300 的请求约需 **178 GB**）远超单卡；② **协调开销要低**——多卡扩显存有两条路，都不理想。

offloading（换出到二级存储）的问题是 **PCIe 争用**（**事实**，§2.2）：多卡共享**一条**通往 CPU 的通道，同时 offload 时带宽争抢严重，即使 CPU:GPU = 1:1 也是瓶颈。TP 的问题是**通信占比**（**事实**，§2.2，实测）：Llama-30B、两节点、无直连电缆、FP16 下，L20 节点 1→4 卡总耗时只降 **1.84×**、4 卡时通信占 **47.39%**；A100 节点只降 **1.64×**、通信占 **53.9%**。所以 TP 在无 NVLink 的商用节点上基本被通信锁死。

PP 的优势是通信量极小（只在层间断点传激活，点对点、数据量小、每几层一次）（**事实**）。**但 PP 有气泡**，而 LLM 推理的气泡来源特别复杂（**事实**，§2.1）：**批间不均**（不同 batch 的 decode step 工作量不同）；**prefill-decode 不均**（prefill 处理很多 token、compute-bound，decode 每步只处理 1 个 token、memory-bound，耗时差异巨大）；**数据依赖**（层间依赖：当前层算完才能进下一层；decode step 间依赖：上一步生成完才能开始下一步）。

现有缓解方案是 **chunked prefill + hybrid batching**（把 prefill 切块混进 decode 批），但有三个问题（**事实**，§2.1）：依赖 prefill-to-decode 比例、**处理不了长度持续变化的请求**；prefill 与 decode 混在一起 + 单次 prefill 的块之间**引入更紧的数据依赖**；**重复的 KV cache 加载**开销。作者的判断是：这些都是"在时间维混杂"的必然结果。

## 核心做法

### 核心思想：时序解耦

一句话（**事实**，§3）：**让每个推理实例在很长一段时间内只做一种 phase**，从而把 phase 切换频率降到最低。

```
传统 hybrid batching（一直在切）:
  时间 →
  [P+D][P+D][P+D][P+D][P+D]        每批都混 prefill 和 decode
           ↑ 每批都要处理跨 phase 的数据依赖 → 气泡密布

TD-Pipe（时序解耦）:
  时间 →
  [ P  P  P  P  P  P  P ]  →  [ D  D  D  D  D  D  D ]  →  [ P P P ] …
       一大批 prefill 做完           一大批 decode 做完        再回 prefill
```

prefill 与 decode 变成**生产者-消费者**关系：decode 依赖 prefill 完成（**事实**）。

但这条架构带来三个新问题，各配一个机制。

### 1. 层级控制器（hierarchy-controller）

问题：不同设备跑连续层，推理负载在输入/输出长度上极不规则，设备间传输不得不是**阻塞式**的（**事实**，§3.1）。

解法：**把调度与执行解耦**（**事实**）：

```
┌─────────────── 控制平面 ───────────────┐
│  集中式引擎 (centralized engine)        │
│   · 按显存容量、请求状态、profiling 结果  │
│     做批调度                              │
│   · 通过 RPC 管理/控制 worker             │
│   · 初始化：把子模型派给 worker、载参数    │
│   · 执行：打包 prompt 直接发，直到触发切换  │
└──────────────┬─────────────────────────┘
               │ RPC
┌──────────────▼─────────────────────────┐
│  执行平面：分布式 runtime                 │
│   · 每个 worker 只知道"我要跟谁、传什么数据"│
│   · 不阻塞的传输                          │
└────────────────────────────────────────┘
```

关键收益：**传输不再阻塞**。集中式引擎统一决策、worker 只执行——这是能做后面三个优化的前提（需要全局视角判断"何时切换"）。

### 2. AI-based greedy prefill

问题：想多跑 prefill（推迟切到 decode），但显存会被 KV cache 吃满（**事实**，§3.2）。解法是**预测输出长度**并模拟显存占用：decode 过程中请求会**陆续完成**、相关 KV cache 被释放，如果能预测"哪些请求会在什么时候完成、释放多少显存"，就能在**当下**多做几个 prefill。这是一笔"借未来的显存"——只要预测误差可控，就能持续把流水线喂饱。名字里的 "AI-based" 指的正是这个输出长度预测模型（**事实**）。

### 3. 批间工作窃取（inter-batch work stealing）

问题：decode 阶段请求**随机完成**，导致各 batch 之间负载失衡（**事实**，§3.2）。解法是**动态在 batch 之间搬请求**，从重 batch 挪到轻 batch。这个机制只在 decode 阶段有意义——decode 的每个请求就是一个 token，搬动成本极低；prefill 搬不动，因为一个请求的 prefill 是个大块连续计算。

### 4. 时空强度比较（spatial-temporal intensity comparison）

问题：**什么时候该从 decode 切回 prefill**？（**事实**，§3.2）论文把这件事变成两种可比较的损失（**事实**）：

| 概念 | 定义 | 切换代价 |
|---|---|---|
| **空间强度** | decode 推进时请求陆续完成，**计算强度逐渐下降**（每卡有效工作量变少） | 继续 decode 的损失 |
| **时间强度** | 切到 prefill 会引入**流水线气泡**，硬件有效利用时间占比下降 | 切换的损失 |

决策规则：**比较两者，谁小就选谁**。这是个很实用的工程判据——它把"该不该切"从拍脑袋变成可算的量。

## 为什么值得读

- **它把 PP 用在了一个"非主流但很大"的场景**。几乎所有 PP 推理工作都在做在线低延迟（Orca、vLLM、Sarathi 那条线），TD-Pipe 明确放弃延迟、只要吞吐。这个定位让它能用一些激进手段（长时段只跑一种 phase），也让它在这个细分里做得更彻底。
- **与 C-08 SlimPipe 是"训练 vs 推理"的镜像对**：SlimPipe 解决 warm-up 气泡（训练，切片），TD-Pipe 解决 phase 切换气泡（推理，解耦）。两者都在"沿某个维度做时间上的重新安排"，但对象完全不同——这是本 track 里最值得并读的一对。
- **与 C-10 OctoPipe 是"推理 vs 训练"的又一个对照**，但 OctoPipe 处理**模型异构**（层型不同），TD-Pipe 处理**请求异构**（长度不同）。异构源不同，解法不可替换。
- **对 NestPipe 的独特价值**：论文明确把"**推荐系统的数据增广**"列为目标场景之一（**事实**，§2.2 引用 Ding et al. 2024）。这把 LLM 推理系统与推荐系统直接连起来了——推荐流水线里越来越多环节要跑 LLM（embedding 生成、内容理解、数据增广），而这些环节恰恰是吞吐优先、可用离线集群。
- **1.91× vs TP 的场景意义**：它证明了在**没有 NVLink 的商用硬件**上，PP 才是对的路。这对成本敏感的部署很关键——不是所有人都买得起 NVLINK 节点。
- **时空强度比较**这个判据可复用。任何"要不要切换执行模式"的决策（包括 C-14 GBA 的 sync/async 切换）都可以套这个框架：比较"维持当前模式的损失"和"切换本身的代价"。

## 局限

1. **完全放弃延迟**。长时段只跑 prefill 意味着某些请求的 TTFT 会非常长（排在 prefill 批末尾的请求要等整批）。论文明确说目标是无 SLO 的离线场景，所以这不是缺陷而是设计选择——但**绝不能用于在线 serving**（**推断**）。
2. **AI-based 长度预测引入误差累积**。预测偏大会 OOM，偏小会浪费窗口。论文未给预测准确率与吞吐的关系（**待核实**）。
3. **工作窃取只在 decode 有效**。prefill 阶段的不均（长 prompt vs 短 prompt）没有对应机制，只能靠 greedy prefill 的长度预测间接缓解（**推断**）。
4. **层级控制器是单点**。集中式引擎挂了整个推理实例就挂。论文未讨论容错（**待核实**）。
5. **只在 PCIe-only 场景验证**。这是它的卖点（省掉 NVLink 成本），但也意味着**在有 NVLink 的集群上，TP 可能反而更优**，TD-Pipe 的相对收益会缩小（**推断**：论文没有 NVLink 对照）。
6. **测试模型以 Llama-30B 为主**，MoE 模型未覆盖（**待核实**）。
7. **只报吞吐，不报"单位成本"**。1.91× 吞吐背后是更多的设备、更长的队列延迟，成本账没算（**推断**）。
