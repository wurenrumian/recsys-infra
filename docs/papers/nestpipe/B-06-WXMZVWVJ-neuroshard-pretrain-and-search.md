## 一句话

预训练代价模型当模拟器，再搜索出近优分片方案。

## 背景与问题

分片是 NP-hard，而且"代价估计准确"与"估计得快"很难兼得。前一版工作 AutoShard（B-05）用 RL 学策略，但作者在本篇 §1 里明确列出三个**部署痛点**（**事实**）：

1. **只做 table-wise**。RL 方法把整表当最小单位，"very likely that one table is extremely large or costly"，于是 OOM 或严重失衡。
2. **策略需要重训**。策略网络只在很少的分片任务上训练过，遇到未见任务得频繁重训。
3. **RL 策略方差大**。原话："even if we train the same policy on the same MDP with multiple independent runs, some of the runs may work well but the others could fail" ——而生产要稳定。

作者从 LLM 的 "pre-train, prompt, and predict" 得到类比，提出 "**pre-train, and search**"：先训一个**通用、一次训好（once-for-all）**的神经代价模型，把它当分片模拟器；再在模拟器上做在线搜索。

### 三个实证观察（决定了整个设计）

论文 §2 用 2080Ti + FBGEMM 做了三组分析实验，得到三条观察：

**Observation 1**：把表按列对半切，**每一半的代价都大于原表代价的一半**。
理由：并行 + 算子融合，融合的嵌入算子在 CUDA kernel 里优化得更好。所以列分片有**代价权衡**：更均衡，但总代价上升。

**Observation 2**：多表代价与单表代价之和是**非线性**关系。
→ 表分片算法必须考虑非线性，不能用线性求和近似（MILP 那套不行）。

**Observation 3**：最大前/后向通信代价与**最大设备维度**（dievice dimension = 该设备上所有表的维度之和）正相关。
→ 通信均衡可以退化为"最小化最大设备维度"，这是个容易得多的目标。

## 核心做法

### 整体流程

```
① 造数据          ② 预训练              ③ 在线搜索
┌──────────┐   ┌──────────────┐   ┌─────────────────────┐
│表增强     │   │3 个神经代价模型│   │外层：列分片 beam search│
│(4..128维) │──►│  · 计算代价    │──►│  ↓                  │
│随机表组合 │   │  · 前向通信    │   │内层：表分片            │
│随机表放置 │   │  · 后向通信    │   │  贪心 + 网格搜 max_dim │
└──────────┘   └──────────────┘   └─────────────────────┘
     ↑ 用 micro-benchmark (PARAM) 采真实代价
```

### ① 合成输入生成（预训练是数据密集型工作）

**表增强**：给定原始表（比如维度 64），额外生成维度 {128, 32, 16, 8, 4} 的增强副本。目的：覆盖"特征选择导致维度调整"和"列分片产生新维度"这两种情况。这直接解决了 AutoShard 无法支持列分片的问题——**代价模型见过所有可能的维度**。

**随机表组合**：先均匀采样表数量 T，再从增强表池里随机选 T 张。用于采**计算**代价。

**随机表放置**：用带随机性的贪心策略生成不同"均衡程度"的放置方案。具体是：按维度降序，以概率 p 分给当前维度总和最小的 GPU，以概率 (1−p) 随机分。p 从 [0,1] 均匀采样，p=1 时完全均衡，p=0 时接近随机。此外**随机生成每张 GPU 的通信起始时间戳**（0–20ms），因为 trace 分析显示前序延迟会累积，导致各 GPU 的通信并非同时开始。

### ② 三个代价模型

| 模型 | 结构 | 输入 |
|---|---|---|
| 计算代价 | 共享 MLP 编码每张表 → 逐元素求和 → MLP 输出（前+后向） | 维度、hash size、pooling factor、索引分布 |
| 前向通信 | MLP | 各 GPU 起始时间戳 + 传输数据量 |
| 后向通信 | MLP（单独一个） | 同上 |

每个模型生成 **10 万条**样本训练。测试 MSE（**事实**，论文 Table 2）：

| | DLRM 4 GPU | DLRM 8 GPU | 生产 128 GPU |
|---|---|---|---|
| 计算 | 0.21 | 0.21 | 0.26 |
| 前向通信 | 0.02 | 0.05 | 0.05 |
| 后向通信 | 0.02 | 0.04 | 0.15 |

作者解读：最大 MSE 0.26，开方后误差约 0.6ms，而真实代价本身有波动，所以这个精度"highly accurate"。

**运维提示**（**事实**）：索引分布会漂移，需要重训/微调；生产环境的经验是**三个月重训一次足够**。维度变化**不需要**重训（表增强已覆盖）。

### ③ 在线搜索：双层

**外层——列分片，beam search**

目标函数：

```
argmin_{c∈C, t∈T} f(c, t)
```
其中 c 是列分片计划（每步选一张表对半切，产生新表追加到表列表末尾），t 是表分片计划（把 T 张表分给 D 张 GPU）。t 依赖 c，所以自然形成外层/内层。

约束：FBGEMM 要求维度能被 4 整除；还要满足 GPU 内存约束。

Beam search 的剪枝依据 Observation 1：列分片会**增加**总代价，所以要"用最少的步数"换取均衡。每步只在"最贵的 top-N 表"和"最大的 top-N 表"里选候选（去重），并只保留上一步 top-K 个方案，跑 L 步。

**内层——表分片，贪心 + 网格搜 max_dim**

1. 选一个 `max_dim` 约束；
2. 按**代价模型预测的代价**降序排表；
3. 从最贵的开始，逐张分给"当前设备代价最低、且加进去不超内存也不超 max_dim"的 GPU；
4. 用代价模型评估总代价。

`max_dim` 的网格：起点 `M_s` = 各设备平均维度，终点 `M_e` = 1.5×M_s，共 M 步均匀取值。这就是 Observation 3 的落地——用"设备维度"这个易控量来管通信均衡。

**缓存优化**：搜索里最贵的是反复调代价模型，共 O(LK NMTD) 次前向。但小改动会导致大量重复查询 → 用 lifelong hash map 缓存。**实测命中率 > 95%**（**事实**）。

| 方法 | 最大维度 128 | 相对提升 |
|---|---|---|
| Random | 33.40 | — |
| Greedy size-based | 54.57 | — |

## 为什么值得读

NeuroShard 是 Track B 分片支线的**方法论枢纽**，它的位置需要用"它修正了谁、被谁修正"来理解：

- **它修正 B-05（AutoShard）**。同一作者，明确列举 RL 的三个部署痛点（只 table-wise / 需重训 / 方差大），并把答案换成"预训练模拟器 + 确定性搜索"。这个转换的**方法论意义大于系统意义**：它说明在 ML-for-Systems 里，"把决策问题的求解器从 RL 换成可复现的搜索"往往比"把 RL 调好"更划算。这是本 track 里最有迁移价值的一条经验。
- **它支持列分片，这直接回应了 B-04（EMBark）与 B-13（OPER）的需求**。大表装不进单卡时，列分片是唯一出路。
- **它与 B-13（OPER）是立场对立**。OPER 说分片必须 input-dependent；NeuroShard 的代价模型输入是表的**静态特征**（维度、hash size、pooling factor 均值、索引分布统计量），不依赖当前 batch。"一次训好、所有任务通用"这个卖点本身就是对 input-dependent 的否定。**这两篇要对着读，结论才立得住。**
- **它是"预训练 + 搜索"范式在系统领域的样板**：模型小（浅 MLP）、数据可合成（表增强）、搜索可加速（缓存 95% 命中）。做别的资源分配问题（拓扑映射、批调度）可以直接套这个模板。

## 局限

- **代价模型的输入是静态统计量**。索引分布只用一个统计量概括，无法捕捉 batch 级波动。若实际 batch 的访问模式与训练时的合成分布差异大，模型会失准。OPER 的核心批评正打在这里。
- **列分片有确定性的代价**（Observation 1）。所以 NeuroShard 的最优解是"尽可能少切"——它天然偏向那些"只有少数表超大"的场景。若所有表都超大到必须切，Observation 1 的罚金会累积。
- **一次训好 ≠ 永远好用**。作者承认索引分布漂移要重训（3 个月一次），且要做严格版本控制（checkpoint 必须绑定同一版代价模型）。这是个持续的运维负担。
- **搜索是启发式，不是最优**。beam + 贪心网格的组合保证"近优"（原文 "empirically near-optimal"），没有最优性保证，也没有给出与真最优的 gap 界。
- **生产数据只有一组**（128 GPU 的多 TB 表）。11.6% / 6.6% 的可复现性未知，MetaProd 细节保密。
- **只覆盖 4/8/128 GPU**，拓扑假设是单机 8 卡 + 多机。对 NVSwitch 全互联、或异构卡混布的场景没验证。
- **没讨论精度影响**：分片只是重排计算顺序，理论上无精度损失，但列分片改变了 embedding bag 的求和顺序，浮点差异未测（**推断**，论文未提）。

## 是否值得读原文

**必读**——如果你在做嵌入表分片或任何"资源分配 + 代价模型"的系统问题。理由：§2 的三条 Observation 是这类问题的**基本事实**（列切有代价、多表非线性、通信由设备维度决定），这三条你会反复用到；§3 的 pre-train-and-search 流程是可直接套用的模板。§4 实验部分可以只读 Table 1 和生产部署那节。
