## 出处

- 作者：Weijie Zhao、Deping Xie、Ronglai Jia、Yulei Qian、Ruiquan Ding、Mingming Sun、Ping Li（Baidu Research 认知计算实验室 / 百度搜索广告 "Phoenix Nest" / 百度系统与基础架构部）。
- 年份与会议：2020 年，第 3 届 MLSys 会议，Austin TX。
- arXiv：`2003.05622`（Zotero 记为 preprint）。
- 中文常见叫法：**HPS / 层级参数服务器**（Hierarchical Parameter Server）。

## 一句话

显存→内存→SSD 三层存 10TB 参数，4 台机器快过 150 台。

## 背景与问题

百度搜索广告的 CTR 模型规模（**事实**，摘要与正文）：
- 稀疏特征数超过 **10¹¹**，模型参数约 **10TB**；
- 单条样本的**非零特征极少**（正文例子：22 维稀疏输入里只有第 1 和第 6 个非零）；
- 稠密参数（全连接层）只有几百万个，占几百 MB。

原有的生产方案是 **MPI 集群 + 参数服务器**（2013 年起）：把参数切到 75–150 个 CPU 节点，每个节点负责一部分，靠 MPI 拉参数、推梯度。缺点很具体（**事实**，§1.2）：
- **贵**：没人能独占一个 150 节点集群做实验，硬件维护与电费很贵；
- **扩展性到顶**：节点数越多，通信与同步开销越大，是主要瓶颈。

作者也考虑过**直接用 GPU**——但 GPU 显存装不下 10TB，而且会有大量 CPU-GPU 搬运。既有工作（如把参数缓存在 CPU 内存）仍要做耗时的 CPU-GPU 传输。

### 为什么不用哈希把模型压小？

论文 §2 花了一整节讲这个——这是本文最有价值的一节之一。作者 2015 年试过 **OP+OSRP**（one permutation + one sign random projection）哈希，用 3 个月搜索广告点击数据做实验：

**图片搜索广告**（表 1，**事实**）：

| 配置 | 非零权重数 | 测试 AUC |
|---|---|---|
| Baseline LR | 31,949,213,205 | 0.7112 |
| Baseline DNN | — | **0.7470** |
| Hash+DNN (k=2³⁴) | 6,439,972,994 | 0.7407 |
| Hash+DNN (k=2²⁴) | 14,617,324 | 0.7113 |

→ 即使 k=2³⁴（压 5×），AUC 已经掉 0.7%。但压到 1460 万参数时 AUC 0.7113，**仍不低于原 LR 基线**。所以对图片搜索，Hash+DNN 可以用来替掉 LR。

**网页搜索广告**（表 2，**事实**）：

| 配置 | 非零权重数 | 测试 AUC |
|---|---|---|
| Baseline LR | 199,359,034,971 | 0.7458 |
| Baseline DNN | — | **0.7670** |
| Hash+DNN (k=2³²) | 3,005,012,154 | 0.7556 |
| Hash+DNN (k=2²²) | 4,125,016 | 0.7408 |

→ 只要哈希，AUC 就掉到 DNN 基线以下。而网页搜索贡献了大部分收入。

作者的结论（**事实**）："even a 0.1% decrease in AUC would result in a noticeable decrease in revenue"。**所以必须无损** → 必须搞层级存储，而不是压缩。

这一节的方法论价值很高：它用真实生产数据证明了"**压缩在广告主模型上不可行**"，这为后面所有"层级存储/无损"路线（B-09、B-15）定了基调，也解释了为什么 B-03/B-10/B-11 那些压缩工作主要出现在**学术/中等规模**场景。

## 核心做法

### 整体架构：三层 + 4 级流水

```
                 ┌──────────────────────────────────────────┐
                 │  GPU 节点 × 4（每节点 8×32GB HBM）        │
   HBM-PS   ─────┤  多 GPU 分布式哈希表（cuDF concurrent_    │
   (L1, 最快)     │  unordered_map），存"working parameters"  │
                 │  参数不重叠分区：每个参数只在一张卡上      │
                 └───────────────┬──────────────────────────┘
                                 │ NVLink（卡间）/ RDMA（机间，绕过 CPU）
                 ┌───────────────▼──────────────────────────┐
   MEM-PS   ─────┤  CPU 主存（~1TB/节点）                    │
   (L2)          │  从本地 SSD 与远端 MEM-PS 汇集"本 batch     │
                 │  引用到的参数"，并做缓存（命中率 46%）      │
                 └───────────────┬──────────────────────────┘
                                 │
                 ┌───────────────▼──────────────────────────┐
   SSD-PS   ─────┤  NVMe SSD RAID-0（~20TB/节点）            │
   (L3)          │  参数按"文件"组织，批量写新文件 + 文件压实 │
                 └──────────────────────────────────────────┘
```

核心洞察（**事实**）：**"working parameters"（当前 batch 引用到的参数）能装进 GPU 显存**，虽然全模型 10TB 装不进。所以把"当前要用的"提到 HBM，"暂时不用的"沉到 SSD。

### 训练流程（论文 Algorithm 1）

```
while not converged:
  batch ← get_batch_from_HDFS()
  working ← pull_local_MEM-PS_and_SSD-PS(batch)     # 本地参数
  working ← working ∪ pull_remote_MEM-PS(batch)     # 远端参数（按 key 取模分片）
  minibatches ← shard_batch(batch, #GPU, #minibatch)
  partitions ← map_parameters_to_GPUs(working, #GPU) # 非重叠分区
  for i in 1..#GPU:
      transfer_to_GPU(i, minibatches[i])
      insert_into_hashtable(i, partitions[i])
  for j in 1..#minibatch:
      pull_HBM-PS_kernel(minibatch[j])
      Δj ← train_mini-batch_kernel(j)
      push_parameters_updates_back_kernel(Δj)
  Δ ← pull_updates_HBM-PS()
  parameters_to_dump ← update_local_cache()
  push_local_SSD-PS(parameters_to_dump)
```

要点：
- **数据并行**：每个节点处理不同 batch，各自负责；
- **卡间参数不重叠**：一个参数只存在一张 GPU 上，需要时通过 NVLink 直接取；
- **每 mini-batch 同步一次**：消除参数过期（一个 mini-batch 有几千样本）；
- **上层是下层的缓存**：HBM-PS 是 MEM-PS 的缓存，MEM-PS 是 SSD-PS 的缓存。

### 三个 HBM-PS 关键设计

**① 多 GPU 分布式哈希表**（Algorithm 2）
- 每张 GPU 在 HBM 里维护自己的本地哈希表，用 cuDF 的 `concurrent_unordered_map`，open-addressing 解冲突；
- **容量预先固定**（因为知道要存多少 key-value 对），避免 GPU 上低效的动态分配；
- 并行更新靠 GPU 原子操作保证完整性；
- `accumulate` 操作：**零拷贝**传入（keys/vals 两个数组的地址）→ 并行按分区规则切分 → 通过 NVLink **异步**发到各 GPU → 各 GPU 异步做本地累加。

**② 跨节点通信用 RDMA**
- 物理上：RDMA 网卡，**零拷贝**，数据从设备内存直接到对端设备内存，不经过操作系统缓冲、不涉及 CPU；
- 逻辑上：跨节点需要 **all-reduce**（每张 GPU 要收到其他所有 GPU 的更新后归约）。

**③ 4 级流水（关键工程手段）**

四个耗时阶段对应四种独立硬件资源：

| 阶段 | 硬件 |
|---|---|
| 数据传输 | 网络 |
| 参数分区 | CPU |
| 物化数据加载/转储 | SSD |
| 神经网络训练 | GPU |

每个阶段一个 worker 线程 + 一个预取队列。线程从队列取任务 → 喂给对应硬件 → 结果推入下一阶段队列。下游队列满则上游阻塞。队列容量按各阶段执行时间预设。**目的：把 I/O 延迟藏在 GPU 计算后面。**

### MEM-PS

- 按**取模哈希**把参数分给各节点（与 GPU 侧的划分策略类似）；
- 远端参数从其他 MEM-PS 拉，本地参数从 SSD 读；
- 维护内存缓存，存"最近/频繁使用"的参数 + 缓冲 working parameters；
- **更新时不需要推送给远端 MEM-PS**——因为远端参数在 HBM-PS 层已经跨 GPU 同步过了，远端节点自己从它的 GPU 上拉更新即可。这个设计砍掉了一轮跨节点通信。

### SSD-PS

- **参数按文件组织**，内存里维护 `参数 → 文件` 映射（文件描述符比参数值小得多，映射表能放进单节点内存）；
- 读：聚合请求的 key，**整文件读**（SSD 的 I/O 单位是块，随机读慢）；
- 写：**不做原地更新**（原地更新会随机写盘），而是把更新后的参数**批量写成新文件**（顺序写），然后更新映射。旧文件里的旧版本成为"陈旧数据"，因为映射已指向新文件，不会再被读到；
- **文件压实（compaction）**：后台线程定期合并"陈旧数据占比高"的旧文件，控制 SSD 用量。

|---|---|---|---|---|---|

## 为什么值得读

这是 Track B 里**层级存储派的奠基文献**，几乎所有"嵌入表放不进内存怎么办"的后续工作都要么引用它、要么针对它：

- **与 B-01（EVStore）是训练/推理的镜像**。EVStore 在推理侧做 DRAM→低精度→key 代理（用近似换内存）；HPS 在训练侧做 HBM→内存→SSD（**坚持无损**）。两者最根本的分歧就是"能不能损失精度"，而这个分歧的根源 HPS 自己用 §2 的哈希实验给了解释：**广告主模型不能损失 0.1% AUC**。这条论证是整个 Track B 分水岭的原始出处。
- **与 B-15（HypeReca）是直接的前后关系**。HypeReca（ATC'25）做的是"分布式异构内存嵌入数据库"，本质上仍是 HBM + host memory + 多节点的层级存储，但它把抽象从"参数服务器"换成了"KV 数据库"，并解决了 HPS 没解决的**动态插入（新 ID 不断出现）**问题。**HPS 是静态分片 + 参数服务器，HypeReca 是动态分配 + KV 抽象**——这是五年间的演进主线。
- **与 B-02（HET）是对照**。HET 说"参数服务器架构本身有通信瓶颈，要用缓存 + 一致性松弛"；HPS 说"我用 RDMA + 4 级流水把通信藏起来"。两条不同的解法，但 HPS 的 4 级流水里"参数 pull/push"最终仍是最大瓶颈（模型 D/E），某种程度上印证了 HET 的批评。
- **与 B-16（Pinterest）的对照很有意思**：Pinterest 那篇的模型只有 2.98 亿参数（1.67 亿在嵌入表），完全装得下；它的问题不是内存而是**收敛与过拟合**。这说明"嵌入表太大"不是普遍问题，而是**特定规模以上**的问题。
- 对工程落地：4 级流水 + SSD 文件压实这套组合，是"用便宜存储替代贵内存"的经典模板，可以迁移到任何"超大稀疏参数 + 稀疏访问"的场景。

## 局限

- **只解决"存得下"，不解决"访问偏斜"**。缓存命中率只有 46%（模型 E），意味着超过一半的参数请求要走 SSD。如果访问更均匀，命中率会更低，SSD 就会成为硬瓶颈。
- **静态分片**。参数按取模哈希固定分给节点和 GPU，**新特征 ID 出现需要扩容**。而推荐系统的 ID 集合是持续增长的（这正是 HypeReca 的主攻点）。论文没有讨论在线扩缩容，**待核实**。
- **MPI 基线是"当时的"生产方案**（2013 年起使用），已经比较老旧。1.8–4.8× 的加速里有多少来自"用了 GPU"、多少来自"层级存储"，论文没有拆分——但成本归一化（4.4–9.0×）部分缓解了这个质疑。
- **SSD 寿命与可靠性未讨论**。批量写新文件 + 定期压实，写放大明显（每次更新都写整文件）。生产上 SSD 磨损成本是真实开支，论文没报。
- **精度"无损"的验证范围有限**。AUC 差 <0.1% 是在 5 个模型上测的，且是**在线 A/B 一天**的结果；更长的训练周期或更多 epoch 下是否仍无损，未验证。
- **压缩派的前提被夸大了**。§2 只测了 OP+OSRP 一种哈希方法，就得出"哈希必然掉精度"的结论。更先进的哈希（如 B-03 的 CAFE+ 用 1 万倍压缩还涨 3.94% AUC）说明"哈希与无损不可兼得"这个结论**至少不是普适的**。这是本文最需要用后续工作来修正的地方（**推断**）。
- **没有对比"不压缩但用更激进的 offload"**，比如直接把表放 NVMe 用 GPU Direct Storage 访问。

## 证据与待核实

证据等级：**fulltext**。取到正文的 URL：`https://ar5iv.labs.arxiv.org/html/2003.05622`（含 §1–§7、Algorithm 1–2、Table 1–4、Figure 1–5 的完整文本）。

事实清单：所有表格数值（Table 1–4）、三层架构与 4 级流水、cuDF 哈希表、RDMA 零拷贝、SSD 文件压实、缓存命中率 46%、扩展性 3.57/4、成本换算 1:10。

待核实：
1. 在线扩容/新 ID 出现的处理（论文未提）；
2. SSD 写放大与寿命；
3. 1.8–4.8× 中"GPU 算力"与"层级存储"各自的贡献；
4. 除 OP+OSRP 之外的哈希方法是否也测过（论文只报了 OP+OSRP）。

## 是否值得读原文

**必读**——但重点是**§2 的哈希失败实验**和 **§7.2 的时间分布分析**，而不是架构细节。理由：
- §2 用真实生产数据（1990 亿非零权重、AUC 0.5% 的差别就影响收入）确立了"广告主模型必须无损"这条约束，这是理解整个 Track B 为何分成压缩派与层级存储派的钥匙；
- §7.2 说明层级存储的收益只在**参数规模达到 TB 级**时才显现（小模型瓶颈在 HDFS 读样本），这直接决定你这套方案该不该上。

架构部分（HBM-PS/MEM-PS/SSD-PS）作为工程参考阅读，但注意它是 2020 年的设计，动态 ID 与扩容问题已被 B-15 解决。
