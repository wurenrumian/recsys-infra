## 一句话

生成式推荐不能丢交叉特征；MTGR 用 token 重排 + 分组归一化把它们留住。

## 背景与问题

美团这篇的出发点**不是**改进架构，而是**反驳一个既有假设**。原文措辞很直接（**事实**，摘要）：

> "their generative approaches require abandoning the carefully constructed cross features ... We found that this approach significantly degrades model performance, and **scaling up cannot compensate for it at all**."

这跟 C-02 HSTU 的立场正相反。HSTU 明确说数值特征（计数器、比率）可以扔掉，理由是"聚合维度已序列化、模型容量够就能算出来"（**事实**，HSTU §2.1）。MTGR 用真实工业数据说：算不出来。

先把 DLRM 的包袱列清楚（**事实**，§3.1）。一个样本是个五元组：

```
D_i = [ U, S→, R→, C_i, I_i ]
       │    │    │    │   └─ 候选物品特征（ID、标签、品牌）
       │    │    │    └───── 交叉特征：用户×候选，如历史 CTR、曝光次数
       │    │    └────────── 实时序列（数小时内的动作）
       │    └─────────────── 长期行为序列
       └──────────────────── 用户画像（年龄、性别…）
```

DLRM 的扩规模有两条路，各有硬伤（**事实**，§3.2）：

| 路线 | 做法 | 硬伤 |
|---|---|---|
| 扩 **user 模块** | 只放大用户侧表示，因为用户表示对所有候选共享、推理只算一次 | 完全不做用户×物品的直接交叉 |
| 扩 **cross 模块** | 放大交叉特征之后的 MLP | 每个候选都要算一遍，成本**随候选数线性涨** → 延迟不可接受 |

GRM 的吸引力在于两个机制（**事实**，§1）：
1. **样本聚合**：同一个用户的 K 次曝光压成一个样本，算一次出 K 个分，天然消除冗余；
2. **高效注意力**：Transformer 系架构让训练/推理能满足工业时延。

但 GRM 靠 next-token 预测一整个行为序列，**必须移除候选与用户之间的交叉特征**。于是有了这篇论文的核心冲突。

## 核心做法

### 1. 数据重排：把交叉特征塞进候选 token

这是全篇唯一真正"新"的结构性想法（**事实**，§4.1）。对比原样本与新样本：

```
DLRM:   D_i = [ U, S→, R→, C_i, I_i ]        ← 每个候选一个样本，C 独立
MTGR:   D   = [ U, S→, R→, [C,I]_1, [C,I]_2, …, [C,I]_K ]
                              └────── 交叉特征与候选特征合并成 token ──────┘
```

变换只做了一件事：**把 C 从"独立特征块"挪进"候选 token 内部"**。代价是零；收益是整条序列变成自注意力的合法输入，而交叉信息没丢。

训练时按**用户**聚合（同一窗口内的候选），推理时按**请求**聚合。由于聚合后的样本共享同一个 `(U, S→, R→)`，用户表示只算一次 → 训练样本数从"候选总数"降到"用户总数"，推理成本对候选数变成**亚线性**（**事实**）。

**这一招直接把 DLRM 两条扩规模路线的硬伤都绕开了**：既是 end-to-end 序列建模（不像 user 模块那样放弃交叉），又不随候选数线性涨（不像 cross 模块那样）。

### 2. token 化：统一维度

`U` 里的标量特征每个一个 token（`R^{N_U × d_model}`）；`S→`、`R→` 里**每个 item 一个 token**（item 内部特征先 embed、concat、过 MLP 压到 `d_model`）；候选的 `[C_i, I_i]` 一起 embed、concat、过 MLP → 一个 token。最终序列 `R^{(N_U+N_S+N_R+N_I) × d_model}`（**事实**，§4.1）。

### 3. 定制 mask：这是本篇最细的工程量

C-02 HSTU 用标准 causal mask，MTGR 说这样不行，两个具体理由（**事实**，§4.1）：causal mask 在 MTGR 里**没带来显著提升**；`R→` 记录的是聚合窗口内**当天**的实时互动，用简单 causal 会造成**信息泄漏**——"用户晚上的互动不应该暴露给下午的候选"。于是三类 token 三套可见性（**事实**，Figure 2(c)）：`U`、`S→` 是**静态**（信息来自聚合窗口之前，不产生因果错误）→ full attention，两两全可见；`R→` 是**动态**（实时逐步纳入互动）→ 自回归，每个 token 只对**之后**出现的 token 可见；候选 `C_i, I_i` → **对角 mask**，只见自己。

```
        age gen seq1 seq2 rt1 rt2 tgt1 tgt2 tgt3
  age [  ■  ■   ■    ■    ■   ■    ·    ·    ·  ]
  gen [  ■  ■   ■    ■    ■   ■    ·    ·    ·  ]
 seq1 [  ■  ■   ■    ■    ■   ■    ·    ·    ·  ]
 seq2 [  ■  ■   ■    ■    ■   ■    ·    ·    ·  ]   ← 静态块：全白
  rt1 [  ■  ■   ■    ■    ■   ■    ·    ·    ·  ]
  rt2 [  ■  ■   ■    ■    ■   ■    ■    ·    ·  ]   ← 动态块：上三角
 tgt1 [  ■  ■   ■    ■    ■   ■    ■    ·    ·  ]
 tgt2 [  ■  ■   ■    ■    ■   ■    ·    ■    ·  ]   ← 候选：只对角
 tgt3 [  ■  ■   ■    ■    ■   ·    ·    ·    ■  ]
```

注意 `rt2` 对 `tgt3` 不可见——因为 tgt3 出现得比所有 rt 都早。这层顺序关系要按时间戳实际算，不是固定模板（**事实**，正文对该 mask 的逐格解释）。

### 4. Group-Layer Normalization（GLN）

HSTU 是单 domain 的（全是 item token）；MTGR 的序列混了**四个语义空间**（画像 / 长期行为 / 实时行为 / 候选），直接归一化会让不同 domain 的分布互相拉扯。GLN 的做法是**按 domain 分组、组内归一化**（**事实**）：

```
X̃ = GroupLN(X)                              # 每个 domain 一组
K,Q,V,U = MLP_{K/Q/V/U}(X̃)                 # QKVU 融合
ÃV = silu(KᵀQ) / (N_U+N_S+N_R+N_I) · M · V   # 注意：分母是总长，非 softmax
Y  = MLP( GroupLN( Ṽ ⊙ U ) ) + X            # 残差 + 输出 MLP
```

消融显示：去掉 GLN 或去掉 dynamic masking，性能跌幅**相当于把模型从 small 升到 medium 的整个增益**（**事实**，Fig.4）——这两项不是"锦上添花"，是"占了半档规模的价值"。

### 5. 训练框架：从 TensorFlow 搬到 TorchRec 并改造

这一节是 NestPipe 最该看的部分（**事实**，§4.2）：

| 改造 | 解决什么 |
|---|---|
| **动态哈希表**（key 存指针、value 存向量+计数器+时间戳，解耦存储） | TorchRec 静态表在流式训练下：① 表满后新用户/新物品**分配不到** embedding；② 为防溢出预留空间 → 内存浪费。改后容量可动态扩、key 存储可单独复制、key 紧凑排列扫描更快 |
| **embedding ID 去重 + 自动表合并** | All-to-all 传输重复 ID → 通信前后各保证 ID 唯一 |
| **动态 batch size** | 长尾序列导致固定 BS 下各 GPU 算力不均（sequence packing 要精细改 mask，代价高）→ 按实际序列长调每个 GPU 的 local BS；梯度按 BS 加权聚合，保持与固定 BS 一致的计算逻辑 |
| **三流流水**（copy / dispatch / compute） | I/O 与查表阻塞计算 → compute 跑 batch T 时 copy 载入 T+1；T 反传完成后 dispatch 立刻开始 T+1 的查表与通信 |
| **bf16 混合精度 + cutlass 定制 attention kernel** | — |

合计：**相比 TorchRec 训练吞吐 1.6×–2.4×，在 100+ GPU 上仍有良好扩展性**（**事实**）。

### 6. 实验配置

三个规模档（**事实**，Table 2）：small（3 层 / `d_model`=512 / 2 heads）、medium（5 / 768 / 3）、large（15 / 768 / 3）。DLRM 基线每 GPU batch 2400、8×A100；MTGR batch 96、16×A100。`S→` 最大长 1000，`R→` 最大长 100。数据用美团真实日志（10 天做离线，6 个月做线上对比）。稀疏参数扩容时的策略值得记：**优先加基数小的稀疏特征维度，极稀疏特征的维度保持不变**，防止稀疏参数无谓膨胀（**事实**，§5.1）。

## 为什么值得读

- **它是 C-02 HSTU 的正面对手，而且是唯一用工业数据把"扔掉交叉特征"这个前提打掉的**。读 C-02 时接受"数值特征可以扔"，读这篇时必须重新怀疑它。二者构成 track 内最重要的一组**反题**。
- **与 C-04 FuXi-α 是"同向不同路"**。FuXi-α 也认为 HSTU 特征交互不足，但解法是**加 MFFN 做隐式交互**；MTGR 的解法是**把交叉特征搬进 token 并改 mask**。一个走结构，一个走数据重排：MTGR 更便宜（不动层结构），FuXi-α 更通用（不依赖手工特征）。
- **与 C-06 DMT 的关系**：DMT 从"数据中心拓扑"出发重构模型，MTGR 从"特征语义"出发重构输入。两者都在做**模型-系统协同设计**，但切分维度不同（网络层级 vs token 类型）。
- **对 NestPipe 的直接价值**：§4.2 那套 TorchRec 改造（动态哈希表、ID 去重、动态 BS、三流流水）是**可直接抄的工程清单**，且给出了每个改动解决的具体故障模式（表满、ID 溢出、load imbalance）。这与 Track B（嵌入表存储/分片）交集很大——动态哈希表本质就是本 track 版的"嵌入表扩容"。
- **它是这条线上"生成式推荐真的上生产"的最强证据之一**：不是 A/B 2%，是 "handling the main traffic"，且训练成本不涨、推理成本还降了。

## 局限

1. **依赖手工交叉特征**。MTGR 的收益完全建立在"你已经有高质量交叉特征"这个前提上。这对已有十年 DLRM 积累的公司是优势，对从零开始的团队是**负债**（**推断**）——你得先造出那批特征。
2. **mask 设计不可迁移**。三类 token 的可见性规则是绑在"画像/长期/实时/候选"这个具体特征分组上的，换业务就要重推一遍，且极易出错（信息泄漏是静默错误，不会报错）。
3. **序列长度上限偏小**。`S→` 只有 1000、`R→` 只有 100。相比 C-05 ULTRA-HSTU 的 16K、SlimPipe 讨论的 128K–512K，这个规模属于中等。所以本篇的"scaling law"验证范围比 C-02 窄得多。
4. **只报了相对数，缺绝对值**。没有给 QPS、P99 延迟、每样本训练成本的具体数值，只有"降 12%""持平"这类相对表述。做容量规划时不好用（**待核实**）。
5. **单业务验证**。只跑了美团外卖场景（虽然流量很大），跨业务（到店、酒旅）未验证（**推断**）。
6. **65× FLOPs 与 "训练成本持平" 怎么同时成立？** 论文的解释是用户聚合把样本数从"候选数"降到"用户数"，两者相乘正好抵消。但这个抵消关系依赖**每个用户的候选数**这个业务特征，换业务会变（**推断**）。
