# 13. 设计清单与决策表

## 本章要解决的问题

**读完这章你应该能回答**：给定自己的业务规模与瓶颈，该按什么顺序做技术选型？每项选择的前提是什么、什么情况下会失效？

前面 12 章给了知识和方法，这章给**可以直接用的东西**。但先声明：**没有一套参数能适用于所有场景**，下面的决策表是按规模分档的，每档的前提都写清楚。

## 第一步：先测量，别先选型

在查任何决策表之前，先回答五个问题。**这五个答案决定了后面的所有选择。**

| 问题 | 怎么测 | 为什么关键 |
|---|---|---|
| 1. 嵌入表多大？ | 参数量 × 字节数 + 优化器状态 | 决定是否必须分布式（>80 GB 就要） |
| 2. 每步访问多大比例？ | profile `gather` 的 unique 行数 | 决定缓存/分层是否有价值 |
| 3. 访问倾斜度？ | 统计 ID 频率的幂律指数 | 决定负载均衡策略 |
| 4. 瓶颈在哪堵墙？ | profile 三部分耗时占比 | 决定优化方向（第 3 章） |
| 5. 能否容忍精度损失？ | 业务方确认（0.1% AUC 值多少钱） | 决定压缩/分层路线 |

**第 5 问最容易被跳过，但它决定了一半的技术选择。** `B-09` 用生产数据证明：广告主模型不能损失 0.1% AUC。如果你的业务能容忍，压缩派（第 9 章）的全部手段都可用；如果不能，只能走层级存储（第 7 章）。

## 决策表：按表大小分档

| 嵌入表大小 | 典型瓶颈 | 首选方案 | 关键论文 | 前提 |
|---|---|---|---|---|
| **< 80 GB**（单卡装得下） | 计算 / 收敛 | 单卡或简单 DP；关注过拟合 | `B-16` Pinterest | 显存够，无需分布式 |
| **80 GB ~ 1 TB** | 内存容量 | 行切（Row-wise）+ 小表复制 | `A-06` NEO 4D | 表大小相对均匀 |
| **1 ~ 10 TB** | 通信 | 行切 + 二维并行（分组副本）+ 通信压缩 | `A-03`、`A-14`、`A-15` | 可接受内存放大 G 倍 |
| **10 ~ 100 TB** | 层级 / 缓存 | 三层存储 + 缓存 + 有界过期 | `B-09`、`B-02`、`A-10` | 能接受精度风险或必须无损 |
| **> 100 TB** | 全部 | 上述组合 + 压缩 + 自动分片 | `A-04`、`B-06`、`B-13` | 需要完整的工程团队 |

⚠️ **这张表是按"表大小"分档的，但真正决定瓶颈的是"表大小 ÷ 单卡容量"和"访问倾斜度"**。如果你的表只有 200 GB 但倾斜极端（0.1% 承担 90%），瓶颈可能是通信而不是容量——那应该看第三档。

## 七个容易踩的坑

这些都是从论文的"局限"和"负面结果"里提炼的。

### 坑 1：只算参数量，忘了优化器状态

```
10 TB 参数 → 实际内存需求 20~30 TB（含优化器状态）
```

`A-06` 的案例：96 TB → 24 TB，靠 row-wise sparse AdaGrad + FP16。**只给被访问的行存状态**这一步本身就省了一半以上。

### 坑 2：以为压缩比等于加速比

`B-11` 的诚实数据：压缩了，但延迟从 **61ms 涨到 110ms**（PyTorch 不支持低精度稀疏 all-reduce + coalescing 开销）。

**评估压缩时算"压缩 + 传输 + 解压"的总时间。**

### 坑 3：以为静态分片够用

`B-13` 的批评：**行为是 input-dependent 的**。静态分片方案在最坏 batch 上必然失衡，而训练有成千上万个 batch。

### 坑 4：以为缓存命中率是稳定的

`A-10` 的数据：静态缓存在 Avazu 上从 day1 的 **91% 掉到 day9 的 82%**。

**缓存策略需要定期更新**，否则命中率会衰减。

### 坑 5：以为"无损"验证过了

`B-09` 的 0.1% 是在 **5 个模型、在线 A/B 一天**上测的。更长训练周期、更多样本时是否仍无损？未验证。

### 坑 6：误读 scaling efficiency

`C-05` 的 5×/21× 是 **scaling efficiency**（性能对算力的回归斜率），**不是"训练快 5 倍"**。论文自己都特意提醒这个定义容易被误引。

### 坑 7：在错误的墙上投入

第 3 章的算例：计算 33%、本地内存 12%、跨机通信 55%。

**在算力上投入最多改善 33%，在通信上投入能改善 55%。** 先测量再投入。

## 一个完整的选型示例

<div class="example">

**场景**：电商推荐，嵌入表 8 TB，200 张表，访问倾斜（1% 承担 90%），业务要求 AUC 不能掉（比照 `B-09` 的约束）。

**测量结果**：

```
表大小 8 TB → 需 ≥100 卡（单卡 80 GB）
瓶颈：跨机 all-to-all 占 52%，本地内存 20%，计算 28%
倾斜：极端（1% 承担 90%）
精度：不能损失
```

**决策链**：

1. **压缩选择要收紧**（精度约束）→ 第 9 章三条轴都有精度代价，**没有一条是无损的**。
   TT 分解（`B-07`）是**低秩近似，精度损失结构性且不可逆**——它的参照数据（TT-Rec 在 Kaggle 上压 4–221×，精度掉 0.03%–0.3%）在"不能掉 0.1% AUC"的场景下**不达标**。
   所以这一档实际上只剩两条路：**层级存储**（不压参数，只挪位置）和不损失精度的分片；
2. **必须是层级存储**（8 TB 装不下）→ `B-09` 模式：HBM → DRAM → SSD；
3. **通信占 52%，但压缩不可用** → 用**融合**（`A-15`）而非压缩（`A-14`）；
4. **倾斜极端** → 二维并行（`A-03`）提高均衡度，或按输入动态分片（`B-13`，⚠️ 机制待核实）；
5. **缓存** → 倾斜极端意味着缓存收益大，用预取（`A-10`，若离线训练）或有界过期（`B-02`）。

**最终方案**：

```
分层存储（B-09 模式）
  + 消息融合（A-15）
  + 二维并行（A-03，G=4）
  + 预取（A-10，若离线；否则 B-02 有界过期）
```

**预期代价**：

- 内存放大 4 倍（二维并行）；
- 显存开销（融合需要缓冲）；
- 若用 `B-02`，有精度风险需实测 s。

</div>

## 什么情况下这套东西不适用

必须说清楚边界：

1. **模型不是"大稀疏+小稠密"**。如果走向深层 Transformer（第 10 章），瓶颈顺序会反转，前九章大半失效。
2. **表小到单卡装得下**。那时瓶颈是收敛与过拟合（`B-16`），不是内存与通信。
3. **在线学习**。预取路线（`A-10`/`A-11`）完全失效，只能用有界过期。
4. **延迟敏感而非吞吐敏感**。本教程绝大部分优化是吞吐导向的；推理侧的尾延迟优化（`B-01`）是另一套东西。

<div class="takeaway">

**本章结论**：**先测量，再选型**。五个必测项里，最容易被跳过的是"能否容忍精度损失"——它决定了一半的选择。

七个坑里，最贵的两个是：**只算参数量忘了优化器状态**（差 2-3 倍）、**以为压缩比等于加速比**（`B-11` 的 61→110ms）。

最后一句：**这张决策表是按 50 篇论文的适用范围画的，超出那个范围就不适用。** 遇到新情况时，回到第 12 章的五步法自己判断，比套表可靠。
