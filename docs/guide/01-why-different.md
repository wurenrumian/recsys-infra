# 1. 推荐系统为什么和 LLM 不一样

## 本章要解决的问题

**读完这章你应该能回答**：为什么把训练 LLM 的那套系统经验搬到推荐系统上会失效？两者的参数结构和访存模式差在哪？

这个问题必须先回答。否则你会把"扩大模型 → 加卡 → 上 ZeRO → 上 FlashAttention"这套 LLM 直觉直接套过来，然后发现加速比远不如预期。

## 先看直觉做法为什么不够

假设你已经会训 LLM。你的经验大概是：

- 模型参数是**稠密**的，每一步前向反向都会碰到**全部**参数；
- 瓶颈通常是**算力**，所以关心 MFU（算力利用率）；
- 显存不够就切参数（ZeRO / FSDP），通信量随切分数线性涨，但至少**负载天然均衡**；
- 数据并行是最简单有效的扩展方式。

按这套经验看推荐模型，你会得出"把它当一个大 MLP 训"的结论。**这个结论在第一步就错了。**

原因：推荐模型的参数结构是**两个性质完全不同的部分拼在一起**。

## 机制拆解：一个模型，两种参数

DLRM 类模型的结构可以这样切：

```
                    ┌─────────────────────────┐
  稀疏特征 ID       │      嵌入表（99%+ 参数）  │
  [用户ID, 商品ID,  │  40 亿行 × 64 维 × 200 张 │  ← 稀疏、随机访问
   类目, 品牌, ...] │  10 TB                    │
        │           └───────────┬─────────────┘
        │                       │ gather（按 ID 取行）
        ▼                       ▼
   ┌──────────────────────────────────────┐
   │  稠密部分：特征交互 + MLP（<1% 参数）    │  ← 稠密、顺序访问
   │  3000 万参数                           │
   └──────────────────┬───────────────────┘
                      ▼
                  预测分数
```

两部分的差异不是"多少"，而是**性质**：

| | 嵌入表 | 稠密部分 |
|---|---|---|
| 参数占比 | **>99%** | **<1%** |
| 每步访问的参数比例 | 极少数行（本次 batch 查到的） | **100%** |
| 访存模式 | **随机**（按 ID 跳着取） | **顺序** |
| 瓶颈资源 | **内存带宽 / 容量** | **算力** |
| 负载均衡性 | **天然不均衡**（热点倾斜） | 天然均衡 |
| 能否容忍异步更新 | **能**（同一行被并发更新的概率低） | **不能**（每步都改全部参数） |

这张表是整门课的地基。后面 12 章几乎每一章都在利用其中某一行。

## 三个具体后果

### 后果一：优化目标从 MFU 变成 MBU

LLM 里衡量"算力用得怎么样"看 **MFU**（Model FLOPS Utilization）。但嵌入表的 `gather`（按 ID 取行）和 `scatter`（把梯度写回）这些算子，**算术强度低于 1**——读 256 字节只做几乎没有的浮点运算。

`A-16`（RecIS）为此提出 **带宽 roofline**：把 roofline 图的 x 轴从"算术强度"换成"**带宽强度**"，核心指标从 MFU 换成 **MBU**（Model Bandwidth Utilization）。

它给的实测数据说明问题有多严重（H20 上，对比 PyTorch）：

| 算子 | PyTorch MBU | RecIS MBU | 提升 |
|---|---|---|---|
| `gather` | 15.00% | **47.50%** | 3.2× |
| `scatter` | 20.75% | **58.00%** | 2.8× |
| `reduce easy` | 2.75% | **13.75%** | 5.0× |
| `bucketize` | 0.40% | **0.88%** | 2.2× |

**注意最后一行的绝对值**：即使优化后，`bucketize` 的带宽利用率只有 0.88%。这说明两个问题：

1. 稀疏算子的优化空间极大（所以有 50 篇论文可写）；
2. 稀疏算子的天花板极低——**用算力指标衡量它们是错的**。

### 后果二：负载天然不均衡

推荐数据是**幂律分布**的。`A-10`（Bagpipe）报告的实测：

- **1% 的嵌入承担 92% 以上的访问**；
- 或 **0.1% 承担近 90%**。

对比 LLM：一个 batch 里每个 token 都要过一次全部参数，**没有任何倾斜**。

这个差异的后果非常具体。`A-03`（2D Sparse Parallelism）的实测：

| 方案 | 负载不均衡比（CTR 模型） |
|---|---|
| 传统模型并行 | **5.70** |
| 4 组二维稀疏并行 | **1.57** |

不均衡比 5.70 意味着"最慢的卡干的事是最快卡的 5.7 倍"——**整个集群等最慢的那张**。这是第 4 章的主题。

### 后果三：异步更新对嵌入无害，对稠密有害

这条结论是 `A-04`（Persia）的立论基础，它把两个事实摆在一起：

| | 嵌入层 | 稠密 NN |
|---|---|---|
| 每步参数更新重叠度 | 几乎不重叠（只碰少数行）| 高度重叠（碰全部参数）|
| staleness 的影响 | 几乎无偏差 | 拖垮收敛 |
| 合适的同步语义 | **异步**（PS） | **同步**（AllReduce）|

作者的推理链是：异步更新在**稀疏访问**下高效，因为单步只改一小部分参数，覆盖写很少；而 staleness 会**限制**异步 SGD 的收敛，在更新重叠严重时偏差会累积。

**所以 Persia 让嵌入走异步 PS、稠密走同步 AllReduce。** 一个模型里用两种同步语义——这在 LLM 里是不可想象的设计。

## 算例：这个差异有多大

用[算例参数](running-example)：

| 项 | 嵌入表 | 稠密部分 |
|---|---|---|
| 参数 | 10.2 TB | 0.12 GB |
| 占比 | **99.9988%** | 0.0012% |
| 单次迭代访问 | 819 万行中的约 210 MB（去重后示意值） | **全部 120 MB** |
| 访问比例 | 0.002% | **100%** |

⚠️ **这张表里的"210 MB"是示意值**（按 10 倍去重假设），不是任何论文的数字。占比与总量按[算例定义](running-example)算得，可以直接复核。

两件事同时成立，很反直觉：

1. 嵌入表占 **99.9988%** 的参数，却每次只碰 **0.002%**；
2. 稠密部分只占 0.0012% 的参数，却每次碰 **100%**。

**这是"一个模型两个系统"的精确含义。** 你没法用一套策略同时优化它们，因为它们的最优解在同一张表的相反两端。

## 代价与边界

这一章的结论有边界，不能无限外推：

- **只适用于"大嵌入表 + 浅稠密层"的 DLRM 系模型**。如果模型走向深层 Transformer（第 10 章），稠密部分变重，两个系统会重新纠缠。
- **"嵌入访问倾斜"是经验观察，不是定律**。倾斜程度取决于业务；`A-10` 也报告了**缓存漂移**问题——静态缓存的命中率在 Avazu 上从 day1 的 91% 掉到 day9 的 82%。倾斜是会变的。
- **异步对嵌入"无害"是相对稠密而言**。`B-02`（HET）就发现可以容忍有界过期，但 `s→∞` 时精度崩掉（WDL AUC 79.64 → 74.61）。所以准确说法是"**允许有界**的异步"，不是"随便异步"。

<div class="takeaway">

**本章结论**：推荐模型不是"小号的 LLM"，而是**两个性质相反的系统拼在一起**。99.9988% 的参数被访问 0.002%，0.0012% 的参数被访问 100%。

后面所有优化都在这句事实上做交易：切开两个系统（第 4、5 章）、把稀疏的那半下沉到慢存储（第 7–9 章）、或者干脆改变模型让两半重新融合（第 10 章）。
