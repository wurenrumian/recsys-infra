# 2. 嵌入表：九成参数所在的地方

## 本章要解决的问题

**读完这章你应该能回答**：嵌入表在训练时到底发生了什么？一个 `gather` 操作在系统层面意味着什么？为什么它比矩阵乘法"昂贵"？

第 1 章说了"嵌入表是稀疏的、带宽受限的"。这章把这句话拆到算子级别——因为后面所有优化（分片、缓存、压缩）都是在对具体的算子做修改。

## 先看直觉做法为什么不够

直觉做法：**嵌入表就是一个 2 维数组，`lookup` 就是数组索引，这是 O(1) 操作，能有多难？**

这个直觉在**单机、小表、顺序访问**时是对的。在 10 TB 表 + 随机访问 + 分布式时，每一步都错：

| 直觉 | 实际 |
|---|---|
| `lookup` 是 O(1) | 是 O(1)，但常数是**一次网络往返**（当表不在本机时）|
| 数组索引很快 | 快，但**带宽受限**——每次 256 字节，随机跳 |
| 表是只读的 | 训练时**每步都要写回梯度**（`scatter`）|
| 参数和梯度分离 | 嵌入表常常**融合反向与优化器**，不落地梯度 |

最后一条尤其重要，第 5 章会讲它引起的算法问题。

## 机制拆解：一次迭代里嵌入表经历什么

以 DLRM 训练的一个 batch 为例：

```
① 前向：gather
   输入：batch 内 16384 个样本，每样本 500 个特征 ID
   → 展开成 819 万个 (table_id, row_id) 查询
   → 从各表取出对应行 → 得到 819 万个 64 维向量
   → 按特征域做 pooling（sum/mean）→ 每样本每域一个向量

② 反向：scatter（梯度回填）
   → 稠密部分算出每个池化向量的梯度
   → 反池化，散播回 819 万个向量
   → 每个向量作为该行的梯度

③ 更新：优化器（常常与 ② 融合）
   → 用行梯度更新对应行
   → 只更新被访问到的行（row-wise sparse update）
```

**关键观察**：这 819 万个查询里，绝大多数 `row_id` **不重复**吗？不一定。`A-10` 报告 1% 的嵌入承担 92% 的访问，所以实际上大量重复。

于是真实系统里有一步**去重（unique）**：

```
819 万次查询
   → unique 去重 → 假设剩 200 万唯一行（示意）
   → 只对这 200 万行做 gather / scatter
```

`A-16`（RecIS）的 MBU 表里专门有 `ids partition` 这个算子（PyTorch 34.60% → RecIS 55.10%），就是在做这个。

## 三个让嵌入表"贵"的机制

### 机制一：随机访问打不满带宽

顺序读内存时，硬件能预取、能合并传输，带宽接近峰值。**随机读 256 字节**时：

- 每次访问只用到一条 cache line 的一部分（256 B 通常跨多个 64B/128B line）；
- 无法预取，延迟全额暴露；
- 在 GPU 上，随机 gather 的有效带宽可能只有峰值的 **10–50%**。

`A-16` 的实测印证了这个区间：即使优化后，`gather` 的 MBU 也只到 **47.50%**。

### 机制二：去重之前，索引本身就是负担

819 万个 `(table_id, row_id)` 对，在系统里是要传输的数据。这是 all-to-all 通信的真正内容——**不是传向量，是先传索引**。

`A-15`（FusedRec）发现的问题正是这个：去重让消息变得**又小又碎**，反而浪费带宽。第 6 章详述。

### 机制三：写完还要写回

训练不是只读。每个被访问的行都要更新：

```
读：gather 256 字节 × 200 万唯一行 = 512 MB（示意）
写：scatter + update 同样量级
```

这让嵌入表的**内存流量是只读场景的 2 倍**。这也是为什么 `B-02`（HET）要设计"写也允许过期"的协议——写是主要开销。

## 算例：嵌入表访问的实际数据量

用[算例参数](running-example)，走一遍完整流程：

<div class="example">

**输入侧**：

```
16,384 样本 × 500 特征/样本 = 819 万次查询
每次 256 字节 → 2.10 GB（未去重）
```

**去重后**（假设 4 倍，保守取法）：

```
819 万 ÷ 4 ≈ 205 万唯一行
205 万 × 256 B ≈ 525 MB
```

**读写合计**（读 + 梯度写回）：

```
525 MB × 2 ≈ 1.05 GB / 迭代
```

**占 51 ms 预算的比例**，假设单卡有效带宽 1.5 TB/s：

```
1.05 GB ÷ 1.5 TB/s ≈ 0.7 ms
```

单看数字很小——**但这是假设所有数据都在本地 HBM 且带宽打满的情况**。现实是：

- 表是分布式的，需要跨网络取 → 变成网络传输，慢 1~2 个数量级；
- 带宽打不满（随机访问）→ 有效值可能只有 30%；
- 819 万次查询是**每个 GPU worker 都要做一遍**（数据并行下各自处理不同样本，但都要查全表）。

</div>

## 代价与边界

- **"嵌入表很大"这个前提不是普适的**。`B-09` 的对照很值得记：Pinterest 那篇（`B-16`）的模型只有 2.98 亿参数（1.67 亿在嵌入表），完全装得下——它的瓶颈是**收敛与过拟合**，不是内存。所以"嵌入表问题"是**特定规模以上**才出现的。
- **去重率是估的，不是算的**。不同业务能差一个数量级，任何基于去重率的容量规划都必须用实测数据。
- **`gather`/`scatter` 的 MBU 天花板低**，这是硬件性质，不是软件没优化好。认清这一点能避免在错误方向上投入。

<div class="takeaway">

**本章结论**：嵌入表的开销不在计算，在**随机访问的带宽效率**和**索引本身的传输**。

「gather → scatter → row-wise update」这三步是后面所有优化的修改点：切分改的是 gather 从哪取（第 5 章），缓存改的是 gather 能不能命中（第 8 章），压缩改的是 gather 传多少（第 9 章）。
