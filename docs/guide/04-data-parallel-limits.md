# 4. 数据并行为什么在这里失效

## 本章要解决的问题

**读完这章你应该能回答**：数据并行在推荐系统上具体在哪一步崩掉？为什么会"必然 OOM"？为什么负载不均衡比平均性能差更要命？

这是第二部分的开头。第 3 章说通信是最大开销，这章回答**为什么最常用的通信方式（数据并行）在这个场景下失效**，从而为第 5 章的切分谱系铺路。

## 先看直觉做法为什么不够

数据并行（DP）的做法：每张卡存一份**完整模型**，各自处理不同 batch，最后 all-reduce 梯度。

在 LLM 上它是默认选择，理由很硬：

- 实现简单（`DistributedDataParallel` 一行）；
- 通信是规则的 all-reduce，可预测；
- 负载天然均衡（每张卡处理的 token 数差不多）。

在推荐系统上，这三条**全部反转**：

| | LLM | 推荐 |
|---|---|---|
| 每卡存完整模型 | 可行（切分后） | **10 TB × 每卡一份 → 直接不可能** |
| 通信规则性 | 规则 all-reduce | 稀疏、不规则（all-to-all） |
| 负载均衡 | 天然均衡 | **1% 承担 92% 访问** |

第一条是最直接的：**10 TB 的表，每张卡存一份，128 卡就是 1.28 PB**。这在第一个算例里就已经判死刑了。

## 机制拆解：三个断裂点

### 断裂点一：内存 —— 副本数量爆炸

纯 DP 要求每卡一份完整参数。用[算例](running-example)：

```
10.2 TB（参数）+ 20.4 TB（优化器状态）= 30.6 TB
× 128 卡副本 = 3.9 PB
```

即使不考虑优化器状态，也是 1.3 PB。

**纯 DP 在第一步就不可能。** 这就是 `A-03` 说"传统模型并行在 >1024 卡时必然 OOM"的原因——即便退一步用模型并行，卡数多了也有内存问题。

### 断裂点二：通信 —— all-reduce 变成了 all-to-all

假设你把嵌入表切开了（模型并行，MP）。这时前向需要：

```
每张卡拿到本 batch 的 819 万个 (table_id, row_id) 查询
    ↓
这些查询分散在所有卡上（因为表切开各卡）
    ↓
需要把每个查询路由到持有该行的卡
    ↓
这是 all-to-all，不是 all-reduce
```

**all-to-all 和 all-reduce 有本质区别**：

| | all-reduce | all-to-all |
|---|---|---|
| 通信量 | 每卡发 O(参数量)，收 O(参数量) | 每卡发给**每个**其他卡不同数据 |
| 模式 | 规则，可流水 | **不规则**，取决于数据分布 |
| 负载 | 均衡 | **极度倾斜** |
| 对网络的要求 | 带宽 | **带宽 + 低尾延迟** |

`A-06` 的 4D 并行里，row-wise 切分的前向通信就是 **ReduceScatter**，column-wise 和 table-wise 是 **AlltoAll**——三种不同原语，因为切的维度不同，通信模式就不一样。

### 断裂点三：负载 —— straggler 拖慢整个集群

这是最隐蔽也最致命的。

`A-03` 的实测数据：

| 方案 | 负载不均衡比（imbalance ratio） |
|---|---|
| 传统模型并行 | **5.70**（CTR）/ **5.18**（ExFM） |
| 4 组二维稀疏并行 | **1.57** / **1.65** |

**不均衡比 5.70 意味着：最慢的卡要做 5.7 倍的工作，全集群等它。**

关键点在于：训练是**成千上万个 batch 的序列**。静态分片方案在每个 batch 上都会失衡，**只是倒霉的卡不同**。所以代价不是"平均性能差一点"，而是**每个 batch 都要等最慢的那张**。

`B-13`（OPER）把这个论点说得最尖锐：

> 静态分片方案在最坏 batch 上必然失衡，而训练是成千上万个 batch 的序列，每个 batch 的 straggler 都在拖慢整体。

## 算例：纯 DP 到底差多少

<div class="example">

**目标**：128 张 H100 训练[算例模型](running-example)。

**方案 A：纯数据并行**

```
每卡需 10.2 TB 参数 → 单卡 80 GB → 需 128 卡才装一份
但 DP 要求每卡一份完整 → 128 卡 × 10.2 TB = 不可能
```

→ **直接失败，无需计算通信**。

**方案 B：纯模型并行（表按行切到 128 卡，每卡 80 GB）**

内存刚好够（10.2 TB ÷ 128 ≈ 80 GB，**没有任何余量给优化器状态和激活**）→ 实际仍然 OOM。

即便假定能跑，通信量：

```
每卡每迭代要查 819 万 / 128 ≈ 6.4 万次（均匀假设）
但实际倾斜：1% 的行承担 92% 访问
→ 持有热点的卡承担绝大部分查询
→ 那张卡成为瓶颈，其余 127 张卡等它
```

按 `A-03` 的不均衡比 5.70 推算，**这 127 张卡的有效利用率约为 1/5.70 ≈ 18%**。

</div>

这个算例解释了为什么需要"既不复制全表、又不纯切表"的第三类方案——第 5 章的主题。

## 为什么二维并行（A-03）能救

`A-03` 的思路很简洁：**MP 外面套一层 DP**。

```
设总卡数 N = 128，分成 G = 4 组，每组 32 卡
每组持有一份完整的表副本，组内按模型并行切分
→ 系统里有 4 份副本
```

三个问题各自被削掉一块（`A-03` 原文的对照表）：

| 问题 | 机制 | 效果 |
|---|---|---|
| 负载不均 | 副本只切到 32 卡（而非 128），切分粒度小、基数小，容易均衡 | 不均衡比 5.70 → **1.57** |
| all-to-all 通信 | 组内 all-to-all 只在自己组内做，参与方少 4 倍 | 通信量按 **1/G** 下降 |
| 激活内存 | 每组只看 1/4 的全局 batch | 查询激活内存按 **1/4** 下降 |

代价是什么？

- **内存放大 4 倍**（4 份副本）；
- 每步末尾要跨组同步 **表权重 + 优化器状态**（不是梯度，见下面）。

### 一个容易被忽略的细节：同步的不是梯度

`A-03` 明确说（3.1 节）：

> rather than synchronizing gradients as in common distributed data parallelism, our 2D sparse parallelism approach synchronizes table weights and optimizer states

为什么？因为**嵌入表的反向与优化是融合的**——反向算完立刻更新，不留梯度。所以跨组要同步的是**更新后的权重和二阶矩**。

这个设计带来了一个算法问题：`A-03` 发现直接套用 row-wise sparse AdaGrad 会掉效果（ExFM 上 NE 退化约 0.1%）。原因是各组独立更新时，**有效学习率被悄悄压小了**。他们的修法是 moment-scaled 变体，把退化拉回 <0.02% 的噪声阈值内。

> **这个细节值得单独记**：系统改动（多副本）会引入统计后果（学习率偏移），需要算法补偿。`A-03` 称这是"系统改动 → 统计后果 → 算法补偿"的闭环，也是我为它打「必读」的原因。

## 代价与边界

- **二维并行的 G 不是越大越好**。G 越大，负载越均衡、通信越少，但内存放大 G 倍。`A-03` 的实验用 G=4，这是内存与均衡的折中。
- **副本同步有额外开销**。每步末尾跨组同步权重+优化器状态，量级不小（10 TB 级）。
- **不均衡比不是万能指标**。5.70 → 1.57 是他们的模型与数据分布；你的业务倾斜程度不同，必须实测。
- **DP 在"小表"上仍然是对的**。`A-06` 的 4D 并行里，**小表就用 data parallelism 复制到所有 trainer**（前向无通信）。所以不是"DP 失效"，而是"DP 只适用于小表"。

<div class="takeaway">

**本章结论**：数据并行在推荐系统上的三个断裂点依次是**内存爆炸 → all-reduce 变 all-to-all → 负载倾斜**。第一个就足以判死刑。

出路是**混合**：小表复制（DP），大表切开（MP），再给大表复制若干副本换均衡（2D）。第 5 章把这条谱系完整展开。

</div>
