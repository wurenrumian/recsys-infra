# 7. 存储层级：把表放到更慢的地方

## 本章要解决的问题

**读完这章你应该能回答**：当机器加到极限、表还是装不下时怎么办？为什么把参数放到 SSD 上反而更快？"层级存储"的收益上限由什么决定？

第二部分的答案是"切开"。但如果切开之后，每张卡还是装不下，切分就走到头了。第三部分换了个方向：**不再切，而是把暂时不用的部分放到更慢、更便宜的介质上**。

## 先看直觉做法为什么不够

直觉：**SSD 比 HBM 慢 1000 倍，放上去不就慢死了？**

这个直觉错在了一个前提：它假设**每一步都要访问全部参数**——那是稠密模型的假设。

在推荐系统里，第 1 章已经证明：**每步只访问 0.002% 的参数**。

所以正确的问法是：**当前 batch 需要的那部分参数能否装进快存储？**

`B-09` 把这个洞察说得很直接：

> "working parameters"（当前 batch 引用到的参数）能装进 GPU 显存，虽然全模型 10TB 装不进。

**这一句话是整个第三部分的地基。**

## 机制拆解：三层存储 + 4 级流水

`B-09` 的架构：

```
┌──────────────────────────────────────────┐
│  GPU 节点 × 4（每节点 8×32GB HBM）        │
│  HBM-PS (L1, 最快)                        │
│  多 GPU 分布式哈希表                      │
│  参数不重叠分区：每个参数只在一张卡上      │
└───────────────┬──────────────────────────┘
                │ NVLink（卡间）/ RDMA（机间，绕过 CPU）
┌───────────────▼──────────────────────────┐
│  CPU 主存（~1TB/节点）                    │
│  MEM-PS (L2)                              │
│  汇集"本 batch 引用到的参数"并缓存        │
│  命中率 46%                               │
└───────────────┬──────────────────────────┘
                │
┌───────────────▼──────────────────────────┐
│  NVMe SSD RAID-0（~20TB/节点）            │
│  SSD-PS (L3)                              │
│  参数按"文件"组织，批量写新文件 + 压实     │
└──────────────────────────────────────────┘
```

三个关键设计：

1. **上层是下层的缓存**——HBM-PS 是 MEM-PS 的缓存，MEM-PS 是 SSD-PS 的缓存；
2. **卡间参数不重叠**——一个参数只存在一张 GPU 上，需要时通过 NVLink 取；
3. **每 mini-batch 同步一次**——消除参数过期（一个 mini-batch 有几千样本）。

### 为什么 SSD 能救

关键在于 **working set 的比例**。用[算例](running-example)：

```
全表 10.2 TB
单次迭代访问（去重后）525 MB → 占全表的 0.005%
```

如果 working set 只有 525 MB，那它完全可以放进 HBM（80 GB 单卡）——**根本不需要碰 SSD**。

SSD 存在的意义是：**大量"本轮不用但以后会用"的参数有地方待着**，而不是每次都从更慢的地方拉。

`B-09` 的实测给出了这个层级的实际效果：**4 台机器快过 150 台**（对比当时的 MPI 集群方案）。

## 算例：三层各自的命中率与延迟

<div class="example">

**设定**：单卡 80 GB HBM，假设 working set 分布如下（示意）：

| 层级 | 容量 | 命中率 | 单次访问延迟 |
|---|---|---|---|
| HBM | 80 GB | 90% | ~0.5 μs |
| DRAM | 1 TB | 9% | ~100 ns + 传输 |
| SSD | 20 TB | 1% | ~100 μs |

**平均延迟**（加权）：

```
0.90 × 0.5 μs  = 0.45 μs
0.09 × 5 μs    ≈ 0.45 μs   （DRAM 含 PCIe 传输开销）
0.01 × 100 μs  = 1.0 μs
合计 ≈ 1.9 μs
```

对比**全部从 SSD 取**（0 命中）：100 μs。

**加速约 52 倍。** 这就是分层的价值。

</div>

⚠️ **命中率数字是我假设的**，实际取决于数据分布。`B-09` 报告 MEM-PS 命中率 **46%**——这是一个真实值，但那是它特定的模型与数据。你的业务必须实测。

## 层级存储的收益上限

`A-10` 给了一个非常有用的判据：

> 优化的收益上限由**瓶颈占比**决定。75% 在嵌入访问上，所以最多 4×。

推导：如果某项占总时间的 75%，把它优化到 0，总时间变成 25%，加速比 = 1/0.25 = **4×**。这就是 Amdahl 定律。

**这个判据比任何具体数字都有用**，因为它让你在投入前就能算出天花板：

| 嵌入访问占比 | 理论上限 |
|---|---|
| 75% | 4× |
| 50% | 2× |
| 90% | 10× |

`A-10` 自己报了 5.6× 端到端加速——等等，这超过了 4× 的上限？

因为它的 75% 是"迭代时间中嵌入访问+同步占比"，而它同时优化了**故障恢复**（13 分钟 → 60 秒），这部分不在那 75% 里。所以严格说，它的加速来自多个来源，不只是嵌入访问优化。

> **这正是看论文数字时最该警惕的地方**：一个声称"5.6×"的数字，可能来自多个部件的组合，而每个部件都有自己单独的收益。要问清楚**每一项贡献多少**。

## 谁在造这些层级

几种不同的层级方案，横向对比：

| 方案 | 介质层级 | 抽象 | 关键数字 |
|---|---|---|---|
| `B-09` HPS | HBM → DRAM → SSD | 参数服务器 | 4 机 > 150 机；AUC 差 <0.1% |
| `B-01` EVStore | DRAM → 低精度 → key 代理（**推理侧**） | 缓存 | 最多省 94% 内存 |
| `B-15` HypeReca | HBM → 宿主内存 → 多节点 | **KV 数据库** | 2.16–16.8× |
| `B-08` UGache | 多卡显存统一成池 | 缓存 | 平均 1.93× |
| `B-17` DCMA | DMA 加多端口缓存 | 硬件 | ResNet-50 最高 17× |

### 一个重要的分野：训练侧 vs 推理侧

`B-01`（EVStore）和 `B-09`（HPS）都把嵌入当"分层存储问题"，但方向相反：

| | `B-01` EVStore | `B-09` HPS |
|---|---|---|
| 场景 | **推理** | **训练** |
| 目标 | 压单次查询延迟（尾延迟） | 提高吞吐 |
| 能否损失精度 | **能**（用近似换内存） | **不能**（坚持无损） |

为什么训练侧不能损失精度？`B-09` 用生产数据回答了这个问题：

> "even a 0.1% decrease in AUC would result in a noticeable decrease in revenue"

**这条论证是理解整个 Track B 分水岭的钥匙**——它解释了为什么"压缩派"（第 9 章）主要出现在学术与中等规模场景，而工业界的超大规模模型走"层级存储"路线。

⚠️ 这条论证的适用范围要说清楚：`B-09` 只测了一种哈希方法（OP+OSRP）就断言"哈希必然掉精度"，而 `B-03` 的 CAFE+ 在一万倍压缩下 AUC 还涨了 3.94%。所以**"必须无损"这个结论至少不是普适的**——它取决于业务对精度的敏感度和压缩方法的先进程度。

## 代价与边界

- **SSD 的写放大未讨论**。`B-09` 用"批量写新文件 + 定期压实"，写放大明显。生产上 SSD 磨损是真实开支，论文没报。这是一个空白。
- **"无损"的验证范围有限**。`B-09` 的 AUC 差 <0.1% 是在 5 个模型、在线 A/B 一天的结果。更长训练周期是否仍无损，未验证。
- **层级越深，一致性越难**。参数分散在多台机器的 SSD 上，如何保证不读到过期版本？这是第 8 章的主题。
- **静态分片不适合动态 ID**。`B-09` 是静态分片（参数按取模哈希固定分给节点），而推荐系统的 ID 集合是**持续增长**的（新商品、新用户每秒都在产生）。`B-15` 的 HypeReca 正是为了解决这个问题。

<div class="takeaway">

**本章结论**：层级存储成立的前提是**每步只访问极小比例的参数**（算例里 0.005%）。把"当前不用"的参数沉到 SSD，把"当前要用"的提到 HBM。

收益上限由 Amdahl 定律决定：**如果嵌入访问占总时间 75%，最多加速 4×**。投入前先算这个天花板。

训练侧的分层必须**无损**（工业广告模型不能损失 0.1% AUC），这是一条来自生产数据的硬约束——但它并非普适，取决于业务与压缩方法。

</div>
