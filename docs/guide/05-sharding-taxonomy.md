# 5. 切分谱系：表/行/列/副本

## 本章要解决的问题

**读完这章你应该能回答**：嵌入表有哪几种切法？每种切法的通信原语是什么、擅长什么、代价是什么？怎么为一张具体的表选切法？

这是全教程最"工具箱"的一章。第 4 章说纯 DP 和纯 MP 都不行，这章给出完整的中间选项。

## 先看直觉做法为什么不够

直觉：**表太大就按行切**，每张卡分一段行，简单。

这个方案在一种情况下很好：**所有表都很大且均匀**。但真实模型的表是**混合**的：

- 用户 ID 表：100 亿行（超大）
- 商品 ID 表：1 亿行（大）
- 类目表：5000 行（小到可以忽略）
- 城市表：300 行（极小）

如果一律按行切 128 份，类目表和城市表会被切成 4 行、2 行一份——**切分的通信开销远大于收益**。

反过来如果一律复制（DP），大表又装不下。

**所以必须按表选切法。** `A-06`（NEO）明确说他们按**算子粒度**选，不是按模型粒度选——同一张模型里不同表可以用不同切法。

## 机制拆解：四种基本切法

`A-06` 的 4D 并行把这四种切法做成了可组合的原语。这张表是本章的核心：

| 维度 | 怎么切 | 前向通信 | 擅长 | 不擅长 |
|---|---|---|---|---|
| **Table-wise** | 按表分给不同 trainer，表不再拆 | **无额外通信** | 大量中小表 | 单表大于单卡内存时失效；表大小倾斜导致失衡 |
| **Row-wise** | 按行（ID 维度）切 | **ReduceScatter** | 超大表；负载均衡好 | 通信量随 trainer 数线性涨 |
| **Column-wise** | 按嵌入维度切 | **AlltoAll** | 维度大时切得更细，均衡更好 | 索引要复制到所有列分片；稀疏优化器要为每个行分片单独存状态 |
| **Data** | 小表当稠密参数复制到所有 trainer | 前向**无通信**，反向 **AllReduce** | 小表（行数少） | 表大时 AllReduce 比 AlltoAll 更贵 |

### 每种切法的数据结构

```
原始：一张表 T，100 亿行 × 64 维

Table-wise（4 张表分 4 卡）：
  GPU0: 表 A 全部        GPU1: 表 B 全部
  GPU2: 表 C 全部        GPU3: 表 D 全部
  → 查表 A 的所有请求都去 GPU0

Row-wise（1 张表切 4 份）：
  GPU0: 25 亿行（ID 0~25亿）
  GPU1: 25 亿行（ID 25亿~50亿）
  → 查 ID 3 去 GPU0，查 ID 70亿 去 GPU2

Column-wise（64 维切 4 份）：
  GPU0: 全部行 × 16 维    GPU1: 全部行 × 16 维
  → 每次查询要 4 张卡都参与，最后拼接

Data（复制 4 份）：
  GPU0~3: 各有一份完整的表
  → 查本地即可，但更新时要 AllReduce 同步
```

### 为什么 Column-wise 的代价容易被低估

`A-06` 特别指出两个代价：

1. **输入索引要复制到所有列分片节点**——每次查询的 ID 都要发给所有列分片；
2. **稀疏优化器要为每个行分片单独存状态**——优化器状态的放大倍数按列分片数再乘一次。

第 2 点很关键：第 2 章算过优化器状态已经是参数的 2 倍，列切分会让它再涨。

## 算例：给[算例模型](running-example)的 200 张表选切法

假设 200 张表按大小分布（示意）：

| 表规模 | 张数 | 单表大小 | 建议切法 | 理由 |
|---|---|---|---|---|
| 超大（>10 亿行） | 10 张 | 26 GB ~ 260 GB | **Row-wise**（可能再叠 Column-wise） | 单卡装不下，且访问均匀 |
| 大（1000 万~10 亿行） | 40 张 | 2.6 GB ~ 26 GB | **Row-wise** 或 **Table-wise** | 视访问倾斜度 |
| 中（100 万~1000 万行） | 80 张 | 0.26 GB ~ 2.6 GB | **Table-wise** | 单张可放一卡，跨表分摊 |
| 小（<100 万行） | 70 张 | < 0.26 GB | **Data（复制）** | 复制 128 份才 33 GB，可接受 |

<div class="example">

**小表复制的账**：

```
70 张小表，每张平均 0.1 GB → 合计 7 GB
复制 128 份 → 896 GB
分摊到每卡 → 7 GB / 卡
```

单卡 80 GB 里拿出 7 GB 放小表副本，换来**前向零通信**。这笔账很划算。

**大表切分的账**（10 张超大表，合计约 200 GB）：

```
Row-wise 切 128 份 → 每卡 1.6 GB
前向 ReduceScatter：每卡发 1.6 GB 的局部结果
```

对比如果这 200 GB 也复制 128 份：**25.6 TB**，直接把单卡撑爆。

⚠️ 这张分档表（10/40/80/70 张、各自大小）是**我按幂律分布构造的示意**，不是任何论文的表。真实模型里表的大小分布要用实际数据统计。

</div>

这个算例说明了切分的核心原则：**按表的"大小 × 访问倾斜度"分档，不同档位用不同切法**。

## 谁在自动做这个决策

手选切法在 200 张表时就不现实了（组合爆炸）。所以有一整条"自动分片"支线：

| 方案 | 方法 | 关键数字 |
|---|---|---|
| `B-05` AutoShard | 神经代价模型 + DRL 分配 | 几百张表**秒级**出方案；均衡度 88.6% |
| `B-06` NeuroShard | 预训练代价模型 + 双层搜索 | 比 SOTA **+23.8%**；生产 128 GPU 上端到端 **+6.6%** |
| `B-04` EMBark | 分簇 + 3D 分片（表、行、列三元组） | 端到端 **1.5×**（最高 1.77×） |
| `B-13` OPER | 启发式搜索 + 分布式共享内存 | 训练 **2.3×**、推理 **4.0×** |

### 一个更深的分歧：分片该不该"看输入"

这是 Track B 里最有价值的一处**辩论**，值得单独记。

`B-05` 和 `B-06`（同一作者群）的代价模型输入是**表的静态特征**：维度、hash size、pooling factor、索引分布统计。

`B-13` OPER 提出了尖锐的反驳：**行为本身是 input-dependent 的**。

它给的论证（我按它的论点构造的例子）：

```
表 T（1 亿行，128 维，分布在 8 张 GPU 上）
Row-wise 均匀切分，每卡 1250 万行

batch A: 访问集中在 ID ∈ [0, 1e6)   → GPU 0 承担 90%，其余 7 卡空闲
batch B: 访问集中在 ID ∈ [9e7, 1e8)  → GPU 7 承担 90%，GPU 0 空闲
```

**同一分片方案在不同 batch 上都会失衡，只是倒霉的卡不同。**

这个批评很硬：它不是"你们的模型不够准"，而是"**你们建模的对象错了**"。

⚠️ `B-13` 目前只有摘要，上面的例子是按它的论点构造的（论文页里标为推断），不是原文的图。**这个分歧本身是确定的**（摘要明确说 input-dependent），但具体机制细节无法完整复述。

## 代价与边界

- **切法不是越细越好**。每次切分都会增加通信原语和优化器状态。`A-06` 的 4D 是"按算子粒度选"，意味着大部分表并不需要 4 维全用上。
- **自动分片的收益依赖基线**。`B-06` 的 +23.8% 是相对 SOTA 方法，生产上端到端只有 +6.6%——因为嵌入只占端到端的一部分。**看到大数字要问基线是什么。**
- **静态 vs 动态分片还没有定论**。`B-13` 指出了静态建模的缺陷，但它自己的方案也只有摘要可查。这是这条线上**明确未解决的问题**。

<div class="takeaway">

**本章结论**：嵌入表切分是一个**四选一 + 按表分档**的问题：

- 小表 → **复制（DP）**，换零通信；
- 超大表 → **行切（Row-wise）**，换内存与均衡；
- 维度特别大 → **列切（Column-wise）**，但要付索引复制 + 优化器状态翻倍；
- 大量中小表 → **表切（Table-wise）**，换无额外通信。

真实系统是这四者的组合。自动分片（`B-05`/`B-06`/`B-04`/`B-13`）在解决"怎么组合"，而**"分片该不该看输入"是这个方向上尚未解决的核心分歧**。

</div>
