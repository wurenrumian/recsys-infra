# 贯穿全教程的算例

13 章共用同一个假想模型。它不是从某一篇论文抄来的，而是按真实工业模型的量级构造，目的是让各章数字能横向比较。

## 定稿参数

| 项 | 取值 |
|---|---|
| 嵌入表数量 | 200 张 |
| 嵌入表总行数 | **400 亿**（4×10¹⁰），平均每张 2 亿行 |
| 嵌入维度 | **64**（fp32，每行 64 × 4 = **256 字节**） |
| 嵌入表总大小 | **≈ 10 TB** |
| 稠密参数量 | 3000 万（0.12 GB，可忽略） |
| 全局 batch size | **16,384** 个样本 |
| 每样本平均查 | **500** 个嵌入行（多特征域） |

总大小的算术：

```
4 × 10¹⁰ 行  ×  256 字节/行  =  1.024 × 10¹³ 字节  ≈  10.2 TB
```

这个规模有依据：`B-09` 实测的就是 10 TB 参数（1990 亿非零权重），`A-06` 是 12 TB，算例数字能和论文直接对照。

## 四个关键派生量

这四个数后面各章反复用到。

### 1. 单卡放不下——需要多少张卡

H100 单卡 80 GB HBM：

```
10.2 TB  ÷  80 GB  ≈  128 张卡
```

这就是"必须分布式"的全部算术：光把参数放下就要 **128 张卡**，还没算优化器状态、梯度、激活。`A-03` 的报告印证了这一点：传统模型并行在 >1024 卡时必然 OOM。

### 2. 优化器状态的放大——比参数本身还大

AdaGrad / Adam 要为每行存累积状态：

```
fp32 一阶矩：10.2 TB  ×1  = 10.2 TB
加 fp32 二阶矩：          + 10.2 TB
合计                     ≈ 20 TB
```

`A-06` 报告的 96 TB → 24 TB 就是这件事：原来的模型参数加优化器状态到 96 TB，靠 row-wise sparse AdaGrad（只给被访问的行存状态）加 FP16 压到 24 TB。

> 重要推论：嵌入表的真实内存压力通常是参数的 **2 倍**，不是 1 倍。只算参数量的容量规划会低估一半。

### 3. 一次迭代要搬多少嵌入数据

```
16,384 样本 × 500 行/样本 = 819 万次查询
819 万 × 256 字节 = 2.1 GB（未去重）
```

这是每张卡都要面对的输入侧数据量（若不做缓存），也只是"要查哪些行"展开成的向量总量。

去重后通常大幅下降。`A-10` 报告 1% 的嵌入承担 92% 以上的访问，这种倾斜下去重收益很高。假设 10 倍去重：

```
去重后 ≈ 210 MB / 迭代
```

⚠️ **210 MB 是示意值**。去重率取决于数据分布的倾斜程度，不同业务能差一个数量级。后面用到它的地方会标出来。

### 4. 时间预算

要达到 **320K 样本/秒**（`A-10` 报告的 16 trainer 吞吐）：

```
16,384 样本 ÷ 320,000 样本/秒 ≈ 51 ms / 迭代
```

51 ms 是所有优化要抢的预算。第 6 章会算 all-to-all 在这 51 ms 里占多少。

## 为什么用这个算例

1. 量级真实：10 TB、400 亿行、16,384 batch，都在工业论文实测范围内。
2. 能手算：每个量都能心算出结果，不需要跑代码，这是教程可验证性的基础。
3. 和论文可比：`B-09`（10 TB）、`A-06`（12 TB / 96 TB 优化器状态）、`B-04`（48B–470B 参数）在同一把尺子上。

## 怎么用它

后面每章出现「算例」块，都是在这套参数上算一遍。某个数字觉得不对，用上面的定义重算即可。你算出的结果和我不一样时，以你的计算为准：算例只是脚手架。
