# 3. 第一个瓶颈不是算力

## 本章要解决的问题

**读完这章你应该能回答**：为什么给推荐训练增加 GPU 的边际收益会迅速衰减？"带宽墙"在三堵墙里为什么排第一？

上一章把嵌入表的开销定位在随机访问。这章把它提升到系统层面：**在三类资源里，哪一类先成为瓶颈**。

## 先看直觉做法为什么不够

直觉做法：**训练慢就加卡**。数据并行是标准答案——把 batch 切开，每张卡算一份，最后 all-reduce 同步梯度。

这在 LLM 上成立，因为瓶颈是算力，加卡就加算力。

但在推荐系统上，加了卡之后你会发现两件事：

1. **吞吐不线性增长**。`A-03` 实测：1024 卡时 QPS 扩展因子降到 **79.7%**，4096 卡时只有 **90%**（相对 512 卡）；
2. **可能反而更慢**。`B-04` 报了一个很关键的数字：**8 卡时嵌入通信占 25%，128 卡时占 51%**。

第二件事是要害：**加卡会让瓶颈从算力转移到通信**，而转移之后，继续加卡只会让通信更糟。

## 机制拆解：三堵墙

`A-16`（RecIS）把推荐系统的瓶颈组织成三堵墙，这个框架我认为是全 50 篇里最清晰的：

```
    ┌──────────┐      ┌──────────────┐      ┌────────────┐
    │  IO 墙    │  →   │   内存墙      │  →   │   计算墙    │
    │ 样本读取  │      │ 稀疏、带宽受限 │      │ 稠密、算力   │
    └──────────┘      └──────────────┘      └────────────┘
         │                   │                     │
     列存格式            全上 GPU              混合精度
     多线程             两层存储              Fused kernel
     CSR 编码           带宽 roofline         ZeRO
```

关键洞察：**三堵墙按顺序成为瓶颈，你现在撞的是哪堵取决于前面的都打通了没有**。

- 如果 IO 没优化好，瓶颈在数据加载，GPU 空转；
- IO 打通了，瓶颈前移到内存带宽；
- 带宽打满了，才轮到算力。

`A-16` 的原话是："只有 IO 充分优化，瓶颈才会前移到计算部分。"

### 为什么"内存墙"在推荐里格外厚

在 LLM 里，内存墙指的是**参数量 > 显存**，解法是切参数（ZeRO），代价是通信——但**负载均衡**，通信是规则的、可预测的。

推荐系统的内存墙有三个额外属性：

| 属性 | LLM | 推荐 |
|---|---|---|
| 参数访问 | 每步全部 | 每步 0.002% |
| 访问模式 | 顺序 | **随机** |
| 负载均衡 | 均衡 | **倾斜（1% 承担 92%）** |
| 带宽效率 | 可接近峰值 | **随机访问下只有 10–50%** |

第三条（倾斜）导致 straggler，第四条（随机）导致物理带宽打不满。两个都不是"多加点带宽"能解决的。

## 算例：三堵墙各自的时间占比

用[算例参数](running-example)，估算一次迭代里三部分的耗时（单卡视角，示意值）：

<div class="example">

**计算墙**：稠密部分 3000 万参数，batch 16,384。

```
每样本约 3000 万 × 2（前向+反向）浮点运算 ≈ 6e7 FLOP
16,384 样本 × 6e7 = 9.8e11 FLOP ≈ 0.98 TFLOP
H100 fp16 有效算力约 500 TFLOPS × 30% 利用率 = 150 TFLOPS
0.98 TFLOP ÷ 150 TFLOPS ≈ 6.5 ms
```

**内存墙**：嵌入数据搬运（第 2 章算过）。

```
去重后 525 MB，读写各一次 → 1.05 GB
本地 HBM 有效带宽 1.5 TB/s × 30%（随机访问）= 450 GB/s
1.05 GB ÷ 450 GB/s ≈ 2.3 ms
```

**通信墙**：如果嵌入表在别的机器上，需要走网络。

```
525 MB 走 IB 400 Gbps（50 GB/s）
525 MB ÷ 50 GB/s ≈ 10.5 ms
```

**对比**：

| 墙 | 耗时 | 占比 |
|---|---|---|
| 计算 | 6.5 ms | 33% |
| 本地内存 | 2.3 ms | 12% |
| **跨机通信** | **10.5 ms** | **55%** |

⚠️ 上面三项都依赖我的假设：**有效算力利用率 30%、随机访存有效带宽 30%、IB 400 Gbps 跑到 50 GB/s**。换硬件或换利用率假设，绝对值会变，但"跨机通信优先于计算"这个结构性结论在多篇论文里都成立（见下）。

</div>

这个算例的结论很清楚：**一旦嵌入表不在本机，通信就是最大开销**。这也解释了为什么 `B-04` 的"8 卡 25% → 128 卡 51%"会发生——卡越多，表越分散，跨机比例越高。

⚠️ **这些数字是示意性的**。真实系统的瓶颈占比必须实测，因为有效带宽、利用率、网络拓扑都差异极大。但这个**数量级关系**（通信 > 计算）在工业论文里反复出现，`A-10` 报告"迭代时间中嵌入访问+同步占比约 75%"，与这里算出的 55–67% 同一量级。

## 三个反直觉的推论

### 推论一：加卡可能让事情变糟

`A-03` 的数据：传统模型并行在 **>1024 卡时必然 OOM**，而且 QPS 扩展因子从 96%（2D 并行）掉到 79.7%。

原因是：卡越多，每张卡分到的表越小，但**跨卡访问的比例上升**。分片粒度小了，热点更容易集中到某一张卡上。

### 推论二：优化目标应该是"减少数据搬运"，不是"提升算力利用率"

如果在算力上投入（更快的 GPU、更高效的 kernel），最多只能改善那 33%。

如果在通信上投入（压缩、缓存、换拓扑），能改善 55%。

`A-16` 把这件事说得很直接：稀疏算子的 **MBU 才是第一等指标**，MFU 对它们没有解释力。

### 推论三：瓶颈会随规模迁移，所以方案必须能"可组合"

`B-04` 的数据说明：8 卡时嵌入通信占 25%（还算可控），128 卡时占 51%（已成主导）。**同一个优化在不同规模下价值完全不同。**

这意味着：没有"最好的方案"，只有"在某个规模下最好的方案"。第 13 章会给一张按规模分档的决策表。

## 代价与边界

- **三堵墙的框架是 `A-16` 的，不是普适定律**。它成立的前提是模型确实是"大稀疏 + 小稠密"。如果模型走向深层 Transformer（第 10 章），计算墙会显著变厚，顺序可能反转。
- **"通信占大头"依赖硬件**。如果嵌入表小到能全部放进一台机器的显存（如 `B-16` 的 Pinterest 模型，2.98 亿参数），通信墙根本不存在——那时瓶颈是收敛与过拟合。
- **算例里的有效带宽 30% 是个粗糙假设**。真实值取决于访问模式、cache line 对齐、并发度。

<div class="takeaway">

**本章结论**：推荐训练的瓶颈按 IO → 内存 → 计算 的顺序迁移。在典型的大嵌入表场景里，**通信是最大的单项开销**（`A-10` 报告 ~75%，本课算例 55%）。

所以优化的正确顺序是：先确认瓶颈在哪堵墙，再针对性投入。**在算力上投资只能改善那 33%，在通信上投资能改善那 55%。**

</div>
