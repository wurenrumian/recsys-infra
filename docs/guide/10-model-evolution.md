# 10. 从 DLRM 到生成式推荐

## 本章要解决的问题

**读完这章你应该能回答**：生成式推荐到底改了什么？为什么它会让前九章的系统技术部分失效？系统需要跟着怎么变？

前九章都在"大嵌入表 + 稀疏访问"这个前提下工作。这章讨论**如果模型结构本身变了，那些前提还成立吗**。

## 先看直觉做法为什么不够

直觉：**生成式推荐就是把 LLM 那套搬到推荐**，换个模型而已，系统照旧。

这个直觉错在：它假设"换模型"只影响模型层。实际上 `C-02`（HSTU）的改动会**同时重构任务定义、模型结构、训练系统、推理算法**——`C-14`（GBA）之外，`C-02` 是 Track C 里唯一一篇四者同时改的。

更关键的是：**它把"稀疏特征"变成了"序列 token"**，这动摇了第 1 章那个"两个系统拼在一起"的前提。

## 机制拆解：HSTU 改了什么

`C-02`（HSTU）的核心：把推荐重写成 **next-token 生成任务**。

```
传统 DLRM：
  用户特征 + 物品特征 → 嵌入查表 → 特征交互 → MLP → 点击率

HSTU（生成式）：
  用户行为序列 [item_1, action_1, item_2, action_2, ...]
  → Transformer 编码
  → 预测下一个 item / 下一个 action
```

三个关键设计：

1. **非 softmax 注意力编码器**（pointwise attention），让计算可以缩放；
2. **Stochastic Length（SL）** 训练策略；
3. **M-FALCON** 推理算法（把多个候选打包成一次前向）。

效果：算力**可缩放**——这是它最大的贡献。`A-01`/`A-02`/`C-05` 讨论的 scaling law，在 HSTU 之后才真正适用于生成式推荐。

## 为什么这动摇了前九章的前提

第 1 章的核心表：

| | 嵌入表 | 稠密部分 |
|---|---|---|
| 参数占比 | >99% | <1% |
| 每步访问 | 0.002% | 100% |
| 瓶颈 | 带宽 | 算力 |

生成式推荐的模型**变"稠密"了**：

```
传统 DLRM：  10.2 TB 嵌入 + 0.12 GB 稠密
HSTU 类模型： 若干 TB 嵌入 + 数十 GB 的 Transformer 层
```

**稠密部分从 0.12 GB 涨到数十 GB**，比例从 0.0012% 涨到 1% 甚至更多。

后果有三条：

1. **计算墙变厚**。第 3 章的三堵墙里，计算墙的占比上升，通信墙的占比相对下降。**瓶颈顺序可能反转**。
2. **注意力是 O(L²)**。`C-05` 指出：Transformer 系推荐模型的注意力是 `O(L²)`（L 是用户历史长），工业场景下 L 常是 `O(100k)`，二次方直接导致"deployable 不了"。
3. **嵌入表技术栈部分失效**。`A-17` 的判断很直接：当推荐模型 LLM 化之后，"嵌入表并行"这一整个 Track A 的技术栈会失效，需要切换到大模型并行范式。

⚠️ `A-17` 只有摘要，这个判断的论证质量我无法评估。但**这个方向性判断本身**值得记——它是 Track A 的**边界标记**：告诉你在什么情况下前九章的技术不再适用。

## 业界怎么应对 O(L²)

`C-05`（ULTRA-HSTU）给了两条业界回避策略，以及它自己的第三条路：

| 策略 | 做法 | 代价 |
|---|---|---|
| ① 换 cross-attention | 只用排序候选或截断的历史做 query | 表达力下降 |
| ② 限制深度 | 只用 2–4 层注意力 | 表达力下降 |
| ③ **改注意力形状**（`C-05`） | 半局部稀疏 + 输入减半 + FP8 | 实现复杂 |

`C-05` 的立场很明确：

> 那些绕过自注意力的方案，是在用表达力换效率。我们两样都要。

它的具体手段：

- **半局部稀疏**：只对局部窗口做完整注意力；
- **输入减半**：把 item 与 action 的表示合并成一个 token（序列长度减半，注意力计算 **4×** 效率提升）；
- **FP8**：降低精度换吞吐。

有个定义必须抠清楚，否则会误读所有数字：

> **scaling efficiency = 模型性能对计算代价的线性回归拟合斜率**

所以 `C-05` 报的 5× / 21× 是**效率倍数**，不是"训练快 5 倍"。这个区分极其重要——`C-05` 自己都特意说明这个定义"让它容易被误引成快 5 倍/21 倍"。

## 生成式推荐的三种技术路线

`C-01`（综述）把路线图讲清楚了。三条主线：

| 路线 | 做法 | 代表 |
|---|---|---|
| **LLM 式** | 把推荐当成语言建模，用 item 序列 | `C-02` HSTU、`C-03` MTGR |
| **语义 ID** | 把 item 映射成离散 token（类似 BPE） | （综述覆盖，本集合无专篇） |
| **扩散式** | 把生成从自回归换成去噪 | （综述提到，本集合**未覆盖**） |

⚠️ 第三行是这批论文的**已知缺口**——扩散式推荐没有专篇解读，只在 `C-01` 的综述里被提及。

### 一个反直觉的发现：交叉特征不能丢

`C-03`（MTGR）指出：**生成式推荐不能丢交叉特征**。

这是对"纯序列化"思路的修正。MTGR 用两招把交叉特征留住：

1. **token 重排**；
2. **分组归一化**。

这个发现的价值在于：它说明**生成式不等于"只吃序列"**。工业落地时必须保留特征交互，否则效果会掉。

## 算例：模型变化后瓶颈怎么迁移

<div class="example">

**传统 DLRM**（第 3 章算过）：

| 墙 | 耗时 | 占比 |
|---|---|---|
| 计算 | 6.5 ms | 33% |
| 本地内存 | 2.3 ms | 12% |
| 跨机通信 | 10.5 ms | **55%** |

**假设换成 HSTU 类模型**，稠密部分从 0.12 GB 涨到 30 GB（250 倍）：

```
计算墙：约 6.5 ms × 250 = 1.6 s（!）
```

这显然不现实，所以实际做法是**缩小 batch 或减少序列长度**。假设减到 batch 2048：

```
计算：6.5 ms × 250 × (2048/16384) ≈ 203 ms
通信：525 MB ÷ 50 GB/s = 10.5 ms
占比：计算 95%，通信 5%
```

**瓶颈完全反转。**

</div>

⚠️ **这个算例是粗略的示意**（HSTU 的实际计算量取决于序列长度、层数、隐藏维度）。但它说明的结构性结论是对的：**模型变稠密后，计算墙会重新成为主导，前九章的通信优化收益会下降**。

这也解释了为什么 `A-17` 说"嵌入表并行的技术栈会失效"——那些技术优化的对象在模型里的占比变小了。

## 代价与边界

- **生成式推荐不是免费的**。`C-05` 的"缩小 batch"就是代价：吞吐下降。
- **`C-05` 的 5×/21× 是效率倍数**，不是训练加速比。这是本教程里**最容易被误读的数字**，请务必记住定义。
- **交叉特征不能丢**（`C-03`）。纯序列化不是最优解。
- **扩散式路线未覆盖**。这是这批论文的缺口，不要以为生成式推荐只有自回归一条路。
- **前九章不是废了**。只要模型仍是"大嵌入表 + 浅稠密层"，前九章全部适用。生成式推荐是**另一种形态**，不是替代品。

<div class="takeaway">

**本章结论**：生成式推荐把模型从"稀疏为主"推向"稀疏+稠密并重"，这会**反转第 3 章的瓶颈顺序**——计算墙变厚，通信墙相对变薄。

两条实用提醒：
1. `C-05` 的 5×/21× 是 **scaling efficiency**（性能对算力的回归斜率），不是训练加速比。
2. 生成式推荐**不能丢交叉特征**（`C-03` 的修正），纯序列化会掉效果。

</div>
