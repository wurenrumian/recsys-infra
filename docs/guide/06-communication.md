# 6. 通信解剖：all-to-all 与两种相反策略

## 本章要解决的问题

**读完这章你应该能回答**：all-to-all 到底在传什么？为什么"压缩数据"和"融合消息"是两个方向相反但都有效的策略？什么时候该用哪个？

第 3 章算过通信占 55%，这章把通信拆到字节级别。

## 先看直觉做法为什么不够

直觉：**通信慢就压缩数据**。既然要传 525 MB，压到 50 MB 不就快 10 倍？

这个思路在 `A-14` 上确实work了（压缩率 19.9×，all-to-all 快 8.6×）。但 `A-15`（FusedRec）发现了**反方向的问题**：

> 现有做法用**去重**把消息变小，反而把带宽用废了。

为什么？因为去重让消息变得**又小又碎**，每个消息的头部开销、寻址开销反而成了主导。

**所以"压缩"和"融合"是两个方向相反的策略，各自成立，且互斥。**

## 机制拆解：all-to-all 的两种病

### 病一：数据太大（A-14 的立场）

all-to-all 传的嵌入向量有**结构特征**，可以压缩。`A-14` 的三个观测：

1. 嵌入向量内部有**同质化**（homogenization）现象——很多维度值接近；
2. 同质化程度**因表而异**（所以需要表级自适应误差界）；
3. 数据常呈**高斯分布**（所以熵编码有效）。

它的方案是**双重自适应**：

```
迭代级自适应：误差界像学习率一样调度
  前期 φ₁（loss 快降）→ 误差界逐步减小，帮助快速收敛
  后期 φ₂（loss 平稳）→ 误差界恒定，保证质量
  默认用阶梯式下降（实测收益最好）

表级自适应：按同质化程度分三档误差界
  Homo Index 0~1，越同质化 → 误差界越小（不能再压）
```

效果：压缩率 **19.9×**，all-to-all 从占训练时间 **31.3% 降到 5.03%**。

### 病二：消息太碎（A-15 的立场）

`A-15` 观察到相反的问题：去重之后，每个消息变得很小，**消息数量却暴增**。

打比方：

```
去重前：1 条大消息，100 MB，传输开销 1 次
去重后：1000 条小消息，每条 0.1 MB，传输开销 1000 次
```

如果单次传输有固定开销（握手、寻址、kernel launch），碎片化会让总开销上升。

`A-15` 的方案：把**多个类别的嵌入融合成一组，一次发**。效果：**快 37.8%**。

## 关键洞察：两个假设不可能同时成立

这是本章最重要的一点，也是我为 `A-14`/`A-15` 都打「必读」的原因。

| | A-14 假设 | A-15 假设 |
|---|---|---|
| 瓶颈是什么 | 消息**太大** | 消息**太碎** |
| 该怎么做 | 压小 | 合大 |
| 有效的场景 | 单消息数据量大 | 消息条数多但单条小 |

**这两个假设不可能在同一个时刻同时成立。** 所以：

> **最优解一定在中间的某个消息尺寸。** 谁能把这个最优尺寸找出来，谁就赢了。

这是 NestPipe 这条线上**最明确的开放问题**。而且两篇自己都意识到可以叠——`A-14` 写了"先融合成合适大小的消息再压缩，两者可叠"（推断，但是合理的）。

## 算例：消息尺寸的权衡

<div class="example">

**设定**：每次迭代要传 525 MB 嵌入数据（[算例](running-example)去重后）。

**方案 A：不融合，按表分开发**

```
200 张表 → 假设 200 条消息
每条 2.6 MB
固定开销假设 0.05 ms/条（握手 + kernel launch）
总固定开销：200 × 0.05 = 10 ms
传输时间：525 MB ÷ 50 GB/s = 10.5 ms
合计：20.5 ms
```

**方案 B：全部融合成 1 条**

```
1 条消息 525 MB
固定开销：0.05 ms
传输时间：10.5 ms
合计：10.55 ms
```

**方案 C：融合 + 压缩（A-14 + A-15 叠）**

```
假设压缩 10×（保守，A-14 报 19.9×）
融合成 1 条 52.5 MB
固定开销：0.05 ms
传输时间：1.05 ms
合计：1.1 ms
```

</div>

这个算例说明：**融合和压缩可以叠加，但前提是先融合**——因为压缩小消息的收益不足以抵消固定开销。

⚠️ **0.05 ms/条的固定开销是我假设的**，实际值取决于框架和网络。但这个**结构性结论**（碎片化的固定开销在场）是确定的，`A-15` 报的 37.8% 就是它的实测体现。

## 第三种策略：改通信原语本身

除了"压"和"融"，还有一条路是**换通信模式**。

### C-06 Disaggregated Multi-Tower：把全局 all-to-all 换成机内 shuffle

`C-06` 的做法：把模型拆成多个 tower，让每个 tower 的嵌入只在自己机器内 shuffle，**避免全局 all-to-all**。

核心是"蹭数据中心的带宽层级"：

```
全局 all-to-all：走 IB，跨机，50 GB/s
机内 shuffle：  走 NVLink，900 GB/s（H100）
```

**差 18 倍。** 所以哪怕多做一些机内的数据搬运，只要能把跨机通信变成机内通信，就是净赚。

### A-03 二维并行：让 all-to-all 只在组内做

第 4 章讲过：分 G 组，组内 all-to-all。参与方少 G 倍，通信量按 1/G 下降。

### A-06 NEO：按切分维度选原语

Row-wise 用 ReduceScatter，Table/Column-wise 用 AlltoAll。**原语跟着切法走**，而不是所有地方都用同一个。

## 四种策略的对照

| 策略 | 代表 | 改动层次 | 收益 | 代价 |
|---|---|---|---|---|
| **压缩** | `A-14` | 数据表示 | all-to-all 8.6× | 有损（但误差有界）；CPU 开销 |
| **融合** | `A-15` | 消息组织 | 37.8% | 需要缓冲，增加显存 |
| **换拓扑** | `C-06` | 通信路径 | 机内 vs 跨机 18× | 模型结构要改（拆塔） |
| **缩范围** | `A-03` | 通信参与方 | 按 1/G 下降 | 内存放大 G 倍 |

**这四种策略可以叠加**，因为它们改的是不同层次。实践中也确实是组合使用的。

## 代价与边界

- **压缩是有损的，必须界定误差**。`A-14` 的核心贡献不是"能压缩"，而是"**误差界可以像学习率一样调度**"这个论证。如果无界压缩，收敛会崩——`B-02` 的对照很说明问题：允许过期阈值 s=100 时 AUC 几乎无损（79.64→79.62），s=∞ 时崩到 74.61。
- **融合受显存限制**。要把多个消息融合成一个大消息，需要先缓冲，这会占用显存。`A-15` 的 37.8% 是在它的显存预算下取得的。
- **换拓扑需要改模型**。`C-06` 的拆塔不是纯系统改动，它改变了模型结构。
- **"最优消息尺寸"仍未解决**。这是本章留下的开放问题，没有论文给出通用解。

<div class="takeaway">

**本章结论**：all-to-all 有两种相反的病——**数据太大**（用压缩解决）和**消息太碎**（用融合解决）。这两个假设互斥，所以最优解在中间的某个消息尺寸，而这个尺寸目前没人算得出来。

实践建议：**先测量你的消息尺寸分布**。如果你的消息平均 < 1 MB，先考虑融合；如果 > 100 MB，先考虑压缩。介于两者之间的，需要实验。

</div>
