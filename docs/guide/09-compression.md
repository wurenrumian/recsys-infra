# 9. 压缩的三条轴

## 本章要解决的问题

**读完这章你应该能回答**：嵌入表压缩有哪几种互不相同的思路？它们能不能叠加？"压缩比"和"加速比"为什么经常不相等？

## 先看直觉做法为什么不够

直觉：**压缩就是降精度**。fp32 改成 fp16，体积减半。

这条路（`B-10` MPE 的混合精度、`B-11` DQRM 的统一 INT4）确实有效，`B-10` 在 Criteo 上压了 **200×** 不掉精度，`B-11` 用 INT4 缩了 **8×** 且精度不降反升。

但**它不是唯一的轴**。`B-12`（AdaEmbed）点出了一个漂亮的分解：

> feature selection can be viewed as a binary case of mixed-precision embeddings

翻译过来：**"这一行要不要保留"是"这一行用几比特"的二进制特例**。

这就把压缩拆成了三条正交的轴。

## 机制拆解：三条轴

```
         一条嵌入表的压缩空间
                  │
    ┌─────────────┼─────────────┐
    │             │             │
 轴一：列（行数） 轴二：行（位宽） 轴三：表示层
    │             │             │
 留下哪些行      每行多少比特    整行怎么表示
    │             │             │
 AdaEmbed      MPE / DQRM     EL-Rec
 (剪枝)        (量化)         (张量分解)
```

| 轴 | 改什么 | 代表 | 压缩比 | 查询代价 | 精度 |
|---|---|---|---|---|---|
| **行数** | 删掉不重要的行 | `B-12` AdaEmbed | 表大小降到 35–60% | 无（少查） | 丢信息 |
| **位宽** | 每行用几 bit | `B-10` MPE（混合）、`B-11` DQRM（统一 INT4） | 200× / 8× | 解码 | 有损（DQRM 反升） |
| **表示层** | 整行换成核矩阵收缩 | `B-07` EL-Rec（TT 分解） | 单卡快 3× | **每次查询多一次张量收缩** | **低秩近似，不可逆** |

### 轴三为什么不一样

这是最容易搞混的一轴。`B-07`（EL-Rec）的论文页说得很清楚：

> 那三篇（CAFE+ / MPE / DQRM）都压**行的数量**或**精度**，压缩比虽高（1 万倍、200 倍、8 倍），但都是**逐行存储**的变体——行还在，只是变少或变短。EL-Rec 压的是**表的数学表示**：一整行被表示成多个核矩阵的收缩结果，**没有"行"这个概念了**。

所以：

- 轴一、轴二：**行还在**，只是变少 / 变短；
- 轴三：**行这个概念消失了**，查询变成一次张量收缩。

代价不同。轴一、轴二在查询时几乎无额外计算；轴三**每次查询多一次收缩**——这是它会引入额外计算、进而引出 `A-13`（EcoRec）去消除冗余计算的原因。

### 三条轴能叠吗

**能，但收益不是简单相乘。**

`B-12` 明确说了三者正交可叠：

> 三者**正交可叠**：AdaEmbed 决定留下哪些行，MPE 决定留下的每行用几 bit，CAFE+ 决定哪些行独享。

`B-03`（CAFE+）是第四种视角：它压的是**行之间的共享关系**（热特征独享、冷特征哈希共享），一万倍压缩下 AUC 还涨了 3.94%。

⚠️ **但"可叠"不等于"无损"**。三条轴都会损失信息，其中**表示层（TT 分解）的损失是结构性的、不可逆**——秩的选择直接决定精度上限。`B-07` 的参照数据是 TT-Rec 在 Kaggle 上压 4–221×、精度掉 0.03%–0.3%；在"不能掉 0.1% AUC"的场景（见第 7 章 `B-09` 的约束）下，221× 不可用。

## 一个重要的分歧：统一精度 vs 混合精度

`B-10`（MPE）和 `B-11`（DQRM）看起来都是"降精度"，但对**量化的副作用**判断完全不同：

| | `B-10` MPE | `B-11` DQRM |
|---|---|---|
| 做法 | 按频率分组，每组搜一个位宽 | 全部统一 INT4 |
| 对量化的理解 | 量化 = **有损压缩**，要小心控制损失 | 量化 = **强正则**，损失本身有益 |
| 精度结果 | 200× 压缩**不掉精度** | 8× 压缩，精度**不降反升** |
| 多 epoch 过拟合 | 未讨论 | **顺带治好了** |

`B-10` 自己在这点上说得很干脆：

> 这两篇对着读能看出一件事：**统一低精度有正则收益，混合精度没有这个副作用也没有这部分收益。**

`B-11` 的证据是 Table 2 的单调趋势：INT16 → INT8 → INT4 精度逐级上升。

**这是一个真正有用的洞察**：如果你有多 epoch 过拟合问题，统一低精度可能是"一箭双雕"；如果你的精度已经吃紧，混合精度更安全。

## 算例：三条轴叠加的效果

<div class="example">

**基线**：[算例](running-example) 10.2 TB 嵌入表。

**只叠轴二（量化）**：

```
假设全部 INT8（4 倍压缩）
10.2 TB ÷ 4 = 2.55 TB
→ 仍需 32 张卡（单卡 80 GB）
```

**叠轴一 + 轴二**：

```
AdaEmbed 剪掉 50% 的行（保守，论文报 35–60% 表大小）
2.55 TB × 0.5 = 1.28 TB
→ 需 16 张卡
```

**再叠轴三（EL-Rec）**：

```
TT 分解假设再压 4×（论文报单卡快 3×，压缩比未直接给）
1.28 TB ÷ 4 = 320 GB
→ 需 4 张卡
```

**但要算上索引/优化器状态**：

```
优化器状态也要相应压缩
否则 320 GB 参数 + 无法压缩的优化器状态 → 仍然是瓶颈
```

</div>

⚠️ **上面的压缩倍数大部分是我的假设**（只有 AdaEmbed 的 35–60% 是论文数字）。这个算例要说明的是**结构**：三条轴叠加确实能把 10.2 TB 降到几百 GB，但**每一条轴都引入新的代价**（剪枝丢信息、量化要解码、TT 要额外计算）。

## 为什么"压缩比"≠"加速比"

这是本章最该记住的一点。

`B-11`（DQRM）给了一个诚实的负面结果：

> 因为 PyTorch 的 sparse tensor all-reduce **不支持低精度算术**，加上稀疏张量合并（coalescing）的开销，**实际每迭代延迟反而从 61ms 涨到 110ms**。

作者原话："achieving speedup from communication reduction remains difficult"，并把它归为超出本文范围。

**这个自我限制极其有价值**——很多论文会把"通信量降低"包装成"速度提升"，而它诚实地承认了没兑现。

`A-16` 的 MBU 数据也印证：

| 算子 | 优化后 MBU |
|---|---|
| `gather` | 47.50% |
| `bucketize` | **0.88%** |

即使压缩了数据，**如果算子本身的带宽效率低，压缩出来的收益会被低效吃掉**。

所以：

> **压缩比 ↓ 是必要条件，不是充分条件。** 要看压缩/解压的开销是否吃掉了带宽节省。

判断方法：算"压缩 + 传输 + 解压"的总时间，而不是只看传输时间。

## 代价与边界

- **剪枝（轴一）需要在线维护**。`B-12` 是训练中在线剪枝，不是一次性离线操作。这意味着它要跟训练流程深度耦合。
- **量化的正则收益不普适**。DQRM 的"精度不降反升"是在它的设定下（INT4 + 特定模型 + Criteo 类数据）。换个场景可能就没这个福利。
- **张量分解改变查询语义**。EL-Rec 之后不能直接 `lookup`，必须做收缩。这对系统实现的要求高得多（`A-13` 花整篇论文去消除它引入的冗余计算）。
- **压缩与稀疏优化器冲突**。低精度算术在稀疏通信上支持不好（DQRM 的 61→110ms 就是这个问题）。
- **200× 与 8× 的对比不可比**。`B-10` 和 `B-11` 的基线、数据集、评测方式都不同，这两个数字不能直接比较优劣。

<div class="takeaway">

**本章结论**：嵌入表压缩有**三条正交的轴**——行数（剪枝）、位宽（量化）、表示层（张量分解）。它们能叠加，但每一轴都有自己的代价。

最重要的判据：**压缩比 ≠ 加速比**。`B-11` 的诚实数据是 61ms → 110ms（压缩了但更慢）。评估任何压缩方案时，要算"压缩 + 传输 + 解压"的总时间。

</div>
