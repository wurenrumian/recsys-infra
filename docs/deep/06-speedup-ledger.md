# 深潜 6. 加速比的账本：把 X× 拆成可核查的项

<div class="deep-anchor">

**对应教程** [第 12 章](../guide/12-how-to-read)给了"把加速比拆开"这一步，[第 13 章](../guide/13-checklist)给了"压缩比不等于加速比"这个坑；这里给拆法与核对的具体算法。

</div>

## 本篇要算的问题

第 12 章的三问——基线是什么、局部还是端到端、是否多来源叠加——已经够判断一篇论文可不可信。但它们还停在"问"的层面。

这一篇把"问"变成"算"，回答三个问题：

1. 看到"端到端 S×"，能反推出什么？反过来，看到"局部 s× 与占比 f"，能预测出多少端到端？
2. 预测值与论文自报值对不上时，差额说明什么？哪几种差额可以由多个来源解释？
3. 哪些论文的数字根本不该用 Amdahl 核算，为什么强行核算会得出荒谬结论？

## 先给结论

- `S = 1/((1−f) + f/s)`，反解给出一个下限：声称端到端 `S×`，就至少有 `f ≥ 1 − 1/S` 的时间被优化了。这条下限比正向公式更有用，因为它只需要一个数字。
- `A-14` 是唯一一篇能被完整核算的：`31.3%` 与 `8.6×` 推出 `1.382×`，实测 `1.38×`；而且它自报的 `5.03%` 不是独立测量，是由前两个数导出的——四个数字只有两个自由参数，"自洽"本身就是可核算的标志。
- 超出 Amdahl 天花板的结果一定有多来源，或者 f 与 S 不同源。`A-10` 的 `5.6×` 对 `75%` 的占比是 40% 的超出——三种解释在论文页里各有依据，但没有一项能单独补齐，所以它**不可核算**。
- 不可核算不代表数字假。它只说明这个数字不能被外部复现者验证，只能被信任或被怀疑。

## 符号与模型

| 符号 | 含义 |
|---|---|
| `f` | 被优化部分占总时间的比例（旧时间轴上的占比） |
| `s` | 该部分的局部加速比（`局部旧时间 / 局部新时间`） |
| `S` | 端到端加速比（`总旧时间 / 总新时间`） |
| `1−f` | 未优化部分的占比 |

三个量只有一个自由度关系：

```
S = 1 / ((1−f) + f/s)
```

两个端点先记住：`f=0 → S=1`（优化没碰到瓶颈）；`s→∞ → S=1/(1−f)`（优化做到底也只有这么多）。第二个端点就是"天花板"，它只由占比决定，与工程水平无关。

## 推导

### Amdahl 与它的反解

正向公式的用法大家都知道，反解才是真正好用的那半：

```
1/S = 1 − f + f/s = 1 − f(1 − 1/s)
⇒  f = (1 − 1/S) / (1 − 1/s)
⇒  s ≫ 1 时:   f ≥ 1 − 1/S
```

不等式方向值得强调：它给的是**下限**。看到"端到端 2×"，至少有一半的时间被优化了；端到端 1.2×，至少 17%。这个下限不依赖 s 的取值，所以看到摘要里只有端到端数字时也能用。

| 自报端到端 S | 至少被优化的占比 f |
|---|---|
| 1.10× | 9% |
| 1.20× | 17% |
| 1.38× | 28% |
| 2.00× | 50% |
| 5.00× | 80% |
| 10.0× | 90% |

反向的用法更有杀伤力：`S` 越大，`f` 的下限越接近 1。声称 10×，等于声称 90% 的时间都在被优化的那一块里——这类声明要么是真的重构了整个系统，要么是把分母换了。

再看固定 f 时 s 的边际收益。取 `f=0.313`：

```
s=2    → 1.24×
s=4    → 1.33×
s=8.6  → 1.38×     ← A-14 的位置
s=100  → 1.44×
s=∞    → 1.456×    ← 天花板
```

从 2× 提到 100×，端到端只从 1.24 挪到 1.44。而 `8.6×` 已经拿到天花板的 95%。这条曲线的意思是：f 是架构级变量，s 是工程级变量。在固定架构上继续磨局部，回报会迅速归零；要让端到端真正上一个台阶，只能改 f——把工作搬到别的段、或者干脆消掉那一段。凡是"把某段的 s 又提高了 30%"的论文，都该先看一眼 f。

### A-14：一次可核算的验证

`A-14` 给了四个数字，先看它们之间的约束关系：

```
f = 31.3%     （all-to-all 占总训练时间）
s = 8.6×      （all-to-all 局部加速）
S = 1.38×     （端到端，Criteo Terabyte）
压缩后 all-to-all 占比 = 5.03%
```

算一遍：

```
S = 1 / (0.687 + 0.313/8.6)
  = 1 / (0.687 + 0.03640)
  = 1 / 0.72340
  = 1.382
```

实测 1.38。差 0.1%。

接着核对第四个数字。压缩后的占比应该是"新的 all-to-all 时间 / 新的总时间"：

```
新的 all-to-all 时间占比 = (0.313/8.6) / (0.687 + 0.313/8.6)
                        = 0.03640 / 0.72340
                        = 5.03%
```

**5.03% 不是一次独立测量，是由前两个数导出的。** 这一点很重要：它意味着这四个数字只有两个自由参数（`f` 与 `s`），后两个是算出来的；内部自洽不能证明测量正确，只能证明"没有隐藏项"。

这个验证同时说明了两件事：

- 占比口径一致。`31.3%` 与 `8.6×` 必须来自同一个系统、同一组测量。如果 31.3% 是在别的配置上量的，1.382 就不会等于 1.38。
- codec 开销被隐藏了。假设压/解压额外花掉总时间的 3%，结果变成 `1/(0.7234+0.03) = 1.33`，与 1.38 对不上。所以 `A-14` 的压缩开销实际小于约 1%——这与它"把压缩和解压与通信重叠"的设计一致。

Kaggle 那一组可以当交叉验证：

```
实测 S = 1.30×，s = 6.22×
反解 f = (1 − 1/1.30) / (1 − 1/6.22) = 0.2308 / 0.8392 ≈ 27.5%
```

反解出的 `f` 是 27.5%，比 Terabyte 的 31.3% 略低。这是个合理方向：Kaggle 的表更小、通信占比本来就更低。**反解 f 比正向算 S 更有诊断力**——它把"两个数据集上的同一个 8.6×"翻译成"两个数据集的瓶颈占比不同"。

### A-10：超过天花板 40% 的三种解释

```
f = 75%       （嵌入访问 + 模型同步占迭代时间，摘要原话）
天花板 = 1/(1−0.75) = 4×
实测  = 5.6×
超出  = 5.6/4 = 1.4，即 40%
```

Amdahl 说 4× 是上限，实测给 5.6×。这不可能是"Amdahl 错了"，只可能是三个前提之一被打破。

解释一，f 与 S 不同源：`75%` 是作者在自建 profiling 上量出来的；`5.6×` 的分母是 FB-Research 系统（论文报 5.6×/4.2× 分别对应 DLRM 与 W&D）。如果 FB-Research 系统的瓶颈分布与 profiling 那套不同，`f` 就不能代进那个 `S`。论文页同时给了 `3.7×`（vs TorchRec 的迭代时间）与 `2.3×`（vs HET），三个数字三个分母——这本身就是"不同源"的证据。

解释二，多来源叠加：`5.6×` 至少含四项：解耦架构（省跨机同步）、LRPP（关键路径字节降约 70%）、延迟同步（缓存同步时间最多再降 44%）、故障恢复（13 分钟 → 60 秒）。Amdahl 一次只能核算一个来源。

解释三，分母含停机时间。这是最常被拿来"补齐差额"的一项，但可以算一下它够不够：

```
若训练 24 小时、中途失败 2 次：
  旧: 2 × 13 分钟 = 26 分钟
  新: 2 × 1 分钟  =  2 分钟
  省下 24 分钟，占 24 小时的 1.7%      ← 不够
若每 30 分钟失败一次（大集群常态）：
  24 小时 48 次 × 12 分钟 ≈ 9.6 小时   ← 足够，但 MTBF 论文没给
```

所以"故障恢复解释差额"这句话，成立与否完全取决于故障频率。论文页没给 MTBF，因此 `5.6×` 与 `75%` 之间的 40% 差额**不能用任何一个已知项单独补齐**。

结论：`A-10` 不可核算。这不影响它的价值（论文页里 W&D 只 1.2×、DeepFM 3.7×+ 那组对照，比 5.6× 更有信息量），但 `5.6×` 这个数字不能被外部复现者验证。

### 三个"不可核算"的样本：A-15 / A-16 / B-11

`A-15` 的 `37.8%` 是吞吐提升，不是加速比，而且摘要没有任何分项：没有消息尺寸从多少到多少，没有通信占总时间多少。它优化的是 all-to-all 内部的**消息尺寸效率**，是整条链上极局部的一环，所以 37.8% 在数值上偏小是合理的——局部 f 小。为什么说它可能含金量最高：生产环境、质量无损、基线是已优化的工业实现，而且它推翻了一个通行做法（去重会让消息变小变碎）。但这三条都是定性判断，⚠️ 基线匿名（只写 "SOTA industry implementation"），所以含金量也无法量化。**"最小加速比"和"最可信"是两件事，这里同时成立，但不能互相替代。**

`A-16` 的口径要单独说清，因为它引入了新指标：

```
MBU = 实测带宽 / 峰值带宽       （算子级，H20 上测）
gather 47.50%   scatter 58.00%   bucketize 0.88%
```

MBU 不是时间占比，不能代进 Amdahl。它甚至不是端到端指标——`47.50%` 说的是 gather 这一个算子跑到了峰值带宽的 47.5%，与整体加速比之间还差着"gather 占总时间多少"这一层。

那为什么不用 MFU？因为稀疏算子的算术强度低于 1（读一字节做不到一次浮点运算），落在 roofline 图最左边，FLOPS 利用率趋近 0——这个 0 与优化好坏无关，是问题形状决定的。所以"稀疏算子的 MFU 没有解释力"不是精度问题，是坐标系选错了。⚠️ `A-16` 没有报任何 MFU 数值，它给的是一张 MBU 表和这个论证；引用时不要写成"A-16 的 MFU 是 x%"。

`B-11` 是整本教程里最干净的反例，值得逐层拆：

```
通信量（PyTorch specified sparsity）:  2.161 GB → 2.010 MB   ≈ 1075×
再加 INT8 梯度量化:                    2.010 MB → 0.509 MB   ≈  4×
合计压缩比:                                                  ≈ 4246×
每迭代延迟:                            61 ms → 110 ms        变慢 1.80×
```

**压缩比 4246×，加速比 0.56×。** 两者之间没有乘法关系。

拆开看：省下的传输量是 2.16 GB 里的绝大部分，而延迟净增 49 ms——这 49 ms 就是 codec 与稀疏张量合并（coalescing）的开销。论文自己把原因写得很清楚：PyTorch 的 sparse tensor all-reduce 不支持低精度算术，所以降下来的通信量转化不成时间。

还有一层必须写清，否则会把功劳记错账：**2.161 GB → 2.010 MB 是 sparse 支持带来的，不是量化**，而且是无损的。量化只贡献了后面的 4×。把 1075× 记到"INT4 量化"头上，就把整篇论文的因果链讲反了。

## 算例

把 `A-14` 的刀拿到[贯穿算例](../guide/running-example)上来，看同一把刀在不同占比下值多少。

<div class="example">

设 51 ms 迭代预算里跨机通信占 55%（这个比例取自[第 3 章](../guide/03-bandwidth-wall)的算例：计算 33%、本地内存 12%、跨机通信 55%），局部加速 8.6×：

```
通信时间:      51 ms × 0.55 = 28.1 ms
压缩后:        28.1 / 8.6    =  3.3 ms
新迭代时间:    51 − 28.1 + 3.3 = 26.2 ms
端到端:        51 / 26.2 ≈ 1.94×
吞吐:          16,384 / 0.0262 s ≈ 625K 样本/秒（原 320K）
```

同一把 8.6× 的刀，扫一遍 f：

| f | 天花板 `1/(1−f)` | `s=8.6` 时实际 S | 拿到天花板的 |
|---|---|---|---|
| 0.20 | 1.25× | 1.22× | 97% |
| 0.313 | 1.46× | 1.38× | 95% |
| 0.55 | 2.22× | 1.94× | 87% |
| 0.75 | 4.00× | 2.97× | 74% |
| 0.90 | 10.0× | 4.89× | 49% |

两件事跳出来：f 越小，8.6× 越接近天花板（因为天花板本来就低，容易撞顶）；f 越大，同样的 s 越吃不满天。所以**"局部加速比很高"和"端到端收益很大"是两个几乎独立的评价**，前者看 s，后者看 f。

</div>

反过来用这张表做判断：如果某篇论文报端到端 1.2×，而它优化的是"占 55% 的通信"，那就对不上（应该接近 1.94×）——要么 f 没那么大，要么它其实没优化多少。

## 代价与边界

先放口径清单，至少五篇，能核算的写能，不能的写不能：

| 论文 | f | s | 端到端 | 可核算？ |
|---|---|---|---|---|
| `A-14` | 31.3% | 8.6× | 1.38× | 可：算出 1.382，且 5.03% 由前两者导出 |
| `A-10` | 75% | — | 5.6×（vs FB-Research）/ 3.7×（vs TorchRec，迭代时间） | 不可：超出 4× 天花板 40%，f 与 S 不同源 |
| `A-15` | 未给 | — | 37.8% 吞吐 | 不可：摘要无任何分项 |
| `A-16` | 未给 | — | "up to 2×" | 不可：基线未定义，MBU 是算子级而非时间占比 |
| `B-11` | 未给 | 通信量 1075× 再 4× | 无（延迟 61→110 ms） | 不可，且方向为负 |
| `C-11` | — | — | 迭代数 −81.7%；GPU 小时 −54.3% | 部分：81.7% 与 slowdown 1.27×/4.24× 自洽，但不是时间口径 |
| `A-13` | — | — | 3.1× vs EL-Rec | 不可：基线是上一代同路线系统 |

四种"不可核算"要分清：

- 缺分项（`A-15`、`A-16`）。只有一个端到端数字，没有 f，没有 s。这时只能用反解给下限：声称 2× 就是声称 f ≥ 50%。
- f 与 S 不同源（`A-10`、`A-13`）。占比是一个系统上量的、加速是另一个基线上量的。这类最常见，也最容易被误算。
- 口径不是时间（`C-11` 的迭代数、`B-11` 的字节数、`A-16` 的带宽利用率）。换成时间要再过一层换算，而那一层常常没有。
- 方向为负（`B-11`）。压缩比涨、时间也涨。这类论文反而最值得读，因为它把不肯兑现的部分写出来了。

再看边界：Amdahl 假设被优化的部分与其余部分是串行相加的。流水线、重叠、异步都能打破这个假设（`A-14` 的 codec 开销被重叠隐藏，就是"相加"不成立的一个小例子）。所以 Amdahl 给你的不是精确预言，是**量级判断**：它能把"5.6×"和"1.38×"这类差 4 倍的声明分出真假，却不会告诉你 1.38 还是 1.42。

最后是那张清单。三问还是第 12 章那三问，但每一问后面都跟一个可执行的核对：

```
问 1  基线是什么？
      → 有没有点名？匿名的基线（"SOTA industry implementation"）无法核算。
      → 同一篇里的多个加速比是不是同一个分母？（A-10: 5.6 / 3.7 / 2.3）

问 2  局部还是端到端？
      → 若能拿到 f 与 s，代进 1/((1−f)+f/s)，对不上就先怀疑口径。
      → 若只有端到端，用 f ≥ 1 − 1/S 反推，看这个下限是否可信。

问 3  多来源叠加吗？
      → 数一数论文报了几个机制，各自有没有单独数字。
      → 若某机制的独立收益（如 13 分钟→60 秒）不足以补齐差额，
        差额就还在别处——或者它根本不该被核算。
```

这三问对接的是第 12 章第三步（把加速比拆开）与第 13 章的坑 2（以为压缩比等于加速比）。第 13 章那张决策表是选型用的，这三问是验收用的：先按表选出方案，再用这三问检查它的数字。

<div class="takeaway">

**本篇结论**：`S = 1/((1−f)+f/s)`，反解 `f ≥ 1 − 1/S` 是看到一个端到端数字时最省力的核对。

`A-14` 能被完整核算（1.382 vs 1.38），`A-10` 不能（超过天花板 40%，f 与 S 不同源），`B-11` 是压缩比与加速比反向的最干净的样本（4246× vs 0.56×）。

f 是架构级变量，s 是工程级变量：在固定架构上继续磨局部，8.6× 已经拿到天花板的 95%，剩下 5% 要改架构才能拿。

</div>

<div class="cite">

本篇引用：`A-14`（31.3%、8.6×、1.38×、5.03%、Kaggle 6.22×/1.30×）、`A-10`（75%、5.6×、3.7×、2.3×、13 分钟→60 秒、W&D 1.2×）、`A-15`（37.8%、质量无损、基线匿名）、`A-16`（MBU gather 47.50% / scatter 58.00% / bucketize 0.88%、带宽 roofline、"up to 2×"）、`B-11`（2.161 GB→2.010 MB 是 sparse 支持、0.509 MB、61 ms→110 ms）、`C-11`（81.7%、1.27×/4.24×、54.3% GPU 小时）、`A-13`（3.1× vs EL-Rec）。标准结果：Amdahl 定律与它的反解。⚠️ `A-10` 的 MTBF、`A-15` 的基线名称、`A-16` 的 "up to 2×" 基线定义均待核实。
