# 深潜 6. 加速比的账本：把 X× 拆成可核查的项

<div class="deep-anchor">

**对应教程** [第 12 章](../guide/12-how-to-read)给了"把加速比拆开"这一步，[第 13 章](../guide/13-checklist)给了"压缩比不等于加速比"这个坑；这里给拆法与核对的具体算法。

</div>

## 一句话版本

论文摘要里的"端到端快 1.38 倍"，能不能被局外人复算一遍，是这篇要回答的问题。

工具只有一条公式：把一个加速比拆成两件事，被优化的那一段占原时间多少，那一段自己快了多少倍。知道这两个数，端到端该是多少就定死了；算出来和论文自报的一比，差额本身就是信息。
把逐项核对的结果摆在一起，就是一张收支表：哪些数字能对上，哪些对不上，对不上的原因归到哪一类。
全篇的答案是分开的：`A-14` 能核到小数点后一位，`A-10` 核不了。而"核不了"是一个可以下判断的结论，它说的是这个数字无法被外部验证，不是这个数字一定错。

## 这篇的地图

第 12 章的三问已经够判断一篇论文可不可信，但它们停在"问"的层面。这一篇把三问变成能算的式子，全篇分四块，加一个算例。

1. **三个量，一个公式** —— 把一次优化的时间切成两段，写出端到端加速比的表达式，以及它碰不到的那个上限。
2. **反过来解更好用** —— 只拿到一个端到端数字时，怎么反推出占比的下限，以及这条下限能读出什么。
3. **一个能核到小数点后的样本** —— `A-14` 的四个数字为什么只有两个自由参数。
4. **超天花板与算不了的账** —— `A-10` 那 40% 的差额，以及 `A-15`、`A-16`、`B-11` 各自卡在哪一步。

这四块是一条链。第 1 块立公式；第 2 块把公式反过来用，因为多数论文只给一个数字；第 3 块找一个条件齐全的样本，把正算与反解都走通；第 4 块处理条件不齐、甚至结果越过上限的情形。最后的算例把同一把刀换到贯穿算例的占比上，看它在不同占比下值多少。

| 概念 | 一句话 |
|---|---|
| 占比 `f` | 被优化的那一段占原来总时间的比例 |
| 未优化部分 `1−f` | 没被碰到的那部分，它的时间原样留在新时间轴上 |
| 局部加速比 `s` | 那一段自己快了多少倍，局部旧时间 ÷ 局部新时间 |
| 端到端加速比 `S` | 整个训练步快了多少倍，总旧时间 ÷ 总新时间 |
| 天花板 | `s` 做到无限大时 `S` 的上限，等于 `1/(1−f)` |
| 自由参数 | 一组数字里真正独立的那几个，其余由它们导出 |
| 可核算 | 用公式能复算出论文自报值，且各项来自同一个系统、同一组测量 |

术语到此交代完毕，后面各块直接用这三个量说话。

## 第一块 · 三个量，一个公式

这块要回答的是：一次优化的收益，由哪几个数决定。

任何一次优化都只作用在迭代时间的一段上，剩下的那段没被碰到。把旧的一次迭代总时间记作一份，被优化的那一段占其中的比例就是 `f`；这一段在新方案里比原来快了多少倍，就是 `s`。
两段加起来是新的总时间，用旧总时间去除它，得到端到端加速比 `S`。

三个量里只有两个是自由的：给定 `f` 与 `s`，`S` 由公式定死，没有第三个自由度。后面所有的核对，都长在这条约束上。

把旧总时间记作 1。没有被碰到的部分照样要花 `1−f`；被优化的部分从 `f` 缩到 `f/s`。两者相加就是新的总时间：

```
S = 1 / ((1−f) + f/s)
```

分母有两项：前一项是没被优化的部分，原样保留；后一项是被优化的部分，被 `s` 除过。分子是旧时间 1，所以 `S` 是"原本要花多久 ÷ 现在要花多久"。
分母越小，`S` 越大。这解释了为什么只优化一小段时端到端几乎不动：大段的时间还留在分母里。

这条公式就是阿姆达尔定律（Amdahl's law）：整体加速比由未优化部分的固定耗时和优化部分的收益共同决定。
两个端点可以当锚点用：

- `f=0 → S=1`：优化没碰到瓶颈，端到端一点不动。
- `s→∞ → S=1/(1−f)`：优化做到底也只有这么多。这个上限叫天花板，它只由占比决定，与工程水平无关。

公式立起来了，但它要三个变量，而论文通常只给一个。下一块把公式反过来解，看一个数字能撑起多少判断。

## 第二块 · 反过来解更好用

这块要回答的是：摘要里只写"端到端 2×"、没有任何分项时，还能核对出什么。

正着用公式需要 `f` 和 `s` 两个输入，论文极少同时给。反过来解只需要 `S` 一个输入，代价是答案从等式变成一个下限。
下限说的是：要让端到端达到 `S`，被优化的部分至少占了原时间的多少。

### 为什么下限够用

从公式出发，两边取倒数：

```
1/S = 1 − f + f/s = 1 − f(1 − 1/s)
⇒  f = (1 − 1/S) / (1 − 1/s)
⇒  s ≫ 1 时:   f ≥ 1 − 1/S
```

最后一步的依据是 `1 − 1/s` 小于 1：分母比 1 小，除出来的 `f` 就一定不小于 `1 − 1/S`。
这一步只需要"局部加速比很大"这个前提，不需要它的具体数值，所以手上只有一个端到端数字时也能代进去。

按这个不等式，端到端数字可以直接翻译成占比下限：

| 自报端到端 S | 至少被优化的占比 f |
|---|---|
| 1.10× | 9% |
| 1.20× | 17% |
| 1.38× | 28% |
| 2.00× | 50% |
| 5.00× | 80% |
| 10.0× | 90% |

这张表怎么读：看到"端到端 2×"，等于作者在说"至少一半的时间在被优化的那一块里"；看到 1.2×，就是至少 17%。
`S` 越大，`f` 的下限越贴近 1。声称 10×，等于声称 90% 的时间都在那一块里。这类声明要么是真的重构了整个系统，要么是把分母换了。

### 固定占比，往上推局部加速比

反过来看另一半：占比不变，把局部加速比一直往上推，端到端能涨多少。取 `f = 0.313`（这是 `A-14` 的占比，下一块会用到）：

```
s=2    → 1.24×
s=4    → 1.33×
s=8.6  → 1.38×     ← A-14 的位置
s=100  → 1.44×
s=∞    → 1.456×    ← 天花板
```

从 2× 提到 100×，端到端只从 1.24 挪到 1.44；而 `8.6×` 已经拿到天花板的 95%。
这条曲线的意思是 `f` 与 `s` 分属两个层级：`f` 由架构决定，`s` 由工程实现决定。在固定架构上继续磨局部，回报会迅速归零；要让端到端上一个台阶，只能改 `f`，也就是把工作搬到别的段上，或者把那段消掉。凡是"把某段的 `s` 又提高了 30%"的论文，都该先看一眼它的 `f`。

反解给了一个数字就能算的下限，代价是它只能确认"至少"，不能确认"正好"。要确认正好，得找一篇把四个数字都摊开的论文。

## 第三块 · 一个能核到小数点后的样本

这块要回答的是：什么样的论文数字，能被外部复算到小数点后一位。

`A-14` 在摘要里给了四个数字，它们之间存在约束关系，可以互相验算：

```
f = 31.3%     （all-to-all 占总训练时间）
s = 8.6×      （all-to-all 局部加速）
S = 1.38×     （端到端，Criteo Terabyte）
压缩后 all-to-all 占比 = 5.03%
```

可核算的意思不是"看起来合理"，而是"用其中几个数能推出另一个数"。这篇的四项正好构成这种关系。

### 代入一遍

把 `f` 与 `s` 代进第 1 块的公式：

```
S = 1 / (0.687 + 0.313/8.6)
  = 1 / (0.687 + 0.03640)
  = 1 / 0.72340
  = 1.382
```

实测 1.38，差 0.1%。

再核对第四个数字。压缩后的占比是"新的 all-to-all 时间 ÷ 新的总时间"：

```
新的 all-to-all 时间占比 = (0.313/8.6) / (0.687 + 0.313/8.6)
                        = 0.03640 / 0.72340
                        = 5.03%
```

`5.03%` 不是一次独立测量，是由前两个数导出的。这一点决定了这四个数字的分量：真正独立的只有两个自由参数，即 `f` 与 `s`，后两个都是算出来的。
内部自洽不能证明测量正确，它能证明的是"没有隐藏项"。

### 这个验证顺带说明两件事

占比口径一致。`31.3%` 与 `8.6×` 必须来自同一个系统、同一组测量。如果 31.3% 是在别的配置上量的，1.382 就不会等于 1.38。

codec 的开销被藏在了这个等式外面。假设压解压额外花掉总时间的 3%，结果变成 `1/(0.7234+0.03) = 1.33`，与 1.38 对不上。所以 `A-14` 的压缩开销实际小于约 1%，这与它"把压缩和解压与通信重叠"的设计一致。

### Kaggle 那一组可以当交叉验证

```
实测 S = 1.30×，s = 6.22×
反解 f = (1 − 1/1.30) / (1 − 1/6.22) = 0.2308 / 0.8392 ≈ 27.5%
```

反解出的 `f` 是 27.5%，比 Terabyte 的 31.3% 略低。这是个合理方向：Kaggle 的表更小，通信占比本来就该更低。
反解 `f` 比正向算 `S` 更有诊断力：它把"端到端 1.38×、局部 8.6×"和"端到端 1.30×、局部 6.22×"这两组数，翻译成两个数据集的瓶颈占比不同。

这个样本能核，是因为四个数字互相约束，两个自由参数之外没藏东西。下一块处理约束不成立的情形。

## 第四块 · 超天花板与算不了的账

这块要回答的是：当结果越过上限，或者论文根本没给分项时，结论该怎么下。

### 越过天花板的那一篇

`A-10` 的数字摆出来是这样的：

```
f = 75%       （嵌入访问 + 模型同步占迭代时间，摘要原话）
天花板 = 1/(1−0.75) = 4×
实测  = 5.6×
超出  = 5.6/4 = 1.4，即 40%
```

公式说 4× 是上限，实测报 5.6×。差额只能来自前提被打破，公式本身没有问题。具体是哪一条，有三种解释，论文页里各有依据。

解释一，`f` 与 `S` 不同源。`75%` 是作者在自建 profiling 上量出来的；`5.6×` 的分母是 FB-Research 系统（论文报 5.6×/4.2× 分别对应 DLRM 与 W&D）。如果 FB-Research 系统的瓶颈分布与 profiling 那套不同，`f` 就不能代进那个 `S`。论文页同时给了 `3.7×`（vs TorchRec 的迭代时间）与 `2.3×`（vs HET），三个数字三个分母，这本身就是不同源的证据。

解释二，多来源叠加。`5.6×` 至少含四项：解耦架构（省跨机同步）、LRPP（关键路径字节降约 70%）、延迟同步（缓存同步时间最多再降 44%）、故障恢复（13 分钟 → 60 秒）。Amdahl 一次只能核算一个来源。

解释三，分母含停机时间。这是最常被拿来补齐差额的一项，但可以算一下它够不够：

```
若训练 24 小时、中途失败 2 次：
  旧: 2 × 13 分钟 = 26 分钟
  新: 2 × 1 分钟  =  2 分钟
  省下 24 分钟，占 24 小时的 1.7%      ← 不够
若每 30 分钟失败一次（大集群常态）：
  24 小时 48 次 × 12 分钟 ≈ 9.6 小时   ← 足够，但 MTBF 论文没给
```

所以"故障恢复解释差额"这句话成立与否，完全取决于故障频率。论文页没给 MTBF，因此 `5.6×` 与 `75%` 之间的 40% 差额，不能用任何一个已知项单独补齐。

`A-10` 因此不可核算。这不影响它的价值，论文页里 W&D 只 1.2×、DeepFM 3.7×+ 那组对照，比 5.6× 更有信息量；但 `5.6×` 这个数字本身不能被外部复现者验证。

### 另外三篇，三种卡法

`A-15` 的 `37.8%` 是吞吐提升，不是加速比，而且摘要没有任何分项：没有消息尺寸从多少到多少，也没有通信占总时间多少。它优化的是 all-to-all 内部的消息尺寸效率，是整条链上极局部的一环，所以 37.8% 在数值上偏小是合理的，因为局部 `f` 小。说它可能含金量最高，理由有三条：生产环境、质量无损、基线是已优化的工业实现，而且它推翻了一个通行做法（去重会让消息变小变碎）。但这三条都是定性判断；⚠️ 基线匿名，只写 "SOTA industry implementation"，所以含金量也无法量化。"最小加速比"和"最可信"是两件事，这里同时成立，但不能互相替代。

`A-16` 的口径要单独说清，因为它引入了新指标：

```
MBU = 实测带宽 / 峰值带宽       （算子级，H20 上测）
gather 47.50%   scatter 58.00%   bucketize 0.88%
```

MBU 不是时间占比，不能代进 Amdahl。它甚至不是端到端指标：`47.50%` 说的是 gather 这一个算子跑到了峰值带宽的 47.5%，与整体加速比之间还隔着"gather 占总时间多少"这一层。

不用 MFU 的理由在坐标系上。稀疏算子的算术强度低于 1（读一字节做不到一次浮点运算），落在 roofline 图最左边，FLOPS 利用率趋近 0。这个 0 与优化好坏无关，是问题形状决定的，所以"稀疏算子的 MFU 没有解释力"不是精度问题。⚠️ `A-16` 没有报任何 MFU 数值，它给的是一张 MBU 表和这个论证；引用时不要写成"A-16 的 MFU 是 x%"。

`B-11` 是整本教程里最干净的反例，值得逐层拆：

```
通信量（PyTorch specified sparsity）:  2.161 GB → 2.010 MB   ≈ 1075×
再加 INT8 梯度量化:                    2.010 MB → 0.509 MB   ≈  4×
合计压缩比:                                                  ≈ 4246×
每迭代延迟:                            61 ms → 110 ms        变慢 1.80×
```

压缩比 4246×，加速比 0.56×。两者之间没有乘法关系。

拆开看：省下的传输量是 2.16 GB 里的绝大部分，而延迟净增 49 ms，这 49 ms 就是 codec 与稀疏张量合并（coalescing）的开销。论文自己把原因写得很清楚：PyTorch 的 sparse tensor all-reduce 不支持低精度算术，所以降下来的通信量转化不成时间。

还有一层不写清就会把功劳记错账：2.161 GB → 2.010 MB 是 sparse 支持带来的，不是量化，而且是无损的；量化只贡献了后面的 4×。把这 1075× 记到"INT4 量化"头上，整篇论文的因果链就讲反了。

四篇的处理各自不同，判断却只有两类：能算的和不能算的。不可核算不代表数字假，它只说明这个数字不能被外部复现者验证，只能被信任或被怀疑。下面用贯穿算例把同一把刀换到几个不同的占比上。

## 算例：同一把 8.6×，换几个占比

这一步在算什么：把 `A-14` 的刀拿到[贯穿算例](../guide/running-example)上，看同一把刀在不同占比下值多少。

⚠️ 口径：这里的 51 ms 沿用 `A-10` 的 16 trainer 迭代预算，用来看各块的相对权重。

<div class="example">

设 51 ms 迭代预算里跨机通信占 55%（这个比例取自[第 3 章](../guide/03-bandwidth-wall)的算例：计算 33%、本地内存 12%、跨机通信 55%），局部加速 8.6×：

```
通信时间:      51 ms × 0.55 = 28.1 ms
压缩后:        28.1 / 8.6    =  3.3 ms
新迭代时间:    51 − 28.1 + 3.3 = 26.2 ms
端到端:        51 / 26.2 ≈ 1.94×
吞吐:          16,384 / 0.0262 s ≈ 625K 样本/秒（原 320K）
```

同一把 8.6× 的刀，扫一遍 `f`：

| f | 天花板 `1/(1−f)` | `s=8.6` 时实际 S | 拿到天花板的 |
|---|---|---|---|
| 0.20 | 1.25× | 1.22× | 97% |
| 0.313 | 1.46× | 1.38× | 95% |
| 0.55 | 2.22× | 1.94× | 87% |
| 0.75 | 4.00× | 2.97× | 74% |
| 0.90 | 10.0× | 4.89× | 49% |

这张表怎么读：每一行的 `s` 都是 8.6，变的只有 `f`。`f` 越小，8.6× 越接近天花板，因为天花板本来就低，容易撞顶；`f` 越大，同样的 `s` 越吃不满天花板。
所以"局部加速比很高"和"端到端收益很大"是两个几乎独立的评价，前者看 `s`，后者看 `f`。

</div>

反过来用这张表做判断：如果某篇论文报端到端 1.2×，而它优化的是"占 55% 的通信"，那就对不上，因为应该接近 1.94×。要么 `f` 没那么大，要么它其实没优化多少。

## 模型在哪里不成立

先把口径清单摊开。这张表覆盖七篇，能核算的写明怎么算的，不能核算的写明卡在哪：

| 论文 | f | s | 端到端 | 可核算？ |
|---|---|---|---|---|
| `A-14` | 31.3% | 8.6× | 1.38× | 可：算出 1.382，且 5.03% 由前两者导出 |
| `A-10` | 75% | — | 5.6×（vs FB-Research）/ 3.7×（vs TorchRec，迭代时间） | 不可：超出 4× 天花板 40%，f 与 S 不同源 |
| `A-15` | 未给 | — | 37.8% 吞吐 | 不可：摘要无任何分项 |
| `A-16` | 未给 | — | "up to 2×" | 不可：基线未定义，MBU 是算子级而非时间占比 |
| `B-11` | 未给 | 通信量 1075× 再 4× | 无（延迟 61→110 ms） | 不可，且方向为负 |
| `C-11` | — | — | 迭代数 −81.7%；GPU 小时 −54.3% | 部分：81.7% 与 slowdown 1.27×/4.24× 自洽，但不是时间口径 |
| `A-13` | — | — | 3.1× vs EL-Rec | 不可：基线是上一代同路线系统 |

四种"不可核算"要分清，因为它们对应的补救办法不一样：

- 缺分项（`A-15`、`A-16`）。只有一个端到端数字，没有 `f`，没有 `s`。这时只能用反解给下限：声称 2× 就是声称 `f ≥ 50%`。
- `f` 与 `S` 不同源（`A-10`、`A-13`）。占比在一个系统上量，加速在另一个基线上量。这类最常见，也最容易被误算。
- 口径不是时间（`C-11` 的迭代数、`B-11` 的字节数、`A-16` 的带宽利用率）。换成时间要再过一层换算，而那一层常常没有。
- 方向为负（`B-11`）。压缩比涨、时间也涨。这类论文反而最值得读，因为它把不肯兑现的部分写出来了。

再看公式本身的边界。Amdahl 假设被优化的部分与其余部分是串行相加的，流水线、重叠、异步都能打破这个假设；`A-14` 的 codec 开销被重叠隐藏，就是"相加"不成立的一个小例子。所以 Amdahl 给的是一份量级判断，不是精确预言：它能把"5.6×"和"1.38×"这类差 4 倍的声明分出真假，却不会告诉你 1.38 还是 1.42。

最后是那张清单。三问还是第 12 章那三问，但每一问后面都跟一个可执行的核对：

```
问 1  基线是什么？
      → 有没有点名？匿名的基线（"SOTA industry implementation"）无法核算。
      → 同一篇里的多个加速比是不是同一个分母？（A-10: 5.6 / 3.7 / 2.3）

问 2  局部还是端到端？
      → 若能拿到 f 与 s，代进 1/((1−f)+f/s)，对不上就先怀疑口径。
      → 若只有端到端，用 f ≥ 1 − 1/S 反推，看这个下限是否可信。

问 3  多来源叠加吗？
      → 数一数论文报了几个机制，各自有没有单独数字。
      → 若某机制的独立收益（如 13 分钟→60 秒）不足以补齐差额，
        差额就还在别处——或者它根本不该被核算。
```

这三问对接的是第 12 章第三步（把加速比拆开）与第 13 章的坑 2（以为压缩比等于加速比）。第 13 章那张决策表是选型用的，这三问是验收用的：先按表选出方案，再用这三问检查它的数字。

<div class="takeaway">

**本篇结论**：`S = 1/((1−f)+f/s)` 是这一篇唯一的公式，反解 `f ≥ 1 − 1/S` 是看到一个端到端数字时最省力的核对。

`A-14` 能被完整核算（1.382 对 1.38），`A-10` 不能（超过天花板 40%，`f` 与 `S` 不同源），`B-11` 是压缩比与加速比反向的最干净的样本（4246× 对 0.56×）。

`f` 是架构级变量，`s` 是工程级变量：在固定架构上继续磨局部，`8.6×` 已经拿到天花板的 95%，剩下 5% 要改架构才能拿。
