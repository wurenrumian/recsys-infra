# 深潜 1. gather/scatter 的 roofline：10–50% 带宽去哪了

<div class="deep-anchor">

**对应教程** [第 2 章](../guide/02-embedding-table)给了"随机访问打不满带宽"的结论；这里把它算出来。

</div>

## 一句话版本

嵌入表的查询是随机访存，随机访存拿不到标称带宽，这是结论；这篇给它一个可计算的模型。

模型只有一句：有效带宽等于"同时有多少请求在路上"乘以"每个请求搬多少字节"，再除以"一次访问要等多久"。
用这个模型可以把教程里的 10%、30% 和 `A-16` 实测的 47.50% 放进同一个坐标系，看出它们各自对应什么条件。
顺着这条线还会得到一个反直觉的账：写路径不是读的两倍，而是五倍。

## 这篇的地图

全篇分四块，加一个算例。

1. **算力为什么帮不上忙** —— 说明 gather 落在 roofline 的带宽段，耗时只能按字节算。
2. **并发决定带宽** —— 把"有效带宽"写成在途请求数的函数，算出打满链路需要多少并发。
3. **两个额外折扣** —— 对齐与页表如何把这 30–50% 再往下压。
4. **写路径的真实字节** —— 数一遍反向与优化器到底搬了几份数据。

这四块是一条链：第 1 块排除算力，把问题压到带宽上；第 2 块给出带宽的公式；第 3 块给公式里的系数找来源；第 4 块换到写路径，用同一套公式重算。最后的算例把四块合起来，解释教程第 3 章那个 2.3 ms 的来历。

| 概念 | 一句话 |
|---|---|
| roofline | 一张把"算力上限"和"带宽上限"画在一起的天花板图，谁更低就以谁为限 |
| 算术强度 | 每搬 1 字节做几次浮点运算；gather 只有 0.01–0.1，算得少、搬得多就受带宽限制 |
| 有效带宽 | 实际跑出来的带宽，通常低于标称值 |
| 在途请求 | 已经发出、还没返回的访存请求；同时在路上的越多，链路填得越满 |
| MBU | 达到的带宽 ÷ 峰值带宽，`A-16` 用来评价稀疏算子 |
| cache line | 显存与缓存之间一次搬运的最小单位，这里是 128 B |
| 页表 | 虚拟地址到物理地址的对照表；表太大时，查表本身也是开销 |

术语到此交代完毕，后面各块直接使用。先从最容易被误解的一点开始。

## 第一块 · 算力为什么帮不上忙

这块要回答的是：给 gather 更多算力，它会不会变快。

roofline 是评价一个算子受什么限制的工具。横轴是算术强度，即每搬 1 字节做多少次浮点运算；纵轴是性能。
图上有一条水平的带宽线，和一条斜向上的算力线，两者的交点叫拐点。

```
带宽                                    算力斜线
 TB/s                                    /
   │                    ┌────────────────/
   │                    │  ← 拐点：AI = peak_flops / BW_peak
   │                    │
   │  gather 落在这里 →  │
   │  (AI ≈ 0.03)       │
   └────────────────────┴────────────────────────→ AI (FLOP/B)
        0.01      0.1       1        10    100
```

读法：图左下角是 gather 待的位置（`AI ≈ 0.03`），性能由纵轴上的带宽线压着；要往上走，只能往右移，也就是在同样的字节里做更多运算，而 gather 没有运算可做。

- 落在拐点左边：算力再多也用不上，时间由"搬多少字节"决定。
- 落在拐点右边：带宽够用，时间由"做多少运算"决定。

### 为什么 gather 落在左边

一次 gather 取一行 256 B，花掉的浮点运算只有几件事：算地址、做 `table_id × rows + row_id` 的乘加、检查边界。按 8 FLOP 算：

```
AI = 8 FLOP / 256 B = 0.031 FLOP/B
```

拐点在 fp32 下是 12.6 FLOP/B（19.5 TFLOPS ÷ 1.55 TB/s，两个数都来自 `A-06` 的 156 TFLOPS 与 12.4 TB/s 除以 8 卡）；fp16 约 200 FLOP/B。两者一比：

```
AI / 拐点 = 0.031 / 12.6 = 0.25%
```

gather 的算术强度落在 0.01–0.1 FLOP/B 这一档。即使把算力提到无限，这一步也只能快 0.25%。所以在 roofline 上，gather 永远贴着那条水平的带宽线，离拐点差三到四个数量级。

`A-16` 把这个观察写成方法论：稀疏算子应该看 MBU（带宽利用率），而不是 MFU（算力利用率）。原因是 MFU 的分母是峰值算力，而这类算子根本不消耗算力，用算力做分母没有解释力。

结论是一句话：gather 的耗时只能写成

```
t = 实际搬运字节 / BW_eff
```

问题于是全部压到 `BW_eff` 上。下一块就回答 `BW_eff` 由什么决定。

## 第二块 · 并发决定带宽

这块要回答的是：一块卡为什么跑不到标称带宽，差的那一半去哪了。

带宽不是"打开就有的水管口径"。一个请求从发出到数据返回要等一段时间，这段时间里链路是空的。
要让链路一直有数据在跑，就得同时发出足够多的请求。这个数量乘以每个请求的字节数，再除以等待时间，就是实际带宽：

```
BW_eff = min( BW_peak , C × L / t_lat )
```

四个符号的意思：`BW_peak` 是标称峰值 1.55 TB/s（`A-06` 的 12.4 TB/s ÷ 8）；`C` 是在途请求数；`L` 是每次事务的字节；`t_lat` 是一次随机访存的延迟，这里取 500 ns（假设）。

这条式子取 `min`，是因为两个上限只有一个生效：并发足够时跑标称带宽，并发不足时按比例缩水。

### 打满需要多少并发

把 `C × L / t_lat = BW_peak` 反解，得到打满带宽所需的在途请求数：

```
C* = BW_peak × t_lat / L
```

代入 1.5 TB/s（教程口径，`A-06` 的精确值是 1.55）、500 ns，看三种事务粒度：

| 每次事务字节 `L` | 所需在途请求 `C*` | 说明 |
|---|---|---|
| 64 B | 11,719 | sector 级事务，最坏情况 |
| 128 B | 5,859 | 一条 cache line |
| 256 B | 2,930 | 一次取完整行（仅当对齐且合并成功） |

这张表怎么读：取 64 B 这一行，1.5e12 × 500e-9 ÷ 64 = 11,719，意思是每秒 1.5 TB 的流量需要一万多个请求同时在路上。

单卡挂不到这么多。一颗 GPU 的并发上限约等于 SM 数乘以每个 SM 能同时未完成的 miss 数。按 108 个 SM、每 SM 约 18 条 line 填充估算（⚠️ 示意假设）：

```
C_max ≈ 108 × 18 = 1,944 条 128 B 事务
BW_eff = 1,944 × 128 B / 500 ns ≈ 498 GB/s ≈ 32%
```

如果并发能到 2,900 条，就是 742 GB/s，约 48%。这两个数就是 30% 与 47.5% 的上下沿：

| 条件 | `C_max` | `BW_eff` | 占峰值 |
|---|---|---|---|
| 保守并发 | ~1,950 | ~500 GB/s | 32% |
| 激进并发（宽访问、深流水） | ~2,900 | ~740 GB/s | 48% |
| 还要再乘对齐系数 | — | ×0.67–1.0 | 掉到 10–48% |

所以 `A-16` 的 47.50% 不是"优化得好"，而是"已经把单卡并发用满了"。同一张表里 bucketize 只有 0.88%，因为那个算子是计算受限的（融合带来了额外计算），不是并发受限。两个算子落在 roofline 的不同位置，这正好说明这张图能区分两类瓶颈。

带宽的上限由单卡能挂多少在途请求决定，落在 30–50% 之间。下一个问题是：为什么有时候还会掉到 10%。

## 第三块 · 对齐与页表，另外两个折扣

这块要回答的是：30% 往下还有哪些扣分项，各扣多少。

前一块算的是"请求够不够多"。这一块算的是"每个请求是不是都花在有用的字节上"。有两件事会让字节白搬：一行数据跨过了 cache line 边界，以及地址翻译没有命中。

### 第一项：跨界

先明确粒度。`A-06` 的 ZionEX 单卡 40 GB HBM、1.55 TB/s，GPU 侧 cache line 是 128 B，sector 是 32 B。一行 256 B 的嵌入恰好是 2 条 line、8 个 sector。

对齐时，2 条 line 装满 256 B，没有浪费。基址偏移 32 B 时就不一样了：

```
命中范围 [o, o+256)，o = 32：
  line0 [0,128)     用到 96 B
  line1 [128,256)   用到 128 B
  line2 [256,384)   用到 32 B
→ 读 384 B，用 256 B，放大 1.5×
```

所以"随机 256 B 访问"不是固定 4 条 64 B line，而是 2 条还是 3 条 128 B line，取决于基址对不对齐：

```
对齐 (o = 0)：   a = 1.00
未对齐 (o ≠ 0)： a = 1.50
```

关键在于行跨距是不是 128 B 的整数倍。跨距是整数倍、基址也对齐时，每行都是 `o = 0`，`a = 1.0`。一旦跨距不是——比如 48 维 fp32 是 192 B，或者几千张小表被打包进同一个大缓冲区——每行都落在 `o ≠ 0`，`a` 逼近 1.5。

这件事由表的内存布局决定，不由访问模式决定。把嵌入表按 256 B 边界对齐、让跨距保持 2 的幂，这一项就从 1.5 压到 1.0，相当于有效带宽提高 50%。这是全篇最便宜的一处优化，也常被忽略，因为它在代码里只是"分配时顺手加的 padding"，不会出现在任何 profiling 图上。

### 第二项：页表

假设用 2 MB 大页：

```
2 MB / 256 B = 8,192 行/页
10.2 TB / 2 MB = 5.1 × 10^6 页
```

一张卡能缓存多少页？按 4,096 条估算（⚠️ 示意，GPU TLB 容量公开资料稀缺）：

```
TLB 覆盖 = 4,096 × 2 MB = 8 GB
覆盖 / 全表 = 8 GB / 10.2 TB = 0.078%
```

如果访问均匀撒在 10.2 TB 上，TLB 命中率约万分之八，几乎每次都要走页表。走一次页表至少多一次访存，延迟从 500 ns 抬到 750–1,000 ns，`BW_eff` 直接掉一半。

但访问不是均匀的。[深潜 3](03-cache-staleness) 会算出热点集的大小：`s=1.2` 时 95% 的访问集中在约 1e6 行（289 MB）。这个集合只有 145 个 2 MB 页，全部装得进 4,096 条的 TLB。于是页表的表现是二值的：热点集里的访问全部命中，冷门那 5% 每次走页表。加权后相当于把平均延迟抬高约 5–10%。

这也解释了为什么同一套硬件在微基准（表小、常驻）和 10 TB 生产表上测出的带宽能差一倍。带宽没有变，是页表在收费。

30% 不是单一原因，而是并发、对齐、页表三项相乘的结果，各自都有上界和下界。最后一块换到写路径，数一遍字节。

## 第四块 · 写路径为什么贵五倍

这块要回答的是：教程说"读写各一次，所以两倍"，这个数在真实训练循环里为什么不成立。

原因是嵌入表的反向与优化器是融合的。`A-06` 的 hybrid kernel fusion 就是把反向和稀疏优化器更新融成一个 kernel，省掉梯度落地再读回来的往返。融合之后，每行每迭代的搬运是：

```
前向 gather：      读 w            256 B
反向 + 更新：      读 w            256 B   （算梯度要用当前值）
                   读 v            256 B   （AdaGrad 累积量）
                   写 w            256 B
                   写 v            256 B
──────────────────────────────────────
合计                             1,280 B = 5 × 行大小
```

五个 256 B 里只有一个属于"读参数"，其余四个属于优化器那一段。这也是为什么 `A-06` 报"96TB → 24TB"需要同时上 row-wise sparse AdaGrad 和 FP16：状态量本身就是参数的一倍。

### 两个偏离两倍的机制

| 机制 | 效果 |
|---|---|
| write-allocate | 只写部分列（列分片的场景）时，写一条 line 前要先读回来合并，多一条 line |
| 原子累加 | 同一行被多个 warp 或卡同时写时，要么用 atomic，要么串行化，吞吐按冲突度下降 |

### 为什么 MBU 会给出相反的印象

写路径也有比读便宜的地方：整行写（256 B 覆盖 2 条完整 line）时可以整套写下去，不需要 read-for-ownership。`A-16` 的 scatter MBU 是 58.00%，高于 gather 的 47.50%，原因就在这里：写回的字节流更连续、对齐更好，字节效率更高。

于是"写更贵"不体现在 MBU 上，体现在字节数上：gather 搬 1 份，更新搬 4 份。只看 MBU 会得出相反的印象，因为 MBU 回答的是"搬得顺不顺"，不回答"搬了多少"。

单行的真实成本是 5 个 256 B，不是 2 个。下面用[贯穿算例](../guide/running-example)把这四块合起来算一遍。

## 算例：把 30% 拆开

算例参数沿用教程：400 亿行、64 维 fp32、每行 256 B、全表 10.2 TB、每迭代去重后 525 MB。

⚠️ 先钉住口径：525 MB 是**全批**去重量，16,384 个样本共用。每卡只 gather 自己那 1/128 的样本，约 4.1 MB。下面保留全批口径，是因为要解释教程第 3 章那个 2.3 ms 从哪来；所有时间除以 128 才是单卡墙钟。

<div class="example">

第一步，把 30% 落到模型上。

教程第 3 章的 450 GB/s 不是拍出来的，它是下面这条链的乘积（全部为推导，假设写在括号里）：

```
峰值带宽            1.55 TB/s      （A-06: 12.4 TB/s ÷ 8 卡）
× 并发利用率  0.32  （C_max ≈ 1,950 条 128 B 事务 / 需要 5,859 条）
× 对齐系数    0.85  （多数行对齐、部分子表跨界，字节有效率 0.67–1.0）
× 页表系数    0.95  （冷行每次走页表，抬高约 5% 的平均延迟）
────────────────────────────────
≈ 0.26 × 1.55 TB/s ≈ 400 GB/s      （对齐全好时 0.30 × 1.55 ≈ 470 GB/s）
```

这条链落在 400–470 GB/s，教程第 3 章取的 450 GB/s 在区间中间，也就是那个 30%。三个系数里任何一个变好，有效带宽都往上走：

```
全对齐 + 热集常驻 + 并发拉满 → 1.55 × 0.48 ≈ 740 GB/s  （对应 A-16 的 47.50%）
并发低 + 跨界 + 冷页          → 1.55 × 0.10 ≈ 155 GB/s  （区间下沿）
```

第二步，gather 的时间。

```
525 MB ÷ 450 GB/s = 1.17 ms
```

这是算例模型在 30% 有效带宽下的纯 gather 时间。

第三步，和教程的 2.3 ms 对齐。教程第 3 章算的是"读写各一次"：

```
525 MB × 2 = 1.05 GB
1.05 GB ÷ 450 GB/s = 2.33 ms
```

所以 2.3 ms = 2 × 1.17 ms，两者口径一致：1.17 ms 是读那一次，2.3 ms 是读加写的朴素估法。

第四步，把写路径按真实字节数重算。

```
读        525 MB × 1 = 525 MB
优化器    525 MB × 4 = 2,100 MB
──────────────────────────────
合计                 2,625 MB

2,625 MB ÷ 450 GB/s = 5.83 ms
2,625 MB ÷ 740 GB/s = 3.55 ms
```

三种口径放在一起：

| 口径 | 字节 | 时间 | 占 51 ms |
|---|---|---|---|
| 只算 gather（全批） | 525 MB | 1.17 ms | 2.3% |
| 教程的"读写各一次"（全批） | 1.05 GB | 2.33 ms | 4.6% |
| 含优化器状态（推导，全批） | 2.63 GB | 5.83 ms | 11.4% |
| 含状态 + 对齐且常驻（全批） | 2.63 GB | 3.55 ms | 7.0% |
| **每卡口径（全部 ÷128）** | **20.5 MB** | **45.6 μs** | **0.09%** |

差出来的 3.5 ms 全部来自"优化器状态也要读写"这件事。教程第 2 章已经说过状态是参数的 2 倍，第 3 章的 1.05 GB 没有把它计入内存墙的时间，这是两章之间的一个缺口。

最后一行才是单卡的真实量级：本地 HBM 上的嵌入搬运在 51 ms 里不到千分之一。这不推翻"嵌入表贵"的结论，它说明贵的地方不在单卡 HBM，而在"表不在本卡"之后的那一跳，以及每步的固定开销。

</div>

算例给出一个反直觉的结果：在这套参数下，本地 HBM 上的嵌入搬运只占 51 ms 的 5–11%。真正让它变成瓶颈的是距离。表一旦不在本卡，延迟从 500 ns 变成 5 μs，`C*` 涨十倍，同样的并发只能换到十分之一的带宽。

## 模型在哪里不成立

- 30% 是四个假设的乘积，不是实测量。每个系数都能上下浮动 50%，乘起来可能落 15%，也可能落 45%。它的用处是给"10–50%"这个区间一个可拆解的结构，不是给一个能抄的数字。
- `C_max ≈ 1,950` 是示意值。GPU 的在途 miss 数、L2 队列深度、每次事务的 sector 数都会改变这个数，公开资料也不完整。这个量只能定性使用：并发不够就打不满，够了也就到 50% 附近。
- 525 MB 是全批去重总量，不是单卡量。教程第 2、3 章把它当作"每卡都要面对"的数据量，在"整批记在一张卡上"的记账法下成立，用于横向比较没问题；单卡真实流量要除以 128（约 4.1 MB），拿它做容量规划会高估两个数量级。
- 47.50% 是 H20 上的微基准，表常驻、访问生成好、没有页表压力。生产环境的落点通常低于它，不能把 47.5% 当作可达值写进规划。
- 这个模型不含网络。跨机之后 `t_lat` 从 500 ns 变成 5 μs，`C*` 涨到 11.7 万条，任何单卡都挂不住。那时决定带宽的是网络拓扑与消息大小，不是 HBM 的并发。这一层在[深潜 2](02-sharding-cost)的通信代数里，以及[网络 1](../network/01-interconnect-layers)的链路模型里。

<div class="takeaway">

**本篇结论**：gather 的耗时只能写成"字节 ÷ 有效带宽"，而有效带宽由在途请求数决定。

打满 1.5 TB/s 需要约 1.17 万个 64 B 在途请求，单卡上限大约给到 2,000–3,000 条 128 B 事务，也就是 30–50%。剩下的落差来自对齐（未对齐放大 1.5 倍）与页表（10 TB 的表在 8 GB 覆盖之外）。写路径的真实字节是 gather 的 5 倍，因为优化器状态要读写两遍。
