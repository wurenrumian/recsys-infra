# 深潜 1. gather/scatter 的 roofline：10–50% 带宽去哪了

<div class="deep-anchor">

**对应教程** [第 2 章](../guide/02-embedding-table)给了"随机访问打不满带宽"的结论；这里把它算出来。

</div>

## 本篇要算的问题

教程里出现过三个数，彼此之间没有接上：

- 随机 gather 的有效带宽是峰值的 10–50%（第 2、3 章）；
- 算例里取 30%，把 525 MB 的读写算成 2.3 ms；
- `A-16` 实测 gather 的 MBU 是 47.50%。

10、30、47.5 是三个不同的数。它们不是互相矛盾，而是三个不同条件下的落点。本篇要做的事：

1. 用 roofline 说明 gather 为什么永远落在带宽斜线上，算力对它没有意义；
2. 把"有效带宽"写成 `在途请求数 × 字节 / 延迟`，算出打满带宽需要多少并发；
3. 用同一套模型解释 10%、30%、47.50% 各对应什么条件；
4. 把写路径（scatter）的字节数重新数一遍，说明为什么"读写各一次"不等于 2 倍。

## 先给结论

1. gather 的算术强度约 0.01–0.1 FLOP/B，离 roofline 的拐点差三到四个数量级。它只能落在带宽斜线上，时间 = 字节 ÷ 有效带宽，跟算力完全无关。
2. 有效带宽 = `C × L / t_lat`，C 是在途请求数、L 是每次传输字节、t_lat 是访存延迟。要打满 1.5 TB/s、500 ns、64 B，需要约 1.17 万个在途请求；单卡挂不到这么多，这就是天花板。
3. 10–50% 这个区间的上沿是单卡并发上限（约 50%），下沿是跨界 + 页表未命中 + 并发不足（可跌到 10%）。`A-16` 的 47.50% 在微基准条件下贴着上沿，30% 是"10 TB 随机 + 未对齐 + 冷页"的落点。
4. 写路径不是读的 2 倍。融合反向与优化器之后，每行每迭代要搬 5 × 256 B（gather 1 份、优化器读改写 4 份），是 gather 的 5 倍。`A-16` 的 scatter MBU 58.00% 高于 gather，说的是效率不是便宜。

## 符号与模型

| 符号 | 含义 | 本篇取值 |
|---|---|---|
| `BW_peak` | 单卡 HBM 峰值带宽 | 1.55 TB/s（`A-06` 的 12.4 TB/s ÷ 8） |
| `L` | 单次事务承载的字节 | 64 / 128 / 256 B |
| `t_lat` | 一次随机访存的延迟 | 500 ns（假设） |
| `C` | 在途（未完成）请求数 | 由硬件决定 |
| `AI` | 算术强度 = FLOP ÷ 字节 | gather ≈ 0.01–0.1 |
| `MBU` | 达到带宽 ÷ 峰值带宽 | `A-16` 的定义 |
| `a` | 流量放大系数（对齐导致） | 1.0–1.5 |

roofline 的形状（横轴算术强度取对数）：

```
带宽                                    算力斜线
 TB/s                                    /
   │                    ┌────────────────/
   │                    │  ← 拐点：AI = peak_flops / BW_peak
   │                    │
   │  gather 落在这里 →  │
   │  (AI ≈ 0.03)       │
   └────────────────────┴────────────────────────→ AI (FLOP/B)
        0.01      0.1       1        10    100
```

拐点位置：fp32 算力 19.5 TFLOPS（`A-06` 的 156 TFLOPS ÷ 8）÷ 1.55 TB/s ≈ 12.6 FLOP/B；fp16 约 200 FLOP/B。

`BW_eff` 的模型只有一行，但它是全篇的基础：

```
BW_eff = min( BW_peak , C × L / t_lat )
```

读法：带宽不是"每秒能搬多少"，而是"同时有多少请求在路上"。请求不够多，延迟就填不满管子。

## 推导

### 推导一：gather 离拐点有多远

一次 gather 每取一行（256 B），花掉的浮点运算只有几件事：地址计算、`table_id × rows + row_id` 的乘加、边界检查。按 8 FLOP 算：

```
AI = 8 FLOP / 256 B = 0.031 FLOP/B
AI / 拐点(12.6) = 0.25%
```

也就是说，即使把算力提高到无限，这一步也只能快 0.25%。`A-16` 把这个结论说成方法论：稀疏算子应该看 MBU 而不是 MFU，因为 MFU 的分母（峰值算力）对它们没有意义。

所以 gather 的耗时只有一种写法：

```
t = 实际搬运字节 / BW_eff
```

问题全部压到 `BW_eff` 上。而 `BW_eff` 由并发度决定，不由带宽标称值决定。

### 推导二：打满带宽需要多少在途请求

把 `C × L / t_lat = BW_peak` 反解，得到打满带宽所需的在途请求数：

```
C* = BW_peak × t_lat / L
```

代入 1.5 TB/s（教程口径；`A-06` 的精确值是 1.55）、500 ns，看三种事务粒度：

| 每次事务字节 `L` | 所需在途请求 `C*` | 说明 |
|---|---|---|
| 64 B | 11,719 | sector 级事务，最坏情况 |
| 128 B | 5,859 | 一条 cache line |
| 256 B | 2,930 | 一次取完整行（仅当对齐且合并成功） |

这就是"约 1.17 万个在途请求"的来源：1.5e12 × 500e-9 ÷ 64 = 11,719。

单卡能挂多少？一颗 GPU 的并发上限 ≈ SM 数 × 每个 SM 可同时未完成的 miss 数。按 108 个 SM、每 SM 约 18 条 line 填充估算（⚠️ 示意假设）：

```
C_max ≈ 108 × 18 = 1,944 条 128 B 事务
BW_eff = 1,944 × 128 B / 500 ns ≈ 498 GB/s ≈ 32%
```

若 C_max 能到 2,900 条，就是 742 GB/s ≈ 48%。**这两个数字框住了 30% 与 47.5%**：

| 条件 | `C_max` | `BW_eff` | 占峰值 |
|---|---|---|---|
| 保守并发 | ~1,950 | ~500 GB/s | 32% |
| 激进并发（宽访问、深流水） | ~2,900 | ~740 GB/s | 48% |
| 还要再乘对齐系数 | — | ×0.67–1.0 | 掉到 10–48% |

`A-16` 的 47.50% 因此不是"优化得好"，而是"已经把单卡并发用满了"。它的 bucketize 只有 0.88%，因为那个算子是计算受限的（融合带来的额外计算），不是并发受限——同一张表里两个算子落在不同位置，正好印证 roofline 的解释力。

### 推导三：cache line、对齐与 TLB

先明确粒度。`A-06` 的 ZionEX 单卡 40 GB HBM、1.55 TB/s，GPU 侧 cache line 128 B，sector 32 B。一行 256 B 的嵌入正好是 2 条 line、8 个 sector。

对齐时：2 条 line，无浪费。

基址偏移 32 B 时（很常见：fp32 × 64 维 = 256 B，但如果表头有元数据或与别的张量拼在一起）：

```
命中范围 [o, o+256)，o = 32：
  line0 [0,128)     用到 96 B
  line1 [128,256)   用到 128 B
  line2 [256,384)   用到 32 B
→ 读 384 B，用 256 B，放大 1.5×
```

这就是"随机 256 B 访问不是 4 条 line 正好"的意思：它不是 4 条 64 B line 拼起来，而是 2 条还是 3 条 128 B line，取决于基址对齐。对一个字节偏移随机的行：

```
对齐 (o = 0)：   a = 1.00
未对齐 (o ≠ 0)： a = 1.50
```

关键在于偏移是不是随机的。行跨距（stride）是 128 B 的整数倍、基址也对齐时，每行都是 `o = 0`，`a = 1.0`；一旦跨距不是 128 B 的倍数——比如 48 维 fp32 是 192 B，或者几千张小表被打包进同一个大缓冲区——每一行都落在 `o ≠ 0`，`a` 逼近 1.5。所以这张表有多大比例在跨界，是表的内存布局决定的，不是访问模式决定的。

结论很硬：把嵌入表按 256 B 边界对齐、让跨距保持 2 的幂，能把这一项从 1.5 压到 1.0，相当于有效带宽提高 50%。这是全篇最便宜的一处优化，而且常常被忽略，因为它在代码里是"分配时顺手加的 padding"，不在任何 profiling 图上。

再算 TLB。假设用 2 MB 大页：

```
2 MB / 256 B = 8,192 行/页
10.2 TB / 2 MB = 5.1 × 10^6 页
```

一张卡的 TLB 能缓存多少页？按 4,096 条估算（⚠️ 示意，GPU TLB 容量公开资料稀缺）：

```
TLB 覆盖 = 4,096 × 2 MB = 8 GB
覆盖 / 全表 = 8 GB / 10.2 TB = 0.078%
```

如果访问均匀随机撒在 10.2 TB 上，TLB 命中率约万分之八，几乎每次都要走页表。页表走一次至少多一次访存，延迟从 500 ns 抬到 750–1,000 ns，`BW_eff` 直接腰斩。

但访问不是均匀的。第 3 篇会算出热点集的大小：`s=1.2` 时 95% 的访问集中在约 1e6 行（289 MB）。把这个集当工作集：

```
289 MB ≈ 145 个 2 MB 页 → 全部装进 TLB（4,096 条）
```

于是 TLB 的实际表现是二值的：热点集里的访问全部命中，冷门那 5% 每次走页表。加权后相当于把平均延迟抬高约 5–10%。这也解释了为什么同一套硬件在微基准（表小、常驻）和 10 TB 生产表上测出的带宽能差一倍——不是带宽变了，是页表在收费。

### 推导四：写路径为什么不是读的两倍

教程第 2 章的写法是"读 256 B、写 256 B，所以 2 倍"。这个数在真实训练循环里不成立，原因是嵌入表的反向与优化器是融合的（`A-06` 的 hybrid kernel fusion 就是做这件事：反向 + 稀疏优化器更新融成一个 kernel，省掉梯度落地再读的往返）。

按融合实现，每行每迭代的搬运是：

```
前向 gather：      读 w            256 B
反向 + 更新：      读 w            256 B   （算梯度要用当前值）
                   读 v            256 B   （AdaGrad 累积量）
                   写 w            256 B
                   写 v            256 B
──────────────────────────────────────
合计                             1,280 B = 5 × 行大小
```

五个 256 B 里只有一个属于"读"，四个属于优化器那一段。这也是为什么 `A-06` 报"96TB → 24TB"要把 row-wise sparse AdaGrad 和 FP16 一起上：状态量本身就是参数的一倍。

还有两个偏离 2 倍的机制：

| 机制 | 效果 |
|---|---|
| write-allocate | 只写部分列（列分片的场景）时，写一条 line 前要先读回来合并，+1 条 line |
| 原子累加 | 同一行被多个 warp 或卡同时写时，要么用 atomic，要么串行化，吞吐按冲突度下降 |

反过来，写路径也有比读便宜的地方：整行写（256 B 覆盖 2 条完整 line）时可以整套写下去，不需要 read-for-ownership。`A-16` 的 scatter MBU 58.00% 高于 gather 的 47.50%，正是这个原因——写回的字节流更连续、对齐更好，所以字节效率更高。

于是"写更贵"这件事不体现在 MBU 上，体现在字节数上：gather 搬 1 份，更新搬 4 份。看 MBU 会得出相反的错觉，因为它只回答"搬得顺不顺"，不回答"搬了多少"。

## 算例

用[贯穿算例](../guide/running-example)：400 亿行、64 维 fp32、每行 256 B、全表 10.2 TB、每迭代去重后 525 MB。

⚠️ 口径先钉死：525 MB 是**全批**去重量（16,384 样本共用），每卡只 gather 自己那 1/128 样本的行，约 **4.1 MB**。下面保留全批口径，是因为要解释教程第 3 章那个 2.3 ms 从哪来；所有时间 **÷128** 才是单卡墙钟。

<div class="example">

第一步，把 30% 落到模型上。

教程第 3 章的 450 GB/s 不是拍出来的，它是下面这条链的乘积（全部为推导，假设在括号里）：

```
峰值带宽            1.55 TB/s      （A-06: 12.4 TB/s ÷ 8 卡）
× 并发利用率  0.32  （C_max ≈ 1,950 条 128 B 事务 / 需要 5,859 条）
× 对齐系数    0.85  （多数行对齐、部分子表跨界，字节有效率 0.67–1.0）
× 页表系数    0.95  （冷行每次走页表，抬高约 5% 的平均延迟）
────────────────────────────────
≈ 0.26 × 1.55 TB/s ≈ 400 GB/s      （对齐全好时 0.30 × 1.55 ≈ 470 GB/s）
```

这条链的落点是 400–470 GB/s，教程第 3 章取的 450 GB/s 落在区间中间，也就是那个 30%。

三个系数里任何一个变好，有效带宽就往上走：

```
全对齐 + 热集常驻 + 并发拉满 → 1.55 × 0.48 ≈ 740 GB/s  （对应 A-16 的 47.50%）
并发低 + 跨界 + 冷页          → 1.55 × 0.10 ≈ 155 GB/s  （区间下沿）
```

第二步，gather 的时间。

```
525 MB ÷ 450 GB/s = 1.17 ms
```

这就是算例模型在 30% 有效带宽下的纯 gather 时间。

第三步，和教程的 2.3 ms 对齐。

教程第 3 章算的是"读写各一次"：

```
525 MB × 2 = 1.05 GB
1.05 GB ÷ 450 GB/s = 2.33 ms
```

所以 2.3 ms = 2 × 1.17 ms，两者口径一致。1.17 ms 是读那一次，2.3 ms 是读 + 写的朴素估法。

第四步，把写路径按真实字节数重算。

```
读        525 MB × 1 = 525 MB
优化器    525 MB × 4 = 2,100 MB
──────────────────────────────
合计                 2,625 MB

2,625 MB ÷ 450 GB/s = 5.83 ms
2,625 MB ÷ 740 GB/s = 3.55 ms
```

对比三种口径：

| 口径 | 字节 | 时间 | 占 51 ms |
|---|---|---|---|
| 只算 gather（全批） | 525 MB | 1.17 ms | 2.3% |
| 教程的"读写各一次"（全批） | 1.05 GB | 2.33 ms | 4.6% |
| 含优化器状态（推导，全批） | 2.63 GB | 5.83 ms | 11.4% |
| 含状态 + 对齐且常驻（全批） | 2.63 GB | 3.55 ms | 7.0% |
| **每卡口径（全部 ÷128）** | **20.5 MB** | **45.6 μs** | **0.09%** |

差出来的 3.5 ms 全部来自"优化器状态也要读写"这件事。教程第 2 章已经说过状态是参数的 2 倍，但第 3 章的 1.05 GB 没有把它计入内存墙的时间，这是两章之间的一个缺口。

最后一行才是单卡的真实量级：**本地 HBM 上的嵌入搬运在 51 ms 里不到千分之一**。这不推翻"嵌入表贵"的结论——它说明贵的地方不在单卡 HBM，而在"表不在本卡"之后的那一跳，以及每步固定开销。

</div>

算例给出了一个反直觉的结论：在这套参数下，本地 HBM 上的嵌入搬运只占 51 ms 的 5–11%。真正让它变成瓶颈的是距离——一旦表不在本卡，延迟从 500 ns 变成 5 μs，`C*` 涨 10 倍，同一份并发只能换到十分之一的带宽。

## 代价与边界

- 30% 是四个假设的乘积，不是实测量。每个系数都能上下浮动 50%，乘起来可能落 15% 也可能落 45%。它的用处是给"10–50%"这个区间一个可拆解的结构，不是给一个可抄的数字。
- `C_max ≈ 1,950` 是示意值。GPU 的 outstanding miss 数、L2 队列深度、每次事务的 sector 数都会改变这个数，公开资料也不完整；这条只能定性使用：并发不够就打不满，够了也就到 50% 附近。
- 525 MB 是全 batch 的去重总量，不是单卡量。教程第 2、3 章把它当作"每卡都要面对的"数据量，这在"整批记在一张卡上"的记账法下成立，用作横向比较没问题；但单卡真实流量要 ÷128（约 4.1 MB），拿它做容量规划会高估两个数量级。
- 47.50% 是 H20 上的微基准，表常驻、访问生成好、没有页表压力。生产环境的落点通常低于它，不能把 47.5% 当作可达值写进规划。
- 这个模型不含网络。跨机之后 `t_lat` 从 500 ns 变 5 μs，`C*` 涨到 11.7 万条，任何单卡都挂不住——那时候决定带宽的是网络拓扑与消息大小，不是 HBM 的并发。这一层在第 2 篇的通信代数里。

<div class="takeaway">

**本篇结论**：gather 的耗时只能写成"字节 ÷ 有效带宽"，而有效带宽由在途请求数决定。

打满 1.5 TB/s 需要约 1.17 万个 64 B 在途请求，单卡上限大约给到 2,000–3,000 条 128 B 事务，也就是 30–50%。剩下的落差来自对齐（未对齐放大 1.5 倍）与页表（10 TB 表在 8 GB 覆盖之外）。写路径的真实字节是 gather 的 5 倍，因为优化器状态要读写两遍。
