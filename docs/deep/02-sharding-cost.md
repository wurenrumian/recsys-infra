# 深潜 2. 切分的成本模型：表、行、列、副本的代数

<div class="deep-anchor">

**对应教程** [第 4 章](../guide/04-data-parallel-limits)给了"纯 DP 失效、纯 MP 也 OOM"的判断，[第 5 章](../guide/05-sharding-taxonomy)给了四种切法的对照表；这里把每一格换成公式，并算出算例到底需要多少卡。

</div>

## 本篇要算的问题

教程第 5 章的四象限表回答"哪种切法擅长什么"。它没回答三个更需要算术的问题：

- 给定卡数和模型大小，每张卡要装多少字节？
- 每迭代的通信是多少字节，其中多少是索引、多少是向量？
- 抄一份副本的好处（均衡、通信）什么时候抵不过代价（内存、同步）？

本篇把 200 张表、400 亿行、10.2 TB 这套算例代进四个公式，得到一个结论：教程第 4 章"128 卡、G=4"的例子在容量上不成立，它是一个通信示意。

## 先给结论

1. 四种切法各改一个变量：表级改"哪些表同卡"，行级把每表字节除以 n，列级把维度除以 c，副本把整个结果乘 G。它们能递归组合，所以任何方案都能写成这四个数的一个向量。
2. 2D 并行的每卡内存是 `G × (S + S_opt) / N`。算例里参数 10.2 TB、AdaGrad 状态 10.2 TB，G=4 时 128 卡每卡要 637 GB，是 80 GB 的 8 倍；只放参数也要 319 GB。容量上 G=4 至少要 512 卡（仅参数）或 1,020 卡（含状态）。
3. 通信有三种量级，不要混。组内 all-to-all 每卡约 2 MB 出站；跨组同步只算脏行，全集群 1.05 GB（每卡约 2 MB）；整表同步是 20.4 TB（每卡约 40 GB）。体积比是 19,000 倍，但**时间不是**——每卡 2 MB 走 50 GB/s 只有 0.04 ms，所以脏行同步与整表同步的差别是"可行 / 不可行"，不是"快 / 慢"。跨组同步的 ring all-reduce 每卡出站约 3 MB，时间约 0.06 ms。
4. G 没有唯一闭式解。它先被内存上限卡死，再被同步频率与不均衡尾部微调；`A-03` 在两个模型上都测到 G=4 最好、G=8 退化，这只能由后一项解释。

## 符号与模型

| 符号 | 含义 | 算例取值 |
|---|---|---|
| `S` | 嵌入参数总字节 | 10.2 TB |
| `S_opt` | 优化器状态字节 | 10.2 TB（AdaGrad fp32 一份累积量） |
| `N` | 总卡数 | 128 / 512 |
| `G` | 副本数（并行组数） | 1 / 2 / 4 / 8 |
| `n` | 每组卡数 `N/G` | 128（N=512, G=4） |
| `c` | 列分片数 | 1 / 2 |
| `M` | 单卡 HBM 可用字节 | 80 GB |
| `b` | 全局 batch | 16,384 样本 |
| `k` | 每样本查询数 | 500 |
| `u` | 去重倍率 | 4（示意） |
| `w` | 每元素字节 | 4（fp32） |
| `d` | 嵌入维度 | 64 |

四种切法的代数（`S_t` 是第 t 张表的字节，`m` 是每卡分到的表数）：

| 切法 | 每卡内存 | 前向通信 | 放大项 | 失效条件 |
|---|---|---|---|---|
| Table-wise | `sum(S_t)` over 本卡的表 | 0 | 无 | `max(S_t) > M` |
| Row-wise | `S / n`（每表） | ReduceScatter，≈ `b·k·u⁻¹·d·w` | 通信 ∝ n | 单表小于一份分片时浪费 |
| Column-wise | `S / c` | AlltoAll，索引复制 `c` 份 | 索引 × c，状态数组 × c | `d` 不能被 c 整除 |
| Data（副本） | `S` | 前向 0，反向 AllReduce | 内存 × N | `S > M` 直接出局 |

2D 并行是把 Row-wise 与 Data 叠起来：组内按行切，组间复制。于是每卡内存只剩一个式子：

```
mem_per_card = G × (S + S_opt) / N
```

这个式子是本篇的主线。`G` 在分子上，`N` 在分母上——加副本等价于把卡数除回去。

## 推导

### 推导一：四种切法只有一个变量在变

把一张表看成一个矩阵 `R × d`，字节 `S = R·d·w`。四种切法分别砍掉一个维度的下标：

```
Table-wise：  {表 t} → 卡        每卡 S 不变，卡数由表数决定
Row-wise：    R → R/n            每卡 S/n，行下标要重映射
Column-wise： d → d/c            每卡 S/c，每行变成 c 段
Data：        全不变，复制 N 份    每卡 S，靠 AllReduce 保持一致
```

Column-wise 有两个隐性代价，`A-06` 明确写了但容易被跳过：

```
索引复制：每次查询的 ID 要发给全部 c 个列分片 → 索引流量 × c
状态碎片：每个（行分片, 列分片）单独维护状态 → 状态数组数 × c，字节不变
```

第二项不增加字节，但它把一份连续的累积量拆成 c 份，每份都要按行分片的边界补齐，元数据与碎片随 c 增长。第一项才是真金白银：当 `c=2` 时每卡参数减半、状态也减半，总字节减半，但索引流量翻倍。而索引在 all-to-all 里本来就占着消息数的大头。

表级切分的代价不在通信，在粒度。200 张表分给 N 张卡：

| N | 每卡表数 | 后果 |
|---|---|---|
| 128 | 1.56 | 每卡拿 1–2 张表，最大那张表落在谁头上就是谁慢 |
| 512 | 0.39 | 一半以上的卡分不到整表，表级切分在这个规模下不可用 |

所以第 5 章的分档表（超大表行切、小表复制）不是风格选择，是算术结果：卡数一多，表就不够分。

### 推导二：2D 的容量约束，与 512 卡那道坎

由 `mem_per_card ≤ M` 直接反解：

```
N ≥ G × (S + S_opt) / M
```

代入 `S = S_opt = 10.2 TB`、`M = 80 GB`：

| G | 只放参数所需 N | 含 AdaGrad 状态所需 N | 512 卡下的每卡字节 |
|---|---|---|---|
| 1 | 128 | 255 | 19.9 GB / 39.8 GB |
| 2 | 256 | 510 | 39.8 GB / 79.7 GB |
| 4 | 512 | 1,020 | 79.7 GB / 159.4 GB |
| 8 | 1,024 | 2,040 | 159.4 GB / 318.8 GB |

（"每卡字节"两列：左为参数，右为参数 + 状态。）

这张表读出三件事：

1. 128 卡、G=1、只放参数，正好 79.7 GB，余量 0.3 GB。教程第 4 章的"内存刚好够"就是这一行，它连激活都放不下。
2. 128 卡、G=4、含状态，要 637.5 GB/卡，是硬件的 8 倍。这一档在容量上不存在。
3. G=4 在容量上从 512 卡起步（只放参数）。要同时放状态，得 1,020 卡，向上取整 1,024。

于是教程第 4 章那个算例要改口径：

```
第 4 章：N=128, G=4, n=32   → 用来演示 all-to-all 按 1/G 缩小、不均衡比按 1/√m 下降
本篇：   容量可行性要 N ≥ 512（仅参数）/ 1,024（含状态）
```

第 4 章的数字是通信示意，不是容量规划。它的三条机制（通信 1/G、激活 1/G、均衡改善）都正确，只是那个 `(128, 4)` 组合在 80 GB 的卡上装不下。`A-03` 自己的实验跑在 4096 卡上，G=4 时每卡 `4 × 20.4 TB / 4096 = 19.9 GB`，只占 HBM 的四分之一——这才是 G=4 能成立的真实前提。

### 推导三：三种通信量级，别混着用

把一次迭代的通信拆成三层，每层的公式与量级都不同。

第一层，组内 all-to-all。组内 n=128 卡，每卡都要看整组的唯一查询（这是行切的本意：卡要判断哪些行归自己）。理想实现会把每条查询只路由一次（`A-16` 的 `ids partition` 干的就是这件事，MBU 从 34.60% 提到 55.10%）：

```
组内唯一查询 = b/G × k / u = 4096 × 500 / 4 = 512,000 条
每卡分到 512,000 / 128 = 4,000 条
索引出：4,000 × 8 B = 32 KB
向量出：4,000 行 × 256 B = 1.02 MB   （别人要的、归本卡的行）
向量入：4,000 行 × 256 B = 1.02 MB   （本卡要的、归别人的行）
────────────────────────────────
每卡合计 ≈ 2.1 MB
```

注意索引只有 32 KB，向量是 2 MB。索引在字节上不占主导，这一点与"先传索引"的直觉相反。索引真正的问题是数量：每卡 4,000 条消息、每条 8 B，消息数与小消息的固定开销会把 `A-15` 说的碎片化问题放大；而 `A-16` 的 `ids partition` 只有 55.10% 的 MBU，说明这条路由路径的效率也就刚过半。

第二层，跨组同步。`A-03` 同步的不是梯度，是表权重与优化器状态（反向与更新融合，不留梯度）。若整表同步：

```
整表同步：20.4 TB 总量 ÷ 512 卡 = 39.8 GB/卡
39.8 GB ÷ 50 GB/s = 0.80 s        ← 是 51 ms 预算的 15 倍，不可能
```

所以只能同步"这一步被写过的行"（脏行）。脏行数 = 本组唯一行数：

```
单组脏行 = 512,000
四组并集上界 = 4 × 512,000 = 2,048,000 行
脏行占全表 = 2.05e6 / 4e10 = 0.005%

集群总同步字节 = 2.05e6 × (256 + 256) B = 1.05 GB   （w 与 v 各 256 B）
每卡分摊      = 1.05 GB / 512 ≈ 2.05 MB
跨 4 组的 ring all-reduce：W = 2 × 2.05 MB × 3/4 ≈ 3.1 MB
时间 = 3.1 MB / 50 GB/s ≈ 0.06 ms
```

关键在最后两行：**1.05 GB 是集群总量，不是某一条链路上的流量**。把它除以单口 50 GB/s 会得到 21 ms（一个常见错误），正确的算法是每卡出站 3.1 MB、0.06 ms。整表同步之所以不可行，是因为每卡要搬 39.8 GB，而不是因为"1.05 GB 太多"。

第三层，组内与跨组的带宽差。`A-03` 实测把组限制在同一台机器内（8 卡同 host）时，同步比跨 host 快 7×。这条决定了 G 的拓扑约束：

```
组内（同 host，NVLink）：同步字节 / 900 GB/s   （B-04 报 NVLink 900 GB/s 双向）
跨组（跨 host，IB 400G）：同步字节 / 50 GB/s
```

同一个 1.05 GB，按带宽算是 1.2 ms 与 21 ms，差 18 倍。`A-03` 测到的端到端同步差距是 7×，比带宽差小——因为跨 host 的同步可以流水，带宽差不会全额转化成延迟差。但 7× 已经足以把 G=4 的收益吃干净，这是 `A-03` 建议把组压进单机的理由。

### 推导四：不均衡比的代数，以及 G 为什么没有闭式解

训练是串行 batch 序列，每一步的有效吞吐由最慢的卡决定：

```
有效吞吐 ≈ 均值 / 最大值 = 均值 × (1 / imbalance)
```

静态表级分片下，最慢的那张卡至少承担"它手里最重的那张表"的全部访问：

```
imbalance ≥ N × max_table_share
```

第 5 章的分档表里，10 张超大表占了大部分访问。设最大一张占 30%：

```
imbalance ≥ 128 × 0.30 = 38.4
```

`A-03` 在 CTR/ExFM 上测到 5.70，说明它的表数多（ExFM 4000+ 张）、最大表占比被摊薄到约 4.5%。这也解释了 2D 为什么能改善均衡：每组只看 N/G 张卡，每卡分到的表数是 `T·G/N`，多了 G 倍。

按随机分配的近似，每卡负载的标准差 ∝ `1/√m`（m = 每卡表数）：

```
m: 31 表/卡 (N=128)  → 125 表/卡 (N=128, G=4)
σ 下降 = √4 = 2×
实测   = 5.70 / 1.57 = 3.63×
```

`1/√m` 解释了大约一半，剩下的一半来自"最大的那张表不再独占一张卡"。所以这个模型只能给方向，不能给数值——要预测自己的 imbalance，得拿真实的表级访问分布去算。

顺带修正教程第 4 章的一句措辞：它说副本"只切到 32 卡，切分粒度小、基数小，容易均衡"。方向对，但"粒度小"容易读反——真正变小的是"单表独占一张卡"的概率，切分粒度其实是变粗了（每卡拿更多表）。

不均衡只回答"最慢的卡慢多少"，不回答"该不该加副本"。把两者接起来，需要把一次迭代的时间写成 G 的函数，四项各有出处：

```
T(G) = A/G          组内 all-to-all，量按 1/G 降（A-03 的机制）
     + B            稠密计算，与 G 无关
     + C·G          跨组同步，G 份副本各发一次
     + D/√G         不均衡尾部，每卡表数 ∝ G 所以 σ ∝ 1/√G
```

求极值：

```
dT/dG = -A/G² + C - D/(2·G^1.5) = 0
```

这是一个 G 的 2.5 次方程，没有漂亮的根。而且它还不是有效区间——内存约束先划走一大块：

```
G ≤ N × M / (S + S_opt)
```

N=4096 时上限是 16；N=512 时上限是 2（含状态）；N=128 时上限是 0.5，即 G=1 都装不下。

所以真实的求解顺序是：

1. 先由内存约束定出 G 的上界；
2. 在上界内，用同步频率（是否每步都同步）与拓扑（组是否压进单机）微调；
3. `A-03` 的经验值 G=4 是"内存还有余量 + 不均衡尾部还占主导"这个区间的产物，G=8 时同步项 `C·G` 反超，QPS 掉 15%。

不要去找一个闭式最优解。能算的只有上界与方向，剩下的靠实测。

## 算例

用[贯穿算例](../guide/running-example)，取 N=512、G=4、n=128。

<div class="example">

每卡内存（`G × (S + S_opt) / N`）：

```
参数：       4 × 10.2 TB / 512 = 79.7 GB     占 80 GB 的 99.6%
参数+状态：  4 × 20.4 TB / 512 = 159.4 GB    199%
fp16 表+状态：4 × 15.3 TB / 512 = 119.5 GB   149%
fp16+列切 c=2：4 × 7.65 TB / 512 = 59.7 GB    75%
```

四行里只有最后一行留得下激活与临时缓冲。要让 G=4 在 512 卡上跑，必须同时做两件事：表压到 fp16、维度切两半。任缺一件就 OOM。

组内 all-to-all（每卡每迭代）：

```
索引入：4,000 × 8 B   = 32 KB
索引出：4,000 × 8 B   = 32 KB
向量入：4,000 × 256 B = 1.02 MB
向量出：4,000 × 256 B = 1.02 MB
──────────────────────────────
合计 ≈ 2.1 MB，按 50 GB/s 走网 = 42 μs
```

跨组同步（只算脏行）：

```
四组脏行并集上界 = 2.05e6 行
每行同步 w + v   = 512 B
集群总字节       = 1.05 GB / 迭代
每卡分摊         = 2.05 MB；跨 4 组 ring W ≈ 3.1 MB
时间             = 3.1 MB / 50 GB/s ≈ 0.06 ms
```

把三个数放进 51 ms：

| 项 | 字节 | 时间 | 占 51 ms |
|---|---|---|---|
| 组内 all-to-all | 2.1 MB/卡 | 42 μs | 0.08% |
| 跨组同步（脏行） | 3.1 MB/卡（集群 1.05 GB） | 62 μs | 0.12% |
| 整表同步（不可行） | 39.8 GB/卡（集群 20.4 TB） | 0.8 s | 1,560% |

这张表给出算例里最反直觉的一条：**两项传输都远低于预算，跨组同步只是组内 all-to-all 的 1.5 倍**。体积比 19,000× 是"脏行 vs 整表"，不是"组内 vs 组间"。真正的大项不在传输，而在每步固定开销与稠密计算——这也是 batch 太小时系统的真实形态。

`A-06` 把 global batch 从 64K 加到 256K 就是为了让卡不空转；按 256K 缩放，上面所有字节乘 15.6，组内 all-to-all 变成 33 MB/卡、0.66 ms，跨组同步 48 MB/卡、0.96 ms，那时它们才开始可见。

不均衡的账：

```
200 张表 / 512 卡 = 0.39 表/卡 → 表级切分不可用，必须行切
若强行表级：最大表占 30% 访问 → imbalance ≥ 512 × 0.30 = 154
按 A-03 的 1.57 推算：有效吞吐 ≈ 均值 × 0.64
```

</div>

算例的结论是三条：容量上 G=4 在 512 卡只是"刚够放参数"，要靠 fp16 与列切才装得下状态；通信上，组内 all-to-all 与跨组脏行同步都在 0.1% 量级，`A-03` 的 1/G 只对第一层成立，而"1.05 GB"是集群总量、不能除以单口带宽；均衡上表级切分在 512 卡这个规模已经失效，200 张表不够分。

## 代价与边界

- 脏行同步是推导，不是 `A-03` 的原文。`A-03` 只说"同步表权重与优化器状态"，没有说明粒度；按行同步需要每个副本维护 per-row dirty bitmap，工程上可行但论文没展开。如果实现退化成整表同步，跨组这一项立刻从 41% 变成不可能。
- `S_opt = S` 是 AdaGrad 一份 fp32 累积量的假设。Adam 要两份，状态变 3 倍，上表所有数字乘 1.5——那时 512 卡连 fp16+列切都装不下。
- 20.6 GB/s 的聚合同步带宽看上去很小，是因为算例的 batch 小。真实系统的 global batch 更大，卡数也更多，这两个数会一起放大，结论（同步是主项）不变，但比例会变。
- `imbalance ≥ N × max_table_share` 是下界，不是估计。真实值取决于 ID 到卡的路由方式：按哈希打散会接近 1，按范围切会接近上界，`A-03` 的 5.70 落在中间。
- `A-03` 的 G=4 是 4096 卡、20.4 TB 状态下的折中，不能直接搬到 512 卡。G 的最优值随 N、表数、拓扑一起变，任何"抄 G=4"的容量规划都要重算。
- 列切分把索引流量乘 c，这一项在本算例里被 32 KB 的量级掩盖了，但 `c` 大起来会反超向量流量。`B-06` 的 Observation 1 还给了另一个代价：列切之后每一半的代价都大于原表的一半，总代价上升。

<div class="takeaway">

**本篇结论**：四维切分的代数只有一行——`mem_per_card = G × (S + S_opt) / N`。它同时说明为什么纯 DP 出局（G=N）和为什么 G 不能随便加（分子上乘 G）。

通信要按三层分开算：组内 all-to-all 每卡几 MB、跨组脏行同步每卡几 MB、整表同步每卡几十 GB。前两者都在 0.1% 量级；体积比 19,000× 说的是"脏行 vs 整表"，不是时间比。`A-03` 的 1/G 只对第一层成立。

G 的最优值先由内存上限决定，再由同步频率微调。教程第 4 章的 128 卡 / G=4 是通信示意；容量上它要 512 卡起步，含优化器状态要 1,024 卡。
