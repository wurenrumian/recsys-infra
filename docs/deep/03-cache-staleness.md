# 深潜 3. 缓存命中与过期：Zipf、漂移与 s=100

<div class="deep-anchor">

**对应教程** [第 8 章](../guide/08-caching-consistency)给了"允许有界过期"的结论和 `B-02` 的 AUC 表；这里把命中率算成缓存大小的函数，把 `s` 算成秒。

</div>

## 本篇要算的问题

教程第 8 章的两个关键数字都是引用的，没有推导：`A-10` 的"1% 承担 92%"与"命中率 91%→82%"，`B-02` 的"s=100 几乎无损、s=∞ 崩溃"。

本篇要回答四个问题：

1. 给定表和缓存大小，命中率是多少？加一倍缓存能涨多少？
2. "1% 承担 92%"对应什么样的分布，这个分布下缓存还有多大用？
3. 91%→82% 这九天里发生了什么，多久该刷一次缓存？
4. `s=100` 是多少秒的过期，业务该拿什么标准定这个数？

## 先给结论

1. 命中率是 `H(C) = sum(i^-s, i=1..C) / sum(i^-s, i=1..N)`。N=4×10¹⁰ 时，缓存 10⁸ 行（整表的 0.25%）能覆盖 76.0%（s=1）、98.3%（s=1.2）、99.99%（s=1.5）。
2. 命中率主要由尾部指数决定，不由缓存大小决定。要 95% 命中，s=1 需要 2.9 TB 缓存（整表的 28.5%），s=1.2 只需 293 MB。两者差四个数量级，缓存策略再聪明也跨不过这道差。
3. 边际收益随 ln C 递减，且 s 越大衰减越快：s=1 时每翻一倍稳定加 2.8 个点（对数律），s=1.2 在 10⁷ 行处每翻一倍只加 0.46 个点。
4. `s=100` 在 51 ms 迭代下是 5.1 秒，但这个数只对"每步都被更新的热点行"成立。`s` 是时钟单位不是时间单位，冷行的 100 步可能是 100 天。

## 符号与模型

| 符号 | 含义 | 本篇取值 |
|---|---|---|
| `N` | 表的总行数 | 4×10¹⁰ |
| `C` | 缓存能放的行数 | 10⁶ / 10⁷ / 10⁸ |
| `s` | Zipf 指数（尾部陡度） | 1 / 1.2 / 1.5 |
| `H(C)` | 缓存 C 行时的命中率 | 待算 |
| `t_step` | 一次迭代的时间 | 51 ms |
| `ρ` | 某行每步被更新的次数 | 1（假设） |
| `τ_drift` | 分布漂移的时间常数 | 天 |
| `Z` | 归一化常数 `sum(i^-s, i=1..N)` | 待算 |

Zipf(s) 假设第 i 热门的行承担 `i^-s / Z` 的访问。这是个假设，不是定理；`A-10` 的两次测量（1% 承担 92%、0.1% 承担近 90%）与 `B-04` 用的 `a = 1.2` 是三个不同的数据点，本篇用它们校准 s，不做统一。（⚠️ 待核实：`A-10` 与 `B-04` 的具体拟合方法。）

命中率的定义只有一行：

```
H(C) = sum(i^-s, i=1..C) / sum(i^-s, i=1..N)
```

注意分母是整表而不是"本 batch 访问到的行"。这两个口径差很多：按 batch 算的分母小，命中率会被系统性地高估。`A-10` 报的"bs=16,384 时只有约 10% 的去重嵌入能从缓存里拿到"，说的就是按 batch 口径的命中率——500 个热门行覆盖了总访问的 92%，但在一个 6.5 万唯一行的大 batch 里，热门行只占很小一部分。

## 推导

### 推导一：Zipf 命中率的三个可算点

N=4×10¹⁰ 时，分母用两种近似：

```
s = 1：   Z ≈ ln N + γ = 24.41 + 0.577 = 24.99
s ≠ 1：   Z ≈ ζ(s) - N^(1-s)/(s-1)
          s=1.2 → 5.5914 - 5 × N^-0.2 = 5.5626
          s=1.5 → 2.6124 - 2 × N^-0.5 = 2.6124
```

分子的近似分别是 `ln C + γ` 与 `ζ(s) - C^(1-s)/(s-1)`。代入：

| 缓存 C | 占整表 | s=1 | s=1.2 | s=1.5 |
|---|---|---|---|---|
| 10⁶ | 0.0025% | 57.6% | 94.8% | 99.92% |
| 10⁷ | 0.025% | 66.8% | 96.9% | 99.98% |
| 10⁸ | 0.25% | 76.0% | 98.3% | 99.99% |
| 4×10⁸（1%） | 1% | 81.6% | 99.2% | 99.997% |

这张表最该记住的是最后一行与 `A-10` 的对照：`A-10` 说 1% 的嵌入承担 92% 的访问，而 s=1 在同样 1% 上只给 81.6%。反解 92% 需要：

```
s ≈ 1.07   （用 ζ(1+ε) ≈ 1/ε + γ 近似，误差约 ±0.01）
```

所以"1% 承担 92%"对应一个比 s=1 陡一档的分布。这个校准决定了容量规划的方向：按 s=1 算，你会以为同样大小的缓存只能覆盖八成，从而过早放弃缓存；按 s≈1.1 算，它其实覆盖九成以上。反过来，如果真实分布是 s=0.9（比 1 更平），10⁷ 行缓存只能拿到四成上下，那时任何缓存方案都不值得投入。三段结论差这么多，源头只是分布尾部的一个指数。

H(C) 的形状值得单独看一眼（s=1，横轴 log C）：

```
H
100% ┤                                    ╭─────  ← 渐近于 100%，但永远到不了
     │                          ╭─────────╯
 80% ┤                 ╭────────╯
     │         ╭───────╯
 60% ┤  ╭──────╯
     │ ╭╯
 40% ┤─╯
     └──┬────────┬────────┬────────┬────────┬───→ log C
        10^4    10^6    10^8    10^10   4×10^10
```

这条曲线没有拐点，只有越来越小的斜率。这就是"加缓存"的边际收益问题。

### 推导二：命中率是尾部指数的函数，不是缓存大小的函数

把要求反过来问：要 95% 命中率，缓存要多大？

```
s = 1：   ln C + γ = 0.95 × 24.99 = 23.74
          C = e^(23.74 - 0.577) = 1.14 × 10^10 行
          字节 = 1.14e10 × 256 B = 2.92 TB（整表的 28.5%）

s = 1.2： 5.5914 - 5 × C^-0.2 = 0.95 × 5.5626 = 5.2845
          C^-0.2 = 0.0614 → C = 1.15 × 10^6 行
          字节 = 1.15e6 × 256 B = 293 MB（整表的 0.003%）
```

2.92 TB 与 293 MB 差四个数量级。同样一张 10.2 TB 的表，同样要 95% 命中率，s 从 1 挪到 1.2 就把缓存需求从"半台机器的内存"变成"一张卡的显存"。

这解释了 `A-11` 那张 Figure 6 的两端：

```
高局部性数据集（Criteo）：一小部分热条目极高频 → 加大缓存边际收益很小
低局部性数据集（Alibaba User 表）：要拿高命中率，需要超过 80% 的表条目进 GPU
```

80% × 10.2 TB = 8.2 TB。这不是"缓存调优"能解决的问题，是分布不允许。所以"该不该做缓存"这个决策的第一问不是"缓存多大"，而是"我们的访问分布有多陡"——这个问题用一条访问频率直方图就能回答，不需要先建系统。

同时注意 95% 命中率还意味着 5% 的访问要走远端。按第 1 篇的口径，本地 450 GB/s、远端 50 GB/s，等效带宽是两者的调和加权：

```
95% 命中：BW_eff = 1 / (0.95/450 + 0.05/50) = 1 / 0.00311 = 321 GB/s
99% 命中：BW_eff = 1 / (0.99/450 + 0.01/50) = 1 / 0.00240 = 417 GB/s
```

等效带宽从 321 GB/s 升到 417 GB/s，同一批字节的时间降 23%。这就是为什么 s 陡一点值那么多钱：它不只省带宽，还直接改延迟。

### 推导三：边际收益，与漂移的时间常数

先算边际收益。对 `H(C)` 关于 `ln C` 求导：

```
s = 1：   dH/dlnC = 1/Z = 1/24.99 = 4.0%（每 e 倍）
          每翻一倍 = 4.0% × ln 2 = 2.77 个百分点
s = 1.2： dH/dlnC = C^(1-s) / ((1-s)·Z)，随时间衰减
          10^7 → 2×10^7：+0.46 个百分点
s = 1.5： 10^7 → 2×10^7：+0.007 个百分点
```

s=1 是唯一"每翻一倍都固定涨 2.8 点"的情形，因为对数律里 `ln C` 的系数是常数。s>1 时斜率本身在衰减：缓存越大，新增的每一行越冷。`B-08` 把这件事说得更彻底——它把缓存目标从"命中率"改成"提取时间"，理由是命中率与延迟不是单调关系，本地命中率的提高可能以全局覆盖为代价。

再看漂移。`A-10` 的实验是固定第一天的 top 0.05% 做缓存，观察后续九天的命中率：

```
day 1：91%      day 9：82%
```

把命中率写成指数衰减：

```
H(t) = H_inf + (H_0 - H_inf)·e^(-t/τ_drift)
0.82 = H_inf + (0.91 - H_inf)·e^(-9/τ)
```

`H_inf` 是热集完全换掉之后的命中率（即"昨天的热集今天还剩多少"的下限）。它的值论文没给，只能反推：

| 假设 `H_inf` | 反解 `τ_drift` | 含义 |
|---|---|---|
| 0.75 | 10.9 天 | 热集换得很慢，旧的还剩很多 |
| 0.70 | 16.1 天 | 中位假设 |
| 0.60 | 26.3 天 | 热集几乎全换 |

τ 的估计在 11–26 天之间，取决于一个没测的量。这说明"91%→82% 九天"这一条数据不足以定出衰减规律，只能定出量级：漂移的时间尺度是周，不是小时，也不是年。

有了 τ 就能算刷新周期。允许掉 `ΔH` 个点：

```
t_refresh = τ · ln( (H_0 - H_inf) / ΔH )
```

按 τ=16 天、H_inf=0.70 算：

| 容忍掉点 | 刷新周期 |
|---|---|
| 3 点 | 16 × ln(21/3) = 31 天 |
| 6 点 | 16 × ln(21/6) = 20 天 |
| 9 点（掉到 82%） | 16 × ln(21/9) = 13.6 天 |

这条式子把"多久刷一次缓存"从经验问题变成参数问题。工程上还该加一条：刷新本身要花时间，所以周期不能短于"重建热集"的耗时——否则永远在刷新。

### 推导四：有界过期，s 步等于多少秒

`B-02` 的 `s` 是时钟单位，不是时间单位。它的判据是两条：

```
c_c ≤ c_s + s        # 本地不能跑得比拉取点太远
c_g ≤ c_c + s        # 本地不能落后全局太远
```

`c_g` 是"这一行在 server 上的累计更新次数"。所以 `s=100` 的意思是"本地副本最多落后 100 次该行的更新"。换算成秒：

```
过期窗口 = s × t_step / ρ
ρ = 1（假设该行每步被更新一次）
s = 100, t_step = 51 ms
过期窗口 = 100 × 51 ms = 5.1 秒
```

这里的 `ρ` 是关键，也是这一节最容易被跳过的地方。`s` 对所有行是同一个数，但每行的 `ρ` 差几个数量级：

| 行的类型 | 更新频率 | `s=100` 的过期窗口 |
|---|---|---|
| 头部热点（top 0.05%） | 每步一次 | 5.1 秒 |
| 中部 | 每千步一次 | 85 分钟 |
| 尾部 | 每万步一次 | 14 小时 |

所以 `s=100` 不是"全局 5 秒的过期"，而是"热点 5 秒、冷门十几小时"。这个不均匀性是有利的：冷行本来就没人读，过期了也无所谓；热点行读得频繁，每次读都会走 `CheckValid`，超界就重拉。于是热点行的实际过期窗口被"访问间隔"再削一刀：

```
实际窗口 = min( s × t_step / ρ , 该行的平均访问间隔 )
```

热点行的访问间隔可能只有几步，所以它几乎总是新鲜的。真正长期过期的只有"被缓存住但很久没人读"的行——这类行的更新对模型也几乎没影响。

写过期的价值在这里。`B-02` 的写协议是"只在本地累加梯度，直到驱逐才写回"：

```
Write(keys, grads):
  for k in keys:
    cache.Update(k, grad)    # 本地累加
    c_c += 1                 # 读己所写
  Evict()                    # 只在缓存满或失效时回写
```

对比 SSP 的 write-through，这一条砍掉了"每次写都走网络"。效果是嵌入通信降低最多 88%（≈ 1 − 1/8.2）。这 88% 属于它自己的配置，换个集群、换个网络不会重现同一个数。

精度代价见 `B-02` 的 Criteo 实测：

| 过期阈值 | WDL | DFM | DCN |
|---|---|---|---|
| s=0 | 79.64 | 79.74 | 80.25 |
| s=100 | 79.62 | 79.73 | 80.24 |
| s=10k | 78.84 | 78.96 | 79.76 |
| s=∞ | 74.61 | 70.91 | 75.29 |

三个非常规数字的语境要分清：78.84 是 WDL 在 s=10k 时的 AUC（比基线掉 0.8 点）；70.91 是 DFM 在 s=∞ 时的 AUC（掉 8.8 点，崩得比 WDL 的 74.61 更狠）；88% 是通信降幅，不是精度。三者在同一张论文里但不同表里，混着引用会得出错误的结论。

要给它一个模型，可以写"读到过期副本的概率"：

```
P(stale) ≈ 1 - e^(-s/τ_upd)
```

τ_upd 是该行两次更新之间的平均时钟间隔，单位与 s 相同。这个模型只解释两件事：

- s 远小于 τ_upd 时 P 接近 0，读到的几乎都是新值，但也几乎拿不到写合并的收益；
- s 远大于 τ_upd 时 P 接近 1，本地副本基本是旧的，`s=∞` 那一行就是这么崩的。

它不能预测拐点在哪。拐点位置由 τ_upd 的分布与优化器对噪声的容忍度共同决定，只能实测。所以"我们的业务 s 该取多少"没有公式可套，只有 `B-02` 那套递进式实测法：从 s=0 起，取 {10, 100, 1000, 10000} 各跑一次短训练，找精度仍在噪声内的最大值。

最后是三选二。缓存这个位置只有三个量，最多同时优化两个：

```
        新鲜度
         /\
        /  \
       /    \
  通信量 ──── 命中率
```

| 取舍 | 谁在做 | 代价 |
|---|---|---|
| 保新鲜 + 高命中 | `A-10`/`A-11` 预知路线 | 只能离线；换来 `A-11` 平均 5.1×、最高 6.6×，代价是约 3 GB 显存与流水复杂度（⚠️ 待核实具体值） |
| 保新鲜 + 省通信 | 严格一致 + 同步写回 | 每次写都要走网，通信量最大 |
| 高命中 + 省通信 | `B-02` 有界过期 | 精度有界损失，s 要实测 |
| 换目标函数 | `B-08` UGache | 不优化命中率而优化提取时间，平均 1.93× |

`A-11` 的四个 RAW 依赖说明了"保新鲜"这条路为什么贵：流水化之后 `RAW-4`（写回的驱逐值 vs 读未命中值，发生在 CPU 表上）必须靠 Hold mask 把"未来 2 个 batch 会用的 ID"全部排除在受害者之外，这直接要求 Storage 能装下 6 个 mini-batch 的最坏情况。新鲜度不是免费的，它要用显存与调度复杂度换。

## 算例

用[贯穿算例](../guide/running-example)：400 亿行、256 B/行、10.2 TB，每迭代去重后 525 MB。

<div class="example">

缓存 10⁸ 行有多大，命中率多少。

```
容量 = 1e8 × 256 B = 25.6 GB        （40 GB 的卡放得下，占整表 0.25%）

s = 1.0 → H = 76.0%，miss = 24.0%
s = 1.2 → H = 98.3%，miss = 1.7%
```

miss 的字节与时间（按**每卡 4.1 MB** 计；全批口径就是下表 ×128）。

```
s=1.0：0.240 × 4.1 MB = 0.98 MB/迭代
       走网络 50 GB/s   → 0.020 ms     占 51 ms 的 0.04%
       走本地 450 GB/s  → 0.0022 ms

s=1.2：0.017 × 4.1 MB = 0.07 MB/迭代
       走网络 50 GB/s   → 0.0014 ms    占 51 ms 的 0.003%
```

在 51 ms 的预算下这两个数都不显眼，但它们的比值不变：s 从 1.0 到 1.2，网络流量差 14 倍——同一个 25.6 GB 的缓存，s=1 时省下 76% 的流量，s=1.2 时省下 98%。命中率值多少钱，取决于每卡 payload 有多大：global batch 到 256K 时每卡 65 MB，这一项会跟着放大 15.6 倍。

要 95%，缓存要多大。

```
s=1.0 → 2.92 TB，占整表 28.5%   → 单机放不下，要跨机，于是"缓存"退化成"分层存储"
s=1.2 → 293 MB，占整表 0.003%   → 一张卡随便放
```

过期窗口。

```
s = 100, t_step = 51 ms, ρ = 1
窗口 = 100 × 0.051 s = 5.1 秒
```

5.1 秒对什么场景是问题？

| 场景 | 5.1 秒的过期可接受吗 |
|---|---|
| 离线批量训练（数据固定） | 可以，`A-10`/`A-11` 干脆用预知做到零过期 |
| 分钟级更新的近线训练 | 可以，5 秒小于数据更新周期 |
| 秒级反馈的在线学习 | 接近边界，要按 `B-02` 的方法实测 |
| 实时出价、风控同步特征 | 不行，语义要求强一致 |

`B-02` 的数据支持前三档：s=100 时 WDL 只掉 0.02 点。但它的实验是 Criteo 上的短期训练，长期是否有累积偏差，论文没给。

反过来问：能容忍 30 秒过期，s 能放多大。

```
s = 30 s / 0.051 s = 588
```

按 `B-02` 的曲线，s 从 100 到 10k 之间精度会开始掉（10k 时掉 0.8 点），588 落在中间，属于必须实测才敢用的区间。

</div>

算例给出一个可操作的判据：先画访问频率直方图估 s，再由 s 定缓存容量（要 95% 就看 2.9 TB 还是 293 MB），最后由业务的更新周期定过期窗口。三个数只要一个变了，另外两个都要重算。

## 代价与边界

- Zipf 是假设。真实访问分布在头部常常偏离幂律（新上架、强运营的商品会形成第二梯队），这时 H(C) 的实际值低于模型值。`A-10` 的两次测量（1%/92% 与 0.1%/90%）本身就互相不一致，说明单一 s 描述不了全部数据。
- s=1.5 那一列是数学上存在、现实里不会出现的边界：它意味着 234 行承担 95% 的访问。列出来是为了展示"分布越陡、缓存越划算"的极限，不能当作可实现的档位。
- 漂移拟合依赖 `H_inf` 这个没测的量，τ 的估计跨 11–26 天。`A-10` 只给了九天两个点，拟合一条指数曲线是过度解读；这里给区间而不是点值。
- `s` 是时钟单位。把它换算成秒需要 `ρ`（每步更新次数）的分布，而 `B-02` 只给了聚合的 AUC，没有给 `ρ`。5.1 秒是 `ρ=1` 的特例，热点行与冷门行的真实窗口差三个数量级。
- 88% 是通信降幅，来自 `B-02` 自己的配置（缓存占全局表 10%、s=100、1–10 Gbps 以太网）。换到 RDMA 集群上，通信占比本来就低，这个数会压缩。
- 缓存容量与 TLB 覆盖是同一件事的两种记账。第 1 篇算过 2 MB 大页的 TLB 只能覆盖 8 GB，而这里算出的热点集在 293 MB–2.9 TB 之间：热点集小于 8 GB 时页表也顺带变好，大于 8 GB 时缓存命中了页表仍然要收费。两个指标要一起看。
- `B-01` 的"最多省 94% 内存"是推理侧的另一条路：用低精度与 key 代理换容量，代价 0.2% 精度。它不改变本篇的命中率算术，但把"缓存放不下"这个约束松掉了一档。

<div class="takeaway">

**本篇结论**：命中率是分布的函数，缓存大小只是自变量之一。s=1 时 10⁸ 行（25.6 GB）覆盖 76%，s=1.2 时覆盖 98%；要 95% 分别需要 2.9 TB 与 293 MB。

边际收益随 ln C 递减，s=1 每翻一倍加 2.8 点，s=1.2 在 10⁷ 行处只加 0.46 点。

过期窗口 = `s × t_step / ρ`。s=100 在 51 ms 下是 5.1 秒，且只对热点行成立。能容忍多少秒，取决于业务的更新周期与一致性语义，没有通用答案。
