# 深潜 4. 压缩的预算与帕累托：位宽、秩与查询代价

<div class="deep-anchor">

**对应教程** [第 9 章](../guide/09-compression)给了"三条轴"；这里给每条轴的代价函数。

</div>

## 一句话版本

第 9 章把嵌入表的压缩分成三条轴：剪枝少存行、量化少存位、张量分解换一种表示。三个方向各有一篇代表作和一个压缩比，判据只有一句——压缩比不等于加速比。

这篇把三条轴各写成一个能代入数字的代价函数，算清它省多少容量、又让每次查询多付多少。前两条轴的账近似线性：省下的字节与删掉的行数、砍掉的位宽成正比，查询端几乎不额外花钱。第三条轴用秩的平方换容量，单次查询读的字节反而可能超过原来的一整行。

答案分两半。量化的门槛极低，算力带宽比超过约 0.6 op/byte 就过线，GPU 上几乎总过线；张量分解在秩稍大时，单次查询读的字节比直接读一行还多。所以判断一个方案能否省时间，只需把这张卡的"每秒运算 ÷ 每秒搬字节"与它的"多算的运算 ÷ 少读的字节"放在一起比。

## 这篇的地图

全篇分四块，加一个算例。前三块一条轴一块，第四块把三条轴合到同一个预算式里。

1. **轴一 · 剪枝**：省容量，付一张索引表。删行让表按比例变小，行号要重映射，删掉的行回不来。
2. **轴二 · 量化**：省容量，付一次解码。位宽减半，每行字节减半，查询时要还原低位宽的数。
3. **轴三 · 张量分解**：容量按秩的平方改善，查询读得更多。收益变成平方关系，代价第一次为正。
4. **一把尺子**：三条轴放进同一个查询预算。用算力带宽比判断谁真省时间，并说明五个方案为什么不能排序。

顺序按查询代价由零变正排：前两条轴几乎不额外花钱，可以先看容量斜率；第三条轴的代价必须单独算；到第四块才把三者放在一列里比较。算例把 10.2 TB 分别按 int8、int4 与张量分解（TT）压一遍。

| 概念 | 一句话 |
|---|---|
| 压缩比（压缩率） | 压缩后体积缩到几分之一；只说装得下，不说读得快 |
| 加速比 | 端到端时间缩短几倍；与压缩比之间隔着一整段查询代价 |
| 帕累托前沿 | 在"多压一点"和"查快一点"之间，无法再两全其美的那条边界 |
| 位宽 | 每个数占几个 bit；位宽减半，每行字节减半 |
| 秩 | 张量分解里每个核的横向尺寸，同时决定压缩比与精度 |
| 算力带宽比 | 每秒能做多少运算，除以每秒能搬多少字节 |
| 剪枝 | 按重要性删掉一部分嵌入行；省容量，但删掉的行物理上没了 |

### 符号与取值

| 符号 | 含义 | 取值 |
|---|---|---|
| `N` | 表总行数 | 4×10¹⁰ |
| `d` | 嵌入维度 | 64 |
| `S` | 表总字节（fp32） | 4×10¹⁰ × 256 B = 1.024×10¹³ B ≈ 10.2 TB |
| `b` | 每行位宽 | 32 / 8 / 4 |
| `ρ` | 剪枝后保留的行比例 | 0.35–0.60 |
| `r` | TT 秩 | 受 `r ≤ d` 约束 |
| `k` | TT 核个数 | 示意取 5 |
| `B_eff` | 单卡有效随机带宽 | ⚠️ 示意 1 TB/s |
| `F` | 单卡有效算力（非张量） | ⚠️ 示意 20 T op/s |
| `R` | `F / B_eff`，算力带宽比 | ⚠️ 示意 20 op/byte |

四条代价函数的完整形式如下，后面每块取一行。`8b` 是 `d·b/8` 在 `d=64` 时的简写。

```
容量（轴一、二）  S = ρ · N · d · b/8
容量（轴三）      S_TT = k · n · r² · 4 字节          n = N^(1/k)
查询（轴二）      T = 8b/B_eff + c·d/F               c ≈ 2
查询（轴三）      T_TT = 4k·r²/B_eff + k·r²/F
```

术语与符号到此交代完毕。先从容量账最干净的那条轴开始。

## 第一块 · 剪枝：省容量，付一张索引表

这块要回答的是：删掉一部分行能省多少，代价落在哪里。

剪枝的做法是给每行打一个重要性分数，只保留分数高的行。`ρ` 是保留比例，`B-12` 报的范围是 0.35–0.60。容量与保留比例成正比：

```
S(ρ) = ρ · N · d · 4 = ρ × 10.2 TB
ρ = 0.5  →  5.12 TB（省一半）
```

### 代价是索引

看起来没有额外代价：少查就是省。但删行之后，原 ID 不能直接当行号用，要经过一张映射表（ID → 新行号），这张表本身要占内存：

```
映射表 = ρ · N × 4 字节 = 0.5 × 4×10¹⁰ × 4 = 80 GB
占省下量的比例 = 80 GB / 5.12 TB ≈ 1.6%
```

1.6% 可以忽略，所以轴一的容量账几乎是纯赚。两件事要写清楚：

- `B-12` 的 35–60% 是部署所需嵌入大小的节省，不是训练峰值显存。它要在训练中在线判定重要性，那部分统计状态不在节省里。
- 查询侧多一次间接寻址（ID → offset → row）。在带宽受限的 gather 里，这次寻址通常被掩盖（⚠️ 示意，<5%），但它让"行号"从物理地址变成逻辑量，这也是剪枝不可逆的根源——删掉的行，物理上没了。

容量与保留比例成正比，代价是一张 1.6% 的索引表和不可逆。第二条轴换一个维度来省：行数不动，改每行占几个 bit。

## 第二块 · 量化：省容量，付一次解码

这块要回答的是：fp32 换成 int4，每行省多少字节、每次查询多付多少计算，门槛在哪。

量化把每个数的位宽压低，比如从 32 bit 的浮点压到 8 bit 或 4 bit 的整数。每行 64 个元素，每行字节数是 `d·b/8 = 8b`：

```
fp32   32 bit × 64 / 8 = 256 B
int8    8 bit × 64 / 8 =  64 B     （4×）
int4    4 bit × 64 / 8 =  32 B     （8×）
```

`B-11` 报的 8× 就是这个除法：2.161 GB → 0.270 GB，比值 8.00。位宽账不需要任何假设，只由位宽决定。

顺带把中间档补齐，好看出这条轴的斜率：

| 位宽 | 每行字节 | 相对 fp32 | 相对上一档 |
|---|---|---|---|
| fp32 (32 bit) | 256 B | 1× | — |
| fp16 / bf16 (16 bit) | 128 B | 2× | 2× |
| int8 | 64 B | 4× | 2× |
| int4 | 32 B | 8× | 2× |

这张表怎么读：每往下一行位宽减半，字节也减半，相对上一档都是 2×。所以这条轴没有"红利区"，只有"你敢砍到多低"。工业上停在 int4 而不是 int2，原因不在表示能力（`B-11` 附录测过 INT2，仍能治过拟合但精度掉得更多），在精度余量——2 bit 只有 4 个量化格点，误差方差是 int4 的 16 倍。

### 损失有多大

给一张表的量化范围 `[min, max]`，b 位均匀量化的步长与误差方差是

```
q = (max − min) / 2^b
e ~ U[−q/2, q/2]
Var(e) = q² / 12
```

q 是步长，e 在半个步长内均匀分布，方差因而是 q²/12。误差方差随 `1/4^b` 下降，等效 SQNR 每 bit 提 6 dB（标准结果，满幅正弦下 `SQNR ≈ 6.02b + 1.76`）。int4 比 fp32 少 28 bit，理论 SQNR 低约 168 dB。

这一步已经把"无损"排除掉了。量化不可能无损，只可能做到"损失在业务指标上看不见"。

那 `B-11` 的"精度不降反升"从哪来？只能由正则解释：

- 若增益来自"压缩无损"，精度应与 b 无关，或在低位宽处掉——实测是单调改善。
- 若增益来自正则，正则强度应随 `1/2^b` 增，精度随 b 单调改善——实测（Table 2：INT16 → INT8 → INT4 逐级上升）正是这个形状。

两条证据都指向后者。⚠️ 具体是噪声注入、平坦极小还是别的机制，论文页没给，属推断；结论也不能外推到不过拟合的场景——`B-11` 自己承认没测。

### 查询只多一次变换

查询代价那一半写成两项：

```
T(b) = 8b/B_eff + c·d/F
T(4) < T(32)  ⟺  (256 − 32)/B_eff > 128/F  ⟺  R = F/B_eff > 0.57
```

第一项是读入字节除以有效带宽（⚠️ 示意 1 TB/s），第二项是解码算力除以有效算力（⚠️ 示意 20 T op/s），`c ≈ 2` 是每元素两次运算。移项之后，判据只剩 `R = F/B_eff`。

门槛只有 0.57 op/byte。⚠️ 按示意值 `R ≈ 20`，余量 35 倍，解码在 GPU 上几乎不额外花时间。所以瓶颈不在解码算力，在粒度：`B-11` 用 per-table 量化（一张表一组 scale），表内 range 差异大时低位宽会截断大值，这是它局限里明写的。

轴二的容量收益是线性的，查询代价在 GPU 上可以忽略。第三条轴两项都不成立：收益是平方关系，查询代价是正的。

## 第三块 · 张量分解：压缩比按 1/r²，查询反而更贵

这块要回答的是：TT 的压缩比由什么决定，为什么它换来的不只是存储。

张量分解不删行也不改位宽，它换一种表示：把 N 行的表拆成 k 个核（core），第 i 个核形状 `r_{i−1} × n_i × r_i`，且 `∏ n_i = N`。取统一的 n 与 r：

```
核参数量  ≈ k · n · r²
压缩比    = N·d / (k·n·r²) = d · N^(1−1/k) / (k·r²)
```

`r` 是秩（rank），核的横向尺寸；`k` 是核个数，示意取 5。三个变量的作用方向不同：

| 变量 | 对压缩比 | 对精度 | 说明 |
|---|---|---|---|
| `r` 增 | 压缩比按 1/r² 掉 | 精确性上升 | 压缩比与精度共用的唯一旋钮 |
| `N` 增 | ∝ N^(1−1/k)，变好 | — | 表越大 TT 越划算 |
| `k` 增 | 变好 | — | 但核数多，单次查询要读更多核 |

这张表怎么读：r 占一行，因为它同时作用于压缩比和精度，方向相反；N 与 k 只影响压缩比与查询成本。r 也是全文最关键的量，它同时是压缩比旋钮和精度旋钮，这是 TT 没有"无损档位"的结构性原因——不存在"把 r 调到无损、压缩比还留在高位"的区域。

`B-07` 引用的 TT-Rec 数据（Kaggle 上 4–221×，精度掉 0.03%–0.3%）正好落在这条曲线上：两端点精度随压缩比单调，中途没有平台。⚠️ 逐点的秩-精度对应待核实，论文页只给了两个端点。

### 查询侧：一次 lookup 变成 k 次短读

查询侧才是这一轴的真正代价。一次 lookup 不再是"读一行"，而是"每个核读一个 `r×r` 的 slice，再把 k 个 slice 收缩成 d 维"：

```
TT 单次查询读：k · r² · 4 B
直接读一行：    d · 4 B = 256 B

r=8, k=5  →  5 × 64 × 4 = 1280 B   是 256 B 的 5 倍
r=4, k=5  →  5 × 16 × 4 =  320 B   仍多 25%
```

这就是"表示层压缩的成本不只在存储"的代数形式：每行 256 B 的定长读，换成 k 个短读加 k·r² 次乘加。容量省了三个数量级，单次查询的字节反而涨了。

救兵是复用：同一 batch 里同一 ID 的 slice 只读一次，摊销字节变成 `k·r²·4/m`（m 为复用次数）。`B-07` 的索引重排就是在提高 m，`A-13` 要消除的"TT 运算冗余"是同一件事——表示层压缩的成本，最终要靠数据布局去回收。

### 秩被两个上限夹住

容量与单次查询字节都挂在 `r²` 上，方向却相反：`r` 减小，容量按 1/r² 变好，但精度崩；`r` 增大，精度回来，容量与查询成本一起变坏。于是"TT 值不值"压成一个二元判断：

```
r 必须 ≤ d            （物理上限：r 超过输出维度就没有意义）
r 必须 ≥ r_需要精度     （数据上限：由这批数据的有效秩决定）
可行 ⟺ d ≥ r_需要精度
```

`d=64` 意味着 TT 在 64 维上最多只有 64 个"表示方向"。表越大、数据越杂，`r_需要精度` 越高，越容易撞到 `d`。所以 TT 的适用面由维度与数据的可压缩性决定，不由表大小决定——这解释了为什么它在大表上反而可能先撞墙。

张量分解把容量按 1/r² 换掉，代价是查询按 k·r² 变贵，而 r 同时被 d 与数据的有效秩夹住。三块各自的式子齐了，下一块把它们放进同一个预算。

## 第四块 · 一把尺子：三条轴放进同一个查询预算

这块要回答的是：什么时候压缩真的省时间，什么时候只是把容量问题换成算力问题。

一次查询的时间永远是两项之和：

```
T_query = 访存 + 解码/收缩
        = (每查询读入字节)/B_eff + (每查询计算量)/F
```

压缩改变第一项（↓），有时抬高第二项（↑）。净赚条件是省下的读入时间大于多付的计算时间：

```
Δ读入字节 / B_eff  >  Δ计算量 / F
即   R = F/B_eff  >  Δ计算量 / Δ读入字节
```

右边由方案决定，左边由机器决定。代入三轴：

| 手段 | Δ读入字节 | Δ计算量 | 门槛 `R >` | 判断 |
|---|---|---|---|---|
| int8/int4 | −224 B/行 | +128 op/行 | 0.57 | 过线（示意 R≈20） |
| TT (r=8,k=5) | **+1024 B/行** | +320 op/行 | 负数，无解 | 必须有复用 |
| 剪枝 | −ρ×256 B/行 | ≈0 | 0 | 过线 |

这张表怎么读：int8/int4 的门槛 0.57 就是上一块算出的数，示意值 `R ≈ 20` 过线；TT 一行的读入字节反而增加 1024 B，门槛算出来是负数，按这条判据无解，必须靠复用把读入摊薄才划算；剪枝几乎不增加计算，门槛为 0。

同一把压缩刀，在"快内存、慢计算"的机器上（CPU 侧解码，R 小）会亏；在 GPU 上会赚。这解释了为什么量化在训练里无损、在 CPU 推理里常被吐槽慢——不是算法不同，是 R 不同。

把五个方案放到"压缩比 × 精度代价 × 查询算力"三维里：

| 论文 | 压缩比 | 精度代价 | 查询算力 | 基线 / 数据 |
|---|---|---|---|---|
| `B-03` CAFE+ | 10000× | AUC +3.94% | HotSketch 一次 + 两路查表 | Criteo（Kaggle / TB） |
| `B-10` MPE | 200× | ±1e-4（噪声级） | 反量化 + 分组查表 | Criteo / Avazu / KDD12，小模型 |
| `B-11` DQRM | 8× | +0.148% acc | 每元素一次变换 | Kaggle / Terabyte |
| `B-07` EL-Rec | 未给（参照 TT-Rec 4–221×） | 0.03%–0.3%（参照） | 每查询 k 次短读 + 收缩 | Criteo TB，单卡 V100 |
| `B-12` AdaEmbed | 表大小 35–60% | 精度升 | 无（少查） | Meta 生产，无公开集 |

这张表怎么读：三列分别回答压了多少、精度掉了多少、每次查询多花什么。帕累托前沿的横轴也不是压缩比，而是"压缩比 × 单次查询成本"；五篇论文的分母不同，就算按这个横轴排，也排不出有意义的次序。

判据只有一条：`R = F/B_eff` 是否大于 `Δ计算/Δ读入`。量化在 GPU 上几乎总过线，TT 在秩稍大时读得比原来更多。下面把三档代进[贯穿算例](../guide/running-example)。

## 算例：把 10.2 TB 压三遍

这一步在算什么：用贯穿算例的 10.2 TB 表作基线，把上面三块的式子各代一遍，看每档的容量、单次查询字节，以及装得下它的卡数。

<div class="example">

**int8**

```
容量:  10.2 TB × 8/32  = 2.55 TB      → 80 GB 卡需 32 张
查询:  读 64 B（原 256 B），解码 128 op/行
```

**int4**

```
容量:  10.2 TB × 4/32  = 1.28 TB      → 16 张
查询:  读 32 B，解码 128 op/行
独立核验（B-11 口径）: 2.161 GB / 0.270 GB = 8.00 ✓
```

**TT**

代数正推在这里会失效，原因是 `r` 被 `r ≤ d = 64` 卡住。取 221×（`B-07` 引用的实测上界）反推：

```
10.2 TB / 221 ≈ 46 GB     → 1 张卡放得下（与 B-07 的"单卡 V100"一致）
剩下的表 = k·n·r²·4 B，解出的 r 就是这批数据真正需要的秩
单次查询读 = 5 × r² × 4 B ≈ 1280 B（r=8）到 80 KB（r=64）
```

所以这条式子最有用的用法是反推：给你一个实测压缩比，就能算出它隐含的秩；正推得到的只是上界，实测与上界的差额就是"真实数据的有效秩"。

三档摊在一张表上：

| 方案 | 表大小 | 每查询读入 | 每查询计算 | 装得下的卡数 |
|---|---|---|---|---|
| fp32 | 10.2 TB | 256 B | 0 | 128 |
| int8 | 2.55 TB | 64 B | 128 op | 32 |
| int4 | 1.28 TB | 32 B | 128 op | 16 |
| TT（221×） | 46 GB | ≥1280 B（r=8） | 320 op | 1 |

这张表怎么读：前三行是同一张表按不同位宽压出来的，容量与查询字节同比例下降；最后一行换了表示，容量再降一个数量级，查询字节反而涨到 1280 B 以上。

从 fp32 到 int4，容量降 8×、查询字节降 8×、算力涨一点点。从 int4 到 TT，容量再降 28×，**查询字节反涨 40×**。这就是为什么 TT 之后必须有 `A-13`：它注入了冗余计算，回收这部分冗余本身就是一篇 SC 论文（3.1× vs `B-07`，38.5% 内存降低）。

</div>

⚠️ TT 那一行的容量按 221× 的实测口径给，读入字节按 r=8 给，两者不是同一个秩——这正是"公式只给上界"的体现。`r` 与压缩比的对应关系在 `B-07` 的论文页里只有两个端点，中间待核实。

## 模型在哪里不成立

那张五方案表里 10000×、200×、8× 看起来是同一个量纲，其实分母不同，三处差异都要先拆开：

- `B-03` 的一万倍分母是"不压缩的嵌入表"；`B-11` 的 8× 分母是位宽（32/4），与表大小无关。两个分数相除，商没有含义。
- 精度口径不同：AUC、测试精度、部署体积、单卡速度，四个不同的量。`B-07` 的 3× 是单卡相对 SOTA 框架，加速里含"省掉 CPU↔GPU 通信"的贡献，与压缩比不可拆。
- 规模与数据不同：`B-10`/`B-11` 是千万级特征的公开 CTR 集、`B-12` 是 Meta 生产（不可复现）、本算例是 400 亿行。同一个压缩比在不同规模上不是同一件事。

所以看到任何"某方案压了多少倍"的横向排名，先问它的分母。这是第 9 章那条判据的前提。

除此之外还有六条边界：

- 三轴收益不相乘。TT 的核若再量化到 int4，单次查询字节 = `4·k·r²·(4/8) = 640 B`，还是比直接读 int4 一行的 32 B 差 20 倍。叠乘的是容量，不叠乘速度。
- 轴一不可逆。删掉的行如果后来变重要（分布漂移、新用户群），信息已丢。`B-03` 的共享方案可逆、但有下限（至少每桶一行），两者是同一目标的两种代价结构。
- 粒度的隐性税。per-table 量化省了 scale 的存储，代价是表内 range 大时低位宽截断大值；per-row 的精度更好但每行一个 fp32 scale，等于给 int4 的 32 B 又加 4 B（+12.5%）。
- 正则收益不普适。`B-11` 的结论依赖"模型本来过拟合"这个前提。
- `d=64` 是这篇所有 TT 结论的关键假设。d 越小 `r ≤ d` 越紧，TT 越吃亏；d 很大时 TT 的表示能力才够。
- ⚠️ 待核实：`B-07` 的逐压缩比精度表（论文页只有端点）、TT 秩的选取策略（自适应还是手调）、`B-10` 的 200× 在工业规模上是否成立。

<div class="takeaway">

**本篇结论**：三条轴的容量收益分别是 `1−ρ`、`1−b/32`、`1/r²`；查询代价分别是 0、每元素一次变换、每查询 k 次短读加 k·r² 次乘加。

判断一个压缩方案能否真的省时间，只用一条式子：`R = F/B_eff` 是否大于 `Δ计算/Δ读入`。量化在 GPU 上几乎总过线；TT 在秩稍大时读得比原来更多，它买的是"装得下"，不是"读得快"。
