# 深潜 4. 压缩的预算与帕累托：位宽、秩与查询代价

<div class="deep-anchor">

**对应教程** [第 9 章](../guide/09-compression)给了"三条轴"；这里给每条轴的代价函数。

</div>

## 本篇要算的问题

第 9 章的三条轴是：行数（剪枝）、位宽（量化）、表示层（张量分解）。它各给了一篇代表作和一个压缩比，判据只有一句——压缩比不等于加速比。

这一篇把三条轴各写成一个能代入数字的代价函数，然后回答三个问题：

1. fp32 到 int4，每行省多少字节、每次查询多付多少计算，门槛在哪？
2. TT 的压缩比由什么决定，为什么它换来的不只是存储？
3. 压缩比、精度、查询算力三者的可行域长什么样，为什么五个方案的数字不能排序？

## 先给结论

- 轴一与轴二的容量收益都是线性的：省下的字节 ∝ (1−ρ) 与 (1 − b/32)。轴三不是——压缩比 ∝ 1/r²，秩翻倍压缩比掉 4 倍。
- 单次查询的账不是"压了就省"。量化的门槛极低（算力/带宽比 > 约 0.6 op/byte），GPU 上几乎总过线；TT 在秩稍大时单次查询读的字节比直接读一行还多。
- 所以 TT 买的是"装得下"，不是"读得快"。它把容量问题换成算力问题，这正是 `A-13` 存在的理由。
- 帕累托前沿的横轴不是压缩比，是"压缩比 × 单次查询成本"。而五篇论文的压缩比分母根本不同，横向排序没有意义。

## 符号与模型

沿用[贯穿算例](../guide/running-example)：400 亿行、64 维、fp32、10.2 TB。

| 符号 | 含义 | 取值 |
|---|---|---|
| `N` | 表总行数 | 4×10¹⁰ |
| `d` | 嵌入维度 | 64 |
| `S` | 表总字节（fp32） | 4×10¹⁰ × 256 B = 1.024×10¹³ B ≈ 10.2 TB |
| `b` | 每行位宽 | 32 / 8 / 4 |
| `ρ` | 剪枝后保留的行比例 | 0.35–0.60 |
| `r` | TT 秩 | 受 `r ≤ d` 约束 |
| `k` | TT 核个数 | 示意取 5 |
| `B_eff` | 单卡有效随机带宽 | ⚠️ 示意 1 TB/s |
| `F` | 单卡有效算力（非张量） | ⚠️ 示意 20 T op/s |
| `R` | `F / B_eff`，算力带宽比 | ⚠️ 示意 20 op/byte |

三个代价函数，后面全部推导都从这三行出发：

```
容量（轴一、二）  S = ρ · N · d · b/8
容量（轴三）      S_TT = k · n · r² · 4 字节          n = N^(1/k)
查询（轴二）      T = 8b/B_eff + c·d/F               c ≈ 2
查询（轴三）      T_TT = 4k·r²/B_eff + k·r²/F
```

`8b` 是 `d·b/8` 在 `d=64` 时的简写：fp32 一行的字节数正是 `8×32 = 256`。

## 推导

### 轴一：收益线性，代价是索引

```
S(ρ) = ρ · N · d · 4 = ρ × 10.2 TB
ρ = 0.5  →  5.12 TB（省一半）
```

看起来没有额外代价——少查就是省。但删行后 ID 要重新映射到新行号，这张映射表本身要占内存：

```
映射表 = ρ · N × 4 字节 = 0.5 × 4×10¹⁰ × 4 = 80 GB
占省下量的比例 = 80 GB / 5.12 TB ≈ 1.6%
```

1.6% 可以忽略，所以轴一的容量账几乎是纯赚。两件事要说清：

- `B-12` 的 35–60% 是**部署所需**嵌入大小的节省，不是训练峰值显存。它要在训练中在线判定重要性，那部分统计状态不在节省里。
- 查询侧多一次间接寻址（ID → offset → row）。在带宽受限的 gather 里这次寻址通常被掩盖（⚠️ 示意，<5%），但它让"行号"从物理地址变成逻辑量，这也是剪枝不可逆的根源——删掉的行，物理上没了。

### 轴二：收益线性，代价是每元素一次变换

每行字节数 = `d·b/8 = 8b`：

```
fp32   32 bit × 64 / 8 = 256 B
int8    8 bit × 64 / 8 =  64 B     （4×）
int4    4 bit × 64 / 8 =  32 B     （8×）
```

`B-11` 报的 8× 就是这个除法：2.161 GB → 0.270 GB，比值 8.00。位宽账不需要任何假设，它只由位宽决定。

顺带把中间档补齐，好看出这条轴的斜率：

| 位宽 | 每行字节 | 相对 fp32 | 相对上一档 |
|---|---|---|---|
| fp32 (32 bit) | 256 B | 1× | — |
| fp16 / bf16 (16 bit) | 128 B | 2× | 2× |
| int8 | 64 B | 4× | 2× |
| int4 | 32 B | 8× | 2× |

这是一条对数直线：每砍一半位宽，字节减半。所以这条轴没有"红利区"，只有"你敢砍到多低"。工业上停在 int4 而不是 int2，原因不在能不能表示（`B-11` 附录测过 INT2，仍能治过拟合但精度掉得更多），在精度余量——2 bit 只有 4 个量化格点，误差方差是 int4 的 16 倍。

量化的损失有多大？给一张表的量化范围 `[min, max]`，b 位均匀量化的步长与误差方差是

```
q = (max − min) / 2^b
e ~ U[−q/2, q/2]
Var(e) = q² / 12
```

所以误差方差随 `1/4^b` 下降，等效 SQNR 每 bit 提 6 dB（标准结果，满幅正弦下 `SQNR ≈ 6.02b + 1.76`）。int4 比 fp32 少 28 bit，理论 SQNR 低约 168 dB。

**这一步已经把"无损"排除掉了。** 量化不可能无损，只可能"损失在业务指标上不可见"。

那 `B-11` 的"精度不降反升"从哪来？只能由正则解释：

- 若增益来自"压缩无损"，精度应与 b 无关，或在低位宽处掉——实测是单调改善。
- 若增益来自正则，正则强度应随 `1/2^b` 增，精度随 b 单调改善——实测（Table 2：INT16 → INT8 → INT4 逐级上升）正是这个形状。

两条证据都指向后者。⚠️ 具体是噪声注入、平坦极小还是别的机制，论文页没给，属推断；也不要外推到不过拟合的场景——`B-11` 自己承认没测。

查询代价那半：

```
T(b) = 8b/B_eff + c·d/F
T(4) < T(32)  ⟺  (256 − 32)/B_eff > 128/F  ⟺  R = F/B_eff > 0.57
```

门槛只有 0.57 op/byte。⚠️ 按示意值 `R ≈ 20`，余量 35 倍——**量化的解码在 GPU 上几乎免费**。所以量化的瓶颈不在解码算力，而在粒度：`B-11` 用 per-table 量化（一张表一组 scale），表内 range 差异大时低位宽会截断大值，这是它局限里明写的。

### 轴三：收益是 1/r²，代价是每次查询一次收缩

把 `N` 行的表拆成 `k` 个核，第 i 个核形状 `r_{i−1} × n_i × r_i`，且 `∏ n_i = N`。取统一 `n` 与 `r`：

```
核参数量  ≈ k · n · r²
压缩比    = N·d / (k·n·r²) = d · N^(1−1/k) / (k·r²)
```

三个变量的方向：

| 变量 | 对压缩比 | 对精度 | 说明 |
|---|---|---|---|
| `r` 增 | 压缩比按 1/r² 掉 | 精确性上升 | 压缩比与精度共用的唯一旋钮 |
| `N` 增 | ∝ N^(1−1/k)，变好 | — | 表越大 TT 越划算 |
| `k` 增 | 变好 | — | 但核数多，单次查询要读更多核 |

`r` 是全文最关键的一个量：**它同时是压缩比旋钮和精度旋钮，两个需求挤在同一个变量上**。这就是 TT 没有"无损档位"的结构性原因——不存在"把 r 调到无损、压缩比还留在高位"的区域。

`B-07` 引用的 TT-Rec 数据（Kaggle 上 4–221×，精度掉 0.03%–0.3%）正好落在这条曲线上：两端点精度随压缩比单调，中途没有平台。⚠️ 逐点的秩-精度对应待核实，论文页只给了两个端点。

查询侧才是这一轴的真正代价。一次 lookup 不再是"读一行"，而是"每个核读一个 `r×r` 的 slice，再把 k 个 slice 收缩成 d 维"：

```
TT 单次查询读：k · r² · 4 B
直接读一行：    d · 4 B = 256 B

r=8, k=5  →  5 × 64 × 4 = 1280 B   是 256 B 的 5 倍
r=4, k=5  →  5 × 16 × 4 =  320 B   仍多 25%
```

这就是"表示层压缩的成本不只在存储"的代数形式：它把"每行 256 B 的定长读"换成"每次 k 个短读 + k·r² 次乘加"。容量省了三个数量级，单次查询的字节反而涨了。

救兵是复用：同一 batch 里同一 ID 的 slice 只读一次，摊销字节变成 `k·r²·4/m`（m 为复用次数）。`B-07` 的索引重排就是在提高 m，`A-13` 要消除的"TT 运算冗余"是同一件事——表示层压缩的成本，最终要靠数据布局去回收。

这里有一个容易被忽略的推论。容量与单次查询字节都挂在 `r²` 上，方向却相反：`r` 减小，容量按 1/r² 变好，但精度崩；`r` 增大，精度回来，容量与查询成本一起变坏。于是"TT 值不值"这个问题被压缩成一个二元判断：

```
r 必须 ≤ d            （物理上限：r 超过输出维度就没有意义）
r 必须 ≥ r_需要精度     （数据上限：由这批数据的有效秩决定）
可行 ⟺ d ≥ r_需要精度
```

`d=64` 意味着 TT 在 64 维上最多只有 64 个"表示方向"。表越大、数据越杂，`r_需要精度` 越高，越容易撞到 `d`。**所以 TT 的适用面不是由表大小决定的，是由维度与数据的可压缩性决定的**——这解释了为什么它在大表上反而可能先撞墙，而不是先受益。

### 查询预算的交叉点

把三条轴并到一张纸上：

```
T_query = 访存 + 解码/收缩
        = (每查询读入字节)/B_eff + (每查询计算量)/F
```

压缩改变第一项（↓），有时抬高第二项（↑）。净赚条件是

```
Δ读入字节 / B_eff  >  Δ计算量 / F
即   R = F/B_eff  >  Δ计算量 / Δ读入字节
```

代入三轴：

| 手段 | Δ读入字节 | Δ计算量 | 门槛 `R >` | 判断 |
|---|---|---|---|---|
| int8/int4 | −224 B/行 | +128 op/行 | 0.57 | 过线（示意 R≈20） |
| TT (r=8,k=5) | **+1024 B/行** | +320 op/行 | 负数，无解 | 必须有复用 |
| 剪枝 | −ρ×256 B/行 | ≈0 | 0 | 过线 |

同一把压缩刀，在"快内存+慢计算"的机器上（CPU 侧解码，R 小）会亏；在 GPU 上会赚。这解释了为什么量化在训练里无损、在 CPU 推理里常被吐槽慢——不是算法不同，是 R 不同。

把五个方案放到"压缩比 × 精度代价 × 查询算力"三维里：

| 论文 | 压缩比 | 精度代价 | 查询算力 | 基线 / 数据 |
|---|---|---|---|---|
| `B-03` CAFE+ | 10000× | AUC +3.94% | HotSketch 一次 + 两路查表 | Criteo（Kaggle / TB） |
| `B-10` MPE | 200× | ±1e-4（噪声级） | 反量化 + 分组查表 | Criteo / Avazu / KDD12，小模型 |
| `B-11` DQRM | 8× | +0.148% acc | 每元素一次变换 | Kaggle / Terabyte |
| `B-07` EL-Rec | 未给（参照 TT-Rec 4–221×） | 0.03%–0.3%（参照） | 每查询 k 次短读 + 收缩 | Criteo TB，单卡 V100 |
| `B-12` AdaEmbed | 表大小 35–60% | 精度升 | 无（少查） | Meta 生产，无公开集 |

## 算例

基线 10.2 TB。三档各算一遍容量与单次查询。

<div class="example">

**int8**

```
容量:  10.2 TB × 8/32  = 2.55 TB      → 80 GB 卡需 32 张
查询:  读 64 B（原 256 B），解码 128 op/行
```

**int4**

```
容量:  10.2 TB × 4/32  = 1.28 TB      → 16 张
查询:  读 32 B，解码 128 op/行
独立核验（B-11 口径）: 2.161 GB / 0.270 GB = 8.00 ✓
```

**TT**

代数正推在这里会失效，原因是 `r` 被 `r ≤ d = 64` 卡住。取 221×（`B-07` 引用的实测上界）反推：

```
10.2 TB / 221 ≈ 46 GB     → 1 张卡放得下（与 B-07 的"单卡 V100"一致）
剩下的表 = k·n·r²·4 B，解出的 r 就是这批数据真正需要的秩
单次查询读 = 5 × r² × 4 B ≈ 1280 B（r=8）到 80 KB（r=64）
```

所以不要用公式正推压缩比——它给的是上界，实测与上界的差额就是"真实数据的有效秩"。这条式子最有用的用法是反推：给你一个实测压缩比，就能算出它隐含的秩。

三档摊在一张表上：

| 方案 | 表大小 | 每查询读入 | 每查询计算 | 装得下的卡数 |
|---|---|---|---|---|
| fp32 | 10.2 TB | 256 B | 0 | 128 |
| int8 | 2.55 TB | 64 B | 128 op | 32 |
| int4 | 1.28 TB | 32 B | 128 op | 16 |
| TT（221×） | 46 GB | ≥1280 B（r=8） | 320 op | 1 |

从 fp32 到 int4，容量降 8×、查询字节降 8×、算力涨一点点。从 int4 到 TT，容量再降 28×，**查询字节反涨 40×**。这就是为什么 TT 之后必须有 `A-13`：它注入了冗余计算，回收这部分冗余本身就是一篇 SC 论文（3.1× vs `B-07`，38.5% 内存降低）。

</div>

⚠️ TT 那一行的容量按 221× 的实测口径给，读入字节按 r=8 给，两者不是同一个秩——这正是"公式只给上界"的体现。`r` 与压缩比的对应关系在 `B-07` 的论文页里只有两个端点，中间待核实。

## 代价与边界

先回答"为什么不能横向排序"。上表里 10000×、200×、8× 看起来是同一个量纲，其实分母不同：

- `B-03` 的一万倍分母是"不压缩的嵌入表"；`B-11` 的 8× 分母是**位宽**（32/4），与表大小无关。两个分数相除，商没有含义。
- 精度口径不同：AUC、测试精度、部署体积、单卡速度，四个不同的量。`B-07` 的 3× 是**单卡相对 SOTA 框架**，加速里含"省掉 CPU↔GPU 通信"的贡献，与压缩比不可拆。
- 规模与数据不同：`B-10`/`B-11` 是千万级特征的公开 CTR 集、`B-12` 是 Meta 生产（不可复现）、本算例是 400 亿行。同一个压缩比在不同规模上不是同一件事。

所以看到任何"某方案压了多少倍"的横向排名，先问它的分母。这是第 9 章那条判据的前提。

再列边界：

- 三轴收益不相乘。TT 的核若再量化到 int4，单次查询字节 = `4·k·r²·(4/8) = 640 B`，还是比直接读 int4 一行的 32 B 差 20 倍。叠乘的是容量，不叠乘速度。
- 轴一不可逆。删掉的行如果后来变重要（分布漂移、新用户群），信息已丢。`B-03` 的共享方案可逆、但有下限（至少每桶一行），两者是同一目标的两种代价结构。
- 粒度的隐性税。per-table 量化省了 scale 的存储，代价是表内 range 大时低位宽截断大值；per-row 的精度更好但每行一个 fp32 scale，等于给 int4 的 32 B 又加 4 B（+12.5%）。
- 正则收益不普适。`B-11` 的结论依赖"模型本来过拟合"这个前提。
- `d=64` 是这篇所有 TT 结论的关键假设。d 越小 `r ≤ d` 越紧，TT 越吃亏；d 很大时 TT 的表示能力才够。
- ⚠️ 待核实：`B-07` 的逐压缩比精度表（论文页只有端点）、TT 秩的选取策略（自适应还是手调）、`B-10` 的 200× 在工业规模上是否成立。

<div class="takeaway">

**本篇结论**：三条轴的容量收益是 `1−ρ`、`1−b/32`、`1/r²`；查询代价是 0、每元素一次变换、每查询 k 次短读 + k·r² 次乘加。

判断一个压缩方案能否真的省时间，只用一条式子：`R = F/B_eff` 是否大于 `Δ计算/Δ读入`。量化在 GPU 上几乎总过线；TT 在秩稍大时读得比原来更多——它买的是"装得下"，不是"读得快"。

</div>

<div class="cite">

本篇引用：`B-12` AdaEmbed（35–60% 部署体积、在线剪枝）、`B-10` MPE（200×、按频率分组、±1e-4）、`B-11` DQRM（INT4 8×、2.161 GB→0.270 GB、INT16→INT8→INT4 单调、per-table 量化）、`B-07` EL-Rec（TT-Rec 4–221×、精度 0.03%–0.3%、单卡 3×）、`B-03` CAFE+（10000×、AUC +3.94%）、`A-13` EcoRec（3.1× vs EL-Rec、内存 38.5%）、`A-16` RecIS（MBU、bucketize 0.88%）。标准结果：均匀量化误差方差 `q²/12`、6 dB/bit、Amdahl 定律。⚠️ 待核实项已在小节内标注。
